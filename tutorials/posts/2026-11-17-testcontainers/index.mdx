[Testcontainers](https://testcontainers.com) is a widely adopted library that runs the real dependencies of your tests, such as a Postgres database or a Kafka broker, as throwaway containers. It's available for Java, Go, .NET, Node.js, Python, and other languages. A test asks for a Postgres container, runs against a real database instead of a mock, and the container is removed when the test ends. To start those containers, Testcontainers needs the Docker API. On a laptop, that's Docker Desktop. On Kubernetes, it's Docker-in-Docker: a privileged container, which can run any kind of untrusted code with full access to its node. In a cluster shared by many developers, giving every test run that access is not an option. Luckily, an open source project, [kubedock](https://github.com/joyrex2001/kubedock), comes to the rescue: it starts those containers as regular pods in your Okteto Namespace.

This tutorial runs the Testcontainers test suite of a sample application with `okteto test` and kubedock.

## Prerequisites

Install the latest version of the Okteto CLI and configure it to access Okteto. [Follow our installation guide](/docs/get-started/install-okteto-cli) if you haven't done it yet.

This tutorial doesn't support the [BuildKit server](/docs/self-hosted/helm-configuration#buildkit) of Okteto in rootless mode or with `network.mode` set to `host`.

## kubedock

[kubedock](https://github.com/joyrex2001/kubedock) implements the Docker API, but it doesn't run containers itself: it translates each call into Kubernetes resources. Testcontainers talks to it as it would to a Docker daemon.

When a test asks for a Postgres container:

1. kubedock creates a pod that runs the `postgres` image, and waits until it's running.
2. It makes the ports of the pod reachable to the test.
3. When the test reads the logs of the container, runs a command in it, or copies a file to it, kubedock does the same on the pod.
4. When the test stops the container, kubedock deletes the pod.

[Vincent van Dam](https://github.com/joyrex2001) started kubedock in 2021 to run tests that need Docker containers without Docker-in-Docker, and still maintains it. It covers far more of the Docker API than a test suite usually needs, and it has the options that make it safe on a shared cluster, which this tutorial relies on. If it's useful to you too, give [the repository](https://github.com/joyrex2001/kubedock) a star.

## Running the tests with Okteto Test

To see how to configure Okteto to run your tests with Testcontainers, this tutorial uses the [testcontainers-kubedock](https://github.com/okteto-community/testcontainers-kubedock) sample: a small Scala web application, built with Maven, whose tests start a Postgres container. Get a local copy of it:

```bash
git clone https://github.com/okteto-community/testcontainers-kubedock
cd testcontainers-kubedock
```

Look at the `test` section of its Okteto Manifest:

```yaml
test:
  unit:
    image: maven:3.9-eclipse-temurin-21
    caches:
      - /root/.m2
      - /root/.kubedock
    commands:
      - ./start-kubedock.sh
      - DOCKER_HOST=tcp://127.0.0.1:2475 TESTCONTAINERS_RYUK_DISABLED=true mvn -B test
    artifacts:
      - target/test-reports
```

`okteto test` runs these commands in a container in the cluster, with [Remote Execution](/docs/core/remote-execution), and that container already has your Kubernetes credentials. kubedock only needs to start in that container before the tests do:

1. `start-kubedock.sh` downloads kubedock, starts it in the background on `tcp://127.0.0.1:2475`, and waits until it answers. kubedock keeps running for the next command.
2. `mvn -B test` runs the tests with `DOCKER_HOST` set to that address, so Testcontainers talks to kubedock instead of a Docker daemon.

This is how the script starts kubedock:

```bash
kubedock server \
  --kubeconfig "${KUBECONFIG:-$HOME/.kube/config}" \
  --namespace "$OKTETO_NAMESPACE" \
  --listen-addr 127.0.0.1:2475 \
  --port-forward \
  --disable-dind \
  --lock \
  --prune-start
```

| Flag | What it does |
|------|--------------|
| `--kubeconfig`, `--namespace` | Create the pods in your Okteto Namespace, with the Kubernetes credentials of the test container. |
| `--listen-addr 127.0.0.1:2475` | Serve the Docker API only inside the test container. |
| `--port-forward` | Make the ports of each pod reachable on `127.0.0.1`. |
| `--disable-dind` | Don't give the Docker socket to the containers that mount it. Without this flag, kubedock adds a sidecar with the socket to their pods. |
| `--lock` | Lock the Okteto Namespace while kubedock runs. Another run in the same Okteto Namespace waits for the lock, for up to 15 minutes. |
| `--prune-start` | Before starting, delete the pods and Services that other kubedock runs created in the Okteto Namespace. With `--lock`, they can only be the leftovers of a cancelled run. |

Now run the tests:

```bash
okteto test unit
```

## Keeping the tests out of the build

`okteto build` doesn't have a Docker API either, so the tests that use Testcontainers run in `okteto test` and not while building the image.

The sample keeps a single Dockerfile for every case. It runs the tests by default and skips them when the `SKIP_TESTS` build argument is `true`:

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build

ARG SKIP_TESTS=false

WORKDIR /src

COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -B dependency:go-offline

COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -B package -DskipTests=${SKIP_TESTS}
```

The Okteto Manifest sets it for `okteto build`:

```yaml
build:
  app:
    context: .
    args:
      SKIP_TESTS: "true"
```

A CI pipeline that builds the image with a Docker daemon available keeps running the tests in the build, with no change. On Okteto, `okteto deploy` builds the image without them and deploys the application:

```bash
okteto deploy
```

## Faster test runs

The sample avoids downloading or uploading anything twice:

- **Caches in `okteto test`.** The Maven repository (`/root/.m2`) and the kubedock binary (`/root/.kubedock`) are kept between runs, so later runs don't download them again.
- **Dependency layer in the build.** The Dockerfile downloads the Maven dependencies in their own layer, with a BuildKit cache for `/root/.m2`, so a change in `src/` doesn't download them again.
- **Smaller context.** `.dockerignore` only sends `pom.xml` and `src/` to the build, and `.oktetoignore` doesn't upload `target/` to `okteto test`.
- **Test reports as artifacts.** `okteto test` downloads the JUnit XML reports to `target/test-reports` on your machine.

## Things to know

- **Ryuk is disabled.** Testcontainers uses a container called Ryuk to remove the containers of a crashed test run. Ryuk needs the Docker socket, which kubedock doesn't provide, so `TESTCONTAINERS_RYUK_DISABLED=true` turns it off. kubedock takes care of the cleanup instead.
- **Runs in the same Okteto Namespace wait for each other.** With `--lock`, a second `okteto test` in the same Okteto Namespace starts when the first one finishes.
- **Port forwarding.** kubedock reaches the ports of each pod through Kubernetes port forwarding, which keeps them on `127.0.0.1`. Its README describes port forwarding as meant for local debugging, and not as fast or stable as a direct connection. It worked well in every run of the sample, but keep it in mind for test suites that move a lot of data through their containers.

## Using kubedock in your project

To run your own Testcontainers tests the same way, copy `start-kubedock.sh` and the `test` section of the Okteto Manifest, and change `mvn -B test` for the command that runs your tests.

## Running Testcontainers safely on a shared cluster

Running Testcontainers through kubedock in `okteto test` avoids the problems that Docker-in-Docker brings to a shared cluster:

- **No privileged containers.** The test container and the pods kubedock creates are regular pods.
- **Nobody else can use kubedock.** It only listens on `127.0.0.1` inside the test container, and it only lives while `okteto test` runs. Nothing is deployed in your Okteto Namespace.
- **Your own permissions.** kubedock creates the pods in your Okteto Namespace with your Kubernetes credentials, so it can't do anything you couldn't already do with `kubectl`.
- **No collisions between runs.** Testcontainers can give a container a network alias, such as `db`, and kubedock creates a Service with that name. Two runs using the same alias in the same Okteto Namespace would collide, so `--lock` makes them run one at a time.
- **No leftovers.** kubedock deletes each pod when the test stops its container. If a run is cancelled before that, the next run deletes what it left behind (`--prune-start`).
- **Visible to Kubernetes.** The containers are pods, so your logs, metrics, and policies see them like any other workload.
