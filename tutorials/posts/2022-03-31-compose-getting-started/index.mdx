Okteto deploys an application defined in a [Docker Compose](/docs/reference/docker-compose/) file to Kubernetes, without writing any Kubernetes manifests. You keep your `docker-compose.yml`, and Okteto builds, deploys, and tests the application in your cluster, where you can also develop each service with hot reload. This tutorial uses a voting application, written in Python with Redis, that is already set up this way. To do the same with your own Docker Compose application, we recommend using an AI agent with the [Okteto agent skills](/docs/agentic/).

## Prerequisites

- Access to an Okteto instance, with your [Okteto context](/docs/reference/okteto-cli/#context) configured.
- The [Okteto CLI](/docs/get-started/install-okteto-cli/) installed on your machine.
- A local copy of the sample application:

```bash
git clone https://github.com/okteto/compose-getting-started
cd compose-getting-started
```

## The Sample Application

The application has two services: `vote`, a [FastAPI](https://fastapi.tiangolo.com/) application that shows two options and counts the votes, and `redis`, which stores the votes. The `docker-compose.yml` file at the root of the repository defines both:

```yaml title="docker-compose.yml"
services:
  vote:
    build:
      context: vote
      target: prod
    ports:
      - 8080:8080

  redis:
    image: redis:8.10.3-trixie
    ports:
      - 6379
    volumes:
      - redis:/data

volumes:
  redis:
```

Okteto turns each part of the file into its Kubernetes equivalent:

- **`build`**: the [Okteto Build Service](/docs/core/build-service/) builds the `vote` image in your cluster, from the `prod` stage of `vote/Dockerfile`.
- **`ports`**: `8080:8080` makes the port public, so Okteto creates an HTTPS endpoint for `vote`. `6379` stays private to the cluster.
- **`volumes`**: `redis` becomes a persistent volume, so the votes survive when Redis restarts.

The [Docker Compose reference](/docs/reference/docker-compose/) lists every field that Okteto supports.

## The Dockerfile

`vote/Dockerfile` defines two images, one per stage:

```dockerfile title="vote/Dockerfile"
FROM python:3.15.2-trixie AS dev

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.15.2-slim-trixie AS prod

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
COPY static static
COPY templates templates
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
```

- `dev` is the development image. It contains Python, the dependencies in `requirements.txt`, and the source code. `requirements.txt` is copied and installed before the source code, so a change to `app.py` doesn't reinstall the dependencies.
- `prod` is the application image. It contains the slim Python runtime, the dependencies in `requirements.txt`, `app.py`, and the static files and templates that the application serves.

## The Okteto Manifest

The Docker Compose file defines the application. The `okteto.yml` file, the [Okteto Manifest](/docs/reference/okteto-manifest/) of the repository, adds what a Docker Compose file can't define: the development image, the unit tests, and the Development Container.

```yaml title="okteto.yml"
build:
  dev:
    context: vote
    target: dev

deploy:
  compose: docker-compose.yml

test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r vote/requirements-test.txt
      - pytest vote --junitxml=report.xml
    artifacts:
      - report.xml

dev:
  vote:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: uvicorn app:app --host 0.0.0.0 --port 8080 --reload
    sync:
      - vote:/usr/src/app
    persistentVolume:
      enabled: false
```

- **`build`** builds the `dev` stage of `vote/Dockerfile` and stores the reference of the image in the `OKTETO_BUILD_DEV_IMAGE` [variable](/docs/core/okteto-variables/#built-in-environment-variables-for-images-in-okteto-registry). Okteto also builds the image of every service in the Docker Compose file that has a `build` field, such as `vote`.
- **`deploy`** [deploys the Docker Compose file](/docs/reference/okteto-manifest/#deploy-with-compose). To deploy what the Docker Compose file doesn't define, such as a Helm chart or cloud resources created with Terraform, add a list of [commands](/docs/reference/okteto-manifest/#deploy-with-commands) to the `deploy` section: Okteto runs them before it deploys the Docker Compose file.
- **`test`** and **`dev`** define the Test Container and the Development Container, explained in [Testing the Application](#testing-the-application) and [Developing a Service](#developing-a-service).

Okteto deploys the Docker Compose file with [Remote Execution](/docs/core/remote-execution/), in a container inside your cluster.

## Deploying the Application

Deploy the application from the root of the repository:

```bash
okteto deploy --wait
```

## Testing the Application

The `test` section of the Okteto Manifest defines a [Test Container](/docs/reference/okteto-manifest/#test) that runs the unit tests in `vote/test_app.py` with [pytest](https://docs.pytest.org/) and the FastAPI `TestClient`:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r vote/requirements-test.txt
      - pytest vote --junitxml=report.xml
    artifacts:
      - report.xml
```

- `image`: the development image, so the tests run with the same Python version and dependencies as the Development Container.
- `caches`: the `pip` cache, kept between runs of the Test Container, so `pip install` doesn't download pytest again.
- `commands`: the commands that install pytest and run the tests. The Test Container fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the JUnit report that pytest writes.

The tests replace Redis with an in-memory fake, so they don't need the `redis` service.

Run the unit tests from the root of the repository:

```bash
okteto test
```

## Developing a Service

If you use AI agents, the Development Container is optional: agents work well with the `okteto deploy` and `okteto test` cycle, and don't need one. To get hot reload on every change, configure a Development Container in your Okteto Manifest and run `okteto up`. While `okteto up` is running, an AI agent with the [Okteto agent skills](/docs/agentic/) skips the build and deploy cycle: your changes already reach the Development Container through File Sync, so the agent waits for you to tell it what to run next.

The `dev` section of the Okteto Manifest defines the [Development Container](/docs/reference/okteto-manifest/#dev) of the `vote` service:

```yaml title="okteto.yml"
dev:
  vote:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: uvicorn app:app --host 0.0.0.0 --port 8080 --reload
    sync:
      - vote:/usr/src/app
    persistentVolume:
      enabled: false
```

- `image`: the development image built in the `build` section.
- `command`: starts the application with Uvicorn. `--reload` restarts it every time a `.py` file changes.
- `sync`: synchronizes the `vote` folder with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach.

Start the Development Container:

```bash
okteto up
```

Okteto replaces the `vote` Deployment with the Development Container, synchronizes your files, and starts the application with `uvicorn --reload`:

## Cleaning Up

`okteto destroy` deletes the services and the endpoint of the application from your Namespace. The `--volumes` flag also deletes the `redis` volume and the votes it stores:

```bash
okteto destroy --volumes
```

## FAQ

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. An AI agent with the [Okteto agent skills](/docs/agentic/) configures what each command uploads for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### What if my services live in several repositories?

List the other repositories in the `dependencies` section of the Okteto Manifest. [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/) shows how.

### Do I need to deploy the whole application in every Namespace?

No. [Divert](/docs/development/divert/) lets you deploy only the services you change and reuse the services of a shared environment.

### How do I start each environment with realistic data?

Create its database from a [Volume Snapshot](/docs/core/use-volume-snapshots/) instead of running a seed script on every deploy. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own cloud resources. [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) shows how, with an Amazon S3 bucket for each environment.

### Where can I find every field that Okteto supports?

The [Docker Compose reference](/docs/reference/docker-compose/) lists the Docker Compose fields that Okteto supports, and the [Okteto Manifest reference](/docs/reference/okteto-manifest/) lists every field of `build`, `deploy`, `destroy`, `test`, and `dev`.
