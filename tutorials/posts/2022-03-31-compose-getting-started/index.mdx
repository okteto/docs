Okteto deploys an application defined in a [Docker Compose](/docs/reference/docker-compose/) file to Kubernetes, with no Kubernetes manifests, and then lets you test and develop each service in that environment. This tutorial uses a voting application written in Python and Redis: Okteto builds its application image and its development image from one Dockerfile, runs its unit tests in a Test Container, and reloads it with `uvicorn --reload` when you save a file.

## Prerequisites

- Access to an Okteto instance, with your [Okteto context](/docs/reference/okteto-cli/#context) configured.
- The [Okteto CLI](/docs/get-started/install-okteto-cli/) installed on your machine.
- A local copy of the sample application:

```bash
git clone https://github.com/okteto/compose-getting-started
cd compose-getting-started
```

## The Sample Application

The application has two services: `vote`, a [FastAPI](https://fastapi.tiangolo.com/) application that shows two options and counts the votes, and `redis`, which stores the votes. The `docker-compose.yml` file at the root of the repository defines both:

```yaml title="docker-compose.yml"
services:
  vote:
    build:
      context: vote
      target: prod
    ports:
      - 8080:8080

  redis:
    image: redis:8.10.3-trixie
    ports:
      - 6379
    volumes:
      - redis:/data

volumes:
  redis:
```

Okteto turns each part of the file into its Kubernetes equivalent:

- **`build`**: the [Okteto Build Service](/docs/core/build-service/) builds the image of `vote` from the `prod` stage of `vote/Dockerfile`, in your cluster.
- **`ports`**: `8080:8080` makes the port public, so Okteto creates an HTTPS endpoint for `vote`. `6379` stays private to the cluster.
- **`volumes`**: `redis` becomes a persistent volume, so the votes survive a restart of Redis.

The [Docker Compose reference](/docs/reference/docker-compose/) lists every field that Okteto supports.

## The Dockerfile

The `vote/Dockerfile` file defines two images, one per stage:

```dockerfile title="vote/Dockerfile"
FROM python:3.15.2-trixie AS dev

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.15.2-slim-trixie AS prod

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
COPY static static
COPY templates templates
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
```

- `dev` is the development image. It contains Python, the dependencies of `requirements.txt`, and the source code. `requirements.txt` is copied and installed before the source code, so a change to `app.py` doesn't reinstall the dependencies.
- `prod` is the application image. It contains the slim Python runtime, the dependencies of `requirements.txt`, `app.py`, and the static files and templates that the application serves.

## The Okteto Manifest

The Docker Compose file defines the application. The `okteto.yml` file, the [Okteto Manifest](/docs/reference/okteto-manifest/) of the repository, adds what a Docker Compose file can't define: the development image, the unit tests, and the Development Container.

```yaml title="okteto.yml"
build:
  dev:
    context: vote
    target: dev

deploy:
  compose: docker-compose.yml

test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r vote/requirements-test.txt
      - pytest vote --junitxml=report.xml
    artifacts:
      - report.xml

dev:
  vote:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: uvicorn app:app --host 0.0.0.0 --port 8080 --reload
    sync:
      - vote:/usr/src/app
    persistentVolume:
      enabled: false
```

- **`build`** builds the `dev` stage of `vote/Dockerfile` and exposes the reference of the image in the `OKTETO_BUILD_DEV_IMAGE` [variable](/docs/core/okteto-variables/#built-in-environment-variables-for-images-in-okteto-registry). Okteto also builds the images of the services of the Docker Compose file that have a `build` field, such as `vote`.
- **`deploy`** [deploys the Docker Compose file](/docs/reference/okteto-manifest/#deploy-with-compose).
- **`test`** and **`dev`** define the Test Container and the Development Container, explained in [Testing the Application](#testing-the-application) and [Developing a Service](#developing-a-service).

Okteto deploys the Docker Compose file with [Remote Execution](/docs/core/remote-execution/), in a container inside your cluster.

## Deploying the Application

Deploy the application from the root of the repository:

```bash
okteto deploy --wait
```

## Testing the Application

The `test` section of the Okteto Manifest defines a [Test Container](/docs/reference/okteto-manifest/#test-object-optional) that runs the unit tests of `vote/test_app.py` with [pytest](https://docs.pytest.org/) and the FastAPI `TestClient`:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r vote/requirements-test.txt
      - pytest vote --junitxml=report.xml
    artifacts:
      - report.xml
```

- `image`: the development image, so the tests run with the same Python version and dependencies as the Development Container.
- `caches`: the `pip` cache, kept between runs of the Test Container, so `pip install` doesn't download pytest again.
- `commands`: the commands that install pytest and run the tests. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the JUnit report of pytest.

The tests replace Redis with an in-memory fake, so they don't need the `redis` service.

```bash
okteto test
```

Running `okteto deploy` and `okteto test` after each change is usually fast enough, especially when an AI agent writes and tests the code autonomously. To get hot reload on every change, configure the `dev` section of the Okteto Manifest and run `okteto up`.

## Developing a Service

The `dev` section of the Okteto Manifest defines the [Development Container](/docs/reference/okteto-manifest/#dev-object-optional) of the `vote` service:

```yaml title="okteto.yml"
dev:
  vote:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: uvicorn app:app --host 0.0.0.0 --port 8080 --reload
    sync:
      - vote:/usr/src/app
    persistentVolume:
      enabled: false
```

- `image`: the development image built in the `build` section.
- `command`: starts the application with Uvicorn. `--reload` restarts it every time a `.py` file changes.
- `sync`: synchronizes the `vote` folder with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach.

Start the Development Container:

```bash
okteto up
```

Okteto replaces the `vote` Deployment with the Development Container, synchronizes your files, and starts the application with `uvicorn --reload`:

## Deploying More Than Docker Compose

The `deploy` section of the Okteto Manifest can deploy things that the Docker Compose file doesn't define, such as a Helm chart or a Terraform resource. Add the commands that deploy them next to the Docker Compose file:

```yaml title="okteto.yml"
build:
  dev:
    context: vote
    target: dev
  worker:
    context: worker

deploy:
  commands:
    - name: Deploy the worker with Helm
      command: helm upgrade --install worker worker/chart --set image=${OKTETO_BUILD_WORKER_IMAGE}
  compose: docker-compose.yml
```

- **`build`** defines the images to build. `${OKTETO_BUILD_WORKER_IMAGE}` holds the `worker` image, which the Helm command passes to its chart. An image with the name of a Compose service replaces the image of that service.
- **`deploy`** runs its [commands](/docs/reference/okteto-manifest/#deploy-with-commands) first and then deploys the [Compose file](/docs/reference/okteto-manifest/#deploy-with-compose).

[Develop a Helm application with Okteto](/tutorials/helm/) shows a complete application deployed with Helm commands.

## Cleaning Up

`okteto destroy` deletes the services and the endpoint of the application from your Namespace. The `--volumes` flag also deletes the `redis` volume and the votes it stores:

```bash
okteto destroy --volumes
```
