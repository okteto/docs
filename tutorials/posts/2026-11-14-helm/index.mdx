Okteto deploys an application packaged as Helm charts with the same charts you use in production, and then lets you develop each service in that environment. This tutorial uses the [Helm Sample App](https://github.com/okteto/helm-getting-started), a to-do list application, to show the four sections of the [Okteto Manifest](/docs/reference/okteto-manifest) you need: `build`, `deploy`, `test`, and `dev`.

## Prerequisites

- Access to an Okteto instance, with your [Okteto context](/docs/reference/okteto-cli#context) configured.
- The [Okteto CLI](/docs/get-started/install-okteto-cli) installed on your machine.
- A local copy of the sample application:

```bash
git clone https://github.com/okteto/helm-getting-started
cd helm-getting-started
```

## The Sample Application

The Helm Sample App has three services, each one in its own folder:

- `client`: a React frontend, built with [Vite](https://vite.dev/).
- `server`: a Node.js backend that serves the API under `/todos`.
- `db`: a PostgreSQL database that stores the to-dos.

Each folder has a `chart` directory with the Helm chart that deploys the service. Two details of these charts make them work with Okteto.

The container image of the `client` and `server` Deployments is a value, not a hardcoded tag:

```yaml title="client/chart/templates/client-deployment.yaml"
spec:
  containers:
    - name: client
      image: {{ .Values.image }}
      ports:
        - containerPort: 3000
```

This lets Okteto pass the image it builds from your code, so every environment runs the code of its branch instead of an image pushed weeks ago.

The Ingress has the `dev.okteto.com/generate-host` annotation, so Okteto creates a public HTTPS endpoint for the application in each environment:

```yaml title="client/chart/templates/ingress.yaml"
metadata:
  name: todolist
  annotations:
    dev.okteto.com/generate-host: "true"
```

The [Ingress endpoints](/docs/core/endpoints/ingress) docs explain the options for endpoints.

The `client` and `server` folders also have a `Dockerfile` with two stages. This is the one of the `server`:

```dockerfile title="server/Dockerfile"
FROM node:26.13.1-trixie AS dev

WORKDIR /usr/src/app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .

FROM node:26.13.1-trixie-slim AS prod

WORKDIR /usr/src/app
COPY --from=dev /usr/src/app .
CMD ["node", "index.js"]
```

- `dev` is the development image: Node.js, the dependencies installed by `npm ci`, and the source code.
- `prod` is the application image that the chart deploys. It runs the code and the dependencies of the `dev` stage on a smaller Node.js image.

The `dev` stage of the `client` also runs `vite build`, and its `prod` stage serves the result with NGINX on port `3000`.

## The Okteto Manifest

The `okteto.yaml` file at the root of the repository tells Okteto how to build, deploy, test, and develop the application:

```yaml title="okteto.yaml"
build:
  server-dev:
    context: server
    target: dev
  server:
    context: server
    target: prod
    depends_on:
      - server-dev
  client-dev:
    context: client
    target: dev
  client:
    context: client
    target: prod
    depends_on:
      - client-dev

deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Deploy the PostgreSQL database
      command: helm upgrade --install db db/chart
    - name: Deploy the Node.js backend
      command: helm upgrade --install server server/chart --set image=${OKTETO_BUILD_SERVER_IMAGE}
    - name: Deploy the React frontend
      command: helm upgrade --install client client/chart --set image=${OKTETO_BUILD_CLIENT_IMAGE}

test:
  server:
    context: server
    image: ${OKTETO_BUILD_SERVER_DEV_IMAGE}
    caches:
      - /root/.npm
    commands:
      - npm ci
      - node --test --experimental-test-coverage --test-reporter=spec --test-reporter-destination=stdout --test-reporter=lcov --test-reporter-destination=lcov.info
    artifacts:
      - lcov.info

dev:
  server:
    image: ${OKTETO_BUILD_SERVER_DEV_IMAGE}
    command: node --watch index.js
    sync:
      - server:/usr/src/app
    persistentVolume:
      enabled: false
  client:
    image: ${OKTETO_BUILD_CLIENT_DEV_IMAGE}
    command: npm run dev
    sync:
      - client:/usr/src/app
    persistentVolume:
      enabled: false
```

- **`build`** defines the two images of each service. `context` is the folder with the Dockerfile, and `target` selects its stage. `depends_on` builds the `dev` image first, so the application image reuses its cached layers. The [Okteto Build Service](/docs/core/build-service) builds the images in your cluster, and skips the ones whose code didn't change.
- **`deploy`** runs the same `helm upgrade --install` commands you would run against production. `${OKTETO_BUILD_SERVER_IMAGE}` and `${OKTETO_BUILD_CLIENT_IMAGE}` hold the application images built in the `build` section, and `--set image=` passes them to the charts. The commands run in your cluster with [Remote Execution](/docs/core/remote-execution), so you don't need Helm on your machine.
- **`test`** defines a Test Container that runs the unit tests of the `server`. The [Testing the Server](#testing-the-server) section explains its fields.
- **`dev`** defines a Development Container for the `client` and `server` services. The [Developing a Service](#developing-a-service) section explains its fields.

`deploy.image` sets the image of the container where Remote Execution runs the commands of `deploy.commands`. The tag of that image chooses the Helm version of your deploys, here Helm 4.3.2, so it only changes when you change the Okteto Manifest. The Helm project doesn't publish an image, so the Helm Sample App uses [`alpine/helm`](https://hub.docker.com/r/alpine/helm), an image with Helm on Alpine Linux. Any image works if it includes `/bin/sh` and every tool that your commands run. Without `deploy.image`, the commands run in the [default image of Remote Execution](/docs/core/remote-execution#enable-remote-execution-per-application), which includes Helm, `kubectl`, and other tools.

## Testing the Server

The `test` section of the Okteto Manifest defines a [Test Container](/docs/reference/okteto-manifest#test-object-optional) that runs the unit tests of `server/index.test.js` with the test runner of Node.js:

```yaml title="okteto.yaml"
test:
  server:
    context: server
    image: ${OKTETO_BUILD_SERVER_DEV_IMAGE}
    caches:
      - /root/.npm
    commands:
      - npm ci
      - node --test --experimental-test-coverage --test-reporter=spec --test-reporter-destination=stdout --test-reporter=lcov --test-reporter-destination=lcov.info
    artifacts:
      - lcov.info
```

- `context`: the folder that Okteto sends to the Test Container, the `server` folder.
- `image`: the development image of the `server`, so the tests run with the same Node.js version as the Development Container.
- `caches`: the npm cache, kept between runs of the Test Container.
- `commands`: the commands that install the dependencies and run the tests. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the coverage report.

Test Containers run with [Remote Execution](/docs/core/remote-execution).

Run the unit tests from the root of the repository:

```bash
okteto test
```

Running `okteto deploy` and `okteto test` after each change is usually fast enough, especially when an AI agent writes and tests the code autonomously. To get hot reload on every change, configure the `dev` section of the Okteto Manifest and run `okteto up`.

## Developing a Service

The `dev` section of the Okteto Manifest defines a Development Container for the `server` and the `client`:

- `image`: the development image of the service, built in the `build` section.
- `command`: starts the service with hot reload. The `server` runs `node --watch`, which restarts Node.js when a file changes. The `client` runs the Vite development server, which updates the page in your browser when a file changes.
- `sync`: synchronizes the folder of the service on your machine with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. The dependencies come from the development image, and Okteto synchronizes the files again on every `okteto up`, so there's no volume to create and attach.

The [Development Container guides](/docs/development/containers/) explain how to configure Test Containers and Development Containers for each language.

Start a Development Container for the backend:

```bash
okteto up server
```

Okteto replaces the `server` Deployment with a Development Container, synchronizes the `server` folder of your machine to `/usr/src/app`, and starts the backend with `node --watch`:


Open `server/index.js` on your machine, change the response of the route that updates a to-do from `Todo was updated!` to `Todo updated with Okteto!`, and save the file:

```js title="server/index.js"
    // update a todo
    app.put('/todos/:id', async (req, res) => {
        try {
            const { id } = req.params;
            const { description } = req.body;
            const updateTodo = await pool.query("UPDATE todo SET description = $1 WHERE todo_id = $2", [description, id]);
            res.json("Todo updated with Okteto!");
```

Okteto synchronizes `index.js` to the Development Container, and Node.js restarts the backend:

```console
Change detected in '/usr/src/app/index.js'
Restarting 'index.js'
server started on port 5050
```

Update the first to-do through the API, with the endpoint that `okteto deploy` printed:

```bash
curl -X PUT -H "Content-Type: application/json" -d '{"description":"Walk the dog"}' https://todolist-cindy.okteto.example.com/todos/1
```

The backend answers with the new message, `"Todo updated with Okteto!"`. The change runs in your cluster without building an image or redeploying the application. Press `Ctrl+C` to exit `okteto up`, and run `okteto down server` to restore the original Deployment.

The frontend works the same way. Run `okteto up client` and edit a file of `client/src`, for example the placeholder text of `client/src/components/InputTodo.jsx`. Vite updates the page in your browser without reloading it:
