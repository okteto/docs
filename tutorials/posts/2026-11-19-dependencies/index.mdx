The `dependencies` section of the [Okteto Manifest](/docs/reference/okteto-manifest#dependencies-string-optional) deploys other Git repositories as part of your Development Environment. Okteto deploys them in parallel, and `depends_on` sets the ones that must deploy first. This tutorial uses the Movies app, whose database, API, and frontend live in three repositories, to deploy the whole application with a single `okteto deploy`. To do the same with your own multi-repo application, use an AI agent with the [Okteto agent skills](/docs/agentic/).

## Prerequisites

- Access to an Okteto instance, with your [Okteto context](/docs/reference/okteto-cli#context) configured.
- The [Okteto CLI](/docs/get-started/install-okteto-cli) 3.25.0 or later installed on your machine.
- A local copy of the repository that deploys the application:

```bash
git clone https://github.com/okteto/movies-multi-repo
cd movies-multi-repo
```

You don't need copies of the other repositories: Okteto clones them in your cluster.

## The Sample Application

The Movies app has a service in each of these repositories:

| Repository | Service | Deployed with |
|------------|---------|---------------|
| [`okteto/mongodb`](https://github.com/okteto/mongodb) | A MongoDB database | Docker Compose |
| [`okteto/movies-api`](https://github.com/okteto/movies-api) | A Node.js API that serves the movies under `/api` | A Helm chart |
| [`okteto/movies-frontend`](https://github.com/okteto/movies-frontend) | A React frontend | A Helm chart |

Each repository has its own Okteto Manifest that builds and deploys its service, so each team works on its repository without knowing how the others deploy. A fourth repository, [`okteto/movies-multi-repo`](https://github.com/okteto/movies-multi-repo), puts the application together: its Okteto Manifest lists the other three as dependencies, and its `deploy` section creates what belongs to the whole application, the Ingress that routes `/` to the frontend and `/api` to the API.

This is how Okteto works with multi-repo applications: a repository for the application lists the repositories of its services in `dependencies`, and one `okteto deploy` from it deploys everything in a Namespace. To work on a service, you run `okteto deploy` from the repository of that service, in the same Namespace, and optionally `okteto up`.

## The Okteto Manifest

The `okteto.yml` file of `movies-multi-repo` deploys the three repositories and then exposes the application:

```yaml title="okteto.yml"
dependencies:
  mongodb:
    repository: https://github.com/okteto/mongodb
    variables:
      MONGODB_PASSWORD: movies
  movies-frontend:
    repository: https://github.com/okteto/movies-frontend
    wait: true
  movies-api:
    repository: https://github.com/okteto/movies-api
    depends_on: mongodb
    variables:
      MONGODB_URL: ${OKTETO_DEPENDENCY_MONGODB_VARIABLE_MONGODB_URL}
    wait: true

deploy:
  - name: Expose the Movies app
    command: kubectl apply -f k8s.yml
```

Each entry of `dependencies` is a repository that Okteto deploys as a Development Environment of its own, with the name of the entry. Okteto clones the default branch of `repository` in your cluster and runs `okteto deploy` with the Okteto Manifest of the repository. The `branch` and `manifest` fields choose another branch or another path for the manifest.

The names of the entries match the names of the repositories. When you run `okteto up` from a clone of `movies-api`, Okteto looks for a Development Environment named after the repository, finds the one that `movies-multi-repo` deployed, and doesn't deploy it again.

### Parallel Deployment and `depends_on`

Okteto deploys the dependencies in parallel. `depends_on` makes a dependency wait until the dependencies it lists have deployed successfully:

- `mongodb` and `movies-frontend` don't depend on anything, so they start at the same time.
- `movies-api` has `depends_on: mongodb`. It starts once `mongodb` has deployed, because the API loads the sample movies into the database when it starts, and because it needs the connection string that `mongodb` exports. It doesn't wait for `movies-frontend`.

Okteto validates the graph when it loads the manifest: a name in `depends_on` that isn't another entry of `dependencies`, a dependency that depends on itself, and cycles fail before anything is deployed.

### Settings with `variables`

`variables` sets environment variables for the Okteto Manifest of a dependency. `mongodb` gets the password of its database user in `MONGODB_PASSWORD`. Its own Okteto Manifest deploys MongoDB with Docker Compose and, before that, writes the connection string to [`$OKTETO_ENV`](/docs/core/okteto-variables#okteto_env):

```yaml title="okteto.yml of okteto/mongodb"
deploy:
  commands:
    - name: Share the connection string
      command: echo "MONGODB_URL=mongodb://okteto:${MONGODB_PASSWORD:-password}@mongodb:27017/okteto" >> $OKTETO_ENV
  compose: docker-compose.yaml
```

Okteto keeps the variables that a dependency writes to `$OKTETO_ENV`, and exposes them to the other dependencies as `OKTETO_DEPENDENCY_<NAME>_VARIABLE_<VARIABLE>`: `MONGODB_URL` of `mongodb` is `OKTETO_DEPENDENCY_MONGODB_VARIABLE_MONGODB_URL`. A dependency gets these [dynamic environment variables](/docs/reference/okteto-cli#dynamic-environment-variables) only from the dependencies of its `depends_on`, which have finished deploying when it starts. That's how `movies-api` gets `MONGODB_URL` without hardcoding the password or the host of the database. Its Okteto Manifest passes the variable to its Helm chart, which stores it in a Secret:

```yaml title="okteto.yml of okteto/movies-api"
deploy:
  - name: Deploy API
    command: helm upgrade --install movies-api chart --set image=${OKTETO_BUILD_API_IMAGE} --set mongodb.url=${MONGODB_URL}
```

To change the password, you change `MONGODB_PASSWORD` in `movies-multi-repo`, and both services get the new value on the next deploy.

### Waiting for Dependencies

The commands of the `deploy` section start when the dependencies they need are ready. `wait: true` makes them wait until the dependency, and every dependency in its `depends_on` chain, is deployed and healthy:

- The Ingress routes traffic to `movies-frontend` and `movies-api`. Both have `wait: true`, so when `okteto deploy` finishes, the endpoint already serves the whole application.
- `mongodb` doesn't need `wait: true`: it's in the `depends_on` chain of `movies-api`, so the `deploy` commands wait for it too.

A dependency without `wait` and outside the `depends_on` chain of a waited dependency deploys at the same time as the `deploy` commands, and `okteto deploy` doesn't wait for it or fail when it fails.

### The `deploy` Section

The `deploy` section creates the Ingress of `k8s.yml`, with the `dev.okteto.com/generate-host` annotation, so Okteto gives the application a public HTTPS endpoint in each Namespace:

```yaml title="k8s.yml"
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: movies
  annotations:
    dev.okteto.com/generate-host: "true"
spec:
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 8080
```

The command runs in your cluster with [Remote Execution](/docs/core/remote-execution), so you don't need `kubectl` on your machine.

## Deploying the Application

Deploy the application from the root of `movies-multi-repo`:

```bash
okteto deploy --wait
```

Okteto deploys the three repositories, and runs the command of the `deploy` section. The lines of each dependency start with its name. This is the output, without the lines about cloning the repositories and starting the deploys:

Open `https://movies-cindy.okteto.example.com` in your browser, with your Namespace and the domain of your Okteto instance, to see the Movies app. Okteto lists each path of the Ingress under the Development Environment of the Service it routes to, so `okteto endpoints --name movies-frontend` prints the endpoint too.

## Redeploying the Dependencies

Run `okteto deploy` again, and Okteto skips the dependencies that are already deployed:

```console
 i  Deploying dependencies
[mongodb]  ✓  Skipping repository 'mongodb' because it's already deployed
[movies-frontend]  ✓  Skipping repository 'movies-frontend' because it's already deployed
[movies-api]  ✓  Skipping repository 'movies-api' because it's already deployed
```

This keeps your deploys fast while you work on `movies-multi-repo`. To deploy the latest code of every repository, for example after other teams merge changes, add the `--dependencies` flag:

```bash
okteto deploy --wait --dependencies
```

Okteto deploys the three repositories again, in the same order: `mongodb` and `movies-frontend` in parallel, and `movies-api` after `mongodb`.

## Developing on One of the Repositories

To change a service, work in its repository and deploy it to the same Namespace: the rest of the application keeps running from the deploy of `movies-multi-repo`. For example, clone the repository of the API next to `movies-multi-repo`:

```bash
git clone https://github.com/okteto/movies-api
cd movies-api
```

The **Continue watching for Cindy** row of the Movies app shows the same movies as the **Movies** row, because the `/api/watching` route of `server.js` reads the `movies` collection. Change that route to read the `watching` collection, and deploy the API from the folder of its repository:

```bash
okteto deploy --wait
```

Okteto finds the `movies-api` Development Environment that `movies-multi-repo` deployed, builds the new image of the API, and upgrades its Helm release, which keeps the connection to MongoDB. Reload the Movies app: the **Continue watching for Cindy** row now shows other movies, such as *Avengers: Infinity War*. The frontend and the database didn't change: you only deployed the service you work on. This is also the loop that an AI agent with the [Okteto agent skills](/docs/agentic/) runs on every change.

Optionally, for hot reload and a debugger on every change, run `okteto up` from the same folder: Okteto replaces the `api` Deployment with the Development Container that the `dev` section of the repository defines. While `okteto up` runs, an AI agent with the Okteto agent skills doesn't run the build and deploy cycle on every change: your changes reach the Development Container through File Sync, and you tell the agent what to run next. Run `okteto down` when you finish. The [Development Container guides](/docs/development/containers/) explain how to configure a Development Container for each language.

The frontend works the same way: clone [`okteto/movies-frontend`](https://github.com/okteto/movies-frontend), change it, and run `okteto deploy` from its folder.

## Cleaning Up

Destroy the application and its dependencies from the root of `movies-multi-repo`:

```bash
okteto destroy --dependencies --volumes
```

```console
 i  Using cindy @ okteto.example.com as context
 ✓  Repository 'movies-api' scheduled for destruction
 ✓  Repository 'mongodb' scheduled for destruction
 ✓  Repository 'movies-frontend' scheduled for destruction
 ✓  Development environment 'movies-multi-repo' successfully destroyed
```

Okteto destroys `movies-multi-repo` and schedules the destruction of each dependency in your cluster. `--volumes` also deletes the volume of MongoDB, with the sample movies. Without `--dependencies`, `okteto destroy` only destroys the resources of `movies-multi-repo`, the Ingress, and keeps the Development Environments of the three dependencies.

## FAQ

### How do I configure the Okteto Manifest of each service?

Each repository builds, tests, and develops its own service. The [Development Container guides](/docs/development/containers/) explain the `build`, `deploy`, `test`, and `dev` sections for each language.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. An AI agent with the [Okteto agent skills](/docs/agentic/) configures what each command uploads for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize your Development Environments](/tutorials/optimize-your-development-environment/) covers these and other optimizations.

### Do I need to deploy every repository in every Namespace?

No. [Divert](/docs/development/divert/) lets you deploy only the services you change and reuse the services of a shared environment.

### How do I start each environment with realistic data?

Create its database from a [Volume Snapshot](/docs/core/use-volume-snapshots/) instead of loading the data on every deploy. [Data from Volume Snapshots](/tutorials/optimize-your-development-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own cloud resources. [Create cloud infrastructure with Terraform](/tutorials/cloud-infrastructure/) creates an Amazon S3 bucket for each environment.

### Where can I find every field of a dependency?

The [`dependencies` reference](/docs/reference/okteto-manifest#dependencies-string-optional) describes every field of a dependency, such as `branch`, `manifest`, and `timeout`.
