Every minute an environment takes to be ready, someone is waiting: a developer who ran `okteto up`, a reviewer who opened a Preview Environment, a test suite in CI, an AI agent that wants to check its change. Agents wait the most, because they deploy and test many times a day, often in several environments at once.

That wait has three sources: images that build from scratch, files sent to the cluster that nobody needs, and databases filled by seed scripts. Each practice on this page removes part of one of them, and they add up: an environment whose images are already built, whose files are already in place, and whose database starts from a snapshot is ready in a fraction of the time.

## Images and Builds

### Pinned Image Tags

Use an explicit version tag or a digest. With `latest`, Kubernetes pulls the image every time a container starts instead of reusing the copy already on the node.

```yaml
# Avoid
image: registry/redis:latest

# Use instead
image: registry/redis:8.2.1
# or
image: registry/redis@sha256:2678c...
```

### Smart Builds

[Smart Builds](/docs/core/build-service/#smart-builds) skip the build of an image when an image built from the same code and configuration already exists, for example because a teammate already built it. They're on by default in most Git repositories. `okteto deploy` shows the images it skips:

```
 i  Okteto Smart Builds is skipping build of 'frontend' because it's already built from cache.
 i  Okteto Smart Builds is skipping build of 'api' because it's already built from cache.
```

### Dockerfile Order

Put the instructions that rarely change first and the ones that change often last, so the build reuses the cached layers up to the first change. Docker's guide on [ordering your layers](https://docs.docker.com/build/cache/optimize/#order-your-layers) explains it in detail.

```docker
# Rarely changes
FROM node:22-alpine
RUN apk add --no-cache bash

# Changes occasionally
COPY package.json package-lock.json ./
RUN npm install

# Changes frequently
COPY src/ ./src
```

### Specific COPY Instructions

Copy only the files the image needs. `COPY . .` invalidates the cache whenever any file of the folder changes. Docker's [best practices for COPY](https://docs.docker.com/build/building/best-practices/#add-or-copy) cover the details.

```docker
# Avoid
COPY . .

# Use instead
COPY package.json .
COPY src/ src/
```

### Ownership on Copy

Set the owner of files when you copy them instead of changing it afterwards with a recursive command, which rewrites every file into a new layer:

```docker
# Avoid
RUN chown -R user:group /app/dist

# Use instead
COPY --from=build --chown=user:group /app/dist /app/dist
```

### Cache Mounts

BuildKit [cache mounts](https://docs.docker.com/build/cache/optimize/#use-cache-mounts) keep dependency and compiler caches between builds, so a build reuses the packages and artifacts it already downloaded or compiled. Common caches are the npm or Yarn cache for Node.js, `.m2` for Maven, and `.cache/go-build` for Go.

```docker
FROM golang:1.24

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY main.go main.go
RUN --mount=type=cache,sharing=private,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -o /usr/src/api
```

## Build Context and File Synchronization

### Build Context

A `.dockerignore` file limits the files sent to build an image. Exclude everything, and then include only the files the build needs:

```gitignore title=".dockerignore"
# Exclude everything
*

# Include only what the build needs
!Dockerfile
!okteto.yml
!docker-compose.yml
!package.json
!src/**
```

When a repository has several Dockerfiles, each one can have its own ignore file next to it, such as `dev.Dockerfile.dockerignore`.

### Deploy and Test Context

A `.oktetoignore` file limits the files sent to run the `deploy` and `test` commands with [Remote Execution](/docs/core/remote-execution/#ignoring-files). It uses the syntax of `.gitignore`, with a section for each phase:

```gitignore title=".oktetoignore"
# Exclude everything
*

# Include only what the deploy commands need
[deploy]
!helm/**
!k8s/**

# Include only what the tests need
[test]
!tests/**
```

### File Synchronization

A `.stignore` file limits the files that `okteto up` [synchronizes](/docs/reference/file-synchronization/#ignoring-files) to the Development Container. Synchronize the source code you edit, not generated artifacts. Unlike `.dockerignore`, `.stignore` applies the first pattern that matches a file, so the `!` patterns go before the catch-all `*`:

```gitignore title=".stignore"
# Include only the source code
!src/**
!public/**

# Exclude everything else
*
```

### Source Code in the Development Image

With a multi-stage Dockerfile, use the stage that already contains your source code as the image of the Development Container. The first synchronization only sends what changed, and the build caches of that stage are already warm:

```docker
FROM golang:1.24 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY main.go main.go
RUN go build -o myapp

FROM alpine AS production
WORKDIR /app
COPY --from=builder /app/myapp .
```

```yaml title="okteto.yaml"
build:
  myapp:
    context: .
    target: production
  myapp-dev:
    context: .
    target: builder

dev:
  myapp:
    image: ${OKTETO_BUILD_MYAPP_DEV_IMAGE}
```

## Data and Shared Services

### Volume Snapshots Instead of Seed Scripts

Seed scripts are slow and break when the schema changes. [Volume Snapshots](/docs/core/use-volume-snapshots/) start the database of each environment with a copy of real data instead. [Create and use Volume Snapshots](/tutorials/create-and-use-volume-snapshots/) shows how.

### Divert

Not every environment needs its own copy of every service. With [Divert](/docs/development/divert/), an environment deploys only the services you change and shares the rest with a shared environment, so it's ready sooner and uses fewer resources. [Why flexibility is key to scaling development environments](/blog/why-flexibility-is-key-to-scaling-development-environments/) explains when to use it.

## Development Containers and Tests

### Volumes in Development Containers

[Volumes](/docs/reference/okteto-manifest/#volumes-string-optional) keep files between `okteto up` sessions, so the Development Container doesn't download or build them again every time it starts. Use them for dependencies, such as `node_modules` or `vendor/`, and for build caches, such as `.m2` or `.cache/go-build`:

```yaml title="okteto.yaml"
dev:
  app:
    volumes:
      - /usr/src/app/node_modules
      - /root/.m2
      - /root/.cache/go-build
```

### Caches in Tests

[Caches](/docs/reference/okteto-manifest/#caches-string-optional) keep files between runs of `okteto test`, so a test doesn't install its dependencies or rebuild its caches every time:

```yaml title="okteto.yaml"
test:
  unit:
    image: node:22
    caches:
      - /usr/src/app/node_modules
      - /usr/src/app/downloaded_assets
    commands:
      - npm install
      - npm test
```

## Agents

The same practices make AI agents faster, because agents get feedback by deploying their changes and running tests in a live environment, and wait for it like a developer does. The [Okteto plugin for Claude Code](/docs/agentic/) packages your `okteto.yaml`, the commands agents should run, and the commands they must never run as agent skills, so an agent deploys, tests, and debugs in the same environments as your team.
