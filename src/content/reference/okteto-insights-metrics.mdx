Okteto Insights exposes a metrics endpoint that you can scrape to collect data on resource usage, builds, and deployments. The data comes from developer activity on the platform: product usage, infrastructure utilization, and performance. Use it to monitor the health of your Okteto cluster, track trends in build and deploy times, and measure user activity.

:::info
On Bring Your Own Cloud (BYOC), Okteto Insights comes with preconfigured Grafana dashboards. [Okteto Insights Dashboards](core/okteto-insights-dashboards.mdx) explains how to open them and what they show. Use this page only if you want another tool to read the Insights data.
:::

## Consuming Okteto Insights Data

Okteto Insights serves its data on an endpoint that tools such as Prometheus can scrape, so Admins can consume it programmatically. To set it up, enable Insights, get your bearer token, and deploy the [open-source Insights Dashboards](https://github.com/okteto/insights-dashboards) to visualize your Okteto data.

### Enabling the Metrics Endpoint

Okteto Insights is disabled by default on Self-Hosted instances. To enable it, set the Helm setting [`insights.enabled`](self-hosted/helm-configuration.mdx#insights) to `true` and upgrade your Okteto instance.

Okteto then serves the data in Prometheus format at `https://okteto.SUBDOMAIN/metrics`. A bearer token that Okteto generates protects the endpoint. To use your own token instead, store it in the secret that the [`insights` Helm setting](self-hosted/helm-configuration.mdx#insights) defines.

### Retrieving Your Bearer Token

In the Admin Dashboard, [**Admin > Integrations > General**](admin/general-integrations.mdx#okteto-insights-token) has your Insights bearer token. Click **Show Insights Token** in the **Insights** row to see it and copy it.

### Setting Up the Dashboards

To collect and visualize Insights data, start from the [Okteto Insights Dashboards repository](https://github.com/okteto/insights-dashboards). It includes setups to deploy Prometheus and Grafana, and sample dashboards.

To configure it yourself, set up a scraper that connects to the endpoint with your bearer token. For example, this Prometheus scrape configuration:

```yaml
- job_name: "okteto_scrapper"
  scrape_interval: 5m
  scrape_timeout: 30s

  scheme: https
  static_configs:
    - targets: ["okteto.<SUBDOMAIN>:443"] # replace <SUBDOMAIN> with your Okteto subdomain
  authorization:
    type: Bearer
    credentials: <bearer-token> # replace <bearer-token> with the token generated by Okteto
```

:::caution
Okteto Self-Hosted **doesn't** include a Prometheus instance or storage for this data.
Deploy your own Prometheus instance, or another data collection platform, to consume the data and manage counters and metrics with Prometheus' built-in features.

The [Okteto Insights Dashboards repository](https://github.com/okteto/insights-dashboards) includes a Prometheus configuration to start from.
:::

## What data is available

Okteto Insights has these groups of metrics:

- [Build Metrics](#build-metrics): build times and results, by environment
- [Deploy Metrics](#deploy-metrics): deploy times and results, by environment
- [Namespace Metrics](#namespace-metrics): sleeping and awake Namespaces
- [Node Metrics](#node-metrics): CPU and memory of your Okteto nodes
- [Pod Metrics](#pod-metrics): CPU and memory of your Okteto pods
- [Preview Metrics](#preview-metrics): sleeping and awake Preview Environments
- [Test Metrics](#test-metrics): test times and results, by environment
- [User Metrics](#user-metrics): user activity

:::note
Every metric that Okteto provides has the `okteto_` prefix.
:::

Okteto adds metrics to this endpoint over time. These are the metrics available today:

### Build Metrics

:::note
Only successful builds are tracked with `okteto_usage_build_duration_seconds`.
:::

| Metric Name  | Type         | Description  | Labels       |
| :----------- | :----------- | :----------- | :----------- |
| `okteto_usage_build_duration_seconds` | [histogram](https://prometheus.io/docs/practices/histograms/) | Time to build each image that Okteto builds. It only reflects successful builds. | `devenv_name`, `image_name`, `namespace`, `repository` |
| `okteto_usage_build_result` | [counter](https://prometheus.io/docs/concepts/metric_types/#counter) | Result of each image build in Okteto. | `devenv_name`, `image_name`, `namespace`, `repository`, `result` |

- **Build Metrics label definitions:**
  - **`devenv_name`**: The name of the deployed application environment that the build belongs to, if any
  - **`image_name`**: The name of the image, as it appears in the Okteto Manifest
  - **`namespace`**: The Okteto CLI context that the request came from
  - **`repository`**: The Git repository that hosts the Okteto Manifest that defines the image
  - **`result`**: The status of the build: `success`, `failure`, or `skipped`

### Deploy Metrics

:::note
Only successful deployments are tracked with `okteto_usage_deploy_duration_seconds`.
:::

| Metric Name  | Type         | Description  | Labels       |
| :----------- | :----------- | :----------- | :----------- |
| `okteto_usage_deploy_duration_seconds` | [histogram](https://prometheus.io/docs/practices/histograms/) | Time to deploy an application environment. It only reflects successful deployments. | `devenv_name`, `namespace`, `repository`, `phase` |
| `okteto_usage_deploy_result` | [counter](https://prometheus.io/docs/concepts/metric_types/#counter) | Result of each deployment of an application environment. | `devenv_name`, `namespace`, `repository`, `result` |

- **Deploy Metrics label definitions:**
  - **`devenv_name`**: The name of the deployed application environment
  - **`namespace`**: The Okteto CLI context that the request came from
  - **`repository`**: The Git repository that hosts the Okteto Manifest that defines the application environment
  - **`phase`**: The phase of the deployment that the time series measures: `compose` for the [Compose](reference/okteto-manifest.mdx#deploy-with-compose) section or `commands` for the [Commands](reference/okteto-manifest.mdx#deploy-with-commands) section of the Okteto Manifest's `deploy` section. The sum of both time series is the total length of a deployment.
  - **`result`**: The status of the deployment: `success` or `failure`

### Namespace Metrics

| Metric Name  | Type         | Description  | Labels       |
| :----------- | :----------- | :----------- | :----------- |
| `okteto_system_namespace_status_condition` | [gauge](https://prometheus.io/docs/concepts/metric_types/#gauge) | Status of a Namespace. It doesn't include the Namespaces of Preview Environments. | `namespace`, `condition`, `owner_id` |
| `okteto_system_namespace_created_time` | [gauge](https://prometheus.io/docs/concepts/metric_types/#gauge) | Creation time of a Namespace. | `namespace`, `owner_id` |

- **Namespace Metrics label definitions:**
  - **`namespace`**: The name of the Namespace
  - **`condition`**: The condition of the Namespace: `active` or `sleeping`
  - **`owner_id`**: The ID of the Namespace's owner

  - **`pod_name`**: The name of the pod

  - **`pod_type`**: Whether the pod is in development mode: `development` or `standard`
  - **`controller_type`**: The type of the top controller that created the pod: `deployment` or `statefulset`
  - **`controller_name`**: The name of the top controller that created the pod

## Troubleshooting

### Metrics Server Availability

Okteto Insights relies on the Kubernetes Metrics Server. If the Metrics Server is unavailable, requests to the `/metrics` endpoint fail, including the requests from a [configured scraper](#setting-up-the-dashboards). See the [Metrics Server documentation](https://kubernetes.io/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/#metrics-server) to troubleshoot it.
