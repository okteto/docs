Okteto runs your Python application in Kubernetes while you edit it on your machine: every time you save a file, the change runs in your cluster a few seconds later, and you can debug it with breakpoints from your IDE. The [Python Sample App](https://github.com/okteto/python-getting-started), a hello world [FastAPI](https://fastapi.tiangolo.com/) application, is configured so that Okteto builds, deploys, and tests it directly in your Kubernetes cluster. To do the same in your own repository, we recommend using an AI agent with the [Okteto agent skills](agentic/index.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [PyCharm Professional](https://www.jetbrains.com/pycharm/), which includes the Python Debug Server.

Clone the Python Sample App:

```bash
git clone https://github.com/okteto/python-getting-started
cd python-getting-started
```

## The Dockerfile

The `Dockerfile` of the Python Sample App defines two images, one per stage:

```dockerfile title="Dockerfile"
FROM python:3.15.2-trixie AS dev

RUN pip install --no-cache-dir pydevd-pycharm==263.7307.329

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.15.2-slim-trixie AS prod

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
```

- `dev` is the development image. It contains Python, the build tools that `pip` needs to compile packages, the dependencies in `requirements.txt` (FastAPI and [Uvicorn](https://www.uvicorn.org/), which also reloads the application in the Development Container), [pydevd-pycharm](https://pypi.org/project/pydevd-pycharm/) for debugging with PyCharm, and the source code. `requirements.txt` is copied and installed before the source code, so a change to `app.py` doesn't reinstall the dependencies.
- `prod` is the application image. It contains the slim Python runtime, the dependencies in `requirements.txt`, and `app.py`, without the debugger. Uvicorn serves the application on port `8080`.

The `dev` stage follows the recommendations for [development images](development/images.mdx): every version is pinned, and the application image installs the same `requirements.txt` as the development image.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the Python Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

## Testing the Python Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the unit tests in `test_app.py` with [pytest](https://docs.pytest.org/) and the [FastAPI test client](https://fastapi.tiangolo.com/tutorial/testing/):

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r requirements-test.txt
      - pytest --junitxml=report.xml
    artifacts:
      - report.xml
```

- `image`: the development image, so the tests run with the same Python version and dependencies as the Development Container.
- `caches`: the pip cache, kept between runs of the Test Container. `pip install` downloads the test dependencies on the first run and installs them from the cache on the next ones.
- `commands`: the commands that run the tests. `requirements-test.txt` adds pytest and `httpx2`, the HTTP client of the FastAPI test client, to the dependencies in `requirements.txt`, which the development image already has. The Test Container fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the JUnit report of pytest.

Test Containers run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the Python Sample App:

```bash
okteto test
```

## Developing in a Development Container

If you use AI agents, the Development Container is optional: agents work well with the `okteto deploy` and `okteto test` cycle, and don't need one. A Development Container gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster.

While `okteto up` is running, an AI agent with the [Okteto agent skills](agentic/index.mdx) skips the build and deploy cycle: your changes already reach the Development Container through File Sync, so the agent waits for you to tell it what to run next.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Python Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: uvicorn app:app --host 0.0.0.0 --port 8080 --reload
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    reverse:
      - 9000:9000
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts Uvicorn with `--reload`, which restarts the application every time a `.py` file changes.
- `sync`: synchronizes the root folder of the Python Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach.
- `reverse`: forwards port `9000` of the Development Container to port `9000` of your machine, where the PyCharm debugger listens.

### Hot reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

### Debugging with PyCharm

PyCharm listens for the debugger on your machine, and the debugger in the Development Container (`pydevd-pycharm`) connects to it through port `9000`, which `okteto up` forwards from the Development Container to your machine.

The version of `pydevd-pycharm` must match the build of your PyCharm. Open **Run > Edit Configurations**, select the **Remote** configuration of the Python Sample App, and check the `pip install pydevd-pycharm~=<build>` command that PyCharm shows. If the build is different from `263.7307.329`, change the version in the `Dockerfile` and run `okteto deploy` to rebuild the development image.

The `.idea/runConfigurations/Remote.xml` file of the Python Sample App defines the **Remote** configuration, a Python Debug Server on port `9000`:

```xml title=".idea/runConfigurations/Remote.xml"
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="Remote" type="PyRemoteDebugConfigurationType" factoryName="Python Remote Debug">
    <module name="python-getting-started" />
    <option name="PORT" value="9000" />
    <option name="HOST" value="localhost" />
    <PathMappingSettings>
      <option name="pathMappings">
        <list>
          <mapping local-root="$PROJECT_DIR$" remote-root="/usr/src/app" />
        </list>
      </option>
    </PathMappingSettings>
    <option name="REDIRECT_OUTPUT" value="true" />
    <option name="SUSPEND_AFTER_CONNECT" value="false" />
    <method v="2" />
  </configuration>
</component>
```

`remote-root` is the path in the `sync` field of the Okteto Manifest. If you synchronize your code to another path, change `remote-root` to match it.

Open the Python Sample App in PyCharm and debug the **Remote** configuration. The **Debug** tool window shows `Waiting for process connection...`. Start the **Remote** configuration before you uncomment `attach()`, because `attach()` connects to it when the application starts.

With `okteto up` running, uncomment the call to `attach()` on line 20 of `app.py` and save the file:

```python title="app.py"
def attach():
    import pydevd_pycharm
    print('Connecting to debugger...')
    pydevd_pycharm.settrace('localhost', port=9000, suspend=False, stdout_to_server=True, stderr_to_server=True)

# uncomment to use PyCharm's remote debugger
attach()
```

Uvicorn restarts the server process, and `attach()` connects it to PyCharm through port `9000` when the server process imports `app.py`:

```console
WARNING:  StatReload detected changes in 'app.py'. Reloading...
INFO:     Finished server process [111]
Connecting to debugger...
INFO:     Started server process [112]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
```

The **Debug** tool window shows `Connected to pydev debugger`:

<Image
  src={require("@site/static/img/python-connected.png").default}
  alt="PyCharm Debug console showing a successful connection to the pydev remote debugger on port 9000"
  width="850"
/>

Add a breakpoint on line 10 of `app.py` and reload the endpoint in your browser. Execution stops at the breakpoint, and you can inspect the request and the variables. Every time you save a file, Uvicorn starts a new server process, and `attach()` connects it to PyCharm again.

To stop debugging, comment the call to `attach()` again and save `app.py`. Press `Ctrl+C` to stop Uvicorn and exit `okteto up`.

## Cleaning up

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

When you're done, `okteto destroy` uninstalls the Helm release of the Python Sample App from your Namespace:

```bash
okteto destroy
```

## FAQ

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](core/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](reference/file-synchronization.mdx#ignoring-files) for File Sync. An AI agent with the [Okteto agent skills](agentic/index.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize your Development Environments](/tutorials/optimize-your-development-environment/) covers these and other optimizations.

### How do I deploy an application with several services and a database?

Follow [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) if you deploy with a Helm chart, or [Develop a Docker Compose application with Okteto](/tutorials/compose-getting-started/) if you use Docker Compose. If your services live in several repositories, see [Deploy a multi-repo application with dependencies](/tutorials/dependencies/).

### Do I need to deploy the whole application in every Namespace?

No. [Divert](development/divert/index.mdx) lets you deploy only the services you change and reuse the services of a shared environment.

### How do I start each environment with realistic data?

Create its database from a [Volume Snapshot](core/use-volume-snapshots.mdx) instead of running a seed script on every deploy. [Data from Volume Snapshots](/tutorials/optimize-your-development-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own cloud resources. [Create cloud infrastructure with Terraform](/tutorials/cloud-infrastructure/) shows how, with an Amazon S3 bucket for each environment.

### Where can I find every field of the Okteto Manifest?

The [Okteto Manifest reference](reference/okteto-manifest.mdx) lists every field of `build`, `deploy`, `destroy`, `test`, and `dev`.
