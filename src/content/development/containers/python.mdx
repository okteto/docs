Okteto replaces your Python application in Kubernetes with a Development Container that reloads it every time you save a file. The [Python Sample App](https://github.com/okteto/python-getting-started) is a hello world [Flask](https://flask.palletsprojects.com/) server that builds its application image and its development image from one Dockerfile, runs its unit tests in a Test Container, reloads with the Flask reloader when a `.py` file changes, and connects to the [PyCharm](https://www.jetbrains.com/pycharm/) debugger so you can debug it from your machine.

:::tip
The `.dockerignore`, `.oktetoignore`, and `.stignore` files are key to performance. They decide which files Okteto sends to the image builds, to Remote Execution, and to File Sync. Without them, every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` transfers the whole repository, `.git` folder included, and a change to any file invalidates the build cache.
:::

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [PyCharm Professional](https://www.jetbrains.com/pycharm/), which includes the Python Debug Server.

Clone the Python Sample App:

```bash
git clone https://github.com/okteto/python-getting-started
cd python-getting-started
```

## The Dockerfile

The `Dockerfile` of the Python Sample App defines two images, one per stage:

```dockerfile title="Dockerfile"
FROM python:3.15.2-trixie AS dev

RUN pip install --no-cache-dir pydevd-pycharm==263.7307.206

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.15.2-slim-trixie AS prod

WORKDIR /usr/src/app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
CMD ["python", "app.py"]
```

- `dev` is the development image. It contains Python, the build tools that `pip` needs to compile packages, the PyCharm debugger (`pydevd-pycharm`), the dependencies of `requirements.txt`, and the source code. `requirements.txt` is copied and installed before the source code, so a change to `app.py` doesn't reinstall the dependencies.
- `prod` is the application image. It contains the slim Python runtime, the dependencies of `requirements.txt`, and `app.py`, without the debugger.

The `dev` stage follows the recommendations for [development images](development/images.mdx): every version is pinned, and the application image installs the same `requirements.txt` as the development image.

The `.dockerignore` file limits the build context to the files that `pip install` and the application need:

```text title=".dockerignore"
*
!requirements.txt
!*.py
```

Without it, the `.git` folder, your local virtual environment, and the rest of the repository end up in the development image, and a change to any file, such as `README.md`, invalidates the build cache. If your application has packages in subfolders or reads other files, for example Flask templates, add them with a `!` pattern.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the Python Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects the stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and exposes their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section deploys the application image:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

`envsubst` replaces `${OKTETO_BUILD_HELLO_WORLD_IMAGE}` in `k8s.yml` with the image that Okteto built, and `kubectl` applies the Deployment, Service, and Ingress of `k8s.yml`.

The deploy commands run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster, with an image that includes `kubectl` and `envsubst`.

:::tip
To run your deploy commands with your own tools, set the image of that container in `deploy.image` and move the commands to `deploy.commands`. The image must include `/bin/sh` and every tool that your commands run. [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) covers the `build`, `deploy`, and `test` sections of an application with several services.
:::

The `[deploy]` and `[destroy]` groups of the `.oktetoignore` file limit the files that the Okteto CLI sends to Remote Execution for `okteto deploy` and `okteto destroy` to `k8s.yml`, the only file the deploy commands read:

```text title=".oktetoignore"
# Files that the Okteto CLI sends to Remote Execution.

# "okteto deploy" and "okteto destroy" only need the Kubernetes manifests
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

## Testing the Python Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the unit tests of `test_app.py` with [pytest](https://docs.pytest.org/) and the Flask test client:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.cache/pip
    commands:
      - pip install -r requirements-test.txt
      - pytest --junitxml=report.xml
    artifacts:
      - report.xml
```

- `image`: the development image, so the tests run with the same Python version and dependencies as the Development Container.
- `caches`: the pip cache, kept between runs of the Test Container. `pip install` downloads pytest on the first run and installs it from the cache on the next ones.
- `commands`: the commands that run the tests. `requirements-test.txt` adds pytest to the dependencies of `requirements.txt`, which the development image already has. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the JUnit report of pytest.

Test Containers run with [Remote Execution](core/remote-execution.mdx#ignoring-files). The `[test]` group of the `.oktetoignore` file sends them only `requirements.txt`, `requirements-test.txt`, and the `.py` files:

```text title=".oktetoignore"
# "okteto test" only needs what "pip install" and "pytest" read
[test]
*
!requirements.txt
!requirements-test.txt
!*.py
```

Run the unit tests from the root folder of the Python Sample App:

```bash
okteto test
```

## Developing in a Development Container

To get the experience of developing on your machine, with hot reload and a debugger on every change, configure a Development Container in your Okteto Manifest. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, synchronizes your local files with it, and runs the hot-reload and debugging tools of the development image in your cluster.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Python Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: python app.py
    environment:
      - FLASK_DEBUG=1
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    reverse:
      - 9000:9000
```

The `hello-world` key matches the name of the Deployment in `k8s.yml`. The fields of the Development Container are:

- `image`: the development image built in the `build` section.
- `command`: starts the application.
- `environment`: `FLASK_DEBUG=1` runs Flask in debug mode, which enables the Flask reloader. The reloader restarts the application every time a `.py` file changes.
- `sync`: synchronizes the root folder of the Python Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach.
- `reverse`: forwards port `9000` of the Development Container to port `9000` of your machine, where the PyCharm debugger listens.

The `.stignore` file lists the files that [File Sync](reference/file-synchronization.mdx#ignoring-files) skips in both directions:

```text title=".stignore"
# Git metadata: large, and only needed on your machine
.git

# Files generated inside the development container
__pycache__
/.pytest_cache
/report.xml

# Local-only files
.venv
venv
.idea
.vscode
.DS_Store
```

`.git`, your local virtual environment (`.venv` or `venv`), and the settings of your IDE stay on your machine. The bytecode that Python (`__pycache__`) and the test files that pytest (`.pytest_cache` and `report.xml`) generate in the Development Container stay in the Development Container.

### Hot reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts the application. With `FLASK_DEBUG=1`, Flask runs the application in a child process that the reloader restarts:

```console

 i  Images were already built. To rebuild your images run 'okteto build'

    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world
    Reverse:   9000 <- 9000

Starting hello-world server...
```

Open `app.py` in your local IDE, change the response message on line 8 to `Hello world from Okteto!`, and save the file:

```python title="app.py"
@app.route('/')
def hello_world():
    msg = 'Hello world from Okteto!'
    return msg
```

Okteto synchronizes `app.py` to the Development Container, and the Flask reloader restarts the application:

```console

 * Restarting with stat
Starting hello-world server...
 * Debugger is active!
```

Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop the application and exit `okteto up`.

### Debugging with PyCharm

PyCharm listens for the debugger on your machine, and the debugger in the Development Container (`pydevd-pycharm`) connects to it through port `9000`, which `okteto up` forwards from the Development Container to your machine.

The version of `pydevd-pycharm` must match the build of your PyCharm. Open **Run > Edit Configurations**, select the **Remote** configuration of the Python Sample App, and check the `pip install pydevd-pycharm~=<build>` command that PyCharm shows. If the build is different from `263.7307.206`, change the version in the `Dockerfile` and run `okteto deploy` to rebuild the development image.

The `.idea/runConfigurations/Remote.xml` file of the Python Sample App defines the **Remote** configuration, a Python Debug Server on port `9000`:

```xml title=".idea/runConfigurations/Remote.xml"
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="Remote" type="PyRemoteDebugConfigurationType" factoryName="Python Remote Debug">
    <module name="python-getting-started" />
    <option name="PORT" value="9000" />
    <option name="HOST" value="localhost" />
    <PathMappingSettings>
      <option name="pathMappings">
        <list>
          <mapping local-root="$PROJECT_DIR$" remote-root="/usr/src/app" />
        </list>
      </option>
    </PathMappingSettings>
    <option name="REDIRECT_OUTPUT" value="true" />
    <option name="SUSPEND_AFTER_CONNECT" value="false" />
    <method v="2" />
  </configuration>
</component>
```

`remote-root` is the path in the `sync` field of the Okteto Manifest. If you synchronize your code to another path, change `remote-root` to match it.

Open the Python Sample App in PyCharm and debug the **Remote** configuration. The **Debug** tool window shows `Waiting for process connection...`. Start the **Remote** configuration before you uncomment `attach()`, because `attach()` connects to it when the application starts.

With `okteto up` running, uncomment the call to `attach()` on line 20 of `app.py` and save the file:

```python title="app.py"
if __name__ == '__main__':
  print('Starting hello-world server...')
  # uncomment to use PyCharm's remote debugger
  attach()

  app.run(host='0.0.0.0', port=8080)
```

The Flask reloader restarts the application, and `attach()` connects it to PyCharm through port `9000`:

```console
 * Detected change in '/usr/src/app/app.py', reloading
 * Restarting with stat
Starting hello-world server...
Connecting to debugger...
```

The **Debug** tool window shows `Connected to pydev debugger`:

<Image
  src={require("@site/static/img/python-connected.png").default}
  alt="PyCharm Debug console showing a successful connection to the pydev remote debugger on port 9000"
  width="850"
/>

If the application stops in `attach()`, press **Resume Program** to let it start. Add a breakpoint on line 9 of `app.py` and reload the endpoint in your browser. The execution stops at the breakpoint, and you can inspect the request and the variables.

To stop debugging, comment the call to `attach()` again and save `app.py`. Press `Ctrl+C` to stop the application and exit `okteto up`.

## Cleaning up

`okteto down` deactivates the Development Container and restores the `hello-world` Deployment with the application image:

```bash
okteto down
```

`okteto destroy` deletes the Deployment, Service, and Ingress of the Python Sample App from your Namespace:

```bash
okteto destroy
```
