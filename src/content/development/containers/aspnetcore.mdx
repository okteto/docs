Okteto replaces your ASP.NET Core application in Kubernetes with a Development Container that updates it every time you save a file. The [ASP.NET Core Sample App](https://github.com/okteto/aspnetcore-getting-started) is a hello world web API that builds its application image and its development image from one Dockerfile, runs its unit tests in a Test Container, reloads with [`dotnet watch`](https://learn.microsoft.com/aspnet/core/test/hot-reload) when a `.cs` file changes, and runs the .NET debugger (`vsdbg`) so you can debug it from VS Code.

:::tip
The `.dockerignore`, `.oktetoignore`, and `.stignore` files are key to performance. They decide which files Okteto sends to the image builds, to Remote Execution, and to File Sync. Without them, every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` transfers the whole repository, `.git` folder included, and a change to any file invalidates the build cache.
:::

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [C# extension](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csharp), and an `ssh` client on your machine.

Clone the ASP.NET Core Sample App:

```bash
git clone https://github.com/okteto/aspnetcore-getting-started
cd aspnetcore-getting-started
```

## The Dockerfile

The `Dockerfile` of the ASP.NET Core Sample App defines two images, one per stage:

```dockerfile title="Dockerfile"
FROM mcr.microsoft.com/dotnet/sdk:10.0.404-noble AS dev

RUN curl -sSL https://aka.ms/getvsdbgsh | bash /dev/stdin -v 18.7.10521.2 -l /usr/local/bin/vsdbg

WORKDIR /usr/src/app
COPY helloworld.csproj .
RUN dotnet restore
COPY . .
RUN dotnet build && \
    dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0.15-noble-chiseled AS prod

WORKDIR /app
COPY --from=dev /app .
ENTRYPOINT ["dotnet", "helloworld.dll"]
```

- `dev` is the development image. It contains the .NET SDK, `vsdbg`, and the source code. `dotnet restore` runs before the source code is copied, so the restore layer stays cached until `helloworld.csproj` changes. `dotnet build` fills the `bin` and `obj` folders of the image, so the first build of `dotnet watch` in the Development Container is incremental. `dotnet publish` writes the application to `/app`.
- `prod` is the application image. It contains only the ASP.NET Core runtime and the application published in the `dev` stage. [Chiseled images](https://learn.microsoft.com/dotnet/core/docker/container-images) have no shell or package manager, and run as a non-root user.

The `dev` stage follows the recommendations for [development images](development/images.mdx): every version is pinned, and the builder stage of the application image is the development image.

The `.dockerignore` file limits the build context to the files that `dotnet restore` and `dotnet publish` need:

```text title=".dockerignore"
*
!*.csproj
!**/*.cs
!appsettings*.json
**/bin/**
**/obj/**
tests/**
```

Without it, the `.git` folder and the rest of the repository end up in the development image, and a change to any file, such as `README.md`, invalidates the build cache. The `bin` and `obj` folders that `dotnet` generates on your machine and the unit tests in `tests` stay out of the images too. If your application reads other files, for example static files in `wwwroot`, add them with a `!` pattern.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the ASP.NET Core Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects the stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so the build of `hello-world` reuses the cached layers of the `dev` stage. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and exposes their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section deploys the application image:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

`envsubst` replaces `${OKTETO_BUILD_HELLO_WORLD_IMAGE}` in `k8s.yml` with the image that Okteto built, and `kubectl` applies the Deployment, Service, and Ingress of `k8s.yml`.

The deploy commands run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster, with an image that includes `kubectl` and `envsubst`.

:::tip
To run your deploy commands with your own tools, set the image of that container in `deploy.image` and move the commands to `deploy.commands`. The image must include `/bin/sh` and every tool that your commands run. [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) covers the `build`, `deploy`, and `test` sections of an application with several services.
:::

The `[deploy]` and `[destroy]` groups of the `.oktetoignore` file limit the files that the Okteto CLI sends to Remote Execution for `okteto deploy` and `okteto destroy` to `k8s.yml`, the only file the deploy commands read:

```text title=".oktetoignore"
# Files that the Okteto CLI sends to Remote Execution.

# "okteto deploy" and "okteto destroy" only need the Kubernetes manifests
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

## Testing the ASP.NET Core Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the [xUnit](https://xunit.net/) tests of the `tests` folder:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.nuget/packages
    commands:
      - dotnet test --project tests --report-xunit-trx --report-xunit-trx-filename test-results.trx --results-directory .
    artifacts:
      - test-results.trx
```

- `image`: the development image, so the tests run with the same .NET SDK as the Development Container.
- `caches`: the NuGet packages folder, kept between runs of the Test Container, so `dotnet test` doesn't download the xUnit packages again.
- `commands`: the commands that run the tests. `dotnet test` builds the `tests` project, runs its tests, and writes the results to `test-results.trx`. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test results.

xUnit v3 runs on [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro), and the `global.json` file tells `dotnet test` to use it:

```json title="global.json"
{
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

Test Containers run with [Remote Execution](core/remote-execution.mdx#ignoring-files). The `[test]` group of the `.oktetoignore` file sends them only `global.json` and the `.csproj` and `.cs` files, without the `bin` and `obj` folders:

```text title=".oktetoignore"
# "okteto test" only needs what "dotnet test" reads
[test]
*
!**/*.csproj
!**/*.cs
!global.json
**/bin/**
**/obj/**
```

Run the unit tests from the root folder of the ASP.NET Core Sample App:

```bash
okteto test
```

## Developing in a Development Container

To get the experience of developing on your machine, with hot reload and a debugger on every change, configure a Development Container in your Okteto Manifest. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, synchronizes your local files with it, and runs the hot-reload and debugging tools of the development image in your cluster.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the ASP.NET Core Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: dotnet watch
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
```

The `hello-world` key matches the name of the Deployment in `k8s.yml`. The fields of the Development Container are:

- `image`: the development image built in the `build` section.
- `command`: starts `dotnet watch`, which builds and runs the application. When a `.cs` file changes, `dotnet watch` applies the change to the running application with hot reload, or rebuilds and restarts the application if hot reload can't apply it.
- `sync`: synchronizes the root folder of the ASP.NET Core Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the NuGet packages and the build output come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/root/.nuget/packages` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the NuGet cache between `okteto up` sessions.
- `securityContext`: adds the `SYS_PTRACE` capability that `vsdbg` needs to attach to the application.

The `.stignore` file lists the files that [File Sync](reference/file-synchronization.mdx#ignoring-files) skips in both directions:

```text title=".stignore"
# Git metadata: large, and only needed on your machine
.git

# Build output generated inside the development container
/bin
/obj
/tests/bin
/tests/obj

# Test reports
*.trx

# Local-only files
.vscode
.idea
.DS_Store
```

`.git`, `.vscode`, `.idea`, `.DS_Store`, and the test results that `okteto test` downloads stay on your machine. The build output that `dotnet watch` and `dotnet build` generate in the Development Container (`bin` and `obj`) stays in the Development Container.

### Hot reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts `dotnet watch`, which builds and runs the application:

```console

 i  'aspnetcore-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world

dotnet watch 🔥 Hot reload enabled. For a list of supported edits, see https://aka.ms/dotnet/hot-reload.
  helloworld -> /usr/src/app/bin/Debug/net10.0/helloworld.dll
Build succeeded.
dotnet watch ⌚ Waiting for changes
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://[::]:8080
info: Microsoft.Hosting.Lifetime[0]
      Application started. Press Ctrl+C to shut down.
```

Open `Controllers/HelloWorldController.cs` in your local IDE, change the response message on line 12 to `Hello world from Okteto!`, and save the file:

```csharp title="Controllers/HelloWorldController.cs"
    [HttpGet]
    public string Get()
    {
        var message = "Hello world from Okteto!";
        return message;
    }
```

Okteto synchronizes `HelloWorldController.cs` to the Development Container, and `dotnet watch` applies the change to the running application without restarting it:

```console
dotnet watch ⌚ File updated: ./Controllers/HelloWorldController.cs
dotnet watch 🔥 C# and Razor changes applied in 731ms.
```

Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop `dotnet watch` and exit `okteto up`.

### Debugging with VS Code

`vsdbg` attaches to the application that `dotnet watch` runs, so keep `okteto up` running. VS Code starts `vsdbg` in the Development Container over SSH: `okteto up` adds the `hello-world.okteto` host to your SSH configuration, and the `.vscode/launch.json` file of the ASP.NET Core Sample App runs `vsdbg` through it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:pickRemoteProcess}",
      "pipeTransport": {
        "pipeProgram": "ssh",
        "pipeArgs": ["-q", "-T", "hello-world.okteto"],
        "debuggerPath": "/usr/local/bin/vsdbg/vsdbg",
        "pipeCwd": "${workspaceFolder}",
        "quoteArgs": true
      },
      "sourceFileMap": {
        "/usr/src/app": "${workspaceFolder}"
      }
    }
  ]
}
```

`sourceFileMap` maps `/usr/src/app`, the path in the `sync` field of the Okteto Manifest, to the folder that you open in VS Code. If you synchronize your code to another path, change `sourceFileMap` to match it. `vsdbg` only works with the Microsoft builds of VS Code and Visual Studio.

Open the ASP.NET Core Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. VS Code lists the processes of the Development Container: select `helloworld`, the process of `/usr/src/app/bin/Debug/net10.0/helloworld`. Add a breakpoint on line 12 of `Controllers/HelloWorldController.cs` and reload the endpoint in your browser. The execution stops at the breakpoint, and you can inspect the request and the variables.

To end the debugging session, click **Disconnect** in the debug toolbar. `vsdbg` detaches, and the application keeps running with `dotnet watch`.

## Cleaning up

`okteto down` deactivates the Development Container and restores the `hello-world` Deployment with the application image:

```bash
okteto down
```

`okteto destroy` deletes the Deployment, Service, and Ingress of the ASP.NET Core Sample App from your Namespace:

```bash
okteto destroy
```
