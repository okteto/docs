Okteto replaces your Java application in Kubernetes with a Development Container that restarts it every time you save a file. The Java Sample App is a hello world Spring Boot application, available for [Maven](https://github.com/okteto/java-maven-getting-started) and for [Gradle](https://github.com/okteto/java-gradle-getting-started). Both versions build their application image and their development image from one Dockerfile, run their unit tests in a Test Container, restart with [Spring Boot DevTools](https://docs.spring.io/spring-boot/reference/using/devtools.html) when a `.java` file changes, and start the JVM with its debug agent so you can debug the application from IntelliJ IDEA.

:::tip
The `.dockerignore`, `.oktetoignore`, and `.stignore` files are key to performance. They decide which files Okteto sends to the image builds, to Remote Execution, and to File Sync. Without them, every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` transfers the whole repository, `.git` folder included, and a change to any file invalidates the build cache.
:::

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [IntelliJ IDEA](https://www.jetbrains.com/idea/).

Clone the Java Sample App for the build tool that you use:

#### Maven

```bash
git clone https://github.com/okteto/java-maven-getting-started
cd java-maven-getting-started
```

#### Gradle

```bash
git clone https://github.com/okteto/java-gradle-getting-started
cd java-gradle-getting-started
```

## The Dockerfile

The `Dockerfile` of the Java Sample App defines two images, one per stage:

#### Maven

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

RUN apt-get update && \
    apt-get install -y --no-install-recommends inotify-tools=4.25.9.0-1 && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /usr/src/app
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline
COPY . .
RUN ./mvnw package -DskipTests

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/target/helloworld-0.0.1.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

#### Gradle

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

WORKDIR /usr/src/app
COPY gradlew settings.gradle build.gradle ./
COPY gradle gradle
RUN ./gradlew --no-daemon dependencies
COPY . .
RUN ./gradlew --no-daemon assemble

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/build/libs/helloworld.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

- `dev` is the development image. It contains the JDK, Maven or Gradle (downloaded by the `mvnw` or `gradlew` wrapper of the repository), the dependencies, and the source code. `./mvnw dependency:go-offline` and `./gradlew dependencies` run before the source code is copied, so a change to the code doesn't download the build tool and the dependencies again. The last step compiles the application, so the first build in the Development Container finds the classes up to date. The Maven image also contains `inotifywait`, which the Development Container uses to compile the code when a file changes.
- `prod` is the application image. It contains only the Java runtime and the JAR file built in the `dev` stage.

The `dev` stage follows the recommendations for [development images](development/images.mdx): every version is pinned, and the builder stage of the application image is the development image. The wrapper pins the version of Maven or Gradle in `.mvn/wrapper/maven-wrapper.properties` or `gradle/wrapper/gradle-wrapper.properties`.

The `.dockerignore` file limits the build context to the files that the build needs:

#### Maven

```text title=".dockerignore"
*
!mvnw
!.mvn/wrapper
!pom.xml
!src
```

#### Gradle

```text title=".dockerignore"
*
!gradlew
!gradle/wrapper
!settings.gradle
!build.gradle
!src
```

Without it, the `.git` folder and the rest of the repository end up in the development image, and a change to any file, such as `README.md`, invalidates the build cache. If your build reads other files, for example a `gradle.properties` file, add them with a `!` pattern.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the Java Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects the stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so the build of `hello-world` reuses the cached layers of the `dev` stage. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and exposes their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section deploys the application image:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

`envsubst` replaces `${OKTETO_BUILD_HELLO_WORLD_IMAGE}` in `k8s.yml` with the image that Okteto built, and `kubectl` applies the Deployment, Service, and Ingress of `k8s.yml`.

The deploy commands run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster, with an image that includes `kubectl` and `envsubst`.

:::tip
To run your deploy commands with your own tools, set the image of that container in `deploy.image` and move the commands to `deploy.commands`. The image must include `/bin/sh` and every tool that your commands run. [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) covers the `build`, `deploy`, and `test` sections of an application with several services.
:::

The `[deploy]` and `[destroy]` groups of the `.oktetoignore` file limit the files that the Okteto CLI sends to Remote Execution for `okteto deploy` and `okteto destroy` to `k8s.yml`, the only file the deploy commands read:

```text title=".oktetoignore"
# Files that the Okteto CLI sends to Remote Execution.

# "okteto deploy" and "okteto destroy" only need the Kubernetes manifests
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

## Testing the Java Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the unit tests of `src/test/java/com/okteto/helloworld/RestHelloWorldTest.java`. The test sends a request to the controller with Spring's `MockMvc` and checks the `Hello world!` response.

#### Maven

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.m2/repository
    commands:
      - ./mvnw test
    artifacts:
      - target/surefire-reports
```

#### Gradle

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.gradle/caches
    commands:
      - ./gradlew test
    artifacts:
      - build/reports/tests/test
```

- `image`: the development image, so the tests run with the same JDK and build tool as the Development Container.
- `caches`: the Maven repository (`/root/.m2/repository`) or the Gradle caches (`/root/.gradle/caches`), kept between runs of the Test Container. The first run downloads the dependencies, and the next runs reuse them.
- `commands`: the commands that run the tests. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test reports.

Test Containers run with [Remote Execution](core/remote-execution.mdx#ignoring-files). The `[test]` group of the `.oktetoignore` file sends them only the wrapper, the build file, and the `src` folder:

In the Maven sample:

```text title=".oktetoignore"
# "okteto test" only needs what the Maven build reads
[test]
*
!mvnw
!.mvn/wrapper
!pom.xml
!src
```

In the Gradle sample:

```text title=".oktetoignore"
# "okteto test" only needs what the Gradle build reads
[test]
*
!gradlew
!gradle/wrapper
!settings.gradle
!build.gradle
!src
```

Run the unit tests from the root folder of the Java Sample App:

```bash
okteto test
```

## Developing in a Development Container

To get the experience of developing on your machine, with hot reload and a debugger on every change, configure a Development Container in your Okteto Manifest. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, synchronizes your local files with it, and runs the hot-reload and debugging tools of the development image in your cluster.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Java Sample App:

#### Maven

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./mvnw spring-boot:run & while inotifywait -qq -r -e close_write,moved_to,delete src; do ./mvnw -q compile; done"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

#### Gradle

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./gradlew --console=plain --continuous classes & ./gradlew --console=plain bootRun"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

The `hello-world` key matches the name of the Deployment in `k8s.yml`. The fields of the Development Container are:

- `image`: the development image built in the `build` section.
- `command`: starts the application and compiles the code every time a `.java` file changes. Spring Boot DevTools restarts the application when the compiled classes change.
  - Maven: `./mvnw spring-boot:run` starts the application, and `inotifywait` waits for a change in the `src` folder to run `./mvnw -q compile`. Maven doesn't have a watch mode.
  - Gradle: `./gradlew --continuous classes` compiles the code every time a file changes, and `./gradlew bootRun` starts the application.
- `sync`: synchronizes the root folder of the Java Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/root/.m2` or `/root/.gradle` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the caches of Maven or Gradle between `okteto up` sessions.
- `forward`: forwards port `5005`, where the debug agent of the JVM listens, to your machine.

The `.stignore` file lists the files that [File Sync](reference/file-synchronization.mdx#ignoring-files) skips in both directions:

#### Maven

```text title=".stignore"
# Git metadata: large, and only needed on your machine
.git

# Build output generated inside the development container
/target

# Local-only files
.idea
*.iml
.vscode
.DS_Store
```

#### Gradle

```text title=".stignore"
# Git metadata: large, and only needed on your machine
.git

# Build output and caches generated inside the development container
/build
/.gradle

# Local-only files
/bin
/out
.idea
*.iml
.vscode
.DS_Store
```

`.git` and the files of your IDE (`.idea`, `*.iml`, `.vscode`, the `bin` and `out` folders where some IDEs compile Gradle projects) stay on your machine. The classes, reports, and JAR files that Maven (`target`) and Gradle (`build` and `.gradle`) generate in the Development Container stay in the Development Container.

### Debugging with IntelliJ IDEA

The JVM of the Development Container runs with the Java Debug Wire Protocol (JDWP) agent, which listens on port `5005`. The build file of the Java Sample App adds the agent to the JVM that runs the application:

#### Maven

```xml title="pom.xml"
<plugin>
	<groupId>org.springframework.boot</groupId>
	<artifactId>spring-boot-maven-plugin</artifactId>
	<configuration>
		<jvmArguments>-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005</jvmArguments>
	</configuration>
</plugin>
```

#### Gradle

```groovy title="build.gradle"
bootRun {
    jvmArgs = ["-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005"]
}
```

`suspend=n` starts the application without waiting for a debugger. The agent only runs in the Development Container: the application image starts the JAR file with `java -jar`, without it.

Spring Boot DevTools restarts the application inside the same JVM, so the debugger stays attached while you change the code, and you debug with the same `okteto up` command that gives you hot reload. With `okteto up` running, create the debug configuration in IntelliJ IDEA:

1. From the main menu, select **Run > Edit Configurations**.
1. Click **+** and select **Remote JVM Debug**.
1. Enter a name in the **Name** field, for example `Debug On Okteto`.
1. Set **Debugger mode** to `Attach to remote JVM`, **Host** to `localhost`, and **Port** to `5005`, the port that `okteto up` forwards to your machine.
1. Click **OK**.

<Image
  src={require("@site/static/img/java-debug.png").default}
  alt="IntelliJ IDEA Run/Debug Configurations dialog with a Remote JVM Debug configuration that attaches to localhost on port 5005"
  width="850"
/>

Select the configuration and click **Debug**. Add a breakpoint on line 11 of `src/main/java/com/okteto/helloworld/RestHelloWorld.java` and reload the endpoint in your browser. The execution stops at the breakpoint, and you can inspect the stack and the variables of the application running in your cluster.

When you stop the debugging session in IntelliJ IDEA, the debugger detaches from the JVM, and the application keeps running in the Development Container. Press `Ctrl+C` in the terminal of `okteto up` to stop the application and exit `okteto up`.

## Cleaning up

`okteto down` deactivates the Development Container and restores the `hello-world` Deployment with the application image:

```bash
okteto down
```

`okteto destroy` deletes the Deployment, Service, and Ingress of the Java Sample App from your Namespace:

```bash
okteto destroy
```
