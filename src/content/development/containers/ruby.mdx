Okteto replaces your Ruby application in Kubernetes with a Development Container that reloads it every time you save a file. The [Ruby Sample App](https://github.com/okteto/ruby-getting-started) is a hello world [Sinatra](https://sinatrarb.com/) application that builds its application image and its development image from one Dockerfile, runs its unit tests in a Test Container, reloads with [`sinatra/reloader`](https://sinatrarb.com/contrib/reloader) when `app.rb` changes, and runs the [debug gem](https://github.com/ruby/debug) (`rdbg`) so you can debug it from VS Code.

:::tip
The `.dockerignore`, `.oktetoignore`, and `.stignore` files are key to performance. They decide which files Okteto sends to the image builds, to Remote Execution, and to File Sync. Without them, every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` transfers the whole repository, `.git` folder included, and a change to any file invalidates the build cache.
:::

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [VSCode rdbg Ruby Debugger extension](https://marketplace.visualstudio.com/items?itemName=KoichiSasada.vscode-rdbg).

Clone the Ruby Sample App:

```bash
git clone https://github.com/okteto/ruby-getting-started
cd ruby-getting-started
```

## The Dockerfile

The `Dockerfile` of the Ruby Sample App defines two images, one per stage:

```dockerfile title="Dockerfile"
FROM ruby:4.0.10-trixie AS dev

RUN gem install debug -v 1.11.1

ENV APP_ENV=development
WORKDIR /opt/app
COPY Gemfile Gemfile.lock ./
RUN BUNDLE_FROZEN=true bundle install
COPY . .

FROM ruby:4.0.10-slim-trixie AS prod

ENV APP_ENV=production
WORKDIR /opt/app
COPY Gemfile Gemfile.lock ./
RUN BUNDLE_FROZEN=true BUNDLE_WITHOUT=test bundle install
COPY . .
CMD ["ruby", "app.rb"]
```

- `dev` is the development image. It contains Ruby, the debug gem, the gems of `Gemfile.lock`, and the source code. `APP_ENV=development` runs Sinatra in development mode, where `sinatra/reloader` reloads `app.rb` when it changes.
- `prod` is the application image. It's based on the slim Ruby image and contains the source code and the gems of `Gemfile.lock`, without the `test` group. `APP_ENV=production` runs Sinatra in production mode, without the reloader.

Both stages follow the recommendations for [development images](development/images.mdx): every version is pinned, and `bundle install` runs before `COPY . .`, so a change to the source code doesn't invalidate the layer with the gems.

The `.dockerignore` file limits the build context to the files that `bundle install` and the application need:

```text title=".dockerignore"
*
!Gemfile
!Gemfile.lock
!**/*.rb
```

Without it, the `.git` folder and the rest of the repository end up in the images, and a change to any file, such as `README.md`, invalidates the build cache. If your application reads other files, for example the `views` and `public` folders of Sinatra, add them with a `!` pattern.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the Ruby Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects the stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image before the `hello-world` image. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and exposes their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section deploys the application image:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

`envsubst` replaces `${OKTETO_BUILD_HELLO_WORLD_IMAGE}` in `k8s.yml` with the image that Okteto built, and `kubectl` applies the Deployment, Service, and Ingress of `k8s.yml`.

The deploy commands run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster, with an image that includes `kubectl` and `envsubst`.

:::tip
To run your deploy commands with your own tools, set the image of that container in `deploy.image` and move the commands to `deploy.commands`. The image must include `/bin/sh` and every tool that your commands run. [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) covers the `build`, `deploy`, and `test` sections of an application with several services.
:::

The `[deploy]` and `[destroy]` groups of the `.oktetoignore` file limit the files that the Okteto CLI sends to Remote Execution for `okteto deploy` and `okteto destroy` to `k8s.yml`, the only file the deploy commands read:

```text title=".oktetoignore"
# Files that the Okteto CLI sends to Remote Execution.

# "okteto deploy" and "okteto destroy" only need the Kubernetes manifests
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

## Testing the Ruby Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the unit tests of `test/app_test.rb`, written with Minitest and Rack::Test:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /usr/local/bundle
    commands:
      - bundle install
      - bundle exec ruby test/app_test.rb
    artifacts:
      - coverage
```

- `image`: the development image, so the tests run with the same Ruby version as the Development Container.
- `caches`: the folder where Bundler installs the gems, kept between runs of the Test Container. `bundle install` only installs the gems that aren't in the cache yet.
- `commands`: the commands that run the tests. The Test Container fails if a command exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the `coverage` folder with the report of SimpleCov.

Test Containers run with [Remote Execution](core/remote-execution.mdx#ignoring-files). The `[test]` group of the `.oktetoignore` file sends them only `Gemfile`, `Gemfile.lock`, and the `.rb` files:

```text title=".oktetoignore"
# "okteto test" only needs what "bundle install" and the tests read
[test]
*
!Gemfile
!Gemfile.lock
!**/*.rb
```

Run the unit tests from the root folder of the Ruby Sample App:

```bash
okteto test
```


## Developing in a Development Container

To get the experience of developing on your machine, with hot reload and a debugger on every change, configure a Development Container in your Okteto Manifest. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, synchronizes your local files with it, and runs the hot-reload and debugging tools of the development image in your cluster.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Ruby Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: ruby app.rb
    sync:
      - .:/opt/app
    persistentVolume:
      enabled: false
    forward:
      - 1234:1234
```

The `hello-world` key matches the name of the Deployment in `k8s.yml`. The fields of the Development Container are:

- `image`: the development image built in the `build` section.
- `command`: starts the application. The development image runs Sinatra in development mode, so `sinatra/reloader` loads `app.rb` again on the first request after the file changes.
- `sync`: synchronizes the root folder of the Ruby Sample App with `/opt/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the gems come from the development image, so there's no volume to create and attach. When you add a gem to the `Gemfile`, run `okteto deploy` to build the development image again.
- `forward`: forwards port `1234`, where `rdbg` listens, to your machine.

The `.stignore` file lists the files that [File Sync](reference/file-synchronization.mdx#ignoring-files) skips in both directions:

```text title=".stignore"
# Git metadata: large, and only needed on your machine
.git

# Bundler settings and gems installed in the project folder, specific to each machine
/.bundle
/vendor/bundle

# Coverage report generated by the tests
/coverage

# Local-only files
.vscode
.idea
.DS_Store
```

`.git`, `.vscode`, `.idea`, and `.DS_Store` stay on your machine. The Bundler settings and gems of the project folder (`.bundle` and `vendor/bundle`) and the coverage report of the tests (`coverage`) stay on the side where they're generated.

### Hot reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts the application:

```console

 i  'ruby-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world
    Forward:   1234 -> 1234

[2026-11-19 04:04:25] INFO  WEBrick 1.9.2
[2026-11-19 04:04:25] INFO  ruby 4.0.10 (2026-11-19) [x86_64-linux]
== Sinatra (v4.2.2) has taken the stage on 8080 for development with backup from WEBrick
[2026-11-19 04:04:25] INFO  Rackup::Handler::WEBrick::Server#start: pid=83 port=8080
```

Open `app.rb` in your local IDE, change the response message on line 10 to `Hello world from Okteto!`, and save the file:

```ruby title="app.rb"
get '/' do
  message = 'Hello world from Okteto!'
  message
end
```

Okteto synchronizes `app.rb` to the Development Container, and `sinatra/reloader` loads it again on the next request, without restarting the server. Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop Sinatra and exit `okteto up`.

### Debugging with VS Code

`rdbg` runs the application with the debugger, so start the Development Container with `rdbg` instead of `ruby app.rb`. The command after `--` replaces the `command` of the Okteto Manifest:

```bash
okteto up -- rdbg --open --nonstop --host 0.0.0.0 --port 1234 app.rb
```

`--open --host 0.0.0.0 --port 1234` makes `rdbg` listen for a debugger on port `1234` of the Development Container, and `--nonstop` starts the application without waiting for the debugger to attach:

```console
DEBUGGER: Debugger can attach via TCP/IP (0.0.0.0:1234)
[2026-11-19 04:06:26] INFO  WEBrick 1.9.2
[2026-11-19 04:06:26] INFO  ruby 4.0.10 (2026-11-19) [x86_64-linux]
== Sinatra (v4.2.2) has taken the stage on 8080 for development with backup from WEBrick
```

The `.vscode/launch.json` file of the Ruby Sample App attaches VS Code to `rdbg` through the port that `okteto up` forwards to your machine:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "rdbg",
      "request": "attach",
      "debugPort": "localhost:1234",
      "localfsMap": "/opt/app:${workspaceFolder}"
    }
  ]
}
```

`localfsMap` maps `/opt/app`, the path in the `sync` field of the Okteto Manifest, to the folder that you open in VS Code. If you synchronize your code to another path, change `/opt/app` to match it.

Open the Ruby Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. Add a breakpoint on line 10 of `app.rb` and reload the endpoint in your browser. The execution stops at the breakpoint, and you can inspect the request and the variables.

Press `Ctrl+C` to stop the application and `rdbg` and exit `okteto up`, and run `okteto up` to go back to `ruby app.rb`.

## Cleaning up

`okteto down` deactivates the Development Container and restores the `hello-world` Deployment with the application image:

```bash
okteto down
```

`okteto destroy` deletes the Deployment, Service, and Ingress of the Ruby Sample App from your Namespace:

```bash
okteto destroy
```
