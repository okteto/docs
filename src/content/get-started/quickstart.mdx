This quickstart takes a sample application and creates an [application environment](application-environments/index.mdx) for it in your Kubernetes cluster. All you need to build, deploy, and test the application is the Okteto CLI. An application environment is a running copy of an application in its own Namespace. It includes the services of the application and its dependencies, such as a database. Each environment gets its own HTTPS URL, so you can open it in your browser.

The Sample App is a small catalog of movies, with four components:

- `frontend`: a React application, built with Vite, that lists the movies and your favorites.
- `api`: a Node.js API that reads the movies from MongoDB, and saves your favorites in it.
- `mongodb`: a MongoDB database that runs the official `mongo` image.
- `seed`: a job that loads the movies into MongoDB on every deployment.

## Prerequisites

You need the [Okteto CLI](get-started/install-okteto-cli.mdx), installed and configured to access your Okteto instance. With that in place, clone the Sample App and move to its folder. Every command of this quickstart runs from there:

```bash
git clone https://github.com/okteto/getting-started
cd getting-started
```

## Okteto Manifest

An application environment is defined in a file, the [Okteto Manifest](reference/okteto-manifest.mdx). It's called `okteto.yaml` and it lives in the repository, next to the code, so every developer, pull request, and coding agent that works on the application creates its environment the same way. This is the Okteto Manifest of the Sample App:

```yaml title="okteto.yaml"
build:
  api:
    context: api

  frontend:
    context: frontend

deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}

test:
  e2e:
    image: mcr.microsoft.com/playwright:v1.65.1-noble
    context: e2e
    caches:
      - /root/.npm
    commands:
      - bash run_tests.sh
    artifacts:
      - test-results
      - playwright-report
```

It has three sections: `build`, `deploy`, and `test`. Each one answers a question (how to build the images, how to deploy the application, and how to test it), and each one has its own command in the Okteto CLI. The rest of this quickstart goes through them in that order.

## Build

Kubernetes runs containers, so before you can deploy the Sample App, you need a container image for each of its services. The `frontend` and the `api` each have their code and a `Dockerfile` in the repository. MongoDB is different: it runs the official `mongo` image, so there's nothing to build for it.

That's what the [build](reference/okteto-manifest.mdx#build-object-optional) section of the Okteto Manifest says: build one image from the `api` folder, and another one from the `frontend` folder.

```yaml title="okteto.yaml"
build:
  api:
    context: api

  frontend:
    context: frontend
```

To build them, run `okteto build`:

```bash
okteto build
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Building '/Users/cindy/getting-started/api/Dockerfile'...
 ...
 ✓  Image 'registry.okteto.example.com/cindy/getting-started-api:okteto' successfully pushed
 i  Building '/Users/cindy/getting-started/frontend/Dockerfile'...
 ...
 ✓  Image 'registry.okteto.example.com/cindy/getting-started-frontend:okteto' successfully pushed
```

You ran the command on your machine, but the build happened somewhere else. The Okteto CLI sent each folder to the [Okteto Build Service](application-environments/build-service.mdx), which built the image inside your cluster and pushed it to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry), a container registry that also runs in your cluster. That's where your application environment pulls the images from.

It also means that you don't need Docker, or access to a Docker daemon, to build your images. Your laptop, a CI job, or the sandbox of a coding agent only needs the Okteto CLI.

## Deploy

Okteto stores the reference of each image it builds in an `OKTETO_BUILD_<IMAGE>_IMAGE` [variable](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry), such as `OKTETO_BUILD_API_IMAGE`. The deploy commands use those variables to deploy the images you just built.

Those commands are in the [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section of the Okteto Manifest, and they're the same ones you'd use to deploy to any Kubernetes cluster, with tools such as Helm or `kubectl`. The Sample App only needs one, which installs the Helm chart of the `chart` folder and passes it the two images:

```yaml title="okteto.yaml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}
```

As with the build, this command doesn't run on your machine. Okteto runs it with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm installed either. The chart creates everything the application needs: the `frontend` and `api` services, MongoDB with its volume, the `seed` job, and the Ingress that exposes the application.

To deploy the application, run `okteto deploy`. With the `--wait` flag, the command doesn't return until the pods of the application are healthy:

```bash
okteto deploy --wait
```

## Test

Now that the application is running, you can test it the way your users use it, against its real services. The `test` section of the Okteto Manifest defines the [tests](application-environments/okteto-test.mdx) of the application. The Sample App has one, `e2e`, with [Playwright](https://playwright.dev/) tests that open the application in a browser, compare the movies it shows with the ones stored in MongoDB, and move a movie to the favorites:

```yaml title="okteto.yaml"
test:
  e2e:
    image: mcr.microsoft.com/playwright:v1.65.1-noble
    context: e2e
    caches:
      - /root/.npm
    commands:
      - bash run_tests.sh
    artifacts:
      - test-results
      - playwright-report
```

The test runs in the official Playwright image, with the same version of Playwright that `e2e/package.json` pins. Okteto sends it the `e2e` folder, which is its `context`, and runs its `commands`: if any of them exits with a non-zero code, the test fails. Two more fields save you time. `caches` keeps the npm cache between runs, and `artifacts` copies the Playwright results and the HTML report to your machine when the test finishes.

Like the deploy command, the test runs with Remote Execution, in a container inside your Namespace, right next to the application. From there, it reaches the application through its public endpoints, which it builds from the `OKTETO_NAMESPACE` and `OKTETO_DOMAIN` variables, and it also reaches its private services, such as MongoDB at `mongodb.${OKTETO_NAMESPACE}`. Nothing is mocked: it tests the real application.

To run the tests, run `okteto test`:

```bash
okteto test
```

## Destroy

When you're done, delete the application environment with [`okteto destroy`](application-environments/destroy.mdx), which uninstalls the Helm release of the Sample App from your Namespace:

```bash
okteto destroy
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Images were already built. To rebuild your images run 'okteto build'
 i  Running 'helm uninstall movies'
release "movies" uninstalled
 ✓  Development environment 'getting-started' successfully destroyed
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I develop with hot reload and a debugger?

Okteto supports hot reload and debuggers: `okteto up` runs a service of your application environment with your local changes as you save them. See the [samples for each language](application-environments/develop/index.mdx#guides-by-language): ASP.NET, Go, Java, Node.js, PHP, Python, Ruby, and Rust.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in this quickstart, where one Helm chart deploys the three services of the Sample App. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, as the `seed` job of the Sample App does, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
