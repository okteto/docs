This quickstart builds, deploys, and tests the [Movies app](https://github.com/okteto/getting-started) in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. The Movies app has three services, deployed by the Helm chart in its `chart` folder:

- `frontend`: a React application, built with Vite, that lists movies.
- `api`: a Node.js API that reads the movies from MongoDB.
- `mongodb`: a MongoDB database that runs the official `mongo` image. A `seed` job loads the movies into it on every deployment.

## Prerequisites

Install the [Okteto CLI](get-started/install-okteto-cli.mdx) and configure it to access your Okteto instance. Then clone the Movies app:

```bash
git clone https://github.com/okteto/getting-started
cd getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yaml` file of the repository, builds four images, two per service:

```yaml title="okteto.yaml"
build:
  api-dev:
    context: api
    target: dev

  api:
    context: api
    target: prod
    depends_on:
      - api-dev

  frontend-dev:
    context: frontend
    target: dev

  frontend:
    context: frontend
    target: prod
    depends_on:
      - frontend-dev
```

`context` is the folder that Okteto sends to the [Okteto Build Service](application-environments/build-service.mdx), which builds the `Dockerfile` it finds there. `target` selects a stage of that `Dockerfile`, and `depends_on` makes Okteto build the development image first, so the application image reuses its cached layers. In `frontend/Dockerfile`, the `dev` stage builds the application and the `prod` stage copies the result into an nginx image:

```dockerfile title="frontend/Dockerfile"
FROM node:26.13.1-trixie-slim AS dev

WORKDIR /usr/src/app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.30.7-alpine AS prod

COPY --from=dev /usr/src/app/dist /usr/share/nginx/html
EXPOSE 80
```

- `dev` is the development image. It contains Node.js, the dependencies that `npm ci` installs from `package-lock.json`, and the source code. The tests run in it.
- `prod` is the application image that the Helm chart deploys.

Run `okteto build` from the root folder of the Movies app:

```bash
okteto build
```

Okteto builds the four images in your cluster, so you don't need Docker on your machine, and pushes them to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry):

With [Smart Builds](application-environments/build-service.mdx#smart-builds), the next `okteto build` skips the images whose context hasn't changed.

## Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart of the Movies app, with the application images that Okteto built:

```yaml title="okteto.yaml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}
```

The command runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine. The chart deploys the `frontend` and `api` services, MongoDB with its volume, the `seed` job, and the Ingress that exposes the application.

If your application is defined in a Docker Compose file, follow the [Develop a Docker Compose Application with Okteto](/tutorials/compose-getting-started/) tutorial instead.

Run `okteto deploy` from the root folder of the Movies app:

```bash
okteto deploy --wait
```

Okteto builds the images that aren't built yet, runs the deploy command, waits until the pods of the application are healthy, and prints its endpoints:

## Test

The `test` section of the Okteto Manifest defines two [tests](application-environments/okteto-test.mdx). `frontend` runs the unit tests of the `frontend` service, written with [Vitest](https://vitest.dev/), and `e2e` runs [Playwright](https://playwright.dev/) tests that open the Movies app in a browser and compare the movies it shows with the data stored in MongoDB:

```yaml title="okteto.yaml"
test:
  frontend:
    image: ${OKTETO_BUILD_FRONTEND_DEV_IMAGE}
    context: frontend
    caches:
      - /root/.npm
    commands:
      - npm ci
      - npm test

  e2e:
    image: mcr.microsoft.com/playwright:v1.65.1-noble
    context: e2e
    caches:
      - /root/.npm
    commands:
      - bash run_tests.sh
    artifacts:
      - test-results
      - playwright-report
```

- `image`: the image that runs the test. `frontend` uses the development image of the service, and `e2e` uses the official Playwright image, with the same version of Playwright that `e2e/package.json` pins.
- `context`: the folder that Okteto sends to the test.
- `caches`: the folders that Okteto keeps between runs of the test, in this case the npm cache.
- `commands`: the commands that run the tests. The test fails if any of them exits with a non-zero code.
- `artifacts`: the files and folders that Okteto copies to your machine when the test finishes, in this case the Playwright results and the HTML report.

The tests run with [Remote Execution](reference/remote-execution.mdx), in a container inside your Namespace, so they reach the application in two ways: its public endpoints, built from the `OKTETO_NAMESPACE` and `OKTETO_DOMAIN` variables, and its private services, such as MongoDB at `mongodb.${OKTETO_NAMESPACE}`. They test against the real application, not a mock.

Run the end-to-end tests from the root folder of the Movies app:

```bash
okteto test e2e
```

Running `okteto deploy` and `okteto test` after each change is usually fast enough, especially when a coding agent writes and tests the code autonomously. With the [Okteto skills](coding-agents/okteto-skills.mdx), the agent runs this loop in its own Namespace and reports back the tests it ran, the endpoints of the application, and a link to that Namespace.

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) uninstalls the Helm release of the Movies app from your Namespace:

```bash
okteto destroy
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I develop with hot reload and a debugger?

Run `okteto up` to develop a service in a [Development Container](application-environments/development-containers/index.mdx). The guide of your language sets one up, with the build, deploy, and test optimizations of that language: [ASP.NET](application-environments/development-containers/aspnetcore.mdx), [Go](application-environments/development-containers/golang.mdx), [Java](application-environments/development-containers/java.mdx), [Node.js](application-environments/development-containers/node.mdx), [PHP](application-environments/development-containers/php.mdx), [Python](application-environments/development-containers/python.mdx), [Ruby](application-environments/development-containers/ruby.mdx), or [Rust](application-environments/development-containers/rust.mdx).

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/development-containers/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in this quickstart, where one Helm chart deploys the three services of the Movies app. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with ten services or fewer.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them from 15 to 20 services.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, as the `seed` job of the Movies app does, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
