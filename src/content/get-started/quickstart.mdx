This quickstart creates an [application environment](application-environments/index.mdx) for the [Movies app](https://github.com/okteto/getting-started) in your Kubernetes cluster. An application environment is a running copy of an application in its own Namespace: its services and the dependencies that run next to them, such as a database, with its own HTTPS endpoints.

The Movies app has three services:

- `frontend`: a React application, built with Vite, that lists the movies and your favorites.
- `api`: a Node.js API that reads the movies from MongoDB, and saves your favorites in it.
- `mongodb`: a MongoDB database that runs the official `mongo` image. A `seed` job loads the movies into it on every deployment.

The [Okteto Manifest](reference/okteto-manifest.mdx) defines the application environment. It's the `okteto.yaml` file at the root of the repository, and each of its sections has a command of the Okteto CLI:

| Section | Command | What the command does |
|---------|---------|-----------------------|
| `build` | `okteto build` | Builds the images of the application in your cluster |
| `deploy` | `okteto deploy` | Deploys the application in your Namespace |
| `test` | `okteto test` | Runs the tests against the deployed application |
| | `okteto destroy` | Deletes the application from your Namespace |

## Prerequisites

Install the [Okteto CLI](get-started/install-okteto-cli.mdx) and configure it to access your Okteto instance. Then clone the Movies app, and run the commands of this quickstart from its root folder:

```bash
git clone https://github.com/okteto/getting-started
cd getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the Okteto Manifest lists the images of the application, one for each service that has a `Dockerfile`:

```yaml title="okteto.yaml"
build:
  api:
    context: api

  frontend:
    context: frontend
```

`api` and `frontend` are the names of the images, and `context` is the folder of each service, with its code and its `Dockerfile`.

Build the two images:

```bash
okteto build
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Building '/Users/cindy/getting-started/api/Dockerfile'...
 ...
 ✓  Image 'registry.okteto.example.com/cindy/getting-started-api:okteto' successfully pushed
 i  Building '/Users/cindy/getting-started/frontend/Dockerfile'...
 ...
 ✓  Image 'registry.okteto.example.com/cindy/getting-started-frontend:okteto' successfully pushed
```

The build doesn't run on your machine. The Okteto CLI sends each folder to the [Okteto Build Service](application-environments/build-service.mdx), which builds the image inside your cluster and pushes it to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry), a container registry that also runs in your cluster. Your application environment pulls the images from there.

The advantage is that you don't need Docker, or access to a Docker daemon, to build your images: your laptop, a CI job, and the sandbox of a coding agent only need the Okteto CLI.

## Deploy

Okteto stores the reference of each image in an `OKTETO_BUILD_<IMAGE>_IMAGE` [variable](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry), such as `OKTETO_BUILD_API_IMAGE`. The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section lists the commands that deploy the application. For the Movies app, one command installs the Helm chart in its `chart` folder with those images:

```yaml title="okteto.yaml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}
```

Like the build, the command doesn't run on your machine. It runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm either. The chart deploys the `frontend` and `api` services, MongoDB with its volume, the `seed` job, and the Ingress that exposes the application.

If your application is defined in a Docker Compose file, follow the [Develop a Docker Compose Application with Okteto](/tutorials/compose-getting-started/) tutorial instead.

Deploy the application. The `--wait` flag makes the command wait until the pods of the application are healthy:

```bash
okteto deploy --wait
```

Okteto builds the images that aren't built yet, runs the deploy command, and prints the endpoints of the application:

## Test

The `test` section of the Okteto Manifest defines the [tests](application-environments/okteto-test.mdx) of the application. The Movies app has one, `e2e`, which runs [Playwright](https://playwright.dev/) tests that open the Movies app in a browser, compare the movies it shows with the data stored in MongoDB, and move a movie to the favorites:

```yaml title="okteto.yaml"
test:
  e2e:
    image: mcr.microsoft.com/playwright:v1.65.1-noble
    context: e2e
    caches:
      - /root/.npm
    commands:
      - bash run_tests.sh
    artifacts:
      - test-results
      - playwright-report
```

- `image`: the image that runs the test, in this case the official Playwright image, with the same version of Playwright that `e2e/package.json` pins.
- `context`: the folder that Okteto sends to the test.
- `caches`: the folders that Okteto keeps between runs of the test, in this case the npm cache.
- `commands`: the commands that run the tests. The test fails if any of them exits with a non-zero code.
- `artifacts`: the files and folders that Okteto copies to your machine when the test finishes, in this case the Playwright results and the HTML report.

The test also runs with Remote Execution, in a container inside your Namespace, next to the application. It reaches the application in two ways: its public endpoints, built from the `OKTETO_NAMESPACE` and `OKTETO_DOMAIN` variables, and its private services, such as MongoDB at `mongodb.${OKTETO_NAMESPACE}`. It tests the real application, not a mock.

Run the tests:

```bash
okteto test
```

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) deletes the application environment: it uninstalls the Helm release of the Movies app from your Namespace.

```bash
okteto destroy
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Images were already built. To rebuild your images run 'okteto build'
 i  Running 'helm uninstall movies'
release "movies" uninstalled
 ✓  Development environment 'getting-started' successfully destroyed
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I develop with hot reload and a debugger?

Okteto supports hot reload and debuggers: `okteto up` runs a service of your application environment with your local changes as you save them. See the [samples for each language](application-environments/develop/index.mdx#guides-by-language): ASP.NET, Go, Java, Node.js, PHP, Python, Ruby, and Rust.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in this quickstart, where one Helm chart deploys the three services of the Movies app. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with ten services or fewer.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them from 15 to 20 services.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, as the `seed` job of the Movies app does, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
