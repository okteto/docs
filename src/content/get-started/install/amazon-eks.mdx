This guide explains how to install Okteto in Amazon Elastic Kubernetes Service (EKS).

## Installation Requirements

Install these CLIs on your machine:

- `okteto` >= {variables.cliVersion} ([installation guide](get-started/install-okteto-cli.mdx))
- `eksctl` >= 0.201 ([installation guide](https://eksctl.io/installation/))
- `aws` >= 2.15 ([installation guide](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html#getting-started-install-instructions))
- `kubectl` >= 1.28 ([installation guide](https://kubernetes.io/docs/tasks/tools/#kubectl))
- `helm` >= 3.14 ([installation guide](https://helm.sh/docs/intro/install/))

You also need:

- An Okteto license
- A domain where you can create wildcard DNS records
- A Kubernetes cluster

## Getting Your Okteto License

You need a license to install Okteto. If you have an Okteto subscription, your license key came with it, and [support](https://okteto.com/support) can send it again if you can't find it. If you don't have a subscription yet, [sign up for the free tier](https://www.okteto.com/free-tier/): you get a one-year license for up to 5 users and 500 environments per month, and you don't need a credit card.

## A Domain and the Ability to Create Wildcard DNS Records for It

You need enough access to a [subdomain](self-hosted/helm-configuration.mdx#subdomain), such as `dev.example.com`, to add a wildcard DNS record to it.
By default, Okteto exposes the endpoints of your application environments on that subdomain.

This guide uses [Amazon Route 53](https://aws.amazon.com/route53/) for the DNS records, but any DNS service works.

## Deploy a Kubernetes Cluster

This guide assumes Okteto runs in a new, dedicated cluster.

:::note
To install Okteto in an existing cluster with other workloads, read this section to check that your cluster meets the requirements.
:::

:::warning

As of Okteto 1.35, Okteto supports Amazon Linux 2 (AL2) and introduces support for Amazon Linux 2023 (AL2023) as the AMI for cluster nodes. We recommend upgrading Okteto to version 1.35 before upgrading your EKS cluster to Kubernetes 1.33 or changing to AL2023. In mixed clusters, make sure both the control plane and development workloads run on nodes with Amazon Linux 2 or Amazon Linux 2023 using [taints](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/) and [tolerations](self-hosted/helm-configuration.mdx#tolerations).

**Bottlerocket OS is not supported.** Okteto requires write access to `/etc/hosts` on cluster nodes, which is not possible on Bottlerocket's read-only root filesystem. If you use Bottlerocket, switch to AL2023. [Troubleshooting](self-hosted/manage/troubleshooting.mdx#daemon-fails-with-open-etchosts-permission-denied) has more details.

:::

### Setting Up Environment Variables

Set these environment variables to script the cluster creation:

Your Kubernetes cluster version:

<CodeBlock language="bash">
  {`export K8S_VERSION="${variables.kubernetesMaxVersion}"`}
</CodeBlock>

:::note
Okteto supports Kubernetes versions {variables.kubernetesMinVersion} through {variables.kubernetesMaxVersion}.
:::

Your Kubernetes cluster name:

```bash
export CLUSTER_NAME="okteto"
```

Your AWS Account ID:

```bash
export AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query "Account" --output text)"
```

Your AWS Region:

```bash
export AWS_REGION="$(aws configure get region)"
```

Disable AWS CLI pagination (optional):

```bash
export AWS_PAGER=""
```

### Create the Cluster

For an initial evaluation, we recommend a Kubernetes cluster with a pool of 3 `m5.xlarge` nodes with 250 GB each:

:::note ARM Clusters (Beta)
To install Okteto on an ARM-based cluster with AWS Graviton instances, use `m7g.xlarge` instead of `m5.xlarge`. ARM support on EKS is in **Beta**. The [ARM Support guide](self-hosted/manage/arm-support.mdx) has the details and the requirements.
:::

```bash
eksctl create cluster -f - <<EOF
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: ${CLUSTER_NAME}
  region: ${AWS_REGION}
  version: "${K8S_VERSION}"

autoModeConfig:
  enabled: false

iam:
  withOIDC: true

nodeGroups:
  - name: ng-1
    instanceType: m5.xlarge
    desiredCapacity: 3
    volumeSize: 250
    volumeType: gp3
    amiFamily: AmazonLinux2023
EOF
```

:::note
Check that the Kubernetes version you select is supported:
- By Amazon EKS in your region. To list the versions, run this command, which needs the `eks:DescribeClusterVersions` IAM permission:
  ```
  eksctl utils describe-cluster-versions --region ${AWS_REGION}
  ```
  Amazon EKS also publishes its list of [available versions](https://docs.aws.amazon.com/eks/latest/userguide/kubernetes-versions.html).
- By your `eksctl` installation. Update it to its latest release to create clusters with the newest versions.
- By the Okteto Helm chart version you plan to install, in its [supported Kubernetes versions](release-notes.mdx).
:::

Amazon's [cluster creation guide](https://docs.aws.amazon.com/eks/latest/userguide/create-cluster.html) has more details.

### Create EBS CSI Addon IAM Role

Okteto needs the EBS CSI Addon to create persistent volumes.
It uses them for the cache of the [Okteto Build Service](application-environments/build-service.mdx) (BuildKit) and, in the default installation, to store your container images in the [Okteto Registry](application-environments/build-service.mdx#okteto-registry).

Before you install the EBS CSI Addon in your Kubernetes cluster, create its IAM Role:

```bash
eksctl create iamserviceaccount \
  --region="${AWS_REGION}" \
  --name="ebs-csi-controller-sa" \
  --namespace="kube-system" \
  --cluster="${CLUSTER_NAME}" \
  --role-name="${CLUSTER_NAME}-ebs-csi-driver-role" \
  --role-only \
  --attach-policy-arn="arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy" \
  --approve
```

The [AWS documentation](https://docs.aws.amazon.com/eks/latest/userguide/csi-iam-role.html) has more details.

### Deploy EBS CSI Addon

With the IAM Role created, deploy the EBS CSI Addon:

```bash
eksctl create addon \
  --region="${AWS_REGION}" \
  --name="aws-ebs-csi-driver" \
  --cluster="${CLUSTER_NAME}" \
  --service-account-role-arn="arn:aws:iam::${AWS_ACCOUNT_ID}:role/${CLUSTER_NAME}-ebs-csi-driver-role" \
  --force
```

The [AWS documentation](https://docs.aws.amazon.com/eks/latest/userguide/managing-ebs-csi.html#adding-ebs-csi-eks-add-on) has more details.

### Create a Storage Class for the EBS CSI Addon

Create a Storage Class for the EBS CSI Addon:

```bash
cat <<EOF | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
EOF
```

The [EBS CSI driver documentation](https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/parameters.md) describes the Storage Class parameters.

### Create Load Balancer Controller IAM Role

Okteto recommends installing the Load Balancer Controller to manage the Okteto certificates with Amazon Certificate Manager.
The [AWS documentation for the Load Balancer Controller](https://docs.aws.amazon.com/eks/latest/userguide/aws-load-balancer-controller.html) has more details.

Before you install the Load Balancer Controller in your Kubernetes cluster, download its IAM Policy manifest:

```bash
curl \
  -s \
  -o iam-policy.json \
  https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v3.1.0/docs/install/iam_policy.json
```

:::note
The maintainers of `kubernetes-sigs/aws-load-balancer-controller` recommend scoping this policy down by the VPC ID or by the cluster name resource tag. Their [installation docs](https://kubernetes-sigs.github.io/aws-load-balancer-controller/v2.7/deploy/installation/#option-a-recommended-iam-roles-for-service-accounts-irsa) explain how.
:::

Create the IAM Policy for the Load Balancer Controller IAM Role:

```bash
aws iam create-policy \
  --policy-name="${CLUSTER_NAME}-load-balancer-controller-policy" \
  --policy-document file://iam-policy.json
```

Create the IAM Role for the Load Balancer Controller:

```bash
eksctl create iamserviceaccount \
  --region="${AWS_REGION}" \
  --name="aws-load-balancer-controller" \
  --namespace="kube-system" \
  --cluster="${CLUSTER_NAME}" \
  --role-name="${CLUSTER_NAME}-aws-load-balancer-controller-role" \
  --attach-policy-arn="arn:aws:iam::${AWS_ACCOUNT_ID}:policy/${CLUSTER_NAME}-load-balancer-controller-policy" \
  --approve
```

### Deploy Load Balancer Controller

With the IAM Role created, deploy the Load Balancer Controller.

Add the EKS Helm chart repository:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update
```

Install the Load Balancer Controller chart:

```bash
helm upgrade --install \
  aws-load-balancer-controller \
  eks/aws-load-balancer-controller \
  --version="3.1.0" \
  --namespace="kube-system" \
  --set clusterName=${CLUSTER_NAME} \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
```

## Installing Okteto

:::note
Argo CD installs the same Helm chart declaratively. See [Configure Argo CD](self-hosted/manage/argocd.mdx) for the `Application` manifest, sync policy, and the `ignoreDifferences` Okteto requires.
It replaces [Add the Okteto Helm repository](#add-the-okteto-helm-repository) and [Installing the Okteto Helm chart](#installing-the-okteto-helm-chart). Every other step on this page still applies, including the DNS record and the sign-in.
:::

You install Okteto with its Helm chart.

### Add the Okteto Helm Repository

Add the Okteto Helm repository:

```bash
helm repo add okteto https://charts.okteto.com
helm repo update
```

### Create the Helm Configuration File

Create a `config.yaml` file with these settings, replacing `license` and `subdomain` with your own values:

```yaml title="config.yaml"
// highlight-next-line
license: "REPLACE ME WITH YOUR OKTETO LICENSE"
// highlight-next-line
subdomain: "REPLACE ME WITH YOUR OKTETO DOMAIN"

ingress-nginx:
  controller:
    service:
      annotations:
        service.beta.kubernetes.io/aws-load-balancer-type: nlb
        service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"

registry:
  storage:
    filesystem:
      persistence:
        enabled: true
```

This is the minimum configuration. The [Helm configuration](self-hosted/helm-configuration.mdx) lists every setting.

The `service.beta.kubernetes.io/aws-load-balancer-type: nlb` annotation tells AWS to expose the ingress controller with a [Network Load Balancer (NLB)](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html) instead of the default [Classic Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/classic/introduction.html). We recommend an NLB because it supports WebSockets and static IPs, and it performs better. AWS publishes a [comparison of the load balancers](https://aws.amazon.com/elasticloadbalancing/features/).

### Installing the Okteto Helm Chart

Install the Okteto Helm chart:

<CodeBlock language="bash">
  {`helm upgrade --install okteto okteto/okteto -f config.yaml --namespace=okteto --create-namespace --version=${variables.chartVersion}`}
</CodeBlock>

After a few seconds, Helm creates all the resources. The output looks like this:

```bash
Release "okteto" has been installed. Happy Helming!
NAME: okteto
LAST DEPLOYED: Thu Mar 26 18:07:55 2020
NAMESPACE: okteto
STATUS: deployed
```

### Retrieve the Ingress Controller IP Address

Use `kubectl` to get the address that EKS allocated to the NGINX ingress controller that Okteto installs:

```bash
kubectl get service -l=app.kubernetes.io/name=ingress-nginx,app.kubernetes.io/component=controller --namespace=okteto
```

The output looks like this:

```
NAME                             TYPE           CLUSTER-IP   EXTERNAL-IP                          PORT(S)                                     AGE
okteto-ingress-nginx-controller  LoadBalancer   10.0.7.73    a519c8b3b27f94...elb.amazonaws.com   80:30795/TCP,443:32481/TCP,1234:30885/TCP   5m
```

Add the `EXTERNAL-IP` address (`a519c8b3b27f94...elb.amazonaws.com` in the example) to the DNS of your domain. In Route 53, create an `A` record with the name `*` that points to the alias of the Elastic Load Balancer.

### Sign In to Your Okteto Instance

:::warning

The default installation isn't meant for production. Once you finish your evaluation, and before you give your team access to your Okteto instance, configure a wildcard [AWS ACM certificate](self-hosted/install/certificates/aws-acm.mdx) and [Okteto Registry storage with S3](self-hosted/install/okteto-registry-storage/aws-s3-bucket.mdx).

:::

Once the installation finishes, your Okteto instance is available at `https://okteto.SUBDOMAIN`. The default installation uses [token-based authentication](self-hosted/install/auth/token.mdx) and a self-signed certificate. The post-installation notes that Helm prints include the URL to log in to the Okteto UI with the token of the Admin user, and the command to configure the Okteto CLI with that token. To show the notes again, run:

```bash
helm get notes okteto --namespace=okteto
```

## Optional: Configure Access to Your Amazon ECR

You can give Okteto [access to your Amazon Elastic Container Registry](admin/registry-credentials/amazon-ecr.mdx). Your Dockerfiles and your deployments can then use its private images without pull secrets.

## Deploy Your First App

With your Okteto instance running, [install the Okteto CLI](get-started/install-okteto-cli.mdx) and configure it with the command of the post-installation notes, replacing `TOKEN` with the token of the Admin user:

```bash
okteto context use https://okteto.SUBDOMAIN --token TOKEN --insecure-skip-tls-verify
```

The `--insecure-skip-tls-verify` flag makes the Okteto CLI accept the self-signed certificate. Without it, the command fails with `x509: certificate signed by unknown authority`.

Then deploy your first application with the [quickstart](get-started/quickstart.mdx).

:::note
The tests of the quickstart open the application in a browser that doesn't trust the self-signed certificate, so `okteto test` fails with `ERR_CERT_AUTHORITY_INVALID`. Configure a wildcard [AWS ACM certificate](self-hosted/install/certificates/aws-acm.mdx) before you run `okteto test`.
:::
