In an autonomous workflow, a coding agent takes a task from a ticket to a pull request without a developer in the loop. It deploys its own application environment, writes the code, verifies the change against the running application, and opens a pull request when everything passes. You review the result, with the tests that passed and the URL of the environment, not the process.

## The Agent Loop

The agent repeats the same loop until the change works:

<Image
  src={require("@site/static/img/coding-agents-loop.webp").default}
  mobileSrc={require("@site/static/img/coding-agents-loop-mobile.webp").default}
  borderless
  alt="The autonomous agent loop: the agent takes a task, edits the code, deploys it with okteto deploy, verifies it with okteto test, the endpoints, and the logs, goes back to edit the code when something fails, and opens a pull request when everything passes"
/>

1. The agent reads the ticket for the requirements and the acceptance criteria.
2. `okteto deploy --wait` deploys the application environment, and `okteto endpoints` gets its URLs.
3. The agent reads `okteto.yaml` to discover the services, and changes the code.
4. If the change touches `okteto.yaml`, `okteto validate` checks it first. Then `okteto build <service>` rebuilds the images that changed, and `okteto deploy --wait` redeploys the application.
5. The agent verifies the change:
   - `okteto test <name>` runs the tests of your Okteto Manifest, inside the cluster.
   - `curl` against the URLs of `okteto endpoints` checks the new behavior.
   - `okteto logs <service> --since 5m` shows runtime errors.
6. If anything fails, the agent fixes the code and goes back to step 4.
7. When everything passes, the agent commits the change, opens a pull request, and reports what it changed, the tests that passed, and the URL of the environment.

Nothing syncs in an autonomous workflow, so the agent redeploys after every change, including changes to a Dockerfile, a dependency manifest, or `okteto.yaml`. `okteto up` is never part of it: it's interactive and hangs the agent's shell.

## Example: Ticket to Pull Request

A CI pipeline or a webhook starts the agent with a ticket:

> Add a `/health` endpoint to the API service that returns the database connectivity status and the uptime.

The agent deploys the environment and gets its URLs:

```bash
okteto deploy --wait
okteto endpoints
```

After it changes the code, the agent rebuilds, redeploys, and verifies the change:

```bash
# Rebuild the api image and redeploy the application
okteto build api
okteto deploy --wait

# Run the integration tests
okteto test integration

# Call the new endpoint
curl -s https://api-agent-proj-123.okteto.example.com/health

# Check the logs of the api service
okteto logs api --since 5m
```

If a test or the endpoint fails, the agent reads the error, fixes the code, and runs the loop again. When everything passes, it opens the pull request:

```bash
git add src/api/health.ts src/api/routes.ts
git commit -m "Add /health endpoint with database status"
gh pr create --title "Add health endpoint" --body "..."
```

## Authentication

An agent that runs without a developer can't sign in to Okteto in a browser. Give it a [Personal Access Token](user-settings/personal-access-tokens.mdx) for the account it deploys as, and connect the Okteto CLI before any other command:

```bash
okteto context use https://okteto.example.com --token $OKTETO_TOKEN
```

Store the token as a secret of your CI system, such as a GitHub Actions secret or a GitLab CI/CD variable. The agent has the same access as the owner of the token.

## Parallel Tasks

An autonomous agent often works on several tickets at once, each on its own branch and git worktree. Tasks that deploy to the same Namespace overwrite each other's environments. Give each task its own Namespace: the agent creates it with `okteto namespace create <ns>` and passes `-n <ns>` to every command. See [Worktree Isolation](coding-agents/best-practices.mdx#worktree-isolation) for the details.

## Running Agents in CI

A CI pipeline can start the agent when someone labels an issue, give it its own Namespace, and destroy that Namespace when the pull request closes. The [Ticket to pull request with an autonomous agent](/tutorials/agent-ticket-to-pr/) tutorial builds this pipeline with GitHub Actions, and the [okteto-agent-skills repository](https://github.com/okteto/okteto-agent-skills/tree/main/examples) has a complete workflow to copy.

The pipeline owns the environments it creates, so it can let the agent destroy them without asking: set the `OKTETO_ALLOW_AGENT_DESTROY` environment variable to `1` in the pipeline, and the [guardrail hooks](coding-agents/okteto-skills.mdx#guardrail-hooks) of the Claude Code plugin allow `okteto destroy` and `okteto namespace delete`. See [Cleanup and Teardown](coding-agents/best-practices.mdx#cleanup-and-teardown) for the rules that the agent follows otherwise.
