The [Okteto skills](coding-agents/okteto-skills.mdx) teach a coding agent how to work with Okteto. If you don't want to install them, give the agent these rules yourself, in the `AGENTS.md` file of your repository.

## Instructions to Copy

Add this to the `AGENTS.md` file of your repository:

```markdown title="AGENTS.md"
## Working with Okteto

This project deploys to Okteto. Verify every change in an Okteto application
environment before you report it as done.

- Create a Namespace for this session with
  `okteto namespace create <name> --use=false`, named after the branch, and
  pass `-n <name>` to every `okteto` and `kubectl` command. Don't run
  `okteto namespace use`.
- Read `okteto.yaml` to find the services, the images, and the tests. Don't
  guess their names. If you change it, run `okteto validate` before you deploy.
- Build images with `okteto build <service>`. Don't run `docker build`.
- Deploy with `okteto deploy --wait`. Don't run `kubectl apply` or
  `helm install`.
- Test with `okteto test <name>`. To run part of a test, pass the command
  after `--`.
- Check the change with the URLs of `okteto endpoints`, and troubleshoot with
  read-only `kubectl` commands: `kubectl logs`, `kubectl get events`, and
  `kubectl top pods`.
- Never run `okteto up`: it's interactive. Ask the developer to run it. While
  it runs, don't build, deploy, or test: only edit the code, and hot reload
  applies your changes.
- After you open the pull request, delete the Namespace you created for this
  session with `okteto namespace delete <name>`. If a developer is working
  with you, ask first. Never delete or destroy a Namespace you didn't create.
```

## Recommendations

Each rule of the instructions has a reason.

### A Namespace for Each Session {#worktree-isolation}

Each session gets an application environment of its own, so two sessions never overwrite each other's work. `--use=false` and the `-n` flag leave the Okteto context untouched, because every session on the same machine shares it. See [A Namespace for Each Session](coding-agents/index.mdx#parallel-tasks).

### Services from okteto.yaml

The `okteto.yaml` file lists the services, the images to build, and the tests, so the agent works the same way in every repository instead of guessing names.

### Builds with okteto build

`okteto build` builds the image inside the cluster and pushes it to the Okteto Registry, where the application environment pulls it. An image built with `docker build` stays in the agent's sandbox, and needs a Docker daemon there.

### Deploys with okteto deploy

`okteto deploy --wait` waits until every service is ready, and Okteto tracks what it creates. Resources that the agent creates with `kubectl apply` or `helm install` don't show up in the Okteto UI, and `okteto destroy` doesn't delete them.

### Tests with okteto test

`okteto test` runs the tests of your Okteto Manifest inside the cluster, against the application environment. The Kubernetes API gives the agent the rest: the logs, the events, and the resource usage of its services.

### okteto up for the Developer

`okteto up` is interactive, and it hangs the agent's shell. In a [collaborative workflow](coding-agents/collaborative-workflows.mdx), you run it in your own terminal, and its hot reload applies the changes that the agent makes.

### Namespace Cleanup

An autonomous workflow ends in a pull request, which gets its own [Preview Environment](previews/index.mdx), so the Namespace of the session isn't needed anymore. The agent only deletes the Namespace that it created: `okteto destroy` and `okteto namespace delete` delete work in progress.
