Divert lets developers deploy only the services they are changing and reuse a shared environment for every other service in the application. A request to your environment reaches your version of the services you deployed, and the shared version of everything else.

## When to Use Divert

A Development Environment with a full replica of your application is the simplest setup, and it's the right choice for many teams: every service runs the version you deploy, and nothing you do affects anyone else.

As your application grows, usually around 30 to 50 services, deploying a full replica of it for every feature starts to have tradeoffs:

- **Longer deploy times**: every environment waits for services nobody is changing to build, start, and become healthy
- **Less reliability**: a deploy fails when any service fails, even one owned by another team that nobody in the environment is touching
- **Higher infrastructure costs**: every environment reserves the resources of the whole application

That's where Divert comes in. The full application runs once in a shared environment, and each developer, Preview Environment, or AI agent deploys only the services it changes. An environment starts in the time it takes to deploy those services, and uses only what those services need.

A full replica is still the better fit when you need control over every service, such as reproducing a bug that depends on specific versions of several services, or working on a change that touches most of the application.

## How Divert Works

Divert routes each request by the divert header it carries: the `baggage` header with the key `okteto-divert=<namespace>`. The diagram below shows the Movies application with Cindy working on the catalog service:

![Requests to the staging host go to the shared services. Requests with baggage okteto-divert=cindy reach Cindy's catalog service, which uses its own MongoDB database](@site/static/img/divert-overview.svg)

1. A shared environment runs the complete application, for example in a `staging` Namespace.
2. Cindy deploys only the catalog service and its MongoDB database in her own Namespace. This is her diverted environment.
3. Requests that carry Cindy's divert header (`baggage: okteto-divert=cindy`) are routed to her catalog service. Cindy opens the application from the Okteto UI, which adds her divert header, or sets the header herself with a browser extension or `curl`.
4. Every other service, and every request without Cindy's divert header, is served by the shared environment.

Several developers can divert from the same shared environment at the same time. Each one only sees their own changes, and the shared environment is not affected by any of them.

## Concepts

- **Shared Environment**: a Namespace that runs the complete application and serves every service that a developer doesn't deploy. It can be a Namespace managed by Okteto, such as a Preview Environment redeployed on every merge, or, with Istio VirtualServices, any other namespace in the same cluster.
- **Diverted Environment**: the Namespace where a developer, a CI job, or an AI agent deploys only the services it is changing. It is configured with the `divert` section of the Okteto Manifest.
- **Diverted Service**: a service deployed in a diverted environment that also runs in the shared environment. Requests with the divert header of that environment reach the diverted service instead of the shared one.
- **Divert header**: the [`baggage`](https://www.w3.org/TR/baggage/) header with the key `okteto-divert=<namespace>`, where `<namespace>` is the diverted Namespace. Okteto routes requests that carry it to the diverted services in that Namespace.
- **Header Propagation**: forwarding the `baggage` header from each incoming request to the outgoing calls it triggers, so the divert header reaches every service in the call chain.
- **Queue Splitting**: making sure a message produced for one environment is consumed by that environment and not by the shared one, or by another developer's.
- **Data Cloning**: giving a diverted service its own copy of a database, cloned from the shared environment, instead of writing to the shared one.

## Application Requirements

Divert routes HTTP and gRPC traffic. For your application to work with it:

- Services must forward the `baggage` header to the services they call. See [Header Propagation](development/divert/header-propagation.mdx).
- Services that produce or consume messages need a strategy to keep messages in the right environment. See [Queue Splitting](development/divert/queue-splitting.mdx).
- Services that write to a database need to decide whether they share the database or use their own copy. See [Data Cloning](development/divert/data-cloning.mdx).

The [Divert section of Development Environments](development/divert/index.mdx) covers how to create a shared environment, configure your Okteto Manifest, adapt your application with [Header Propagation](development/divert/header-propagation.mdx), [Queue Splitting](development/divert/queue-splitting.mdx), and [Data Cloning](development/divert/data-cloning.mdx), the best practices for each, and how to [troubleshoot](development/divert/troubleshooting.mdx) requests that don't reach your diverted services.
