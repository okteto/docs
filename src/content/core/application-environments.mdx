An application environment is a running copy of your application on Kubernetes: its services, its data, and the cloud resources it depends on, deployed in an [Okteto Namespace](core/namespaces.mdx) from the Okteto Manifest (`okteto.yaml`) in your repository. Developers, pull requests, and AI coding agents create application environments from the same definition, so a change that works in one environment works in the others.

## Okteto Manifest

The Okteto Manifest (`okteto.yaml`) is the file in your repository that defines how Okteto builds, deploys, tests, and develops your application. These are its main sections:

| Section | What it defines |
|---|---|
| [`build`](#build) | The images of your services, built by the [Okteto Build Service](core/build-service.mdx) |
| [`dependencies`](#dependencies) | Other Git repositories deployed with the application, such as a database |
| [`deploy`](#deploy) | The commands that deploy the application: Helm, `kubectl`, [Docker Compose](reference/docker-compose.mdx), or your own scripts |
| [`destroy`](#destroy) | The commands that delete the resources of the application outside the cluster |
| [`dev`](#dev) | The Development Containers that `okteto up` syncs your local code to |
| [`external`](#external) | Cloud resources and dashboards that are part of the application, shown in the Okteto UI |
| [`test`](#test) | The Test Containers that [`okteto test`](reference/okteto-cli.mdx#test) runs against the environment |

The [Okteto Manifest reference](reference/okteto-manifest.mdx) describes every option. A minimal Okteto Manifest that builds two images, deploys them with Helm, and runs the end-to-end tests looks like this:

```yaml title="okteto.yaml"
build:
  api:
    context: api
  frontend:
    context: frontend

deploy:
  - name: Helm Install
    command: |
      helm upgrade --install movies chart \
        --set api.image=${OKTETO_BUILD_API_IMAGE} \
        --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}

test:
  e2e:
    image: ghcr.io/okteto/playwright:chromium
    context: e2e
    commands:
      - bash run_tests.sh
```

Okteto runs the `deploy` and `test` commands in the cluster with [Remote Execution](core/remote-execution.mdx), and exposes the endpoints of the application on HTTPS. The deploy commands can also create cloud resources, such as a database or a queue, with the [Cloud Credentials](admin/cloud-credentials/index.mdx) that the Admin configures, and delete them in the `destroy` section.

## Environments for each workflow

Every workflow deploys the same `okteto.yaml`:

| Workflow | How the environment is created |
|---|---|
| Development | A developer runs `okteto deploy`, or deploys from the Okteto UI. The result is a [Development Environment](development/index.mdx), and `okteto up` syncs local code to it. |
| Pull requests | The CI pipeline runs `okteto preview deploy`, or the `okteto/deploy-preview` GitHub Action. The result is a [Preview Environment](previews/index.mdx) with its own URL, destroyed when the pull request closes. |
| Coding agents | The agent creates a Namespace for its task with `okteto namespace create`, then runs `okteto deploy` and `okteto test` in it. [Agentic Workflows](agentic/index.mdx) covers the skills that teach the agent these commands. |

`okteto test` runs the same Test Containers in all three, so developers, agents, and CI validate a change with the same tests.

With [Divert](development/divert/index.mdx), an environment deploys only the services that change, on top of a shared Namespace that runs the rest of the application.

## Application environments and agent sandboxes

A coding agent runs in an agent sandbox, where it reads and edits code and runs commands. The application runs in the application environment. Okteto keeps the two apart: the agent runs the Okteto CLI, and Okteto builds the images and runs the deploy and test commands in the cluster. The agent sandbox needs the Okteto CLI and access to your Okteto instance, not a Docker daemon or the dependencies of your application.

Because the sandbox doesn't run the application, the agent uses application environments the same way whether it runs in your cluster, in a hosted runtime, or on a developer's laptop.

## Lifecycle of an application environment

- `okteto destroy` deletes the resources of an environment and runs the commands of the `destroy` section.
- The CI pipeline destroys a Preview Environment when its pull request closes, with `okteto preview destroy` or the `okteto/destroy-preview` GitHub Action.
- The [Garbage Collector](admin/cleanup.mdx) scales idle environments to zero and deletes the unused ones, after the periods the Admin configures.

## Sections of the Okteto Manifest

### Build

The `build` section defines the images of your services. Okteto builds them with the [Okteto Build Service](core/build-service.mdx):

```yaml
build:
  api:
    context: api
  frontend:
    context: frontend
    dockerfile: Dockerfile
    secrets:
      npmrc: .npmrc
```

Okteto builds the `api` image from the `api` folder, and the `frontend` image from the `frontend` folder with its `Dockerfile` and the `.npmrc` file as a build secret. The [`build` reference](reference/okteto-manifest.mdx#build-object-optional) describes every option.

### Dependencies

The `dependencies` section lists other Git repositories that Okteto deploys with your application:

```yaml
dependencies:
  mongodb:
    repository: https://github.com/okteto/mongodb
    wait: true
```

Okteto deploys the `okteto/mongodb` repository and, because of `wait: true`, waits until its resources are ready before it runs the commands of the `deploy` section. The [`dependencies` reference](reference/okteto-manifest.mdx#dependencies-string-optional) describes every option.

### Deploy

The `deploy` section lists the commands that deploy your application, usually `helm`, `kubectl`, and `okteto` commands. The Okteto UI shows every resource these commands create as part of one application environment. Resources outside the cluster appear in the Okteto UI when you list them in the [`external`](#external) section.

```yaml
deploy:
  - name: Deploy PostgreSQL
    command: helm upgrade --install postgresql postgresql/postgresql-11.6.21.tgz -f postgresql/values.yml --version 11.6.21
  - name: Deploy Frontend
    command: helm upgrade --install frontend frontend/chart --set image=${OKTETO_BUILD_FRONTEND_IMAGE}
  - name: Deploy API
    command: helm upgrade --install api api/chart --set image=${OKTETO_BUILD_API_IMAGE} --set load=${API_LOAD_DATA:-true}
```

Okteto runs the three commands in order: it deploys a PostgreSQL database, then the `frontend` Helm chart, then the `api` Helm chart. Each chart gets the image that Okteto built for it from the `OKTETO_BUILD_FRONTEND_IMAGE` and `OKTETO_BUILD_API_IMAGE` variables. The [`deploy` reference](reference/okteto-manifest.mdx#deploy-string-optional) describes every option.

### Destroy

The `destroy` section lists the commands that delete the resources of your application outside the cluster. `okteto destroy` deletes the Kubernetes resources that `okteto deploy` created, and then runs these commands:

```yaml
destroy:
  image: ghcr.io/okteto/pipeline-runner:1.0.0-sam
  commands:
    - name: destroy worker service
      command: |
        sam delete --no-prompts --stack-name "${OKTETO_NAMESPACE}-worker" --region us-east-1
```

The command deletes the worker service that the application runs in AWS, so it doesn't stay active after the environment is gone. The [`destroy` reference](reference/okteto-manifest.mdx#destroy-string-optional) describes every option.

### Dev

The `dev` section defines the Development Containers of your application. `okteto up` replaces a service with its Development Container and syncs your local code to it, so you see your changes in the application environment as you edit, and debug the service from your computer:

```yaml
dev:
  api:
    command: ["bash"]
    forward:
      - 8080:8080
      - 9229:9229
    sync:
      - api:/usr/src/app
  frontend:
    command: yarn start
    sync:
      - frontend:/usr/src/app
```

The `api` Development Container syncs the local `api` folder to `/usr/src/app`, opens a shell, and forwards ports `8080` and `9229` to your computer. The `frontend` Development Container syncs the local `frontend` folder and runs `yarn start`. The [`dev` reference](reference/okteto-manifest.mdx#dev-object-optional) describes every option.

### External

The `external` section lists resources outside the cluster that are part of your application, such as cloud resources or dashboards, so the Okteto UI shows them with the rest of the environment:

```yaml
external:
  readme:
    icon: okteto
    notes: README.md
    endpoints:
      - name: Try it out!
        url: https://github.com/okteto/voting-app-with-external-resources
  lambda:
    icon: aws
    notes: docs/lambda.md
    endpoints:
      - name: function
```

This section only describes the resources and links to them. It doesn't create anything in a cloud provider: the commands of the [`deploy`](#deploy) and [`destroy`](#destroy) sections create and delete them. The [`external` reference](reference/okteto-manifest.mdx#external-object-optional) describes every option.

### Test

The `test` section defines the Test Containers of your application. `okteto test` runs them with [Remote Execution](core/remote-execution.mdx#how-remote-execution-works) against the environment, so the tests behave the same in a [Development Environment](development/index.mdx), in a [Preview Environment](previews/index.mdx), and in CI:

```yaml
test:
  unit:
    image: ghcr.io/okteto/golang:1
    artifacts:
      - coverage.out
    caches:
      - /go
      - /root/.cache
    commands:
      - "go test . -v"

  integration:
    depends_on:
      - unit
    image: ghcr.io/okteto/golang:1
    context: integration
    commands:
      - make tests
```

`okteto test` runs every Test Container. To run one, pass its name as an argument, for example `okteto test unit`.

To run a single Test Container with different commands without editing your Okteto Manifest, pass them after `--` or with the `--command` flag, for example `okteto test unit -- go test ./pkg/api -run TestLogin`. The [`okteto test` reference](reference/okteto-cli.mdx#overriding-the-commands-of-a-test-container) describes the override rules.
