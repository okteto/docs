An application environment is a running copy of your application on Kubernetes: its services, its data, and the cloud resources it depends on, deployed in an [Okteto Namespace](core/namespaces.mdx) from the Okteto Manifest (`okteto.yaml`) in your repository. Developers, pull requests, and AI coding agents create application environments from the same definition, so a change that works in one environment works in the others.

## Environment workflows

Developers, pull requests, and coding agents go through the same steps with an application environment, from the same `okteto.yaml`:

1. **Namespace:** the environment runs in its own [Okteto Namespace](core/namespaces.mdx). A developer uses their personal Namespace, `okteto preview deploy` creates one for each pull request, and a coding agent creates one for its task with `okteto namespace create`.
2. **Deploy:** `okteto deploy` builds the images of the [`build`](#build) section and runs the commands of the [`deploy`](#deploy) section. A developer runs it, or deploys from the Okteto UI, and gets a [Development Environment](development/index.mdx) where `okteto up` syncs local code. In a pull request, the CI pipeline runs `okteto preview deploy`, or the `okteto/deploy-preview` GitHub Action, and gets a [Preview Environment](previews/index.mdx) with its own URL. With [Divert](development/divert/index.mdx), the environment deploys only the services that change, on top of a shared Namespace that runs the rest of the application.
3. **Test:** `okteto test` runs the Test Containers of the [`test`](#test) section against the environment, so developers, coding agents, and CI validate a change with the same tests.
4. **Destroy:** `okteto destroy` deletes the resources of the environment and runs the commands of the [`destroy`](#destroy) section. The CI pipeline destroys a Preview Environment when its pull request closes, with `okteto preview destroy` or the `okteto/destroy-preview` GitHub Action. The [Garbage Collector](admin/cleanup.mdx) scales idle environments to zero and deletes the unused ones, after the periods the Admin configures.

Okteto runs every step in the cluster with [Remote Execution](core/remote-execution.mdx): the [Okteto Build Service](core/build-service.mdx) builds the images, and the deploy, test, and destroy commands run in the cluster. No step depends on the machine where the Okteto CLI runs, whether it's the sandbox of a coding agent, a developer's laptop, or a CI job. That machine needs the Okteto CLI and access to your Okteto instance, not a Docker daemon or the dependencies of your application:

## Okteto Manifest

The Okteto Manifest (`okteto.yaml`) is the file in your repository that defines how Okteto builds, deploys, tests, and develops your application. These are its main sections:

| Section | What it defines |
|---|---|
| [`build`](#build) | The images of your services, built by the [Okteto Build Service](core/build-service.mdx) |
| [`dependencies`](#dependencies) | Other Git repositories deployed with the application, such as a database |
| [`deploy`](#deploy) | The commands that deploy the application: Helm, `kubectl`, [Docker Compose](reference/docker-compose.mdx), or your own scripts |
| [`destroy`](#destroy) | The commands that delete the resources of the application outside the cluster |
| [`dev`](#dev) | The Development Containers that `okteto up` syncs your local code to |
| [`external`](#external) | Cloud resources and dashboards that are part of the application, shown in the Okteto UI |
| [`test`](#test) | The Test Containers that [`okteto test`](reference/okteto-cli.mdx#test) runs against the environment |

The [Okteto Manifest reference](reference/okteto-manifest.mdx) describes every option. A minimal Okteto Manifest that builds two images, deploys them with Helm, and runs the end-to-end tests looks like this:

```yaml title="okteto.yaml"
build:
  api:
    context: api
  frontend:
    context: frontend

deploy:
  image: ghcr.io/okteto/pipeline-runner:1.0.0
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}

test:
  e2e:
    image: ghcr.io/okteto/playwright:chromium
    context: e2e
    commands:
      - bash run_tests.sh
```

Okteto exposes the endpoints of the application on HTTPS. The deploy commands can also create cloud resources, such as a database or a queue, with the [Cloud Credentials](admin/cloud-credentials/index.mdx) that the Admin configures, and delete them in the `destroy` section.

## Sections of the Okteto Manifest

### Build

The `build` section defines the images of your services. The [Okteto Build Service](core/build-service.mdx) builds them in the cluster:

```yaml
build:
  api:
    context: api
  frontend:
    context: frontend
```

Okteto builds an image from the `api` folder and another from the `frontend` folder, and the deploy commands get them from the `OKTETO_BUILD_API_IMAGE` and `OKTETO_BUILD_FRONTEND_IMAGE` variables. The [`build` reference](reference/okteto-manifest.mdx#build-object-optional) describes every option.

### Dependencies

The `dependencies` section lists other Git repositories that Okteto deploys with your application:

```yaml
dependencies:
  mongodb:
    repository: https://github.com/okteto/mongodb
    wait: true
```

Okteto deploys the `okteto/mongodb` repository from its own Okteto Manifest, and waits until it's ready before it deploys your application. The [`dependencies` reference](reference/okteto-manifest.mdx#dependencies-string-optional) describes every option.

### Deploy

The `deploy` section lists the commands that deploy your application, such as `helm` or `kubectl` commands:

```yaml
deploy:
  image: ghcr.io/okteto/pipeline-runner:1.0.0
  commands:
    - name: Deploy PostgreSQL
      command: helm upgrade --install postgresql postgresql/chart
    - name: Deploy the Movies app
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}
```

Okteto runs the commands in order, in a container of the `image` you set, in the cluster. The Okteto UI shows every resource they create as part of the application environment. The [`deploy` reference](reference/okteto-manifest.mdx#deploy-string-optional) describes every option.

### Destroy

The `destroy` section lists the commands that delete the resources of your application outside the cluster:

```yaml
destroy:
  image: ghcr.io/okteto/tfenv-ci:1.4
  commands:
    - name: Delete the cloud resources
      command: terraform destroy --auto-approve
```

`okteto destroy` deletes the Kubernetes resources of the environment, and then runs these commands in a container of the `image` you set, in the cluster, to delete the cloud resources that the deploy commands created. The [`destroy` reference](reference/okteto-manifest.mdx#destroy-string-optional) describes every option.

### Dev

The `dev` section defines the Development Containers of your application:

```yaml
dev:
  api:
    command: bash
    sync:
      - api:/usr/src/app
```

`okteto up api` replaces the `api` service with a Development Container, syncs the local `api` folder to `/usr/src/app`, and opens a shell in it, so you run your changes in the application environment as you edit them. The [`dev` reference](reference/okteto-manifest.mdx#dev-object-optional) describes every option.

### External

The `external` section lists resources outside the cluster that are part of your application, such as cloud resources or dashboards:

```yaml
external:
  lambda:
    icon: aws
    notes: docs/lambda.md
    endpoints:
      - name: function
```

The Okteto UI shows the `lambda` function with the rest of the environment, with its notes and its endpoint. This section only describes the resources: the commands of the [`deploy`](#deploy) and [`destroy`](#destroy) sections create and delete them. The [`external` reference](reference/okteto-manifest.mdx#external-object-optional) describes every option.

### Test

The `test` section defines the Test Containers of your application:

```yaml
test:
  unit:
    image: ghcr.io/okteto/golang:1
    commands:
      - go test ./...
```

`okteto test` runs each Test Container in a container of its `image`, in the cluster, against the application environment. The [`test` reference](reference/okteto-manifest.mdx#test-object-optional) describes every option.
