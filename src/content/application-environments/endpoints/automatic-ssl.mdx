Okteto serves the applications deployed in your Namespaces on HTTPS endpoints, so everyone on your team can open an application environment in a browser. Okteto generates a hostname for each endpoint with the format `<name>-<namespace>.<okteto-subdomain>`, serves it with the wildcard certificate of your Okteto instance, and shows it in the Okteto UI and in the output of `okteto endpoints`. The same manifests work in every Namespace, and a hostname stays the same across redeploys as long as the name of the resource doesn't change.

You create endpoints with the resources you already deploy:

- [HTTPRoutes](application-environments/endpoints/httproutes.mdx): your own Gateway API HTTPRoutes, which Okteto attaches to its `Gateway`.
- [Docker Compose](application-environments/endpoints/docker-compose.mdx): the public ports and the `endpoints` section of your Docker Compose file.
- [Ingress](application-environments/endpoints/ingress.mdx): your own Ingress objects, for several paths or specific routing rules.
- [Services](application-environments/endpoints/services.mdx): a Service with the `dev.okteto.com/auto-ingress` annotation.
- [VirtualServices](application-environments/endpoints/virtual-services.mdx): your own Istio VirtualServices, with the hosts you set in them. An Admin enables them in the Helm configuration of your Okteto instance.
- [Custom Endpoints](application-environments/endpoints/custom-endpoints.mdx): annotations that hide the endpoints of a resource from the Okteto UI, or replace the ones it shows.
- [Private Endpoints](application-environments/endpoints/private-endpoints.mdx): endpoints that only the Okteto users with access to your Namespace can open. Private Endpoints are deprecated.

The Okteto CLI and UI only show an endpoint while the services behind it are running. If your endpoints still don't show up, see [Why don't my endpoints show up in the Okteto CLI or UI?](https://community.okteto.com/t/why-dont-my-endpoints-show-up-in-the-okteto-cli-or-ui/1490) in the Okteto Community forum.
