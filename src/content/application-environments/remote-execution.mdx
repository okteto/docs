Remote Execution runs the [`deploy`](application-environments/okteto-manifest.mdx#deploy), [`destroy`](application-environments/okteto-manifest.mdx#destroy), and [`test`](application-environments/okteto-manifest.mdx#test) commands of your Okteto Manifest in a container inside the cluster. The machine that runs the Okteto CLI, whether it's a developer's laptop, a CI job, or a coding agent's sandbox, doesn't need Helm, `kubectl`, or any other tool of your deploy commands, and every run works the same way on all of them.

## How Remote Execution Works {#how-remote-execution-works}

When you run `okteto deploy`, the Okteto CLI sends your local folder to the [Okteto Build Service](application-environments/build-service.mdx), and BuildKit runs your commands in a container started from the `image` of the `deploy` section:

The commands run in the `/okteto/src` folder of the container, with the [Okteto Variables](application-environments/okteto-variables.mdx) of your Namespace. Okteto also mounts its [Git SSH key](admin/integrations.mdx#git-ssh-key), so your commands can clone the private Git repositories that the key has access to, and the [known hosts](admin/ssh-known-hosts.mdx) that your Admin configures.

## When Commands Run Remotely

`okteto test` always runs your tests with Remote Execution. For `okteto deploy` and `okteto destroy`, the **Deploy Execution Mode** of [**Admin > Command Line (CLI)**](admin/cli.mdx) sets the default:

- **Remote**, the default: the commands run in the cluster. To run the commands of an application on your machine, set `remote: false` in its `deploy` section, or run `okteto deploy --remote=false`.
- **Local**, which is deprecated: the commands run on your machine, unless the `deploy` section sets an `image` or `remote: true`, or you run `okteto deploy --remote`.

```yaml title="okteto.yaml"
deploy:
  remote: true
  commands:
    - helm upgrade --install movies chart
```

## The Runner Image {#defining-your-own-image}

By default, your commands run in the [`okteto/pipeline-runner`](https://github.com/okteto/pipeline-runner) image, a Debian container with these tools:

- `bash`
- `curl`
- `envsubst`
- `git`
- `helm`
- `kubectl`
- `kustomize`
- `make`
- `okteto`
- `openssh`
- `wait-for-it`

To use other tools, or to pin the versions of your deploy tools for your whole team, set the `image` of the `deploy` section to your own image, or to the public image of the tool you use:

```yaml title="okteto.yaml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install movies chart
```

To change the default image of every repository that doesn't set its own, an Admin sets a [custom installer image](self-hosted/helm-configuration.mdx#custom-installer-image) in the Okteto Helm chart.

## Ignoring Files {#ignoring-files}

Okteto sends the folder of your Okteto Manifest to the container. To send another folder, set the `context` field:

```yaml title="okteto.yaml"
deploy:
  image: alpine/helm:4.3.2
  context: .
  commands:
    - helm upgrade --install movies chart
```

To leave out files that your commands don't use, such as large or sensitive files, add a `.oktetoignore` file to the `context` folder. It uses the format of [`.dockerignore` files](https://docs.docker.com/engine/reference/builder/#dockerignore-file), with a group of patterns for each kind of command:

```text title=".oktetoignore"
# Applied to all commands
docs

# Applied to deploy commands only
[deploy]
integration/*

# Applied to destroy commands only
[destroy]
app

# Applied to all tests
[test]
app

# Applied to the unit test only
[test.unit]
integration
```

With this file, Okteto ignores:

- `docs` and `integration/**` for the `deploy` commands.
- `docs` and `app` for the `destroy` commands.
- `docs` and `app` for every test.
- `docs`, `app`, and `integration` for the `unit` test.

:::note
For `deploy` and `destroy`, Okteto also reads the legacy `.oktetodeployignore` file, which is deprecated.
:::
