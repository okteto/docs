This guide builds, deploys, tests, and develops the [Rust Sample App](https://github.com/okteto/rust-getting-started), a hello world HTTP server, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. Each step uses the optimizations for Rust: the layers of the development image, the caches of the tests, watchexec for hot reload, and LLDB for debugging with VS Code. To see the Okteto workflow in an application with several services first, follow the [quickstart](get-started/quickstart.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [CodeLLDB extension](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb).

Clone the Rust Sample App:

```bash
git clone https://github.com/okteto/rust-getting-started
cd rust-getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yml` file of the repository, builds two images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so `hello-world` reuses its cached layers.

The `Dockerfile` of the Rust Sample App defines both images, one per stage:

```dockerfile title="Dockerfile"
FROM rust:1.100.0-trixie AS dev

RUN apt-get update && \
    apt-get install -y --no-install-recommends lldb-19=1:19.1.7-3+b1 && \
    rm -rf /var/lib/apt/lists/* && \
    cargo install --locked --root /usr/local watchexec-cli@2.8.0

WORKDIR /usr/src/app
COPY Cargo.toml Cargo.lock ./
RUN cargo fetch
COPY . .
RUN cargo build && \
    cargo build --release && \
    cp target/release/hello-world /usr/local/bin/hello-world

FROM debian:trixie-slim AS prod

COPY --from=dev /usr/local/bin/hello-world /usr/local/bin/hello-world
CMD ["/usr/local/bin/hello-world"]
```

- `dev` is the development image. It contains the Rust toolchain, [watchexec](https://github.com/watchexec/watchexec) for hot reload, [LLDB](https://lldb.llvm.org/use/remote.html) for debugging, the dependencies, and the source code. `cargo fetch` downloads the dependencies in their own layer, so the image only downloads them again when `Cargo.toml` or `Cargo.lock` change. `cargo build` compiles the dependencies in the `target` folder of the image, so the first build in the Development Container only compiles the code of the application.
- `prod` is the application image. It contains only the binary built in release mode in the `dev` stage.

The `dev` stage follows the recommendations for [development images](application-environments/development-containers/index.mdx#development-images): every version is pinned, and the stage that builds the application doubles as the development image.

Okteto pushes both images to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry). `okteto deploy` builds the images that aren't built yet before it deploys the application. To build them on their own, run `okteto build`.

## Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

Run `okteto deploy` from the root folder of the Rust Sample App:

```bash
okteto deploy
```

Okteto builds the `dev` and `hello-world` images, runs the deploy command, and prints the endpoint of the application:

## Test

The `test` section of the Okteto Manifest defines the `unit` [test](application-environments/okteto-test.mdx), which runs the unit test in `src/main.rs`, which sends a request to the axum router without opening a network connection:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /usr/local/cargo/registry
      - /okteto/src/target
    commands:
      - bash -o pipefail -c "cargo test 2>&1 | tee test-report.txt"
    artifacts:
      - test-report.txt
```

- `image`: the development image, so the tests run with the same Rust toolchain as the Development Container.
- `caches`: the Cargo registry and the `target` folder, kept between runs of the test. Tests run in `/okteto/src`, so the `target` folder of the tests is `/okteto/src/target`.
- `commands`: the commands that run the tests. The test fails if any of them exits with a non-zero code. `cargo test` has no stable report format, so `tee` copies its output to `test-report.txt`, and `bash -o pipefail` keeps the exit code of `cargo test`.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test report.

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the Rust Sample App:

```bash
okteto test
```


Running `okteto deploy` and `okteto test` after each change is usually fast enough, especially when a coding agent writes and tests the code autonomously. With the [Okteto skills](coding-agents/okteto-skills.mdx), the agent runs this loop in its own Namespace and reports back the tests it ran, the endpoints of the application, and a link to that Namespace.

## Develop

A [Development Container](application-environments/development-containers/index.mdx) gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` cycle, and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Rust Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: watchexec --restart --watch src --watch Cargo.toml -- cargo run
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
    forward:
      - 2345:2345
      - 2346:2346
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts watchexec, which runs `cargo run` and restarts it every time a file of the `src` folder or `Cargo.toml` changes.
- `sync`: synchronizes the root folder of the Rust Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies and the `target` folder come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/usr/local/cargo/registry` and `/usr/src/app/target` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the Cargo caches between `okteto up` sessions.
- `securityContext`: adds the `SYS_PTRACE` capability that LLDB needs to attach to the running application.
- `forward`: forwards ports `2345` and `2346`, where `lldb-server` listens, to your machine.

### Hot Reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts watchexec, which builds and runs the application:

```console
 i  Using cindy @ okteto.example.com as context
 i  'rust-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 i  Images were already built. To rebuild your images run 'okteto build'
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world
    Forward:   2345 -> 2345
               2346 -> 2346

[Running: cargo run]
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1.62s
     Running `target/debug/hello-world`
Starting hello-world server on 0.0.0.0:8080...
```

Open `src/main.rs` in your IDE, change the response message on line 7 to `Hello world from Okteto!`, and save the file:

```rust title="src/main.rs"
async fn hello() -> &'static str {
    "Hello world from Okteto!"
}
```

Okteto synchronizes `src/main.rs` to the Development Container, and watchexec rebuilds and restarts the application:

```console
[Running: cargo run]
   Compiling hello-world v0.1.0 (/usr/src/app)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.79s
     Running `target/debug/hello-world`
Starting hello-world server on 0.0.0.0:8080...
```

Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop watchexec and exit `okteto up`.

### Debugging with VS Code

`lldb-server` runs next to watchexec, so you debug the application that `okteto up` runs with hot reload. With `okteto up` running, start `lldb-server` in the Development Container from another terminal, in the root folder of the Rust Sample App:

```bash
okteto exec hello-world -- lldb-server-19 platform --server --listen '*:2345' --gdbserver-port 2346
```

`lldb-server` waits for a debugger on port `2345`, and starts a debugging session on port `2346` for each debugger that connects. It prints `Connection established.` every time VS Code connects.

The `.vscode/launch.json` file of the Rust Sample App attaches VS Code to the application through the ports that `okteto up` forwards to your machine:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "lldb",
      "request": "attach",
      "program": "/usr/src/app/target/debug/hello-world",
      "initCommands": [
        "platform select remote-linux",
        "platform connect connect://127.0.0.1:2345"
      ],
      "sourceMap": {
        "/usr/src/app": "${workspaceFolder}"
      }
    }
  ]
}
```

`program` is the binary that `cargo run` builds in the Development Container: CodeLLDB attaches to the process that runs it and downloads it from the Development Container to read its debug symbols. `sourceMap` maps `/usr/src/app`, the path in the `sync` field of the Okteto Manifest, to your local folder. If you synchronize your code to another path, change both to match it.

Open the Rust Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. Add a breakpoint on line 7 of `src/main.rs` and reload the endpoint in your browser. Execution stops in the `hello` function, and you can inspect the call stack and the variables.

When you save a file, watchexec restarts the application and the debugging session ends. Run the **Connect to okteto** configuration again to attach to the new process. Press `Ctrl+C` in the `okteto exec` terminal to stop `lldb-server`.

### Stopping the Development Container

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) uninstalls the Helm release of the Rust Sample App from your Namespace:

```bash
okteto destroy
```
