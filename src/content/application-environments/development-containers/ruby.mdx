This guide builds, deploys, tests, and develops the [Ruby Sample App](https://github.com/okteto/ruby-getting-started), a hello world HTTP server, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. Each step uses the optimizations for Ruby: the layers of the development image, the caches of the tests, `sinatra/reloader` for hot reload, and `rdbg` for debugging with VS Code. To see the Okteto workflow in an application with several services first, follow the [quickstart](get-started/quickstart.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [VSCode rdbg Ruby Debugger extension](https://marketplace.visualstudio.com/items?itemName=KoichiSasada.vscode-rdbg).

Clone the Ruby Sample App:

```bash
git clone https://github.com/okteto/ruby-getting-started
cd ruby-getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yml` file of the repository, builds two images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image before the `hello-world` image.

The `Dockerfile` of the Ruby Sample App defines both images, one per stage:

```dockerfile title="Dockerfile"
FROM ruby:4.0.10-trixie AS dev

RUN gem install debug -v 1.11.1

ENV APP_ENV=development
WORKDIR /opt/app
COPY Gemfile Gemfile.lock ./
RUN BUNDLE_FROZEN=true bundle install
COPY . .

FROM ruby:4.0.10-slim-trixie AS prod

ENV APP_ENV=production
WORKDIR /opt/app
COPY Gemfile Gemfile.lock ./
RUN BUNDLE_FROZEN=true BUNDLE_WITHOUT=test bundle install
COPY . .
CMD ["ruby", "app.rb"]
```

- `dev` is the development image. It contains Ruby, the gems in `Gemfile.lock` (among them [`sinatra/reloader`](https://sinatrarb.com/contrib/reloader) for hot reload), the [debug gem](https://github.com/ruby/debug) (`rdbg`) for debugging, and the source code. `APP_ENV=development` runs Sinatra in development mode, where `sinatra/reloader` reloads `app.rb` when it changes.
- `prod` is the application image. It's based on the slim Ruby image and contains the source code and the gems in `Gemfile.lock`, without the `test` group. `APP_ENV=production` runs Sinatra in production mode, without the reloader.

Both stages follow the recommendations for [development images](application-environments/development-containers/index.mdx#development-images): every version is pinned, and `bundle install` runs before `COPY . .`, so a change to the source code doesn't invalidate the layer with the gems.

Okteto pushes both images to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry). `okteto deploy` builds the images that aren't built yet before it deploys the application. To build them on their own, run `okteto build`.

## Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

Run `okteto deploy` from the root folder of the Ruby Sample App:

```bash
okteto deploy
```

Okteto builds the `dev` and `hello-world` images, runs the deploy command, and prints the endpoint of the application:

## Test

The `test` section of the Okteto Manifest defines the `unit` [test](application-environments/okteto-test.mdx), which runs the unit tests in `test/app_test.rb`, written with Minitest and Rack::Test:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /usr/local/bundle
    commands:
      - bundle install
      - bundle exec ruby test/app_test.rb
    artifacts:
      - coverage
```

- `image`: the development image, so the tests run with the same Ruby version as the Development Container.
- `caches`: the folder where Bundler installs the gems, kept between runs of the test. `bundle install` only installs the gems that aren't in the cache yet.
- `commands`: the commands that run the tests. The test fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the `coverage` folder with the report of SimpleCov.

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the Ruby Sample App:

```bash
okteto test
```

With the [Okteto skills](coding-agents/okteto-skills.mdx), the agent runs this loop in its own Namespace and reports back the tests it ran, the endpoints of the application, and a link to that Namespace.

## Develop

A [Development Container](application-environments/development-containers/index.mdx) gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` cycle, and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Ruby Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: ruby app.rb
    sync:
      - .:/opt/app
    persistentVolume:
      enabled: false
    forward:
      - 1234:1234
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts the application. The development image runs Sinatra in development mode, so `sinatra/reloader` loads `app.rb` again on the first request after the file changes.
- `sync`: synchronizes the root folder of the Ruby Sample App with `/opt/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the gems come from the development image, so there's no volume to create and attach. When you add a gem to the `Gemfile`, run `okteto deploy` to build the development image again.
- `forward`: forwards port `1234`, where `rdbg` listens, to your machine.

### Hot Reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts the application:

```console

 i  'ruby-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized

    Namespace: cindy
    Name:      hello-world
    Forward:   1234 -> 1234

[2026-11-19 04:04:25] INFO  WEBrick 1.9.2
[2026-11-19 04:04:25] INFO  ruby 4.0.10 (2026-11-19) [x86_64-linux]
== Sinatra (v4.2.2) has taken the stage on 8080 for development with backup from WEBrick
[2026-11-19 04:04:25] INFO  Rackup::Handler::WEBrick::Server#start: pid=83 port=8080
```

Open `app.rb` in your IDE, change the response message on line 10 to `Hello world from Okteto!`, and save the file:

```ruby title="app.rb"
get '/' do
  message = 'Hello world from Okteto!'
  message
end
```

Okteto synchronizes `app.rb` to the Development Container, and `sinatra/reloader` loads it again on the next request, without restarting the server. Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop Sinatra and exit `okteto up`.

### Debugging with VS Code

`rdbg` runs the application with the debugger, so start the Development Container with `rdbg` instead of `ruby app.rb`. The command after `--` replaces the `command` of the Okteto Manifest:

```bash
okteto up -- rdbg --open --nonstop --host 0.0.0.0 --port 1234 app.rb
```

`--open --host 0.0.0.0 --port 1234` makes `rdbg` listen for a debugger on port `1234` of the Development Container, and `--nonstop` starts the application without waiting for the debugger to attach:

```console
DEBUGGER: Debugger can attach via TCP/IP (0.0.0.0:1234)
[2026-11-19 04:06:26] INFO  WEBrick 1.9.2
[2026-11-19 04:06:26] INFO  ruby 4.0.10 (2026-11-19) [x86_64-linux]
== Sinatra (v4.2.2) has taken the stage on 8080 for development with backup from WEBrick
```

The `.vscode/launch.json` file of the Ruby Sample App attaches VS Code to `rdbg` through the port that `okteto up` forwards to your machine:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "rdbg",
      "request": "attach",
      "debugPort": "localhost:1234",
      "localfsMap": "/opt/app:${workspaceFolder}"
    }
  ]
}
```

`localfsMap` maps `/opt/app`, the path in the `sync` field of the Okteto Manifest, to the folder that you open in VS Code. If you synchronize your code to another path, change `/opt/app` to match it.

Open the Ruby Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. Add a breakpoint on line 10 of `app.rb` and reload the endpoint in your browser. Execution stops at the breakpoint, and you can inspect the request and the variables.

Press `Ctrl+C` to stop the application and `rdbg` and exit `okteto up`, and then run `okteto up` to go back to `ruby app.rb`.

### Stopping the Development Container

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) uninstalls the Helm release of the Ruby Sample App from your Namespace:

```bash
okteto destroy
```
