This guide builds, deploys, tests, and develops the [ASP.NET Core Sample App](https://github.com/okteto/aspnetcore-getting-started), a hello world web API, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. Each step uses the optimizations for ASP.NET: the layers of the development image, the caches of the tests, `dotnet watch` for hot reload, and `vsdbg` for debugging with VS Code. To see the Okteto workflow in an application with several services first, follow the [quickstart](get-started/quickstart.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [C# extension](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csharp), and an `ssh` client on your machine.

Clone the ASP.NET Core Sample App:

```bash
git clone https://github.com/okteto/aspnetcore-getting-started
cd aspnetcore-getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yml` file of the repository, builds two images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so `hello-world` reuses its cached layers.

The `Dockerfile` of the ASP.NET Core Sample App defines both images, one per stage:

```dockerfile title="Dockerfile"
FROM mcr.microsoft.com/dotnet/sdk:10.0.404-noble AS dev

RUN curl -sSL https://aka.ms/getvsdbgsh | bash /dev/stdin -v 18.7.10521.2 -l /usr/local/bin/vsdbg

WORKDIR /usr/src/app
COPY helloworld.csproj .
RUN dotnet restore
COPY . .
RUN dotnet build && \
    dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0.15-noble-chiseled AS prod

WORKDIR /app
COPY --from=dev /app .
ENTRYPOINT ["dotnet", "helloworld.dll"]
```

- `dev` is the development image. It contains the .NET SDK, which includes [`dotnet watch`](https://learn.microsoft.com/aspnet/core/test/hot-reload) for hot reload, [`vsdbg`](https://github.com/dotnet/vscode-csharp/wiki/Attaching-to-remote-processes) for debugging, and the source code. `dotnet build` fills the `bin` and `obj` folders of the image, so the first build of `dotnet watch` in the Development Container is incremental. `dotnet publish` writes the application to `/app`.
- `prod` is the application image. It contains only the ASP.NET Core runtime and the application published in the `dev` stage. [Chiseled images](https://learn.microsoft.com/dotnet/core/docker/container-images) have no shell or package manager, and run as a non-root user.

The `dev` stage follows the recommendations for [development images](application-environments/develop/index.mdx#development-images): every version is pinned, and the stage that builds the application doubles as the development image.

Okteto pushes both images to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry). `okteto deploy` builds the images that aren't built yet before it deploys the application. To build them on their own, run `okteto build`.

## Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

Run `okteto deploy` from the root folder of the ASP.NET Core Sample App:

```bash
okteto deploy
```

Okteto builds the `dev` and `hello-world` images, runs the deploy command, and prints the endpoint of the application:

## Test

The `test` section of the Okteto Manifest defines the `unit` [test](application-environments/okteto-test.mdx), which runs the [xUnit](https://xunit.net/) tests of the `tests` folder:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.nuget/packages
    commands:
      - dotnet test --project tests --report-xunit-trx --report-xunit-trx-filename test-results.trx --results-directory .
    artifacts:
      - test-results.trx
```

- `image`: the development image, so the tests run with the same .NET SDK as the Development Container.
- `caches`: the NuGet packages folder, kept between runs of the test.
- `commands`: the commands that run the tests. `dotnet test` builds the `tests` project, runs its tests, and writes the results to `test-results.trx`. The test fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test results.

xUnit v3 runs on [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro), and the `global.json` file tells `dotnet test` to use it:

```json title="global.json"
{
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the ASP.NET Core Sample App:

```bash
okteto test
```

## Develop

A [Development Container](application-environments/develop/index.mdx) gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` cycle, and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the ASP.NET Core Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: dotnet watch
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts `dotnet watch`, which builds and runs the application. When a `.cs` file changes, `dotnet watch` applies the change to the running application with hot reload, or rebuilds and restarts the application if hot reload can't apply it.
- `sync`: synchronizes the root folder of the ASP.NET Core Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the NuGet packages and the build output come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/root/.nuget/packages` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the NuGet cache between `okteto up` sessions.
- `securityContext`: adds the `SYS_PTRACE` capability that `vsdbg` needs to attach to the application.

```bash
okteto up
```

Open `Controllers/HelloWorldController.cs` in your IDE, change the response message on line 12 to `Hello world from Okteto!`, and save the file:

Press `Ctrl+C` to stop `dotnet watch` and exit `okteto up`.

### Debugging with VS Code

`vsdbg` attaches to the application that `dotnet watch` runs, so keep `okteto up` running. VS Code starts `vsdbg` in the Development Container over SSH: `okteto up` adds the `hello-world.okteto` host to your SSH configuration, and the `.vscode/launch.json` file of the ASP.NET Core Sample App runs `vsdbg` through it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:pickRemoteProcess}",
      "pipeTransport": {
        "pipeProgram": "ssh",
        "pipeArgs": ["-q", "-T", "hello-world.okteto"],
        "debuggerPath": "/usr/local/bin/vsdbg/vsdbg",
        "pipeCwd": "${workspaceFolder}",
        "quoteArgs": true
      },
      "sourceFileMap": {
        "/usr/src/app": "${workspaceFolder}"
      }
    }
  ]
}
```

`sourceFileMap` maps `/usr/src/app`, the path in the `sync` field of the Okteto Manifest, to the folder that you open in VS Code. If you synchronize your code to another path, change `sourceFileMap` to match it. `vsdbg` only works with the Microsoft builds of VS Code and Visual Studio.

Open the ASP.NET Core Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. VS Code lists the processes of the Development Container: select `helloworld`, the process of `/usr/src/app/bin/Debug/net10.0/helloworld`. Add a breakpoint on line 12 of `Controllers/HelloWorldController.cs` and reload the endpoint in your browser. Execution stops at the breakpoint, and you can inspect the request and the variables.

To end the debugging session, click **Disconnect** in the debug toolbar. `vsdbg` detaches, and the application keeps running with `dotnet watch`.

### Stopping the Development Container

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) uninstalls the Helm release of the ASP.NET Core Sample App from your Namespace:

```bash
okteto destroy
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of the Movies app. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with ten services or fewer.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them from 15 to 20 services.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
