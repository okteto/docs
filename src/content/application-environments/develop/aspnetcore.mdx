This guide takes the [ASP.NET Core Sample App](https://github.com/okteto/aspnetcore-getting-started) through the whole Okteto workflow, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. The ASP.NET Core Sample App is a hello world service. Its page shows a message, the .NET version, and the pod that serves it.

The sample is small, but its configuration is optimized, so you can use it as a reference for your own ASP.NET application. Along the way, the guide points out what makes each step fast in an ASP.NET project: the cache mount that the build and the tests share, the ignore files that keep every upload small (`.dockerignore`, `.oktetoignore`, and `.stignore`), and `dotnet watch` and `vsdbg` for hot reload and debugging from VS Code.

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [C# extension](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csharp), and an `ssh` client on your machine.

Clone the ASP.NET Core Sample App and move into its folder. Every command in this guide runs from there:

```bash
git clone https://github.com/okteto/aspnetcore-getting-started
cd aspnetcore-getting-started
```

## Build

The ASP.NET Core Sample App uses two container images. `dev` is the image you develop in: it has the .NET SDK and the tools to test, reload, and debug the application. `hello-world` is the production image: a small image with nothing but the ASP.NET Core runtime and the published application. The [build](reference/okteto-manifest.mdx#build-object-optional) section of the `okteto.yml` file defines both:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

Both images come from the same `Dockerfile`. `target` picks the stage each image builds, and `depends_on` tells Okteto to build `dev` first, so `hello-world` reuses its cached layers:

```dockerfile title="Dockerfile"
FROM mcr.microsoft.com/dotnet/sdk:10.0.404-noble AS dev

RUN curl -sSL https://aka.ms/getvsdbgsh | bash /dev/stdin -v 18.7.10521.2 -l /usr/local/bin/vsdbg

WORKDIR /usr/src/app
COPY helloworld.csproj .
# The cache mounts keep the NuGet packages folder in the Okteto Build
# Service, which reuses it between builds. The tests of the Okteto Manifest
# use the same cache
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore
COPY . .
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet build && \
    dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0.15-noble-chiseled AS prod

WORKDIR /app
COPY --from=dev /app .
ENTRYPOINT ["dotnet", "helloworld.dll"]
```

The `Dockerfile` installs [`vsdbg`](https://github.com/dotnet/vscode-csharp/wiki/Attaching-to-remote-processes), the debugger, and restores the project's packages before `COPY . .`, so a code change doesn't run those steps again. Hot reload needs no extra tool: [`dotnet watch`](https://learn.microsoft.com/aspnet/core/test/hot-reload) is part of the .NET SDK.

The two `RUN` instructions that restore and compile the application mount the NuGet packages folder (`/root/.nuget/packages`) as a [cache mount](https://docs.docker.com/build/cache/optimize/#use-cache-mounts), which the Okteto Build Service keeps between builds. When a change to `helloworld.csproj` runs `dotnet restore` again, NuGet doesn't download any package twice.

The build context makes the biggest difference, here and in any application. Every `okteto build` starts by uploading the `Dockerfile`'s folder to the Okteto Build Service, and the `.dockerignore` file decides what goes in. The ASP.NET Core Sample App's `.dockerignore` excludes everything and then allows only what `dotnet restore` and `dotnet publish` read: the project file, the C# files, the settings files, and the `wwwroot` folder with the page. Its last three lines leave out the build output and the tests, which are a project of their own.

```text title=".dockerignore"
*
!*.csproj
!**/*.cs
!appsettings*.json
!wwwroot
**/bin/**
**/obj/**
tests/**
```

The upload stays small, and a change to any other file, such as the README or `k8s.yml`, doesn't rebuild the images.

## Deploy

`okteto deploy` first builds the images that aren't built yet. Okteto pushes them to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

The ASP.NET Core Sample App deploys with a plain Kubernetes manifest. Its [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section has a single command, which applies `k8s.yml` with `kubectl`:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

In `k8s.yml`, the Deployment's image is the `OKTETO_BUILD_HELLO_WORLD_IMAGE` variable. `envsubst` replaces it with the image Okteto built, and then `kubectl` applies the file.

The deploy has its own ignore file. `okteto deploy` uploads your folder to the container that runs the command, and the `.oktetoignore` file decides what goes in. Its `deploy` section excludes everything except `k8s.yml`, the only file the command reads, so there's almost nothing to upload. Its `destroy` section does the same for `okteto destroy`:

```text title=".oktetoignore"
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

To deploy the application, run `okteto deploy`:

```bash
okteto deploy
```

Okteto builds the two images, runs the deploy command, and prints the application's endpoint:

## Test

The ASP.NET Core Sample App has [xUnit](https://xunit.net/) unit tests in the `tests` folder. The `test` section of the Okteto Manifest defines a [test](application-environments/okteto-test.mdx), `unit`, that runs them:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.nuget/packages
    commands:
      - dotnet test --project tests --report-xunit-trx --report-xunit-trx-filename test-results.trx --results-directory .
    artifacts:
      - test-results.trx
```

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster. The container starts from the development image, so it has the same .NET SDK as the Development Container. If any of the `commands` exits with a non-zero code, the test fails. When the test finishes, Okteto copies its `artifacts`, here the test results, to your machine.

`dotnet test` builds the `tests` project and runs its tests on [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro), the test runner that the `global.json` file selects.

The [`caches`](reference/okteto-manifest.mdx#caches-string-optional) entry is the same folder that the `Dockerfile` mounts, and it's the same cache too: Okteto identifies a cache by its repository, context, and path, and the test and the build share all three. So `dotnet test` starts with the packages that the build and the earlier test runs downloaded, and downloads only the ones that are missing.

The tests have their own section in the `.oktetoignore` file, so `okteto test` uploads only what `dotnet test` reads:

```text title=".oktetoignore"
[test]
*
!**/*.csproj
!**/*.cs
!global.json
!appsettings*.json
!wwwroot
**/bin/**
**/obj/**
```

Run the unit tests with `okteto test`:

```bash
okteto test
```

```console

With the [Okteto skills](coding-agents/okteto-skills.mdx), the agent runs this loop in its own Namespace and reports back the tests it ran, the application's endpoints, and a link to that Namespace.

## Develop

A [Development Container](application-environments/develop/index.mdx) feels like developing on your machine: every change you save reloads the application, and you can attach a debugger. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the development image's hot reload and debugging tools in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` loop and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the Okteto Manifest defines the ASP.NET Core Sample App's Development Container:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: dotnet watch
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
```

The `hello-world` key is the name of the Deployment in `k8s.yml` that the Development Container replaces. This is what each field does:

- `image`: the development image from the `build` section.
- `command`: starts `dotnet watch`, which builds and runs the application. Every time a `.cs` file changes, `dotnet watch` applies the change to the running application with hot reload, without restarting it. If hot reload can't apply a change, `dotnet watch` asks you whether to restart the application.
- `sync`: synchronizes the ASP.NET Core Sample App's root folder with `/usr/src/app`, the development image's working directory.
- `persistentVolume`: disables the Development Container's persistent volume, so there's no volume to create and attach. Okteto synchronizes every file on each `okteto up`, and `dotnet watch` builds the application when it starts. The NuGet packages folder isn't part of the development image, because it's a cache mount of the build, so a project with NuGet packages downloads them again on every `okteto up`. The ASP.NET Core Sample App has none. For a larger project, keep the Development Container's NuGet packages folder in a persistent volume. [Caches in Development Containers](/tutorials/optimize-your-application-environment/#caches-in-development-containers) explains how.
- `securityContext`: adds the `SYS_PTRACE` capability, which `vsdbg` needs to attach to the application.

The third ignore file is `.stignore`, for File Sync. `okteto up` synchronizes your folder with the Development Container in both directions, and this file leaves out what shouldn't travel. That's the Git metadata, which is large and only matters on your machine, and the build output and the test reports that `dotnet` generates inside the Development Container, which would otherwise come back to your machine:

```text title=".stignore"
.git
/bin
/obj
/tests/bin
/tests/obj
*.trx
.vscode
.idea
.DS_Store
```

### Hot Reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts `dotnet watch`, which builds and runs the application:

```console
 i  Using cindy @ okteto.example.com as context
 i  'aspnetcore-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world

dotnet watch 🔥 Hot reload enabled. For a list of supported edits, see https://aka.ms/dotnet/hot-reload.
  helloworld -> /usr/src/app/bin/Debug/net10.0/helloworld.dll
Build succeeded.
dotnet watch ⌚ Waiting for changes
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://[::]:8080
info: Microsoft.Hosting.Lifetime[0]
      Application started. Press Ctrl+C to shut down.
```

Now change the code. Open `Controllers/HelloWorldController.cs` in your IDE, edit the message on line 11, and save the file:

```csharp title="Controllers/HelloWorldController.cs"
    public static string Message => "Built, deployed, and tested on Okteto.";
```

Okteto synchronizes `HelloWorldController.cs` to the Development Container. `dotnet watch` notices the change and applies it to the running application, without restarting it:

```console
dotnet watch ⌚ File updated: ./Controllers/HelloWorldController.cs
dotnet watch 🔥 C# and Razor changes applied in 927ms.
```

A moment later, the page in your browser shows the new message. You don't even have to reload it, because the page asks the service for its info every second. Your change is running in your cluster, and you didn't build an image or redeploy the application.

When you're done, press `Ctrl+C` to stop `dotnet watch` and exit `okteto up`.

### Debugging with VS Code

To debug the application, keep `okteto up` running, or run it again if you stopped it: `vsdbg` attaches to the application that `dotnet watch` runs. VS Code starts `vsdbg` in the Development Container over SSH. `okteto up` adds the `hello-world.okteto` host to your SSH configuration, and the ASP.NET Core Sample App's `.vscode/launch.json` file tells VS Code to run `vsdbg` through it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:pickRemoteProcess}",
      "pipeTransport": {
        "pipeProgram": "ssh",
        "pipeArgs": ["-q", "-T", "hello-world.okteto"],
        "debuggerPath": "/usr/local/bin/vsdbg/vsdbg",
        "pipeCwd": "${workspaceFolder}",
        "quoteArgs": true
      },
      "sourceFileMap": {
        "/usr/src/app": "${workspaceFolder}"
      }
    }
  ]
}
```

`sourceFileMap` maps the path of the code in the Development Container, the same one as in the `sync` field of the Okteto Manifest, to the folder you open in VS Code. If you synchronize your code to another path, change `sourceFileMap` to match. `vsdbg` only works with the Microsoft builds of VS Code and Visual Studio.

Open the ASP.NET Core Sample App in VS Code, go to the **Run and Debug** view, and run the **Connect to okteto** configuration. VS Code lists the processes of the Development Container: select `helloworld`, the process of `/usr/src/app/bin/Debug/net10.0/helloworld`. Now add a breakpoint on line 17 of `Controllers/HelloWorldController.cs`, the first line of the `Get` method. The page in your browser asks the service for its info every second, so execution stops at the breakpoint right away, and you can inspect the request and the variables.

To end the debugging session, click **Disconnect** in the debug toolbar. `vsdbg` detaches, and the application keeps running with `dotnet watch`.

### Stopping the Development Container

When you finish developing, run `okteto down`. It stops the Development Container and brings back the `hello-world` Deployment with the production image:

```bash
okteto down
```

```console
 i  Using cindy @ okteto.example.com as context
 ✓  Development container 'hello-world' deactivated
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of Kube Movies. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx), for [GitLab CI/CD](previews/using-gitlab-cicd.mdx), or for [other CI tools](previews/using-other-ci-tools.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Kubeconfig](application-environments/kubeconfig.mdx) for the commands to inspect your application environment.
