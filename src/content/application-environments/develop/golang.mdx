This guide takes the [Go Sample App](https://github.com/okteto/go-getting-started) through the whole Okteto workflow, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster: you build it, deploy it, test it, and develop it with hot reload and a debugger. The Go Sample App is a hello world service whose page shows a message, the Go version, and the pod that serves it. Along the way, the guide points out the choices that make each step fast in a Go project: how the development image is built, the ignore files that keep every upload small (`.dockerignore`, `.oktetoignore`, and `.stignore`), and how Air and Delve give you hot reload and debugging from VS Code. The sample is small, but its configuration is optimized, so you can use it as a reference to configure your own Go application with Okteto.

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [Go extension](https://marketplace.visualstudio.com/items?itemName=golang.go).

Clone the Go Sample App and move to its folder. Every command of this guide runs from there:

```bash
git clone https://github.com/okteto/go-getting-started
cd go-getting-started
```

## Build

The Go Sample App uses two container images, and each one has its purpose. The first one, `dev`, is the image you develop in: it has the Go compiler and the tools to test, reload, and debug the application. The second one, `hello-world`, is the production image: a small image with nothing but the compiled binary. Both are defined in the [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yml` file of the repository:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

Both images come from the same `Dockerfile`. `target` picks the stage that each image builds, and `depends_on` makes Okteto build `dev` first, so that `hello-world` reuses its cached layers. This is the `Dockerfile`:

```dockerfile title="Dockerfile"
FROM golang:1.26.5-trixie AS dev

RUN GOBIN=/usr/local/bin go install github.com/air-verse/air@v1.67.4 && \
    GOBIN=/usr/local/bin go install github.com/go-delve/delve/cmd/dlv@v1.27.1

WORKDIR /usr/src/app
COPY . .
RUN go build -o /usr/local/bin/hello-world

FROM debian:trixie-slim AS prod

COPY --from=dev /usr/local/bin/hello-world /usr/local/bin/hello-world
CMD ["/usr/local/bin/hello-world"]
```

- The `dev` stage is the development image. It has the Go toolchain, [Air](https://github.com/air-verse/air) for hot reload, [Delve](https://github.com/go-delve/delve) for debugging, and the source code.
- The `prod` stage is the production image. It only has the binary that the `dev` stage built, on a small base image.

The tools are installed before `COPY . .`, so a change in the code doesn't install them again.

What makes the biggest difference, in this and in any application, is the build context. Every `okteto build` starts by uploading the folder of the `Dockerfile` to the Okteto Build Service, and the `.dockerignore` file decides what goes in it. The one of the Go Sample App excludes everything, and then allows only what `go build` reads: the Go files, `go.mod`, and the `static` folder with the page.

```text title=".dockerignore"
*
!go.mod
!go.sum
!**/*.go
!static
```

With this file, the upload is small, and a change to any other file, such as the README or `k8s.yml`, doesn't rebuild the images.

The `Dockerfile` doesn't use cache mounts, so the Go build cache stays in the development image, and the tests and the Development Container start from it. [Caches in the Image or in Cache Mounts](/tutorials/optimize-your-application-environment/#caches-in-the-image-or-in-cache-mounts) explains when each option is the better one.

## Deploy

`okteto deploy` builds the images that aren't built yet. Okteto pushes them to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and keeps their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

The Go Sample App deploys with plain Kubernetes manifests. Its [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section has a single command, which applies `k8s.yml` with `kubectl`:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

In `k8s.yml`, the image of the Deployment is the `OKTETO_BUILD_HELLO_WORLD_IMAGE` variable. `envsubst` replaces it with the image that Okteto built, before `kubectl` applies the file.

The deploy has its own ignore file. `okteto deploy` uploads your folder to the container that runs the command, and the `.oktetoignore` file decides what goes in it. Its `deploy` section excludes everything except `k8s.yml`, the only file that the command reads, so there's almost nothing to upload. The `destroy` section does the same for `okteto destroy`:

```text title=".oktetoignore"
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

To deploy the application, run `okteto deploy`:

```bash
okteto deploy
```

Okteto builds the two images, runs the deploy command, and prints the endpoint of the application:


## Test

The Go Sample App has unit tests in `main_test.go`, and the `test` section of the Okteto Manifest defines a [test](application-environments/okteto-test.mdx), `unit`, that runs them:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    commands:
      - go test -v -coverprofile=coverage.out ./...
    artifacts:
      - coverage.out
```

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the development image. It has the same Go toolchain as the Development Container, and the Go build cache that the image already brings, so the test doesn't need `caches` of its own. If any of the `commands` exits with a non-zero code, the test fails. When it finishes, Okteto copies its `artifacts`, in this case the coverage profile, to your machine.

The tests have their section in the `.oktetoignore` file too. `okteto test` uploads only what `go test` reads:

```text title=".oktetoignore"
[test]
*
!go.mod
!go.sum
!**/*.go
!static
```

To run the unit tests, run `okteto test`:

```bash
okteto test
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Images were already built. To rebuild your images run 'okteto build'
 i  Executing test container 'unit'
 i  Running 'go test -v -coverprofile=coverage.out ./...'
=== RUN   TestHello
--- PASS: TestHello (0.00s)
=== RUN   TestPage
--- PASS: TestPage (0.00s)
PASS
coverage: 44.4% of statements
ok  	github.com/okteto/go-getting-started	0.007s	coverage: 44.4% of statements
 ✓  Command 'go test -v -coverprofile=coverage.out ./...' successfully executed
 ✓  Test container 'unit' passed
```

The coverage profile is now in `coverage.out`, in the root folder of the Go Sample App on your machine, and you can inspect it with the Go tools:

```bash
go tool cover -func=coverage.out
```

Running `okteto deploy` and `okteto test` after each change is usually fast enough, especially when a coding agent writes and tests the code autonomously. With the [Okteto skills](coding-agents/okteto-skills.mdx), the agent runs this loop in its own Namespace and reports back the tests it ran, the endpoints of the application, and a link to that Namespace.

## Develop

A [Development Container](application-environments/develop/index.mdx) gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` cycle, and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the Okteto Manifest defines the Development Container of the Go Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: air
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
    forward:
      - 2345:2345
```

The `hello-world` key is the name of the Deployment in `k8s.yml`, the one that the Development Container replaces. This is what each field does:

- `image`: the development image built in the `build` section.
- `command`: starts Air, which rebuilds and restarts the application every time a `.go` file changes.
- `sync`: synchronizes the root folder of the Go Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the Go build cache comes from the development image, so there's no volume to create and attach. In a project with many dependencies, enable it and add `/go/pkg/mod` and `/root/.cache/go-build` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional), to keep the Go caches between `okteto up` sessions.
- `securityContext`: adds the `SYS_PTRACE` capability that Delve needs.
- `forward`: forwards port `2345`, where Delve listens, to your machine.

The third ignore file is `.stignore`, for File Sync. `okteto up` synchronizes your folder with the Development Container, in both directions, and this file leaves out what shouldn't travel: the Git metadata, which is large and only matters on your machine, and the binaries that Air and Delve generate inside the Development Container, which would otherwise come back to your machine:

```text title=".stignore"
.git
/tmp
/go-getting-started
__debug_bin*
*.test
*.out
.vscode
.DS_Store
```

### Hot Reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts Air, which builds and runs the application:

```console
 i  Using cindy @ okteto.example.com as context
 i  'go-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world
    Forward:   2345 -> 2345

watching .
!exclude tmp
building...
running...
Starting hello-world server...
```

Now change the code. Open `main.go` in your IDE, edit the message on line 14, and save the file:

```go title="main.go"
const message = "Built, deployed, and tested on Okteto."
```

Okteto synchronizes `main.go` to the Development Container, and Air notices the change, rebuilds the application, and restarts it:

```console
main.go has changed
building...
running...
Starting hello-world server...
```

A moment later, the page in your browser shows the new message. You don't even have to reload it, because it asks the service for its info every second. The change is running in your cluster, and you didn't build an image or redeploy the application.

When you're done, press `Ctrl+C` to stop Air and exit `okteto up`.

### Debugging with VS Code

To debug the application, start the Development Container with Delve instead of Air, because Delve builds and runs its own copy of the application. Pass the command after `--`, and it replaces the `command` of the Okteto Manifest:

```bash
okteto up -- make debug
```

`make debug` runs `dlv debug --headless --listen=:2345 --log --api-version=2`. Delve builds the application, but it doesn't start it until a debugger connects on port `2345`:

```console
API server listening at: [::]:2345
info layer=debugger launching process with args: [./__debug_bin3004072740]
```

That's the port that `okteto up` forwards to your machine, and the `.vscode/launch.json` file of the Go Sample App tells VS Code to attach to it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "go",
      "request": "attach",
      "mode": "remote",
      "remotePath": "/usr/src/app",
      "port": 2345,
      "host": "127.0.0.1"
    }
  ]
}
```

`remotePath` is the path of the code in the Development Container, the one in the `sync` field of the Okteto Manifest. If you synchronize your code to another path, change `remotePath` to match it.

Open the Go Sample App in VS Code, go to the **Run and Debug** view, and run the **Connect to okteto** configuration. The application starts. Now add a breakpoint on line 42 of `main.go`, the first line of the `hello` function. Since the page in your browser asks the service for its info every second, execution stops at the breakpoint right away, and you can inspect the request and the variables:

<Image
  src={require("@site/static/img/golang-debug.png").default}
  alt="VS Code editor with main.go open and a line highlighted in the helloServer function"
  width="850"
/>

`Ctrl+C` doesn't stop Delve. To end the debugging session, run `okteto down` in another terminal, from the root folder of the Go Sample App. Then run `okteto up` again to go back to hot reload.

### Stopping the Development Container

When you finish developing, `okteto down` stops the Development Container and brings back the `hello-world` Deployment, with the application image:

```bash
okteto down
```

```console
 i  Using cindy @ okteto.example.com as context
 ✓  Development container 'hello-world' deactivated
```

## Destroy

To delete the application, run [`okteto destroy`](application-environments/destroy.mdx). It removes the Deployment and the Service of the Go Sample App from your Namespace:

```bash
okteto destroy
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Images were already built. To rebuild your images run 'okteto build'
 ✓  Development environment 'go-getting-started' successfully destroyed
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of the Movies app. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
