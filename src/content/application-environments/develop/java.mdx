This guide takes the Java Sample App through the whole Okteto workflow, in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. The Java Sample App is a hello world service built with Spring Boot, available for [Maven](https://github.com/okteto/java-maven-getting-started) and for [Gradle](https://github.com/okteto/java-gradle-getting-started). Its page shows a message, the Java version, and the pod that serves it.

The sample is small, but its configuration is optimized, so you can use it as a reference for your own Java application. Along the way, the guide points out what makes each step fast in a Java project: the cache mount that the build and the tests share, the ignore files that keep every upload small (`.dockerignore`, `.oktetoignore`, and `.stignore`), and Spring Boot DevTools and the JVM debug agent for hot reload and debugging from IntelliJ IDEA.

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [IntelliJ IDEA](https://www.jetbrains.com/idea/).

Clone the Java Sample App for the build tool you use, and move into its folder. Every command in this guide runs from there:

#### Maven

```bash
git clone https://github.com/okteto/java-maven-getting-started
cd java-maven-getting-started
```

#### Gradle

```bash
git clone https://github.com/okteto/java-gradle-getting-started
cd java-gradle-getting-started
```

## Build

The Java Sample App uses two container images. `dev` is the image you develop in: it has the JDK and the Maven or Gradle wrapper, which builds, tests, and runs the application. `hello-world` is the production image: a small image with nothing but the Java runtime and the application's JAR file. The [build](reference/okteto-manifest.mdx#build-object-optional) section of the `okteto.yml` file defines both:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

Both images come from the same `Dockerfile`. `target` picks the stage each image builds, and `depends_on` tells Okteto to build `dev` first, so `hello-world` reuses its cached layers:

#### Maven

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

RUN apt-get update && \
    apt-get install -y --no-install-recommends inotify-tools=4.25.9.0-1 && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /usr/src/app
COPY . .

# The cache mount keeps the Maven repository, with the Maven distribution and
# the dependencies, in the Okteto Build Service, which reuses it between
# builds. The tests of the Okteto Manifest use the same cache
RUN --mount=type=cache,target=/root/.m2 \
    ./mvnw package -DskipTests

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/target/helloworld-0.0.1.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

#### Gradle

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

WORKDIR /usr/src/app
COPY . .

# The cache mount keeps the Gradle home, with the Gradle distribution and the
# dependencies, in the Okteto Build Service, which reuses it between builds.
# The tests of the Okteto Manifest use the same cache
RUN --mount=type=cache,target=/root/.gradle \
    ./gradlew --no-daemon assemble

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/build/libs/helloworld.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

The Maven `Dockerfile` installs [inotify-tools](https://github.com/inotify-tools/inotify-tools) before `COPY . .`, so a code change doesn't install it again. The Development Container uses its `inotifywait` command to compile the code when a file changes. Gradle has a watch mode of its own, so the Gradle `Dockerfile` has nothing to install. Hot reload and debugging need nothing else in the image: [Spring Boot DevTools](https://docs.spring.io/spring-boot/reference/using/devtools.html), for hot reload, is one of the application's dependencies, and the [Java Debug Wire Protocol (JDWP)](https://docs.oracle.com/en/java/javase/25/docs/specs/jpda/conninv.html) agent, for debugging, is part of the JDK.

The `RUN` instruction that builds the application mounts the Maven repository (`/root/.m2`) or the Gradle home (`/root/.gradle`) as a [cache mount](https://docs.docker.com/build/cache/optimize/#use-cache-mounts), which the Okteto Build Service keeps between builds. That folder is where the `mvnw` or `gradlew` wrapper downloads Maven or Gradle, and where the build tool downloads the dependencies. When a code change runs `./mvnw package` or `./gradlew assemble` again, the build doesn't download any of them twice.

The build context makes the biggest difference, here and in any application. Every `okteto build` starts by uploading the `Dockerfile`'s folder to the Okteto Build Service, and the `.dockerignore` file decides what goes in. The Java Sample App's `.dockerignore` excludes everything and then allows only what the build reads: the wrapper, the build files, and the `src` folder with the code and the page.

#### Maven

```text title=".dockerignore"
*
!mvnw
!.mvn/wrapper
!pom.xml
!src
```

#### Gradle

```text title=".dockerignore"
*
!gradlew
!gradle/wrapper
!settings.gradle
!build.gradle
!src
```

The upload stays small, and a change to any other file, such as the README or `k8s.yml`, doesn't rebuild the images.

## Deploy

`okteto deploy` first builds the images that aren't built yet. Okteto pushes them to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

The Java Sample App deploys with a plain Kubernetes manifest. Its [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section has a single command, which applies `k8s.yml` with `kubectl`:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

In `k8s.yml`, the Deployment's image is the `OKTETO_BUILD_HELLO_WORLD_IMAGE` variable. `envsubst` replaces it with the image Okteto built, and then `kubectl` applies the file.

The deploy has its own ignore file. `okteto deploy` uploads your folder to the container that runs the command, and the `.oktetoignore` file decides what goes in. Its `deploy` section excludes everything except `k8s.yml`, the only file the command reads, so there's almost nothing to upload. Its `destroy` section does the same for `okteto destroy`:

```text title=".oktetoignore"
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

To deploy the application, run `okteto deploy`:

```bash
okteto deploy
```

Okteto builds the two images, runs the deploy command, and prints the application's endpoint. This is the Maven version's output (the Gradle version's images and application are named `java-gradle-getting-started`):

## Test

The Java Sample App has unit tests in `src/test/java/com/okteto/helloworld/RestHelloWorldTest.java`. The `test` section of the Okteto Manifest defines a [test](application-environments/okteto-test.mdx), `unit`, that runs them:

#### Maven

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.m2
    commands:
      - ./mvnw test
    artifacts:
      - target/surefire-reports
```

#### Gradle

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.gradle
    commands:
      - ./gradlew test
    artifacts:
      - build/reports/tests/test
```

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster. The container starts from the development image, so it has the same JDK and wrapper as the Development Container. If any of the `commands` exits with a non-zero code, the test fails. When the test finishes, Okteto copies its `artifacts`, here the test reports, to your machine.

The [`caches`](reference/okteto-manifest.mdx#caches-string-optional) entry is the same folder that the `Dockerfile` mounts, and it's the same cache too: Okteto identifies a cache by its repository, context, and path, and the test and the build share all three. So the test starts with Maven or Gradle and the dependencies that the build downloaded, and downloads only what the tests need on top of them.

The tests have their own section in the `.oktetoignore` file, so `okteto test` uploads only what the build tool reads:

#### Maven

```text title=".oktetoignore"
[test]
*
!mvnw
!.mvn/wrapper
!pom.xml
!src
```

#### Gradle

```text title=".oktetoignore"
[test]
*
!gradlew
!gradle/wrapper
!settings.gradle
!build.gradle
!src
```

Run the unit tests with `okteto test`:

```bash
okteto test
```

Maven, Gradle, and Spring Boot log every step of the build. These outputs keep only the lines with the tests and their result.

## Develop

A [Development Container](application-environments/develop/index.mdx) feels like developing on your machine: every change you save reloads the application, and you can attach a debugger. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the development image's hot reload and debugging tools in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` loop and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the Okteto Manifest defines the Java Sample App's Development Container:

#### Maven

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./mvnw spring-boot:run & while inotifywait -qq -r -e close_write,moved_to,delete src; do ./mvnw -q compile; done"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

#### Gradle

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./gradlew --console=plain --continuous classes & ./gradlew --console=plain bootRun"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

The `hello-world` key is the name of the Deployment in `k8s.yml` that the Development Container replaces. This is what each field does:

- `image`: the development image from the `build` section.
- `command`: starts the application and compiles the code every time a `.java` file changes. Spring Boot DevTools restarts the application when the compiled classes change.
  - Maven: `./mvnw spring-boot:run` starts the application, and `inotifywait` waits for a change in the `src` folder to run `./mvnw -q compile`. Maven doesn't have a watch mode.
  - Gradle: `./gradlew --continuous classes` compiles the code every time a file changes, and `./gradlew bootRun` starts the application.
- `sync`: synchronizes the Java Sample App's root folder with `/usr/src/app`, the development image's working directory.
- `persistentVolume`: disables the Development Container's persistent volume, so there's no volume to create and attach. Okteto synchronizes every file on each `okteto up`, and the wrapper downloads Maven or Gradle and the dependencies when the Development Container starts, because the build's cache mount isn't part of the development image. For a larger project, keep the Development Container's Maven repository or Gradle home in a persistent volume or a distributed cache. [Caches in Development Containers](/tutorials/optimize-your-application-environment/#caches-in-development-containers) explains both.
- `forward`: forwards port `5005`, where the JVM debug agent listens, to your machine.

The third ignore file is `.stignore`, for File Sync. `okteto up` synchronizes your folder with the Development Container in both directions, and this file leaves out what shouldn't travel. That's the Git metadata, which is large and only matters on your machine, and the build output that Maven or Gradle generates inside the Development Container, which would otherwise come back to your machine:

#### Maven

```text title=".stignore"
.git
/target
.idea
*.iml
.vscode
.DS_Store
```

#### Gradle

```text title=".stignore"
.git
/build
/.gradle
/bin
/out
.idea
*.iml
.vscode
.DS_Store
```

### Debugging with IntelliJ IDEA

To debug the application, you don't need another command: the JVM in the Development Container already runs with the JDWP agent, which listens on port `5005`. The Java Sample App's build file adds the agent to the JVM that runs the application:

#### Maven

```xml title="pom.xml"
<plugin>
	<groupId>org.springframework.boot</groupId>
	<artifactId>spring-boot-maven-plugin</artifactId>
	<configuration>
		<jvmArguments>-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005</jvmArguments>
	</configuration>
</plugin>
```

#### Gradle

```groovy title="build.gradle"
bootRun {
    jvmArgs = ["-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005"]
}
```

`suspend=n` starts the application without waiting for a debugger. The agent only runs in the Development Container: the production image starts the JAR file with `java -jar`, without it.

`okteto up` forwards port `5005` to your machine. Spring Boot DevTools restarts the application inside the same JVM, so the debugger stays attached while you change the code. Run `okteto up` if it isn't running, and create the debug configuration in IntelliJ IDEA:

1. From the main menu, select **Run > Edit Configurations**.
1. Click **+** and select **Remote JVM Debug**.
1. Enter a name in the **Name** field, for example `Debug On Okteto`.
1. Set **Debugger mode** to `Attach to remote JVM`, **Host** to `localhost`, and **Port** to `5005`.
1. Click **OK**.

<Image
  src={require("@site/static/img/java-debug.png").default}
  alt="IntelliJ IDEA Run/Debug Configurations dialog with a Remote JVM Debug configuration that attaches to localhost on port 5005"
  width="850"
/>

Select the configuration and click **Debug**. Now add a breakpoint on line 23 of `src/main/java/com/okteto/helloworld/RestHelloWorld.java`, the first line of the `hello` method. The page in your browser asks the service for its info every second, so execution stops at the breakpoint right away, and you can inspect the stack and the variables.

When you stop the debugging session in IntelliJ IDEA, the debugger detaches from the JVM, and the application keeps running in the Development Container. Press `Ctrl+C` in the `okteto up` terminal to stop the application and exit `okteto up`.

### Stopping the Development Container

When you finish developing, run `okteto down`. It stops the Development Container and brings back the `hello-world` Deployment with the production image:

```bash
okteto down
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of Kube Movies. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx), for [GitLab CI/CD](previews/using-gitlab-cicd.mdx), or for [other CI tools](previews/using-other-ci-tools.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/kubeconfig.mdx) for the commands to inspect your application environment.
