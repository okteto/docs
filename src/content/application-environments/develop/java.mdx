This guide builds, deploys, tests, and develops the Java Sample App, a hello world HTTP server built with Spring Boot and available for [Maven](https://github.com/okteto/java-maven-getting-started) and for [Gradle](https://github.com/okteto/java-gradle-getting-started), in an [application environment](application-environments/index.mdx) in your Kubernetes cluster. Each step uses the optimizations for Java: the layers of the development image, the caches of the tests, Spring Boot DevTools for hot reload, and the JVM debug agent for debugging with IntelliJ IDEA. To see the Okteto workflow in an application with several services first, follow the [quickstart](get-started/quickstart.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [IntelliJ IDEA](https://www.jetbrains.com/idea/).

Clone the Java Sample App for the build tool that you use:

#### Maven

```bash
git clone https://github.com/okteto/java-maven-getting-started
cd java-maven-getting-started
```

#### Gradle

```bash
git clone https://github.com/okteto/java-gradle-getting-started
cd java-gradle-getting-started
```

## Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section of the [Okteto Manifest](reference/okteto-manifest.mdx), the `okteto.yml` file of the repository, builds two images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so `hello-world` reuses its cached layers.

The `Dockerfile` of the Java Sample App defines both images, one per stage:

#### Maven

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

RUN apt-get update && \
    apt-get install -y --no-install-recommends inotify-tools=4.25.9.0-1 && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /usr/src/app
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline
COPY . .
RUN ./mvnw package -DskipTests

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/target/helloworld-0.0.1.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

#### Gradle

```dockerfile title="Dockerfile"
FROM eclipse-temurin:25.0.5_8-jdk-resolute AS dev

WORKDIR /usr/src/app
COPY gradlew settings.gradle build.gradle ./
COPY gradle gradle
RUN ./gradlew --no-daemon dependencies
COPY . .
RUN ./gradlew --no-daemon assemble

FROM eclipse-temurin:25.0.5_8-jre-resolute AS prod

COPY --from=dev /usr/src/app/build/libs/helloworld.jar /usr/local/lib/hello-world.jar
CMD ["java", "-jar", "/usr/local/lib/hello-world.jar"]
```

- `dev` is the development image. It contains the JDK, Maven or Gradle (downloaded by the `mvnw` or `gradlew` wrapper of the repository), the dependencies, including [Spring Boot DevTools](https://docs.spring.io/spring-boot/reference/using/devtools.html) for hot reload, and the source code. The Maven image also contains `inotifywait`, from [inotify-tools](https://github.com/inotify-tools/inotify-tools), to compile the code when a file changes. The JVM includes the [Java Debug Wire Protocol (JDWP)](https://docs.oracle.com/en/java/javase/25/docs/specs/jpda/conninv.html) agent for debugging. The last step compiles the application, so the first build in the Development Container finds the classes up to date.
- `prod` is the application image. It contains only the Java runtime and the JAR file built in the `dev` stage.

The `dev` stage follows the recommendations for [development images](application-environments/develop/index.mdx#development-images): every version is pinned, and the stage that builds the application doubles as the development image. The wrapper pins the version of Maven or Gradle in `.mvn/wrapper/maven-wrapper.properties` or `gradle/wrapper/gradle-wrapper.properties`.

Okteto pushes both images to the [Okteto Registry](application-environments/build-service.mdx#okteto-registry) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](application-environments/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry). `okteto deploy` builds the images that aren't built yet before it deploys the application. To build them on their own, run `okteto build`.

## Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

Run `okteto deploy` from the root folder of the Java Sample App:

```bash
okteto deploy
```

Okteto builds the `dev` and `hello-world` images, runs the deploy command, and prints the endpoint of the application. This is the output of the Maven version (the images and the application of the Gradle version are named `java-gradle-getting-started`):

## Test

The `test` section of the Okteto Manifest defines the `unit` [test](application-environments/okteto-test.mdx), which runs the unit tests in `src/test/java/com/okteto/helloworld/RestHelloWorldTest.java`. The test sends a request to the controller with Spring's `MockMvc` and checks the `Hello world!` response.

#### Maven

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.m2/repository
    commands:
      - ./mvnw test
    artifacts:
      - target/surefire-reports
```

#### Gradle

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.gradle/caches
    commands:
      - ./gradlew test
    artifacts:
      - build/reports/tests/test
```

- `image`: the development image, so the tests run with the same JDK and build tool as the Development Container.
- `caches`: the Maven repository (`/root/.m2/repository`) or the Gradle caches (`/root/.gradle/caches`), kept between runs of the test.
- `commands`: the commands that run the tests. The test fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test reports.

The test runs with [Remote Execution](reference/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the Java Sample App:

```bash
okteto test
```

## Develop

A [Development Container](application-environments/develop/index.mdx) gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` cycle, and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the Java Sample App:

#### Maven

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./mvnw spring-boot:run & while inotifywait -qq -r -e close_write,moved_to,delete src; do ./mvnw -q compile; done"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

#### Gradle

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: sh -c "./gradlew --console=plain --continuous classes & ./gradlew --console=plain bootRun"
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 5005:5005
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts the application and compiles the code every time a `.java` file changes. Spring Boot DevTools restarts the application when the compiled classes change.
  - Maven: `./mvnw spring-boot:run` starts the application, and `inotifywait` waits for a change in the `src` folder to run `./mvnw -q compile`. Maven doesn't have a watch mode.
  - Gradle: `./gradlew --continuous classes` compiles the code every time a file changes, and `./gradlew bootRun` starts the application.
- `sync`: synchronizes the root folder of the Java Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the dependencies come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/root/.m2` or `/root/.gradle` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the caches of Maven or Gradle between `okteto up` sessions.
- `forward`: forwards port `5005`, where the JVM debug agent listens, to your machine.

### Debugging with IntelliJ IDEA

The JVM in the Development Container runs with the Java Debug Wire Protocol (JDWP) agent, which listens on port `5005`. The build file of the Java Sample App adds the agent to the JVM that runs the application:

#### Maven

```xml title="pom.xml"
<plugin>
	<groupId>org.springframework.boot</groupId>
	<artifactId>spring-boot-maven-plugin</artifactId>
	<configuration>
		<jvmArguments>-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005</jvmArguments>
	</configuration>
</plugin>
```

#### Gradle

```groovy title="build.gradle"
bootRun {
    jvmArgs = ["-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005"]
}
```

`suspend=n` starts the application without waiting for a debugger. The agent only runs in the Development Container: the application image starts the JAR file with `java -jar`, without it.

Spring Boot DevTools restarts the application inside the same JVM, so the debugger stays attached while you change the code, and you debug with the same `okteto up` command that gives you hot reload. With `okteto up` running, create the debug configuration in IntelliJ IDEA:

1. From the main menu, select **Run > Edit Configurations**.
1. Click **+** and select **Remote JVM Debug**.
1. Enter a name in the **Name** field, for example `Debug On Okteto`.
1. Set **Debugger mode** to `Attach to remote JVM`, **Host** to `localhost`, and **Port** to `5005`, the port that `okteto up` forwards to your machine.
1. Click **OK**.

<Image

Select the configuration and click **Debug**. Add a breakpoint on line 11 of `src/main/java/com/okteto/helloworld/RestHelloWorld.java` and reload the endpoint in your browser. Execution stops at the breakpoint, and you can inspect the stack and the variables of the application running in your cluster.

When you stop the debugging session in IntelliJ IDEA, the debugger detaches from the JVM, and the application keeps running in the Development Container. Press `Ctrl+C` in the `okteto up` terminal to stop the application and exit `okteto up`.

### Stopping the Development Container

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

## Destroy

[`okteto destroy`](application-environments/destroy.mdx) uninstalls the Helm release of the Java Sample App from your Namespace:

```bash
okteto destroy
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](reference/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](application-environments/develop/index.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](coding-agents/okteto-skills.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of Kube Movies. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](application-environments/deploy.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](application-environments/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](application-environments/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See [External Resources](application-environments/external-resources.mdx), and the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Troubleshooting with kubectl](application-environments/troubleshooting.mdx) for the commands to inspect your application environment.
