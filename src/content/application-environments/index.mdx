An application environment is a running copy of your application. It runs in an [Okteto Namespace](application-environments/namespaces.mdx) on Kubernetes, and Okteto creates it from the definition in your [Okteto Manifest](#okteto-manifest). Developers, pull requests, and coding agents all create their environments from that same definition, so a change that works in one environment works in the others.

An application environment includes your services and their dependencies, such as databases and queues. It's either a full replica, which runs every service of the application, or an Overlay Namespace, which runs only the services that change, on top of a Shared Namespace that runs the rest. [Divert](application-environments/divert/index.mdx) routes the requests between the two Namespaces. Application environments are ephemeral: you create one for a branch, a pull request, or an agent task, and delete it when the work is done.

## Application Environment Workflow

The Okteto CLI builds, deploys, and tests your application with [Remote Execution](reference/remote-execution.mdx): every operation runs in a container inside the cluster. Nothing depends on how the machine running the Okteto CLI is set up, whether that's a developer's laptop, a CI job, or a coding agent's sandbox:

Working with an application environment takes three steps:

1. `okteto namespace create` creates the [Okteto Namespace](application-environments/namespaces.mdx) for the environment.
2. Repeat this loop until your change works:
   - `okteto deploy` builds the images for your services and deploys the application.
   - Optionally, `okteto up` speeds up the inner feedback loop with hot reloading and debuggers.
   - `okteto test` runs your tests against the application.
   - The [URLs of the environment](application-environments/endpoints/automatic-ssl.mdx) let you try the change yourself, or hand it to someone else to try.
3. `okteto namespace delete` deletes the Okteto Namespace and the application environment in it.

To see this workflow in practice, follow the [quickstart](get-started/quickstart.mdx), which takes a sample application through each step.

## Okteto Manifest {#okteto-manifest}

The Okteto Manifest (`okteto.yaml`) is a file in your repository that defines how to build, deploy, test, and develop your application. Developers, pull requests, and coding agents create their application environments from it, so they all build, deploy, and test the application the same way. This Okteto Manifest builds two images, deploys them with Helm, runs the end-to-end tests, and defines a Development Container for the `api` service:

```yaml title="okteto.yaml"
build:
  api:
    context: api
  frontend:
    context: frontend

deploy:
  image: alpine/helm:4.3.2
  commands:
    - name: Helm Install
      command: |
        helm upgrade --install movies chart \
          --set api.image=${OKTETO_BUILD_API_IMAGE} \
          --set frontend.image=${OKTETO_BUILD_FRONTEND_IMAGE}

test:
  e2e:
    image: mcr.microsoft.com/playwright:v1.65.1-noble
    context: e2e
    commands:
      - bash run_tests.sh

dev:
  api:
    command: node --watch server.js
    sync:
      - api:/usr/src/app
```

Each section of the Okteto Manifest has its own page in this section, and the [Okteto Manifest reference](reference/okteto-manifest.mdx) lists every option.
