The Okteto Build Service builds the images for your services inside the cluster, on [BuildKit](https://github.com/moby/buildkit) servers that Okteto deploys and manages, and pushes them to the [Okteto Registry](application-environments/container-registry.mdx). A developer's laptop, a CI job, and a coding agent's sandbox all build the same way: they need the Okteto CLI, but no Docker daemon, and they reuse the images and the cache layers that others already built.

Admins can run BuildKit in [rootless mode](self-hosted/helm-configuration.mdx#rootless), so builds don't run in a privileged container.

## Building Images

The `build` section of your Okteto Manifest defines the images of your services:

```yaml title="okteto.yaml"
build:
  api:
    context: api
    dockerfile: Dockerfile
    args:
      GO_VERSION: 1.20
```

`okteto build` builds every image of the `build` section and pushes it to the Okteto Registry. `okteto deploy` runs the same builds before it deploys your application, for the images that aren't built yet.

```bash
okteto build
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Building 'api/Dockerfile' in tcp://buildkit.okteto.example.com:443...
 ...
 ✓  Image 'registry.okteto.example.com/cindy/api:okteto' successfully pushed
```

The Okteto CLI connects to the Build Service of your Okteto instance with no extra configuration. To install it, see [Install the Okteto CLI](get-started/install-okteto-cli.mdx). See the [`build` reference](reference/okteto-manifest.mdx#build-object-optional) and the [`okteto build` reference](reference/okteto-cli.mdx#build) for every option.

## Dockerfile Compatibility

The Okteto Build Service supports every feature of BuildKit, so any valid Dockerfile works with it.

### Mount Cache IDs {#mount-cache-id-management}

The Okteto Build Service gives [cache mounts](https://docs.docker.com/build/cache/optimize/#use-your-package-manager-wisely) a different default ID than Docker:

- **Docker:** the default ID of a cache mount is its target path. For example, `RUN --mount=type=cache,target=/go/pkg/mod` uses the ID `/go/pkg/mod`.
- **Okteto:** the default ID is the name of the Git repository and the target path. For example, in the `myapp` repository, the same cache mount uses the ID `myapp-/go/pkg/mod`.

This way, two repositories that use the same target folder don't share a cache by accident. To share a cache between repositories on purpose, set its `id`:

```dockerfile
# Share the Go modules cache between repositories
RUN --mount=type=cache,target=/go/pkg/mod,id=shared-go-cache \
    go mod download

# Share the npm cache between repositories
RUN --mount=type=cache,target=/root/.npm,id=shared-npm-cache \
    npm ci
```

## Smart Builds

BuildKit reuses the cached layers of a build, but a fully cached build still takes a minute or two: the Okteto CLI sends the build context, BuildKit pulls the base image and checks every instruction, and the final image is pushed to the registry again. Smart Builds skip all of that when someone already built the same image.

For each image, Okteto computes a hash of its build context and its build parameters. The first time someone builds the image, Okteto pushes it with that hash as its tag, in the `okteto` namespace of the Okteto Registry, and tags the image of their own Namespace to it:

```console
 i  Using cindy @ okteto.example.com as context
 i  Building 'api/Dockerfile' in tcp://buildkit.okteto.example.com:443...
 ...
 => pushing manifest for registry.okteto.example.com/okteto/api:09f8e
 ✓  Image 'registry.okteto.example.com/cindy/api:okteto' successfully pushed
```

When anyone builds the same image again, with the same build context and parameters, Okteto computes the same hash. The image `okteto/api:09f8e` already exists, so Okteto skips the build and only tags the image of their Namespace to it, in a few seconds:

```console
 i  Using david @ okteto.example.com as context
 i  Okteto Smart Builds is skipping build of "api" because it's already built from cache.
```

Smart Builds work across every Namespace of your Okteto instance: developers, pull requests, and coding agents that build the same code share the same images.

### Git Repository Requirement

Smart Builds compute the hash from the Git repository of your application: its commit, its diffs, its untracked files, and the content of its folders. Without a Git repository, Okteto builds every image. Setting `OKTETO_GIT_BRANCH` or `OKTETO_GIT_COMMIT` isn't enough.

If the `deploy` commands of your Okteto Manifest run Okteto CLI commands that build images, such as `okteto deploy -f compose.yml`, don't exclude the `.git` folder in your [`.oktetoignore` file](application-environments/remote-execution.mdx#ignoring-files). Otherwise, Smart Builds can't read the Git repository and build every image.

### Explicit Image Tags

Smart Builds use the hash as the tag of the image, so they're off for an image whose `image` field sets its own tag:

```yaml title="okteto.yaml"
build:
  api:
    # The explicit tag turns off Smart Builds for this image
    image: registry.okteto.example.com/${OKTETO_NAMESPACE}/movies-api:custom
    context: api
```

Leave the `image` field out to use Smart Builds:

```yaml title="okteto.yaml"
build:
  api:
    context: api
```

### Turning Off Smart Builds

To build your images even if someone already built them, add the `--no-cache` flag. It also skips the BuildKit cache:

```bash
okteto build --no-cache
```

To turn off Smart Builds for every build of a machine or a pipeline, set the `OKTETO_SMART_BUILDS_ENABLED` variable to `false`. Set it as an [Admin Variable](admin/admin-variables.mdx) to turn off Smart Builds for every user of your Okteto instance.

## Build Queue System {#build-queue-system}

The Okteto Build Service sends each build to the BuildKit pod with the lowest load, from its CPU pressure, memory usage, and IOPS. When every BuildKit pod is over its load thresholds, the build waits in a queue until a pod is ready: a build finishes, or the [Horizontal Pod Autoscaler](self-hosted/install/buildkit-high-performance.mdx#4-hpa-for-performance-and-costs) adds a BuildKit pod. This way, builds keep a consistent speed when many people and agents build at the same time.

While a build waits, the Okteto CLI shows its position in the queue. After 10 minutes, the build fails with a message that asks you to contact your Admins, who can add BuildKit pods or change the load thresholds. To wait longer, set the `OKTETO_BUILDKIT_QUEUE_WAIT_TIMEOUT` variable, for example to `15m`.

Admins monitor the BuildKit pods and configure the queue in [**Admin > Build Service**](admin/build-service.mdx).
