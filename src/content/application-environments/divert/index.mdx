Divert lets an application environment deploy only the services that change, and use a Shared Namespace for every other service of the application. A request with the environment's divert header reaches the environment's version of the services it deployed, and the shared version of everything else. Developers, pull requests, and coding agents use Divert the same way.

## When to Use Divert

An application environment with a full replica of your application is the simplest setup, and it's the right choice for many teams: every service runs the version you deploy, and nothing you do affects anyone else.

As your application grows, usually around 30 to 50 services, deploying a full replica of it for every feature starts to have tradeoffs:

- **Longer deploy times**: every namespace waits for services nobody is changing to build, start, and become healthy
- **Less reliability**: a deploy fails when any service fails, even one owned by another team that nobody in the namespace is touching
- **Higher infrastructure costs**: every namespace reserves the resources of the whole application

With Divert, the full application runs once in a Shared Namespace, and each developer, pull request, or coding agent deploys only the services it changes in an Overlay Namespace. An Overlay Namespace starts in the time it takes to deploy those services, and uses only what those services need.

A full replica is still the better fit when you need control over every service, such as reproducing a bug that depends on specific versions of several services, or working on a change that touches most of the application.

## How Divert Works

Divert routes each request by the divert header it carries: the `baggage` header with the key `okteto-divert=<namespace>`. In the Movies application, Cindy works on the rent service:

1. The Shared Namespace, `staging`, runs the complete application. Requests enter through the API gateway.
2. Cindy deploys the rent service and its MongoDB database in her Overlay Namespace, `cindy`.
3. When the API gateway calls the rent service, requests with Cindy's divert header (`baggage: okteto-divert=cindy`) reach her rent service.
4. Cindy's rent service calls the catalog service. She didn't deploy it, so the call reaches the shared catalog service.
5. Every other service, and every request without Cindy's divert header, is served by the Shared Namespace.

Several Overlay Namespaces can use the same Shared Namespace at the same time. Each one only sees its own changes, and the Shared Namespace is not affected by any of them. An Overlay Namespace can also run several overlay services: they call each other directly, and use the Shared Namespace for everything else.

## What Divert Routes

| | How Divert handles it |
|---|---|
| **HTTP and gRPC requests** | Routed by the divert header to the overlay service when one exists, and to the shared service otherwise |
| **Message queues** | Divert doesn't intercept message brokers such as Kafka, RabbitMQ, or SQS. [Queue Splitting](application-environments/divert/queue-splitting.mdx) keeps each message in its namespace: deploy a subsystem with its own broker, or filter messages by the divert header |
| **Databases** | Divert doesn't split databases. [Data Cloning](application-environments/divert/data-cloning.mdx) gives your Overlay Namespace its own copy, restored from a Volume Snapshot of the shared database |
| **Service mesh** | The Gateway API driver, the default, creates an `HTTPRoute` per overlay service and works with any mesh that implements [GAMMA](https://gateway-api.sigs.k8s.io/mesh/gamma/), such as Linkerd and Istio. The VirtualServices driver adds the routing rules to your Istio VirtualServices. Only the Shared Namespace needs the mesh |
| **Shared Namespace** | A namespace managed by Okteto, such as a Preview Environment your CI redeploys on every merge, or any namespace that Okteto doesn't manage in the same cluster, such as an existing staging namespace. See [Shared Namespace](application-environments/divert/shared-namespace.mdx) |

## Concepts

- **Shared Namespace**: the namespace that runs the complete application. It serves every service that an Overlay Namespace doesn't deploy. It's usually a namespace that your CI redeploys on every merge. If Okteto manages your Shared Namespace, make it [persistent](application-environments/namespaces.mdx#mark-a-namespace-as-persistent-to-prevent-it-from-sleeping-and-deletion) so it never goes to sleep.
- **Overlay Namespace**: a namespace where a developer, a pull request, or a coding agent deploys only the services it changes, on top of a Shared Namespace.
- **Shared services** and **overlay services**: the services deployed in the Shared Namespace and in an Overlay Namespace.
- **Subsystem**: a group of services that belong together and that you deploy as a unit, such as an API, its workers, its queues, and its databases.
- **Divert header**: the [`baggage`](https://www.w3.org/TR/baggage/) header with the key `okteto-divert=<namespace>`, where `<namespace>` is the Overlay Namespace. Requests with the divert header reach the overlay service when one exists, and the shared service otherwise.
- **Header Propagation**: forwarding the `baggage` header from each incoming request to the requests and messages it triggers, so the divert header reaches every service in the call chain, including the consumers of your queues.
- **Queue Splitting**: making sure each message is consumed by the namespace it belongs to.
- **Data Cloning**: giving an Overlay Namespace its own copy of a database, instead of writing to the shared one.

## Cluster Requirements

Divert requires a service mesh in each Shared Namespace, and Divert enabled in the Helm values of your Okteto instance. An Admin sets it up with [Configure Divert in Your Cluster](self-hosted/install/divert/index.mdx).
