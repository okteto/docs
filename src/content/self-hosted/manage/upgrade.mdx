You upgrade your Okteto instance with `helm upgrade`. Some Okteto releases need extra steps, listed in the section for each release.

## Upgrading Your Okteto Instance

:::tip
We recommend testing each Okteto upgrade on a dedicated test cluster first. Contact your sales representative to request a test license for your test cluster.
:::

### Running the Upgrade

To upgrade to a new release, make your changes in `config.yaml` and run:

```bash
helm repo update
helm upgrade okteto okteto/okteto -f config.yaml --namespace=okteto --version <version_number>
```

For example:

<CodeBlock language="bash">
  {
`helm repo update
helm upgrade okteto okteto/okteto -f config.yaml --namespace=okteto --version ${variables.chartVersion}
`}
</CodeBlock>

Run `helm ls` to find the name of your release.

Review the [release notes](release-notes.mdx) before upgrading: they list new features, known issues, and configuration changes.

Okteto Chart 2.0 will make Gateway API the default installation mode. Migrate your instance with [Migrate to Gateway API](self-hosted/manage/migrate-to-gateway-api.mdx) before you upgrade to 2.0.

### Upgrading with Helm 4

Helm 4 installs releases with server-side apply by default: Kubernetes records which field manager owns each field of a resource. If another controller in your cluster changes a field that the Okteto chart sets, `helm upgrade` fails with a conflict that names the field manager of that controller. `helm upgrade` keeps the apply method of the release, so a release that you installed with Helm 3 keeps client-side apply, which doesn't check field ownership, and doesn't hit these conflicts.

On AKS, the [Admissions Enforcer](https://learn.microsoft.com/en-us/azure/aks/faq#can-admission-controller-webhooks-affect-kube-system-and-internal-aks-namespaces-) adds `matchExpressions` to the `namespaceSelector` of the Okteto admission webhooks and takes ownership of that field. If you installed Okteto with Helm 4, every `helm upgrade` then fails with an error like:

```
Error: UPGRADE FAILED: conflict occurred while applying object /okteto-mutation-webhook admissionregistration.k8s.io/v1, Kind=MutatingWebhookConfiguration: Apply failed with 12 conflicts: conflicts with "admissionsenforcer"
```

To fix it, starting with Okteto 1.51, add the `admissions.enforcer/disabled` annotation to both webhooks in your `config.yaml`, so the Admissions Enforcer skips them:

```yaml
webhook:
  annotations:
    admissions.enforcer/disabled: "true"

regcredsManager:
  annotations:
    admissions.enforcer/disabled: "true"
```

Then run the upgrade once with `--force-conflicts`, so Helm takes back the ownership of the fields that the Admissions Enforcer changed:

```bash
helm repo update
helm upgrade okteto okteto/okteto -f config.yaml --namespace=okteto --version <version_number> --force-conflicts
```

The next upgrades work without `--force-conflicts`.

## Upgrading to Okteto 1.51.x – Okteto Autoscaler Removed

Okteto 1.51 removes the Okteto Autoscaler and the Helm settings related to it. `helm upgrade` deletes their resources, and prints a warning if your values still use these settings. Remove them from your `config.yaml`:

- `autoscaler`: The Okteto Autoscaler told the Kubernetes cluster autoscaler to add nodes when the real CPU and memory usage of the nodes went beyond its thresholds. The cluster autoscaler now adds nodes based on the CPU and memory requests of your pods. The upgrade removes what the Okteto Autoscaler left in your cluster: its `autoscaler-agent` Deployments, the `dev.okteto.com/overloaded` label of the nodes, and the `cluster-autoscaler.kubernetes.io/scale-down-disabled` annotation of the nodes where the Okteto Autoscaler set it. If you set this annotation yourself, the upgrade keeps it.
- `nodeReadinessChecker`: Okteto no longer labels new nodes with `dev.okteto.com/node-ready`. The upgrade removes the node selector on this label from the DaemonSets of your Namespaces, so they also run on new nodes. Existing nodes keep the label.
- `prepullImages`: Okteto no longer pulls its images on every node. This setting was enabled by default, so it affects every installation: the jobs that Okteto runs on a new node, such as the pipelines of your application environments, pull the Okteto images first.

If you used the Okteto Autoscaler, prepare for the change before upgrading:

- **Requests that match real usage**: Configure the [Resource Manager](admin/resource-manager.mdx) in **Automatic** mode from **Admin > Resource Manager**. It sets the CPU and memory requests of new pods from the real usage of their containers, so the cluster autoscaler adds and removes nodes according to what your workloads use.
- **Warm nodes**: Enable [warm nodes](self-hosted/helm-configuration.mdx#warmnodes) to keep nodes ready for your application environments, with the Okteto images and the images you choose already pulled. A pod that doesn't fit on any other node runs on a warm node, without waiting for a new node. Warm nodes also pull the images that `prepullImages` used to pull on every node.

If you enabled warm nodes and roll back to Okteto 1.50 with `helm rollback`, delete the `okteto-warm-nodes` Deployment, which Helm doesn't manage:

```bash
kubectl delete deployment okteto-warm-nodes --namespace=okteto
```

## Upgrading to Okteto 1.51.x – CatalogItem CRD {#upgrading-to-okteto-151x--catalogitem-crd}

Okteto 1.51 adds fields to the `catalogitems.git.okteto.com` CRD: the [description](admin/catalog.mdx#add-a-description) of a Catalog item, and the [options](admin/catalog.mdx#multi-value-variables) and [description](admin/catalog.mdx#variable-descriptions) of its variables. With the default [`crds.install`](self-hosted/helm-configuration.mdx#crds) setting, `helm upgrade` updates the CRD and you don't need to do anything.

If you set `crds.install` to `false`, apply the new CRD yourself when you upgrade:

```bash
helm template okteto okteto/okteto --namespace=okteto --version <version_number> --set crds.install=true --show-only templates/crds/git-catalog-item-crd.yaml | kubectl apply -f -
```

Until you apply it, Kubernetes drops these fields when Okteto saves a Catalog item: the save succeeds, but the descriptions and the values of multi-value variables are lost.

During the upgrade, or after a `helm rollback` to Okteto 1.50, an Okteto API that runs 1.50 removes these fields from any Catalog item it saves.

## Upgrading to Okteto 1.50.x – Okteto Registry Images in Azure Storage

Okteto 1.50 upgrades the Okteto Registry to [distribution](https://github.com/distribution/distribution) 3.1.2, which names the blobs in Azure Storage without the leading `/` that earlier versions used ([distribution#4278](https://github.com/distribution/distribution/issues/4278)). Only [Azure Storage](self-hosted/install/okteto-registry-storage/azure-storage-container.mdx) is affected: Google Cloud Storage, Amazon S3, DigitalOcean Spaces, and filesystem storage keep their images.

With Azure Storage, the Okteto Registry starts normally, but it doesn't find the images pushed before the upgrade, and requests for them fail with errors such as `manifest unknown` or `repository name not known`. These images aren't deleted: they stay in your storage container and keep using space. New pushes work normally.

Before upgrading, decide how to handle these images:

- **Start with a new storage container**: Create a new container in your storage account and set it in `registry.storage.provider.azure.storage.container` when you upgrade. Once you no longer need the previous container, delete it to free its space.
- **Keep specific images**: Copy them to another registry before the upgrade, and copy them back to the Okteto Registry after the upgrade. For example, use `regctl image copy <source-image> <destination-image>` from [regclient](https://github.com/regclient/regclient). An [Admin Access Token](admin/admin-access-tokens.mdx) is enough to copy them, since Admins can pull and push the images of every Namespace. Run `okteto context show --include-token` to see the Okteto Registry hostname and the credentials for your current Okteto context.

Images built by your application environments are rebuilt when you redeploy them, and images pushed by your pipelines are rebuilt when you rerun those pipelines. Push any other image you need again.

If you roll back to Okteto 1.49 with the same storage container, the Okteto Registry finds the images pushed before the upgrade again, but not the ones pushed with 1.50.

## Upgrading to Okteto 1.40.x – Default Registry Change to GitHub Container Registry

Starting with Okteto 1.40, the default installation pulls Okteto images from **GitHub Container Registry (ghcr.io)** instead of Docker Hub. Images are still published to both registries, so you can choose which one to use.

### Configuring Your Installation to Pull from Docker Hub

To keep pulling images from Docker Hub, add the following configuration to your Helm values file (`config.yaml`):

```yaml
globals:
  registry: docker.io

cli:
  image:
    registry: docker.io

ingress-nginx:
  controller:
    image:
      registry: docker.io

okteto-nginx:
  controller:
    image:
      registry: docker.io

reloader:
  global:
    imageRegistry: docker.io
```

Then upgrade your Okteto instance:

<CodeBlock language="bash">
  {
`helm repo update
helm upgrade okteto okteto/okteto -f config.yaml --namespace=okteto --version ${variables.chartVersion}
`}
</CodeBlock>

:::tip
To use a different registry (neither ghcr.io nor docker.io), configure a custom registry as described in [Air-Gapped Networks](self-hosted/manage/air-gapped.mdx).
:::

## Upgrading to Okteto 1.38.x – Certificate Configuration Changes

- **Internal Certificate Unification**: Internal certificates have been unified into a [single configuration](self-hosted/helm-configuration.mdx#internalcertificate). During the upgrade, you may see communication issues for a few seconds while the new certificate configuration takes effect. This is expected, and it should resolve on its own.
- **Argo CD Installations**: If you manage your Okteto installation with Argo CD, review [Argo CD](self-hosted/manage/argocd.mdx). The certificate unification may need special attention during the Argo CD sync to avoid deployment interruptions.

## Upgrading to Okteto 1.37.x – Redis Migration from Bitnami

Starting with Okteto 1.37, the bundled Redis deployment no longer uses the Bitnami Helm chart. The workload has changed from a **StatefulSet** to a **Deployment** and Redis persistence is disabled. The available configuration options [have been reduced and standardized](self-hosted/helm-configuration.mdx#redis).

If you customized Redis with Bitnami-specific Helm values, review and update your values file before upgrading. Unsupported Bitnami values are silently ignored, which can cause unexpected Redis behavior.

## Upgrading to Okteto 1.35.x – Kubernetes 1.33 Support and Amazon Linux 2023 (AL2023) Compatibility

Okteto 1.35 is the first release with official support for **Kubernetes 1.33** and **Amazon Linux 2023 (AL2023)**.

If you run Okteto on AWS, we recommend the following upgrade order to keep compatibility:

1. Upgrade Okteto to **version 1.35**.
1. (Recommended) Upgrade your node pool to Amazon Linux 2023 and verify that your workloads are healthy.
1. Upgrade your EKS cluster to **Kubernetes 1.33**.

This order keeps your rollback options in case of unexpected issues. If you upgrade to Kubernetes 1.33 before you upgrade Okteto to 1.35, you may run into compatibility problems: Okteto 1.34 and earlier don't support Kubernetes 1.33.


## Upgrading to Okteto 1.31.x – Schema 1 Image Deprecation

Okteto 1.31 removed support for **Docker Image Manifest Schema 1**, because of upgrades in its dependencies.

**What This Means for You**

- Older container images that rely on **Schema 1** will fail to pull or deploy
- This change aligns with the broader container ecosystem: Schema 1 images have been deprecated since 2021, and modern container runtimes no longer support them

### Checking Your Images

To check an image, run:

```sh
docker manifest inspect <image-name>
```
- If the output contains `"schemaVersion": 1`, you need to update the image
- If it contains `"schemaVersion": 2`, no action is required

### Migrating to Schema 2

- If you use Schema 1 images, migrate them to Schema 2 before you upgrade to Okteto 1.31
- If your image is outdated, look for an updated version, or rebuild and push it with a recent Docker version:

```sh
docker pull <old-image>
docker tag <old-image> myrepo/myimage:v2
docker push myrepo/myimage:v2
```

## Upgrading to Okteto 1.26.x – Hostname Limits, Helm Release Name Changes

- **ACTION REQUIRED: Hostname Length Limit**\
Deployments now fail with an error message if a service hostname exceeds 63 characters. This limit applies automatically to all resources. Previously, application environments could deploy successfully even if their endpoints didn't work. This change may affect environments that deployed without issues before.
- **Helm Release Name Limit**:\
Helm release names are now limited to 63 characters. This limit is enforced automatically for most resources, but the `DefaultBackend` service can still fail during installation if its name exceeds it. \
To avoid installation errors, shorten the `DefaultBackend` service name with the `defaultBackend.nameOverride` setting. Renaming the `DefaultBackend` during an upgrade may impact the installation: follow the [manual migration steps](https://www.okteto.com/docs/1.26/self-hosted/helm-configuration/#manual-migration-steps-when-renaming-the-defaultbackend-service) if you need to.
- **Private Repository Deploys**: Deploying private repositories now uses the Okteto backend as the SSH agent, instead of mounting the local SSH agent. This gives remote and local deploys the same features, but it may affect deploy commands that clone private repositories during Remote Execution
- **BuildKit Persistence Enabled**: BuildKit persistence is now enabled by default, with a 100Gi disk and the cache set to 90% of the disk size. If you used `buildkit.persistence.cache`, adjust to the new ratio: that setting no longer applies

## Upgrading to Okteto 1.25.x – Okteto CLI 3.0.0 Upgrade {#upgrading-to-okteto-125x--cli-300-upgrade}

Starting with the [1.25 release](archived-release-notes.mdx#1250), Okteto uses Okteto CLI 3.0.0 to deploy and destroy pipelines. Review the [changes in Okteto CLI 3.0.0](https://github.com/okteto/okteto/releases/) before upgrading your cluster.


## Upgrading to Okteto 1.22.x – Role & Binding Config Migration

The [1.22 release](archived-release-notes.mdx#1220) reorganizes the Helm settings that configure the annotations, labels, and role bindings for users' service accounts. These settings moved:

* `clusterRole` moved to [`serviceAccounts.roleBindings.namespaces`](self-hosted/helm-configuration.mdx#serviceaccounts)
* `globalClusterRole` moved to [`serviceAccounts.clusterRoleBinding`](self-hosted/helm-configuration.mdx#serviceaccounts)
* `user.serviceAccounts.annotations` moved to [`serviceAccounts.annotations`](self-hosted/helm-configuration.mdx#serviceaccounts)
* `user.serviceAccounts.labels` moved to [`serviceAccounts.labels`](self-hosted/helm-configuration.mdx#serviceaccounts)
* `user.extraRoleBindings.roleBindings` moved to [`serviceAccounts.extraRoleBindings`](self-hosted/helm-configuration.mdx#serviceaccounts)

For example, if you configured some or all of these settings the old way:

```yaml
clusterRole: cluster-admin

globalClusterRole: example-cluster-role

user:
  serviceAccount:
    annotations:
      custom.annotation/one: one
      custom.annotation/two: two
    labels:
      custom.label/one: one
      custom.label/two: two
  extraRoleBindings:
    enabled: true
    roleBindings:
      namespace-name1:
        - cluster-role1
        - cluster-role2
      namespace-name2:
        - cluster-role3
```

The 1.22 configuration is:

```yaml
serviceAccounts:
  annotations:
    custom.annotation/one: one
    custom.annotation/two: two
  labels:
    custom.label/one: one
    custom.label/two: two
  roleBindings:
    namespaces: cluster-admin
  clusterRoleBinding: example-cluster-role
  extraRoleBindings:
    namespace-name1:
      - cluster-role1
      - cluster-role2
    namespace-name2:
      - cluster-role3
```

:::note
Okteto still reads the old settings, and they take precedence, but their support will be removed in a future version. Migrate them as soon as possible.
:::

Okteto `1.22` also stops automatically binding the custom service accounts created in the Namespaces it manages to the cluster role set in `serviceAccounts.roleBindings.namespaces` (`clusterRole` in previous versions). If your application creates a custom service account, also create the roles and role bindings it needs.

If this causes permission issues, we recommend creating an explicit role and role binding. As an alternative, you can bind the service account to the `cluster-admin` role manually:

1. Create the `k8s/rb.yml.tpl` file with the following content:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: <service-account-name>
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: ServiceAccount
  name: <service-account-name>
  namespace: ${OKTETO_NAMESPACE}
```
2. Replace `<service-account-name>` with the name of the service account you want to bind to the `cluster-admin` role.
3. In the deploy commands of your Okteto Manifest, use `envsubst` to replace the `${OKTETO_NAMESPACE}` variable:
```yaml
deploy:
  - envsubst < k8s/rb.yml.tpl > k8s/rb.yml
  - kubectl apply -f k8s
```

## Upgrading to Okteto 1.20.x – Pull Secrets Enabled by Default

The Okteto [1.20 release](archived-release-notes.mdx#1200) enables [Pull Secrets by default](admin/registry-credentials/index.mdx). If you don't want Okteto to manage Pull Secrets, disable the following Helm values:

- Set `regcredsManager.pullSecrets.enabled` to `false`
- Set `daemonset.configurePrivateRegistriesInNodes.enabled` to `false` (if you already prevent Okteto from managing credentials in the nodes, this may already be configured)
