The Okteto Helm chart accepts the following values to configure your Okteto instance.

## General Settings

### license

You receive a license key with your Okteto subscription. If you haven't received it, [open a support ticket](https://okteto.com/support).

To evaluate Okteto, sign up for the [free tier](https://www.okteto.com/free-tier/): 5 users, 500 environments per month, and a one-year license, with no credit card required.

```yaml
license: XXXXX
```

> You can also store the license in a [secret](self-hosted/helm-configuration.mdx#store-sensitive-configuration-values-using-a-secret).

### subdomain

Okteto [Endpoints](application-environments/endpoints/automatic-ssl.mdx) expose your application environments on secure, unique public URLs. By default, every endpoint Okteto creates combines the app name, the Namespace, and the `subdomain`. For example, if `subdomain` is `example.com`, an application environment named `app` in the `cindy` Namespace is available at https://app-cindy.example.com.

```yaml
subdomain: "example.com"
```

The Okteto frontend and API are available at https://okteto.$SUBDOMAIN. Once Okteto is installed, get the public address of the Okteto NGINX Ingress Controller with `kubectl`:

```bash
kubectl get service -l=app.kubernetes.io/name=ingress-nginx,app.kubernetes.io/component=controller --namespace=okteto
```

The output looks like this:

```
NAME                              TYPE           CLUSTER-IP   EXTERNAL-IP     PORT(S)                                     AGE
okteto-ingress-nginx-controller   LoadBalancer   10.0.7.73    34.68.230.234   80:30795/TCP,443:32481/TCP,1234:30885/TCP   5m
```

Create a DNS entry for `*.$SUBDOMAIN` that points to the `EXTERNAL-IP` address.

To change the Okteto public URL, use the [publicOverride](self-hosted/helm-configuration.mdx#publicoverride) field.

### publicOverride

Overrides the public URL where Okteto is available. It replaces `okteto.$SUBDOMAIN` with the [FQDN](https://en.wikipedia.org/wiki/Fully_qualified_domain_name) you choose.

```yaml
publicOverride: "example.com"
```

After you set it in your Helm configuration file, use your DNS provider to point this domain to the IP address of the Okteto Ingress Controller. Get the IP address with the same command that the [installation guides](get-started/install/index.mdx) use:

```bash
kubectl get service -l=app.kubernetes.io/name=ingress-nginx,app.kubernetes.io/component=controller --namespace=okteto
```

**Important**: When you use `publicOverride`, the certificate that [wildcardCertificate.name](self-hosted/helm-configuration.mdx#wildcardcertificate) refers to must be valid for `publicOverride`, `registry.$SUBDOMAIN`, and `buildkit.$SUBDOMAIN`.

When `publicOverride` is set, Okteto deploys an additional component for [Okteto Private Endpoints](application-environments/endpoints/private-endpoints.mdx). Configure it in the [privateEndpoints](self-hosted/helm-configuration.mdx#privateendpoints) section.

The callback URL and the origin URL of your [auth provider](self-hosted/helm-configuration.mdx#auth) change to:

**Callback URL**:

```
https://${publicOverride}/auth/callback
https://private-endpoints.${subdomain}/auth/callback
```

**Origin URL**:

```
https://${publicOverride}
https://private-endpoints.${subdomain}
```

Okteto integrates with these OAuth2 providers:

### Theme

Customizes the logo and the sidebar colors of the Okteto UI to match your team's identity.

- `logo`: The logo at the top left of the Okteto UI. The value is a URL or a Base64-encoded image.
- `primary`: The primary color of the sidebar, used for the sidebar itself. The value is an [HTML color name](https://en.wikipedia.org/wiki/Web_colors#HTML_color_names) (for example, `blue` or `red`) or a hexadecimal code.
- `secondary`: The secondary color of the sidebar, used for its icons and text. The value is an [HTML color name](https://en.wikipedia.org/wiki/Web_colors#HTML_color_names) (for example, `blue` or `red`) or a hexadecimal code.

```yaml
theme:
  logo: http://example.com/icon.png
  primary: \#EFF3F2
  secondary: black
```

## Okteto Components

### api

The API service. It manages accounts and Kubernetes credentials, creates and shares Namespaces, and deploys from the Okteto Catalog, among other tasks.

- `annotations`: Annotations to add to the API pods.
- `extraEnv`: Environment variables for the API containers.
- `labels`: Labels to add to the API pods.
- `priorityClassName`: The priority class for the API pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `replicaCount`: The number of API pods. It defaults to 2.
- `resources`: The resources for the API pods.

```yaml
api:
  extraEnv:
  - name: NO_PROXY
    value: ".example.com"
  replicaCount: 2
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
```

### buildkit

The [Okteto Build Service](application-environments/build-service.mdx). `okteto build` uses it to build container images in the cluster.

- `port`: The port of the BuildKit StatefulSet. Defaults to `443`.
- `annotations`: Annotations to add to the BuildKit pods.
- `extraEnv`: Environment variables for the BuildKit containers.
- `hpa.enabled`: Enables horizontal pod autoscaling for the BuildKit pods. Disabled by default.
- `hpa.min`: Minimum number of BuildKit pods to keep running. Defaults to `1`.
- `hpa.max`: Maximum number of BuildKit pods to scale to. Defaults to `5`.
- `hpa.metrics`: The [target metrics](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/#autoscaling-on-multiple-metrics-and-custom-metrics) that make the HPA scale the BuildKit pods. Defaults to the `okteto_build_active_builds` metric with an average value target of `0.99`.
- `hpa.behavior`: The [scaling behavior](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/#configurable-scaling-behavior) of the HPA for the BuildKit pods. By default, it adds up to one pod every 30 seconds when builds pile up, and after a 600-second stabilization window it removes up to one pod every 150 seconds.
- `hpa.adapter.enabled`: Creates the metrics adapter Deployment, Service, and APIService. Enabled by default when the HPA is enabled. The adapter exposes BuildKit metrics through the Kubernetes custom metrics API.
- `hpa.adapter.extraEnv`: Environment variables for the adapter containers.
- `hpa.adapter.priorityClassName`: The priority class for the adapter pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `hpa.adapter.replicaCount`: The number of adapter pods. Defaults to `2`.
- `hpa.adapter.resources`: The resources for the adapter pods. Defaults to 100m CPU and 128Mi memory requests.
- `hpa.adapter.apiService.name`: The name of the APIService. Defaults to `v1beta2.custom.metrics.k8s.io`.
- `hpa.adapter.apiService.group`: The API group. Defaults to `custom.metrics.k8s.io`.
- `hpa.adapter.apiService.version`: The API version. Defaults to `v1beta2`.
- `hpa.adapter.apiService.groupPriorityMinimum`: The priority of the API group. Defaults to `100`.
- `hpa.adapter.apiService.versionPriority`: The priority of the API version. Defaults to `100`.
- `labels`: Labels to add to the BuildKit pods.
- `podManagementPolicy`: The [podManagementPolicy](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#pod-management-policies) of the BuildKit pods. Defaults to `Parallel`.
- `priorityClassName`: The priority class for the BuildKit pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `replicaCount`: The number of BuildKit pods. It defaults to 1.
- `resources`: The resources for the BuildKit pods.
- `serviceAccount.create`: Creates a service account for BuildKit. Defaults to `true`.
- `serviceAccount.name`: The name of the BuildKit service account. Defaults to `okteto-buildkit`.
- `serviceAccount.annotations`: Annotations for the BuildKit service account.
- `serviceAccount.labels`: Labels for the BuildKit service account.
- `service.loadBalancerSourceRanges`: List of CIDR blocks allowed to access the BuildKit service when using a LoadBalancer. Defaults to `[]`. Ignored for other service types.
- `persistence.enabled`: Attaches a persistent volume to BuildKit. Enabled by default.
- `persistence.class`: The storage class of the persistent volume attached to every BuildKit pod.
- `persistence.size`: The size of the persistent volume attached to every BuildKit pod. Defaults to `750Gi`.
- `persistence.cacheRatio`: The fraction of the persistent volume used for the cache, between 0 and 1. Defaults to `0.5`.
- `terminationGracePeriodSeconds`: Duration in seconds for graceful pod termination. Defaults to `600` (10 minutes). It lets running builds finish before the pod terminates.
- `readinessProbe.periodSeconds`: How often, in seconds, the readiness probe runs `buildctl debug workers` against the local BuildKit socket. Defaults to `15`.
- `readinessProbe.timeoutSeconds`: Seconds before a readiness check is considered failed. Defaults to `10`. Keep it above `5`, the time `buildctl` waits for the daemon before giving up.
- `readinessProbe.failureThreshold`: Consecutive failed checks before the pod is marked not ready. Defaults to `3`.
- `readinessProbe.successThreshold`: Consecutive successful checks before the pod is marked ready. Defaults to `1`.
- `tolerations`: Tolerations for the BuildKit pods. If not set, the BuildKit pods inherit the tolerations from [`globals.tolerations.okteto`](self-hosted/helm-configuration.mdx#tolerations).
- `nodeSelectors`: Node selectors for the BuildKit pods. If not set, the BuildKit pods inherit the node selectors from [`globals.nodeSelectors.okteto`](self-hosted/helm-configuration.mdx#nodeselectors).
- `network.mode`: The network mode of the build containers: `auto` (default), `host`, `none`, or `bridge`. Bridge mode isolates the network of each build, so concurrent builds don't collide on ports. It isn't compatible with [rootless mode](#rootless).
- `network.ipv4.enabled`: Adds the IPv4 subnet `network.ipv4.subnet` to the network that the `RUN` instructions of your builds use. Defaults to `true`. At least one of `network.ipv4.enabled` and `network.ipv6.enabled` must be `true`.
- `network.ipv4.subnet`: The IPv4 subnet for the network of the `RUN` instructions. Defaults to `10.10.0.0/16`.
- `network.ipv6.enabled`: Adds the IPv6 subnet `network.ipv6.subnet` to the network that the `RUN` instructions use, required in [IPv6 networks](self-hosted/manage/ipv6.mdx). Defaults to `false`. Not used in rootless mode.
- `network.ipv6.subnet`: The IPv6 subnet for the network of the `RUN` instructions. Defaults to `fdbd:6b1d:2c0e::/64`.
- `rootless.enabled`: Runs BuildKit in [rootless mode](#rootless), without a privileged container. Defaults to `false`.
- `rootless.image.repository`: The image repository for rootless mode. Defaults to `okteto/buildkit`, pulled from the registry defined in `globals.registry`.
- `rootless.image.tag`: The image tag for rootless mode. Defaults to the `-rootless` tag that matches your chart version, for example <code>{variables.chartVersion}-rootless</code>.

```yaml
buildkit:
  port: 443
  extraEnv:
  - name: NO_PROXY
    value: ".example.com"
  replicaCount: 1
  persistence:
    enabled: true
    class: ssd
    size: 180Gi
    cacheRatio: 0.8
  tolerations:
  - key: "okteto-buildkit"
    operator: "Equal"
    value: "buildkit"
    effect: "NoExecute"
  nodeSelectors:
    okteto-node-label: build
    region: west
  terminationGracePeriodSeconds: 600
  hpa:
    enabled: true
    min: 1
    max: 5
    metrics:
      - type: Pods
        pods:
          metric:
            name: okteto_build_active_builds
          target:
            type: AverageValue
            averageValue: "0.99"
    behavior:
      scaleUp:
        policies:
          - type: Pods
            value: 1
            periodSeconds: 30
      scaleDown:
        stabilizationWindowSeconds: 600
        policies:
          - type: Pods
            value: 1
            periodSeconds: 150
    adapter:
      enabled: true
      replicaCount: 2
      resources:
        requests:
          cpu: 100m
          memory: 128Mi
```

To handle timeouts in the communication between the client and the BuildKit daemon, set these environment variables on the server side:

- `OKTETO_KEEPALIVE_SERVER_TIME_MS`: If the server sees no activity for this duration, it pings the client to check that the transport is still alive. Values below 1s are raised to 1s. Defaults to 2 hours.
- `OKTETO_KEEPALIVE_SERVER_TIMEOUT_MS`: After a keepalive ping, the server waits this long for activity. If it sees none, it closes the connection. Defaults to 20 seconds.
- `OKTETO_KEEPALIVE_SERVER_MAX_CONN_IDLE_MS`: How long a connection can stay idle before the server closes it by sending a GOAWAY. A connection is idle since it was established or since the number of outstanding RPCs last dropped to zero, whichever is more recent. Defaults to infinity.
- `OKTETO_KEEPALIVE_SERVER_MAX_CONN_AGE_MS`: The maximum time a connection can exist before the server closes it by sending a GOAWAY. The server adds a random jitter of +/-10% to the value to spread out connection storms. Defaults to infinity.
- `OKTETO_KEEPALIVE_SERVER_MAX_CONN_AGE_GRACE_MS`: An extra period after `OKTETO_KEEPALIVE_SERVER_MAX_CONN_AGE_MS`, after which the server forcibly closes the connection. Defaults to infinity.
- `OKTETO_KEEPALIVE_SERVER_POLICY_MINTIME_MS`: The minimum time a client should wait before sending a keepalive ping. Defaults to 5 minutes.
- `OKTETO_KEEPALIVE_SERVER_POLICY_PERMIT_WITHOUT_STREAM`: If `true`, the server allows keepalive pings even when there are no active streams (RPCs). If `false` and the client sends pings with no active streams, the server sends a GOAWAY and closes the connection. Defaults to `false`.

#### rootless

By default, the BuildKit pods run as a privileged container so that `buildkitd` can create the namespaces and mounts that build steps need. Rootless mode runs `buildkitd` as a non-root user instead, using the `okteto/buildkit:<version>-rootless` image. A build step that escapes its sandbox lands in an unprivileged container rather than in a root process on the node, which limits the impact of a malicious or compromised Dockerfile.

Rootless mode is disabled by default because it depends on kernel features that aren't available on every Linux distribution. The nodes that run BuildKit must allow unprivileged user namespaces (`user.max_user_namespaces` greater than zero), and the `overlayfs` snapshotter requires kernel 5.11 or later (older kernels fall back to `fuse-overlayfs`). Some distributions need extra node configuration. For example, Ubuntu 24.04 and later require `kernel.apparmor_restrict_unprivileged_userns=0`, and Bottlerocket requires `user.max_user_namespaces` to be set through its kernel settings. The [BuildKit rootless documentation](https://github.com/moby/buildkit/blob/master/docs/rootless.md) lists the requirements for each distribution. Test rootless mode in a non-production cluster before you enable it.

When `rootless.enabled` is `true`, the chart makes these changes to the BuildKit StatefulSet:

- Pulls the image defined in `rootless.image` instead of the default BuildKit image.
- Runs the `buildkitd` container and its init container with `runAsNonRoot: true` and `fsGroup: 1000`, and removes the `privileged` flag.
- Sets the seccomp and AppArmor profiles to `Unconfined`, because `buildkitd` still needs the `mount` and `unshare` syscalls. On Kubernetes 1.29 and earlier, the AppArmor profile is set through the `container.apparmor.security.beta.kubernetes.io/buildkitd` pod annotation.
- Starts `buildkitd` with the `--oci-worker-no-process-sandbox` flag, as in the upstream Kubernetes examples.
- Mounts the build cache volume at `/home/user/.local/share/buildkit`.

Rootless mode has two limitations:

- `network.mode: bridge` isn't supported. The Helm install fails if you combine both settings.
- The BuildKit StatefulSet name includes the rootless setting, so enabling or disabling it creates a new StatefulSet and a new persistent volume. The build cache starts empty after the change. Kubernetes keeps the previous StatefulSet's persistent volume claim, so delete it manually once you no longer need it.

```yaml
buildkit:
  rootless:
    enabled: true
```

If you mirror the Okteto images to a private registry, override `rootless.image` as the [air-gapped installation guide](self-hosted/manage/air-gapped.mdx#step-2-setting-up-a-private-registry-for-required-images) describes.

### cli

Settings for the Okteto CLI. The `cli` section sets the Docker image that the Okteto CLI uses for cluster-wide operations. Change it to use your own Docker images.

- `image`: The image settings for the Okteto CLI.
  - `registry`: The registry where the Okteto CLI image is hosted. Defaults to `ghcr.io`.
  - `repository`: The repository path for the Okteto CLI image. Defaults to `okteto/okteto`.

```yaml
cli:
  image:
    registry: "my-custom-registry:5000"
    repository: "okteto/okteto"
```
:::note
- Changing these settings changes the image for every Okteto CLI user in the cluster.
- The version of your hosted image must match the original version to stay compatible with the remote. For example, if your cluster supports `ghcr.io/okteto/okteto:3.2.0`, the hosted image should be `myregistry/okteto:3.2.0`.
- This configuration is separate from the `initContainer` setting in `okteto.yaml`. The Okteto CLI settings apply to all users and operations, while the `initContainer` setting is specific to an application environment, and you can customize it for pre-startup tasks.
:::

### daemonset

The daemonset configures every node in your cluster to work with Okteto.

- `enabled`: Whether to install the daemonset. Defaults to `true`.
- `annotations`: Annotations to add to the daemonset pods.
- `extraEnv`: Environment variables for the daemonset containers.
- `labels`: Labels to add to the daemonset pods.
- `configurePrivateRegistriesInNodes.enabled`: Whether the daemonset configures the private registry credentials on the nodes for the kubelet. It defaults to `false`. It's disabled when `regcredsManager.pullSecrets.enabled=true`.
- `injectCA.enabled`: Controls whether the daemonset installs the CA into each node's trust store, so the kubelet can pull images from the Okteto Registry when you use a private CA or a self-signed certificate. It defaults to `true`. Set it to `false` only if you add the CA to your nodes' trust store through your own mechanism; otherwise, image pulls from the Okteto Registry fail with a certificate verification error. Disabling it only affects the daemonset: the other daemonset tasks still run, and the Okteto components keep mounting the CA. This setting has no effect when neither `wildcardCertificate.privateCA.enabled` nor `wildcardCertificate.create` is set.
- `priorityClassName`: The priority class for the daemonset pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.

The daemonset runs these tasks on each node:

- [Overrides](self-hosted/helm-configuration.mdx#overrideregistryresolution) the Okteto Registry hostname resolution to use internal IPs.
- [Overrides](self-hosted/helm-configuration.mdx#overridefilewatchers) the default kernel values for file watchers on every node.
- Configures the kubelet with registry credentials for [private registries](self-hosted/helm-configuration.mdx#daemonset) (if `configurePrivateRegistriesInNodes.enabled=true` and `regcredsManager.pullSecrets.enabled=false`).
- Installs your private CA, if you provide one (`wildcardCertificate.privateCA.enabled: true`), into each node's trust store. Setting `injectCA.enabled: false` disables this task.
- Installs the Okteto-generated CA into each node's trust store when using self-signed certificates (`wildcardCertificate.create: true`). Setting `injectCA.enabled: false` disables this task.

To restrict the nodes where the daemonset runs, use the `dev` [tolerations](self-hosted/helm-configuration.mdx#tolerations) and [nodeSelectors](self-hosted/helm-configuration.mdx#nodeselectors):

```yaml
globals:
  nodeSelectors:
    dev:
      okteto-node-pool: dev
  tolerations:
    dev:
      - key: okteto-node-pool
        operator: Equal
        value: dev
        effect: NoSchedule
```

### defaultBackend

The defaultBackend receives failed requests from the ingress controller, transforms them, and returns them to the client.

- `affinity`: Affinities to add to the defaultBackend pods.
- `annotations`: Annotations to add to the defaultBackend pods.
- `enabled`: Whether to deploy the defaultBackend. Defaults to `true`.
- `extraEnvs`: Environment variables for the defaultBackend containers.
- `labels`: Labels to add to the defaultBackend pods.
- `nameOverride`: Overrides the full name of the defaultBackend service.
- `port`: The internal port of the defaultBackend. Defaults to `8080`.
- `priorityClassName`: The priority class for the defaultBackend pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `replicaCount`: The number of defaultBackend pods. It defaults to 2.
- `resources`: The resources for the defaultBackend pods.

```yaml
defaultBackend:
  replicaCount: 3
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
```

The defaultBackend provides these features:

- **Autowake Namespaces**: When a user accesses an endpoint of a sleeping Namespace, the defaultBackend issues a wake command.
- **Custom error pages**: When an endpoint returns an error, the defaultBackend serves a custom error page with hints to resolve the issue, instead of a generic error message. Common cases are sleeping Namespaces and unavailable services. The error pages work automatically, with no configuration.

### gc

The Okteto Garbage Collector scales idle applications to zero and deletes unused Namespaces to reduce infrastructure costs. It's enabled by default.

You can also [configure the Garbage Collector in the Admin Dashboard](admin/cleanup.mdx), under **Admin → Garbage Collector** in the Settings section.

- `annotations`: Annotations to add to the Garbage Collector pods.
- `labels`: Labels to add to the Garbage Collector pods.
- `slackWebhook`: If set, the Garbage Collector sends a notification when it scales a resource to zero or deletes a Namespace.
- `upSessionByLastSyncedFile`: If `true`, the Garbage Collector scales `okteto up` sessions to zero when no files were synchronized during the scale-to-zero period. By default, it checks for an active connection, regardless of inactivity.
- `priorityClassName`: The priority class for the Garbage Collector pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.

```yaml
gc:
  enabled: true
  upSessionByLastSyncedFile: false
  slackWebhook: https://hooks.slack.com/services/T00000000/B00000000/XXXXXXXXXXXXXXXXXXXXXXXX
```

### insights

Configures the [Okteto Insights](admin/okteto-insights.mdx#consuming-insights-metrics-from-other-tools) component in your Okteto instance.

- `enabled`: Whether to enable Okteto Insights. Defaults to `false`.
- `bearerSecret.name`: The name of the secret that stores the token to access the Okteto Insights metrics. Defaults to `okteto-insights`.
- `bearerSecret.key`: The key in the secret that stores the token to access the Okteto Insights metrics. Defaults to `bearer`.

```yaml
insights:
  enabled: false
  bearerSecret:
    name: okteto-insights
    key: bearer
```

When Okteto Insights is enabled, Okteto also installs the Event Exporter component and the Insights Metrics CronJob.

The Event Exporter receives Okteto CLI events through Kubernetes Events and injects them as Okteto Insights metrics.

- `priorityClassName`: The priority class for the Event Exporter pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `podAnnotations`: Annotations to add to the Event Exporter pods.
- `podLabels`: Labels to add to the Event Exporter pods.
- `resources`: The resources for the Event Exporter pods.

```yaml
insights:
  eventsExporter:
    priorityClassName:
    podLabels: {}
    podAnnotations: {}
    resources:
      requests:
        cpu: 50m
        memory: 20Mi
      limits:
        memory: 100Mi
```

Insights Metrics is a CronJob that precomputes metrics for the Okteto Insights `/metrics` endpoint.

- `annotations`: Annotations to add to the Insights Metrics pods.
- `labels`: Labels to add to the Insights Metrics pods.
- `priorityClassName`: The priority class for the Insights Metrics pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `resources`: The resources for the Insights Metrics pods.
- `schedule`: How often the CronJob runs, in cron syntax. Defaults to every 5 minutes (`*/5 * * * *`).

```yaml
insights:
  metrics:
    annotations: {}
    labels: {}
    priorityClassName:
    resources:
      requests:
        cpu: 50m
        memory: 20Mi
      limits:
        memory: 100Mi
    schedule: "*/5 * * * *"
```

### installer

The jobs that deploy your [application environments from Git](application-environments/deploy.mdx#deploying-from-the-okteto-ui).

- `annotations`: Annotations to add to the installer job pods.
- `extraEnv`: Environment variables for the installer job containers.
- `labels`: Labels to add to the installer job pods.
- `runner`: The image that runs the deploy and destroy commands of every repository that doesn't set its own image. See [Custom installer image](#custom-installer-image).
  - `registry`: The registry where the installer image is hosted. Defaults to the value of `globals.registry`.
  - `repository`: The repository path for the installer image. Defaults to `okteto/pipeline-runner`.
  - `tag`: The image tag to deploy. Defaults to <code>{variables.chartVersion}</code>.
- `activeDeadlineSeconds`: The maximum duration of the pipeline, in seconds.
- `gitSSHUser`: The user for cloning Git repositories over SSH.
- `sshSecretName`: The name of the secret with the private key for cloning Git repositories over SSH. If the secret doesn't exist, Okteto generates the key and the secret.
- `resources`: The resources for the installer job pods.
- `priorityClassName`: The priority class for the installer job pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `securityContext`: The security context for the installer job container, in the [Kubernetes syntax](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/). Not set by default.
- `extraInitContainers`: List of init containers to add to the installer job pods.

<CodeBlock language="yaml"> 
{`installer:
    runner:
      repository: okteto/pipeline-runner
      tag: ${variables.chartVersion}
    extraEnv:
    - name: NO_PROXY
      value: ".example.com"
    activeDeadlineSeconds: 1800
    gitSSHUser: git
    sshSecretName: "okteto-ssh"
    securityContext:
      allowPrivilegeEscalation: false
    resources:
      requests:
        cpu: 10m
        memory: 50Mi
`}
</CodeBlock>

#### Custom Installer Image

The installer runs the commands of the `deploy` and `destroy` sections in the image that `installer.runner` sets, unless the Okteto Manifest of the repository sets its own `deploy.image`. Each repository usually sets its own image. Change the default image only when you want the same tools available in every repository that doesn't.

Build your image from the default pipeline runner image, so it keeps the tools that Okteto needs, and push it to a registry that your Okteto instance can pull from:

<CodeBlock language="dockerfile">
{`FROM ghcr.io/okteto/pipeline-runner:${variables.chartVersion}
RUN apt-get update && apt-get install -y wget`}
</CodeBlock>

Then set it in your Helm configuration file and [upgrade your Okteto instance](self-hosted/manage/upgrade.mdx):

```yaml
installer:
  runner:
    registry: REGISTRY
    repository: REPOSITORY
    tag: TAG
```

The pipeline logs in the Okteto UI show the image that each deployment uses. On Okteto BYOC, [contact support](https://okteto.com/support) to set a custom installer image.

### migration

The Helm hook Job that applies the data and resource migrations required by the Okteto version you're installing. ### namespaceDestroyAll

The Job that destroys every resource in a Namespace, plus the CronJob that recovers Namespaces whose destroy-all Job didn't finish.

Okteto creates a destroy-all Job in the `okteto` namespace each time a Developer runs [`okteto destroy --all`](reference/okteto-cli.mdx#destroy) or uses **Destroy All** in the Okteto UI. The Job runs `okteto pipeline destroy` for application environments with a `destroy` section or a [Divert](application-environments/divert/index.mdx) driver, uninstalls Helm releases, and deletes the remaining resources. It times out after 2 hours. To read its logs for a Namespace:

```bash
kubectl logs -l app.kubernetes.io/component=namespace-destroy-all,dev.okteto.com/namespace=<namespace> --namespace=okteto
```

If a destroy-all Job hangs, a resource with a blocked [finalizer](https://kubernetes.io/blog/2021/05/14/using-finalizers-to-control-deletion/) is the most likely cause. The checker CronJob resets Namespaces stuck in `DestroyingAll` or `DestroyAllFailed` for longer than 2 hours back to `Active`, so the Developer can retry.

- `priorityClassName`: The priority class for the per-Namespace destroy-all job pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `checker`: Configures the CronJob that recovers stuck Namespaces.
  - `schedule`: The cron schedule for the checker. Defaults to `*/3 * * * *` (every 3 minutes).
  - `timeoutInSeconds`: The maximum duration of each checker run, in seconds. Defaults to `120`.
  - `priorityClassName`: The priority class for the checker pods, following the same precedence rules as the destroy-all job `priorityClassName`.

```yaml
namespaceDestroyAll:
  checker:
    schedule: "*/3 * * * *"
    timeoutInSeconds: 120
```

### resourceManager

Configures the [Resource Manager](admin/resource-manager.mdx).

- `annotations`: Annotations to add to the Resource Manager pods.
- `deletePeriodDays`: The retention period for recommendations, in days. When a service is no longer deployed in your cluster, Okteto deletes its recommendation after this period. It defaults to 15 days.
- `enabled`: Whether to install the Resource Manager. When it's installed, Okteto creates a CronJob that computes CPU and memory recommendations for your pods. It defaults to `true`.
- `labels`: Labels to add to the Resource Manager pods.
- `priorityClassName`: The priority class for the Resource Manager pods. The PriorityClass must already exist in your cluster. This value takes precedence over `globals.priorityClassName`. If it isn't set, the pods inherit the priority class from `globals.priorityClassName`.
- `recommendations.correction`: A floating-point multiplier that adjusts for over- or under-provisioning of resources. It must be greater than 0. The default is `1.1`, which over-provisions by 10%. For example, `0.9` under-provisions by 10% compared to the average utilization.
- `recommendations.min.cpu`: The minimum CPU request that the Resource Manager sets when it applies recommendations. It uses this value when a recommendation isn't calculated yet or is lower. It defaults to `5m`.
- `recommendations.min.memory`: The minimum memory request that the Resource Manager sets when it applies recommendations. It uses this value when a recommendation isn't calculated yet or is lower. It defaults to `10Mi`.
- `recommendations.weight`: A floating-point number between 0 and 1 used to stabilize CPU and memory recommendation calculations. A higher value (closer to 1) gives more weight to historical resource usage trends, making the Resource Manager less responsive to recent changes or spikes. A lower value (closer to 0) makes it more reactive to recent usage patterns, including spikes. The default value is `0.9`, which makes the Resource Manager conservative: it favors existing trends and tries to ignore minor fluctuations.
- `resources`: The resources for the Resource Manager pods.
- `schedule`: How often Okteto calculates resource recommendations, in cron syntax. Defaults to every 5 minutes (`*/5 * * * *`).

```yaml
resourceManager:
  enabled: true
  schedule: "*/5 * * * *"
  deletePeriodDays: 15
  recommendations:
    weight: 0.9
    correction: 1.1
    min:
      cpu: 5m
      memory: 10Mi
  priorityClassName:
  labels: {}
  annotations: {}
  resources: {}
```

### warmNodes

Warm nodes are nodes for your application environments that Okteto keeps ready, with the Okteto images and the images in `extraImages` already pulled. When a pod in a Namespace doesn't fit on any other node, Kubernetes runs it on a warm node, so it starts without waiting for those images to download. Warm nodes are disabled by default. Once you enable them, Okteto keeps 1 warm node, and Admins set how many to keep, from 0 to 20, in [**Admin > Nodes**](admin/nodes.mdx#warm-nodes).

> **Requirements**: the Kubernetes cluster autoscaler must be installed in your cluster.

Each warm node runs a pod of the `okteto-warm-nodes` Deployment, in the `okteto` namespace:

- Each warm pod runs alone on its node: no other warm pod and no pod of a Namespace managed by Okteto runs on the same node. The warm pods run on the nodes for your application environments, with the same [`globals.nodeSelectors.dev`](#nodeselectors), [`globals.tolerations.dev`](#tolerations), and [`affinity.devPool`](#affinity) as the pods of your Namespaces. When you set them, Development Containers use `affinity.upPool` and installer jobs use `affinity.installerPool` instead of `affinity.devPool`, so they only run on the warm nodes if those affinities allow it.
- The warm pods have a lower priority than the pods of your Namespaces. When one of your pods doesn't fit on any other node, the Kubernetes scheduler preempts a warm pod and runs your pod on its node.
- The Deployment then creates a new warm pod, which stays `Pending` until the cluster autoscaler adds a node for it. That node is the new warm node.

Each warm node is an idle node of the node pool, which adds to your infrastructure costs. If the node pool is at its maximum size, the new warm pods stay `Pending`, and **Admin > Nodes** shows fewer warm nodes than the number you set.

:::warning
The warm pods request almost no CPU or memory, so warm nodes assume that all the nodes for your application environments have the same size. Provisioners that choose the size of each new node from the pending pods, such as Karpenter or node auto-provisioning, create warm nodes that are too small for the pods of your Namespaces.
:::

The warm nodes pull the images of the Okteto CLI, the pipeline runner, and the Okteto backend, in the versions of your Okteto installation, and then the images in `extraImages`.

:::note
The warm pods pull private images with the [Registry Credentials](admin/registry-credentials/index.mdx) of your Okteto instance, or with the credentials available to the nodes, such as IAM roles. An image in `extraImages` that can't be pulled doesn't keep the other images from being pulled.
:::

The [migration](#migration) job creates or updates the `okteto-warm-nodes` Deployment on every install and upgrade, and deletes it when you disable warm nodes. Upgrades keep the number of warm nodes, and revert any other change made by hand to the Deployment. If the job can't apply or delete the Deployment, the install or upgrade fails. `helm uninstall` deletes the Deployment too. After a `helm rollback` to a version earlier than 1.51, delete the Deployment yourself:

```bash
kubectl delete deployment okteto-warm-nodes --namespace=okteto
```

- `enabled`: Whether Okteto keeps warm nodes. Defaults to `false`.
- `countManagedExternally`: Whether you set the number of warm nodes outside of Okteto. Defaults to `false`: Admins set it in **Admin > Nodes**, up to 20. When `true`, Okteto doesn't change the number, **Admin > Nodes** shows it as read-only, and you set it by scaling the `okteto-warm-nodes` Deployment, for example from your GitOps tool, with `kubectl scale deployment okteto-warm-nodes --replicas=5 --namespace=okteto`, or [on a schedule](admin/nodes.mdx#read-only-number-of-warm-nodes).
- `extraImages`: Images to pull on the warm nodes besides the Okteto images, for example the images that your application environments use.
- `labels`: Labels to add to the `okteto-warm-nodes` Deployment.
- `annotations`: Annotations to add to the `okteto-warm-nodes` Deployment.
- `podLabels`: Labels to add to the warm pods, besides the global `podLabels`. If both set the same key, this value wins.
- `podAnnotations`: Annotations to add to the warm pods, besides the global `podAnnotations`. If both set the same key, this value wins.
- `priorityClass.create`: Whether to create the priority class of the warm pods. Defaults to `true`. Set it to `false` to use an existing priority class with the name in `priorityClass.name`: the install or upgrade fails if it doesn't exist.
- `priorityClass.name`: The name of the priority class of the warm pods. Defaults to `okteto-warm-nodes`.
- `priorityClass.value`: The priority of the warm pods. Defaults to `-10`. It must be lower than the priority of the pods of your Namespaces, so they can preempt the warm pods, and greater than or equal to the `--expendable-pods-priority-cutoff` of the cluster autoscaler (`-10` by default), so the pending warm pods make it add nodes. With `create: false`, the value of your priority class applies, and Okteto doesn't check it.
- `priorityClass.preemptionPolicy`: The preemption policy of the priority class. Defaults to `Never`, so the warm pods never preempt other pods.

Kubernetes doesn't allow changing the `value` or the `preemptionPolicy` of an existing priority class, so `helm upgrade` fails if you change them after the priority class is created.

```yaml
warmNodes:
  enabled: true
  extraImages:
    - node:24
    - python:3.13
```

## Advanced Configuration

### addSafeToEvictAnnotation

Controls the [`cluster-autoscaler.kubernetes.io/safe-to-evict`](https://kubernetes.io/docs/reference/labels-annotations-taints/#cluster-autoscaler-kubernetes-io-safe-to-evict) annotation that Okteto adds to the pods it creates in development Namespaces.

- `enabled`: Whether Okteto adds the annotation. Enabled by default. If a pod already carries the annotation, Okteto keeps the existing value.
- `value`: The value Okteto sets for the annotation, `true` or `false`. Defaults to `false`.

```yaml
addSafeToEvictAnnotation:
  enabled: true
  value: false
```

The annotation controls whether the Kubernetes cluster autoscaler may evict a pod when it scales down the node running it:

- `enabled: true`, `value: false` (default): marks Okteto pods as not safe to evict. The autoscaler won't scale down a node that runs one of these pods, regardless of the pod's shape. This keeps active development sessions stable, at the cost of slower node scale-down and potentially higher infrastructure cost. We recommend keeping this default: development clusters already scale down aggressively outside working hours and over the weekend, so stable development sessions matter more than aggressive scale-down during the working day.
- `enabled: true`, `value: true`: marks Okteto pods as safe to evict, even when the autoscaler would otherwise protect them (for example, pods with local storage). This favors aggressive scale-down and cost savings, at the cost of development sessions restarting during scale-down.
- `enabled: false`: Okteto doesn't add the annotation. Pods that already carry it keep their value, and for the rest, the autoscaler falls back to its own default heuristics. This doesn't reliably prevent eviction: for many pod shapes it behaves like `value: true`, so it isn't equivalent to `value: false`. Use it when you want the cluster to decide.

:::note
Before Okteto Chart 1.49, this annotation defaulted to `value: true`. To keep that behavior after upgrading, set `addSafeToEvictAnnotation.value` to `true`.
:::

### affinity

Default affinities for the pods in Namespaces managed by Okteto (`devPool`) and for the Okteto pods (`oktetoPool`).

- `devPool`: Affinities for pods created in Namespaces managed by Okteto.
- `oktetoPool`: Affinities for pods created during the Okteto installation.

```yaml
affinity:

        matchExpressions:
        - key: cloud.google.com/spot
          operator: In
          values:
          - "true"
      weight: 10
```

In this example, pods in Namespaces created by Okteto prefer to land on spot nodes.

#### nodeSelectors

Node selectors for pods, grouped under `okteto` and `dev`:

:::note
If the nodes you select are tainted, you must also define a matching toleration in [`globals.tolerations.dev`](#tolerations). A node selector on its own places user workloads on nodes they can't tolerate, and they stay `Pending`.

These node selectors don't apply to the ingress controllers or Reloader, which you configure as described in [Node selectors and tolerations](#node-selectors-and-tolerations).
:::

#### priorityClassName

The priority class for all pods in the `okteto` namespace. The priority class must already exist in your cluster.

```yaml
globals:
  priorityClassName: okteto-priority
```

#### registry

The registry for all Okteto components, except the Okteto CLI. The [air-gapped installation guide](self-hosted/manage/air-gapped.mdx) has more details.

```yaml
globals:
  registry: my-custom-registry:5000
```

#### tolerations

Tolerations for pods, grouped under `okteto` and `dev`:

- `okteto`: Tolerations for the pods in the `okteto` namespace, except the [Okteto Daemonset](#daemonset).
- `dev`: Tolerations for the pods of user applications, which run in Namespaces managed by Okteto. They also apply to the [Okteto Daemonset](#daemonset).

```yaml
globals:
  tolerations:
    okteto:
    - key: "kubernetes.io/arch"
      operator: "Equal"
      value: "arm64"
      effect: "NoSchedule"
    dev:
    - key: "kubernetes.io/arch"
      operator: "Equal"
      value: "arm64dev"
      effect: "NoSchedule"
```

:::warning
The older `tolerations.oktetoPool`, `tolerations.buildPool`, and `tolerations.devPool` values are deprecated and will be removed in Okteto Chart 2.0. Installing the chart while they are set prints a deprecation warning. Use `globals.tolerations` and [`globals.nodeSelectors`](#nodeselectors) instead, together with [`buildkit.tolerations` and `buildkit.nodeSelectors`](#buildkit) for BuildKit. The [migration guide](https://community.okteto.com/t/important-update-migrating-to-new-implementation-of-okteto-pod-tolerations-and-node-selectors/1281) has the full mapping.
:::

:::note
If the nodes selected by [`globals.nodeSelectors.dev`](#nodeselectors) are tainted, define a matching toleration under `globals.tolerations.dev` so that user workloads can schedule onto them.

These tolerations don't apply to the ingress controllers or Reloader, which you configure as described in [Node selectors and tolerations](#node-selectors-and-tolerations).
:::

### ingress

Default values for the ingresses that Okteto creates.

- `annotations`: The annotations to apply to all the ingresses created during the Okteto installation.
- `oktetoIngressClass`: The `ingressClassName` to apply to all the ingresses created during the Okteto installation (defaults to `okteto-controlplane-nginx`).
- `class`: If set, Okteto sets it as the `ingressClassName` of every ingress it manages. Set it when your cluster has more than one ingress controller. If not set, Okteto falls back to the cluster's default ingress class.
- `forceIngressClass`: If enabled, every ingress deployed in Namespaces managed by Okteto gets the ingress class defined in `ingress.class` (default: `false`).
- `forceIngressSubdomain`: If enabled, the host subdomain of every ingress deployed in Namespaces managed by Okteto must match the Okteto wildcard subdomain (default: `false`).
- `ip`: The internal IP of the ingress. Pods call the Okteto API and the Okteto Registry on this IP. Required if you disable the installation of the Okteto [NGINX Ingress Controller](self-hosted/helm-configuration.mdx#using-your-own-ingress-controller).

```yaml
ingress:
  annotations: {}
  oktetoIngressClass: nginx
  class: nginx
  forceIngressClass: false
  forceIngressSubdomain: true
  ip: ""
```

### kubetoken

- `lifetimeSeconds`: The lifetime, in seconds, of the tokens that Okteto generates for its [Kubernetes credentials](user-settings/setup.mdx). It must be equal to or greater than [`installer.activeDeadlineSeconds`](self-hosted/helm-configuration.mdx#installer), so the tokens stay valid for the whole installer run. Defaults to 86400 seconds (1 day).

> The maximum expiration time depends on the `--service-account-max-token-expiration` flag of the [Kubernetes API server](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/), so your tokens might get a different expiration time than the one you set here. If you set a higher value, you get the maximum that the API server allows. Some Kubernetes providers don't let you change this flag and enforce their own value.

### namespace

Custom annotations and labels for the Namespaces that Okteto creates. Okteto adds them to the annotations and labels it already applies.

- `annotations`: Annotations for each Namespace that Okteto creates.
- `labels`: Labels for each Namespace that Okteto creates.
- `ingress.annotations`: Annotations for the ingresses in Namespaces that Okteto creates.
- `ingress.labels`: Labels for the ingresses in Namespaces that Okteto creates.
- `autoRoleBinding.enabled`: Binds the default service account of every Namespace managed by Okteto to the cluster role set in [`serviceAccounts.roleBindings.namespaces`](self-hosted/helm-configuration.mdx#serviceaccounts). This gives every pod without a custom service account access to the Kubernetes API. Defaults to `true`.

```yaml
namespace:
  annotations:
    development: "true"

    istio-injection: enabled

      cert-manager.io/issuer: "letsencrypt"

      development: "true"
```

### networkPolicies

Configures [network policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/) that isolate the network traffic of each Namespace. Disabled by default.

- `ingress`: A list of ingress rules (NetworkPolicyIngressRule) for every Namespace managed by Okteto. Optional.
- `egress`: A list of egress rules (NetworkPolicyEgressRule) for every Namespace managed by Okteto. Optional.
- `blockedCIDRs`: IPv4 CIDRs that Namespaces, the installer jobs, and BuildKit can't send traffic to. Defaults to `169.254.169.254/32`, the cloud instance metadata service.
- `ipv6.enabled`: Allows IPv6 egress traffic, required in [IPv6 networks](self-hosted/manage/ipv6.mdx). Defaults to `false`, which blocks all IPv6 egress traffic.
- `ipv6.blockedCIDRs`: IPv6 CIDRs that Namespaces, the installer jobs, and BuildKit can't send traffic to. Defaults to `fd00:ec2::254/128`, the AWS instance metadata service.

```yaml
networkPolicies:
  enabled: true
  ingress:
  - from:
    - ipBlock:
        cidr: 172.17.0.0/16
        except:
        - 172.17.1.0/24
    - namespaceSelector:
        matchLabels:
          project: myproject
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - protocol: TCP
      port: 6379
  egress:
  - to:
    - ipBlock:
        cidr: 10.0.0.0/24
    ports:
    - protocol: TCP
      port: 5978
```

### quotas

Enables [resource quotas](https://kubernetes.io/docs/concepts/policy/resource-quotas/) per Namespace. They apply to every Namespace that Okteto manages, including development Namespaces and Preview Environments.

- `resources`: Limits the number of resources that a user can create.
  - `maxNamespaces`: Maximum number of Namespaces that a user can create. It doesn't apply to the `okteto-bot` user for [Admin access tokens](admin/admin-access-tokens.mdx).
  - `maxPods`: Maximum number of pods per Namespace.
  - `maxReplicationControllers`: Maximum number of replication controllers per Namespace.
  - `maxSecrets`: Maximum number of secrets per Namespace.
  - `maxServices`: Maximum number of services per Namespace.
  - `maxJobs`: Maximum number of jobs per Namespace.
  - `maxCronjobs`: Maximum number of cronjobs per Namespace.
  - `maxLoadBalancers`: Maximum number of services of type `LoadBalancer` per Namespace.
  - `maxNodePorts`: Maximum number of services of type `NodePort` per Namespace.
  - `maxConfigMaps`: Maximum number of config maps per Namespace.
  - `maxPVCs`: Maximum number of persistent volume claims per Namespace.
  - `maxVolumeSnapshots`: Maximum number of volume snapshots per Namespace.
  - `maxIngresses`: Maximum number of ingresses per Namespace.
- `bandwidth`: Limits the incoming and outgoing bandwidth per pod. Requires the Okteto [NGINX Ingress Controller](self-hosted/helm-configuration.mdx#ingress-nginx).
  - `ingress`: Maximum ingress bandwidth.
  - `egress`: Maximum egress bandwidth.
  - `up`: Limits the incoming and outgoing bandwidth per Development Container.
    - `ingress`: Maximum ingress bandwidth for a Development Container.
    - `egress`: Maximum egress bandwidth for a Development Container.
- `requests`: Limits the maximum [resource requests](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits) per Namespace.
  - `cpu`: Maximum CPU resource requests.
  - `memory`: Maximum memory resource requests.
  - `storage`: Maximum storage resource requests.
- `limits`: Limits the maximum [resource limits](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits) per Namespace.
  - `cpu`: Maximum CPU resource limits.
  - `memory`: Maximum memory resource limits.
  - `storage`: Maximum storage resource limits.
- `limitranges`: Configures the [limit ranges](https://kubernetes.io/docs/concepts/policy/limit-range/) of each Namespace.
  - `max`: Configures the maximum resources per container.
    - `cpu`: Maximum CPU resource limits.
    - `memory`: Maximum memory resource limits.
  - `requests`: Configures the default resource requests per container.
    - `cpu`: Default CPU resource requests.
    - `memory`: Default memory resource requests.
  - `limits`: Configures the default resource limits per container.
    - `cpu`: Default CPU resource limits.
    - `memory`: Default memory resource limits.

This example shows the default values. A value of `"-1"` means that no quota is enforced for that resource:

```yaml
quotas:
  resources:
    enabled: false
    maxNamespaces: "3"
    maxPods: "-1"
    maxServices: "-1"
    maxLoadBalancers: "0"
    maxNodePorts: "0"
    maxReplicationControllers: "-1"
    maxSecrets: "-1"
    maxConfigMaps: "-1"
    maxPVCs: "-1"
    maxVolumeSnapshots: "-1"
    maxIngresses: "-1"
    maxJobs: "-1"
    maxCronjobs: "-1"
  bandwidth:
    enabled: false
    ingress: "800M"
    egress: "800M"
    up:
      enabled: false
      ingress: "800M"
      egress: "800M"
  requests:
    enabled: false
    cpu: "1"
    memory: "2Gi"
    storage: "20Gi"
  limits:
    enabled: false
    cpu: "4"
    memory: "8Gi"
    storage: "20Gi"
  limitranges:
    max:
      enabled: false
      cpu: "3"
      memory: "12Gi"
    requests:
      enabled: true
      cpu: "10m"
      memory: "50Mi"
    limits:
      enabled: true
      cpu: "2"
      memory: "8Gi"
```

### serviceAccounts

The `serviceAccounts` section configures the labels, annotations, and role bindings of the service accounts that Okteto generates for user accounts.

- `annotations`: Annotations for each service account that Okteto generates for a user account.
- `labels`: Labels for each service account that Okteto generates for a user account.
- `roleBindings.namespaces`: Okteto binds this cluster role to every admin, owner, and member of each Namespace it manages, with a namespace-scoped role binding. Okteto does **not** create this cluster role: it must already exist in the cluster. Defaults to `cluster-admin`.
- `roleBindings.previews`: Okteto binds this cluster role to every Okteto user in every **global** Preview Environment, with a namespace-scoped role binding. Okteto does **not** create this cluster role: it must already exist in the cluster. Defaults to `view`.
- `clusterRoleBinding`: Okteto binds this cluster role to every user with a cluster role binding. Disabled by default. Use it to give every developer account access to cluster-level resources, such as the Node API. Okteto does **not** create this cluster role: it must already exist in the cluster.
- `extraRoleBindings`: Okteto binds every cluster role listed under a namespace to every user, with a namespace-scoped role binding in that namespace. Okteto doesn't create the ClusterRoles or the namespaces: they must already exist in the cluster.

```yaml
serviceAccounts:
  annotations:
    custom.annotation/one: one
    custom.annotation/two: two
  labels:
    custom.label/one: one
    custom.label/two: two
  roleBindings:
    namespaces: cluster-admin
    previews: view
  clusterRoleBinding: "example-cluster-role"
  extraRoleBindings:
    namespace-name1:
      - cluster-role1
      - cluster-role2
    namespace-name2:
      - cluster-role3
```

> To bind more than one cluster role in any of these settings, use [ClusterRole aggregation](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#aggregated-clusterroles) to combine them into one.

### store

Configures how Okteto persists user data.

- `personalAccessToken.max`: The maximum number of [Personal Access Tokens](user-settings/personal-access-tokens.mdx) each user can create. Defaults to `5`.

```yaml
store:
  personalAccessToken:
    max: 5
```

:::note
Okteto stores each Personal Access Token as a Kubernetes Secret. A cluster has a finite capacity for the total number of Secrets it can hold, so set `personalAccessToken.max` in proportion to the number of users on your instance. A high value multiplied across many users can exhaust the cluster's Secret capacity.
:::

### userDefinedNamespaces

Disable it to enforce the `username` as a suffix for Namespaces and ingress hosts. Enabled by default.


### userPodAffinity

When enabled, Okteto adds a preferred pod affinity to every pod of a Namespace, so the Kubernetes scheduler places the pods of the same Namespace on the same node when it can (default: `true`). Packing the pods of each Namespace on fewer nodes lets the cluster autoscaler remove the nodes that are left empty.

- `weight`: Weight of the preferred pod affinity, from `1` to `100` (default: `100`). The scheduler weighs it against its other preferences, such as spreading the replicas of a Deployment or placing pods on the nodes with more free resources. Lower values spread the pods of a Namespace across more nodes. The Okteto components fail to start if the value is outside that range.
- `antiAffinity`: When enabled, Okteto adds a required pod anti-affinity, so pods of different Namespaces never run on the same node (default: `false`).

The affinity applies when a pod is created: pods that are already running keep their node until they are recreated.

```yaml
userPodAffinity:
  enabled: true
  weight: 100
  antiAffinity:
    enabled: false
```

### virtualServices

Istio must be installed in the cluster.

```yaml
virtualServices:
  enabled: false
```

Settings for volumes.

  - `enabled`: Enables volume validation. Disabled by default.
  - `supportedStorageClasses`: List of supported storage classes.
  - `forceStorageClass`: Whether to enforce a storage class when a volume uses an unsupported one. If set, Okteto enforces the first storage class in `supportedStorageClasses`.
  - `supportedAccessModes`: List of supported access modes.


### volumeSnapshots

Lets users initialize persistent volume claims with the contents of an existing volume snapshot.

This feature requires a CSI driver in your cluster.

- `driver`: The name of the CSI driver used when creating snapshots.
- `class`: The VolumeSnapshotClass of the volume snapshot.
- `storageClass`: The storage class required by volumes initialized from snapshots (optional).
- `enableNamespaceAccessValidation`: When enabled, only users with access to the Namespace that stores a volume snapshot can use it in their application environments. Defaults to `false`.
- `allowIDAnnotation`: Allows your cloud provider's snapshot ID as the data source. Defaults to `true`.

```yaml
volumeSnapshots:
  enabled: true
  driver: ebs.csi.aws.com
  class: snapclass
  storageClass: ebs-sc
```

To initialize a persistent volume claim from a snapshot, add the `dev.okteto.com/from-snapshot-id` annotation to it:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  annotations:
    dev.okteto.com/from-snapshot-id: snap-xxxxxxxx
  name: pvc-name
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

When the persistent volume claim is created, Okteto imports the snapshot into Kubernetes as a [VolumeSnapshotContent](https://kubernetes.io/docs/concepts/storage/volume-snapshots/) and sets it as the source of the persistent volume claim.

### wildcardCertificate

By default, Okteto configures a self-signed wildcard certificate for your instance, which makes evaluations simpler. For a production installation, [configure your own wildcard certificate](self-hosted/install/certificates/index.mdx) and disable the default behavior.

The certificate settings are:

- `create`: If `false`, Okteto doesn't create a self-signed wildcard certificate.
- `duration`: The duration of the self-signed certificate. Ignored if `create` is `false`.
- `name`: The name of the secret that stores the certificate.
- `privateCA.enabled`: Set it to `true` when you use a private certificate authority.
- `privateCA.secret.name`: The name of the secret that stores the private certificate authority's certificate.
- `privateCA.secret.key`: The key in the secret that stores the private certificate authority's certificate.
- `annotations`: Annotations to add to the self-signed certificate that Okteto generates.

```yaml
wildcardCertificate:
  create: true
  duration: 2160h0m0s
  name: default-ssl-certificate
  annotations:
    argocd.argoproj.io/compare-options: IgnoreExtraneous
  # if using a private CA, specify the name of the TLS secret that stores the certificate
  privateCA:
    enabled: false
    secret:
      name: "okteto-ca"
      key: "ca.crt"
```

:::note
Setting `create: false` isn't enough on its own to serve your own certificate. The [ingress-nginx](self-hosted/helm-configuration.mdx#ingress-nginx) ingress controller reads its default certificate from `ingress-nginx.controller.extraArgs.default-ssl-certificate`, which isn't derived from `wildcardCertificate.name`. Whenever you set `create: false`, point that argument at the same secret, as shown in [bring your own certificate](self-hosted/install/certificates/bring-your-own-certificate.mdx). Otherwise that secret no longer exists, the ingress controller falls back to its own built-in fake certificate, and browsers show a certificate warning.
:::

## Dependencies

The default Okteto installation includes two instances of the [NGINX Ingress Controller](https://kubernetes.github.io/ingress-nginx/), installed from its official [Helm chart](https://kubernetes.github.io/ingress-nginx).

Each instance has a specific role:

- `ingress-nginx`: The ingress controller for all inbound traffic to the Okteto cluster, including BuildKit, the Okteto Registry, the Okteto API, the Okteto frontend, and users' ingresses.
- `okteto-nginx`: The ingress controller dedicated to the inbound traffic of users' ingresses. By default, it runs behind `ingress-nginx`.

### Okteto Ingress Controllers

Your Helm configuration file (for example, `config.yaml`) has two keys for the NGINX ingress controllers, `ingress-nginx` and `okteto-nginx`. Each one has a different function.

#### ingress-nginx

Configures the ingress behavior for the Okteto components (for example, the API, BuildKit, and the registry), and supports passthrough and proxying to `okteto-nginx`. It serves a `*.$subdomain` internal ingress that points to `okteto-nginx`. This ingress controller runs in the control plane of the Okteto cluster.

#### okteto-nginx

Configures the ingress behavior for application environments. It parses and registers developers' ingresses. This ingress controller runs in the cluster and manages ingress traffic to and between developers' applications.

When a user request arrives at Okteto, `ingress-nginx` receives it and proxies it to `okteto-nginx`, which proxies it to the backend pod.

#### Sample Configuration

This example changes the number of `ingress-nginx` replicas:

```yaml
ingress-nginx:
  controller:
    replicaCount: 2
```

The [ingress-nginx chart values](https://github.com/kubernetes/ingress-nginx/blob/main/charts/ingress-nginx/values.yaml) list every available value.

#### Node Selectors and Tolerations

[`globals.nodeSelectors`](#nodeselectors) and [`globals.tolerations`](#tolerations) apply to Okteto's own components. They do **not** reach the two ingress controllers or [Reloader](#reloader), which are separate charts and read their own values instead.

If you run Okteto on dedicated node pools, or on any node pool that carries a taint, configure all of them:

```yaml
globals:
  nodeSelectors:
    okteto:
      okteto-node-pool: okteto
  tolerations:
    okteto:
      - key: okteto-node-pool
        operator: Equal
        value: okteto
        effect: NoSchedule

ingress-nginx:
  controller:
    nodeSelector:
      okteto-node-pool: okteto
    tolerations:
      - key: okteto-node-pool
        operator: Equal
        value: okteto
        effect: NoSchedule

okteto-nginx:
  controller:
    nodeSelector:
      okteto-node-pool: okteto
    tolerations:
      - key: okteto-node-pool
        operator: Equal
        value: okteto
        effect: NoSchedule

reloader:
  reloader:
    deployment:
      nodeSelector:
        okteto-node-pool: okteto
      tolerations:
        - key: okteto-node-pool
          operator: Equal
          value: okteto
          effect: NoSchedule
```

:::warning
Leaving these out fails silently. The chart installs successfully, and the ingress controllers and Reloader schedule onto whichever nodes accept them, which on a cluster with dedicated pools is usually the untainted default pool. If every pool in the cluster is tainted, they stay `Pending` instead.
:::

These charts also accept `affinity`, `topologySpreadConstraints` and `priorityClassName` under the same keys. They are maintained upstream, so check their own value references for the authoritative list: [ingress-nginx](https://github.com/kubernetes/ingress-nginx/blob/main/charts/ingress-nginx/values.yaml), used by both the `ingress-nginx` and `okteto-nginx` keys, and [Reloader](https://github.com/stakater/Reloader#parameters).

[ARM Support](self-hosted/manage/arm-support.mdx) has a worked example for ARM node pools, which GKE taints by default.

#### ingress-nginx & okteto-nginx default values

Okteto sets specific values on the embedded ingress-nginx chart to enable features that depend on the ingress controller. To check them, run:

- `ingress-nginx`:

  ```
  helm show values okteto/okteto --jsonpath '{.ingress-nginx}'
  ```

- `okteto-nginx`:
  ```
  helm show values okteto/okteto --jsonpath '{.okteto-nginx}'
  ```

#### Using Your Own Ingress Controller

The [community guide on using your own ingress controller](https://community.okteto.com/t/how-do-i-configure-my-own-ingress-controller/887) explains how to disable the Okteto NGINX Ingress Controller and expose Okteto behind your own ingress controller.

### Reloader

The Okteto chart uses [Reloader](https://github.com/stakater/Reloader) to run rolling upgrades of the Okteto components when specific secrets change. To customize Reloader, set its [parameters](https://github.com/stakater/Reloader#parameters) under the `reloader.reloader` value.

Reloader doesn't inherit [`globals.nodeSelectors`](#nodeselectors) or [`globals.tolerations`](#tolerations). If you run Okteto on dedicated or tainted node pools, set its own scheduling values as shown in [Node selectors and tolerations](#node-selectors-and-tolerations).

## Handling a Long Release Name

The Okteto chart combines the release name and the chart name into a prefix for the names of the Kubernetes resources it creates.

Kubernetes limits the length of resource names. For example, CronJob names can't exceed 52 characters, and Service names can't be longer than 63 characters. Helm also limits release names to 53 characters.

The Okteto chart creates many Kubernetes resources, so it uses specific strategies to stay within these limits and to minimize the need for extra configuration.

The Okteto prefix can be up to 34 characters long: the maximum name length in Kubernetes (63 characters) minus the length of the longest Okteto component suffix (`-ingress-nginx-defaultbackend`). The 34 characters split into 27 for the release name and 7 for the chart name (`-okteto`).

To extend the limit to 40 characters, override the name of the defaultBackend component with the `defaultBackend.nameOverride` value.

For a release name longer than 40 characters, use the [nameOverride](#nameoverride) or [fullnameOverride](#fullnameoverride) settings to shorten the prefix.
