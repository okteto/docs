This guide will walk you through the steps necessary to configure GitHub as the authentication provider for Okteto.

Please refer to [GitHub's official documentation](https://developer.github.com/apps/building-oauth-apps/creating-an-oauth-app/) on how to create an OAuth App for more information.

## Prerequisites

- A working installation of [Okteto](get-started/install/index.mdx)
- [Helm](https://helm.sh/docs/intro/install/) 3.0+ installed in your local machine
- Access to a [GitHub account](https://github.com/) with permissions to create an OAuth App

> If you are planning on using our GitHub Integration for accessing private repositories, you should follow [the guide to configure our GitHub App](self-hosted/install/github.mdx).
You'll then use the same Github Application for the Integration as the one from Oauth.

## Create the OAuth App

When creating the OAuth App, you will need to provide the following values:

**Homepage URL**:

```
https://okteto.DOMAIN
```

**Authorization callback URL**:

```
https://okteto.DOMAIN/auth/callback
```

Copy the `Client ID` and `Client Secret` values. You'll need them to configure Okteto.

## Configure Okteto

Once you have the GitHub OAuth App ready, update the `auth` section of your Helm configuration file with the following values:

```yaml title="config.yaml"
auth:
  github:
    enabled: true
    // highlight-next-line
    clientId: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_ID"
    // highlight-next-line
    clientSecret: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_SECRET"
    // highlight-next-line
    organization: "REPLACE_ME_WITH_YOUR_GITHUB_ORGANIZATION"
```

> You can also use a [secret](self-hosted/helm-configuration.mdx#store-sensitive-configuration-values-using-a-secret) to store the sensitive part of these credentials.

[Upgrade your Okteto instance](self-hosted/manage/upgrade.mdx) for the new configuration to be applied.
We recommend that you upgrade to the same version that you already have to minimize the changes and help you troubleshoot any issues.

The `organization` field is optional but recommended. Setting it restricts login to members of the given GitHub organization, giving you finer control over who can access your Okteto instance. An empty `organization` field permits any user with a GitHub account to log in.

:::warning
If your Okteto instance is publicly reachable, we highly recommend that you set up access restrictions. Leaving the organization field blank lets anyone with a GitHub account log in to your Okteto instance.
::: 


If you want to provide access to users outside of your GitHub organization, you can additionally use the `allowList` key to list the GitHub accounts you want to allow.

```yaml title="config.yaml"
auth:
  github:
    enabled: true
    clientId: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_ID"
    clientSecret: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_SECRET"
    organization: "REPLACE_ME_WITH_YOUR_GITHUB_ORGANIZATION"
    // highlight-next-line
    allowList: ["acct1","acct2","acct3"]
```

## Installing the GitHub App in your organization

When you set the `organization` field, Okteto verifies each user's GitHub organization membership at login and only admits members of that organization. To read that membership, the [Okteto GitHub App](self-hosted/install/github.mdx) must be installed in the organization you configured.

GitHub only exposes a user's organization membership to an installed GitHub App that has the `Members` organization permission set to `Read-only`. The OAuth login flow does not require the App to be installed, so a login can complete while the membership check still fails. When the App is not installed in the configured organization, Okteto cannot confirm that a user belongs to it and rejects the login as unauthorized, even for members of the organization.

To install the App, open `https://github.com/apps/YOUR_GITHUB_APP_NAME/installations/new` and select the organization you set in the `organization` field. This is the same GitHub App you configure for private repository access, so a single App covers both authentication and repository access.

:::info
The `organization` filter and the App installation must point to the same GitHub organization. If you change the `organization` value, install the App in the new organization as well.
:::

## Restricting access to GitHub teams

The `teams` field restricts login to members of specific teams in the GitHub organization set in `organization`. Access is then managed from GitHub: adding a user to one of the teams lets them log in, without changes to your Helm configuration.

```yaml title="config.yaml"
auth:
  github:
    enabled: true
    clientId: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_ID"
    clientSecret: "REPLACE_ME_WITH_YOUR_OAUTH_APP_CLIENT_SECRET"
    organization: "REPLACE_ME_WITH_YOUR_GITHUB_ORGANIZATION"
    // highlight-next-line
    teams: ["platform", "backend"]
```

Each entry is a team slug, the last segment of the team URL. For `https://github.com/orgs/acme/teams/platform`, the slug is `platform`. The `organization` field is required when `teams` is set. The Helm chart fails to render without it, or when an entry isn't a slug, such as a team name with spaces.

:::warning
Okteto doesn't check that the teams exist. GitHub answers the same way for a team that doesn't exist as for a user who isn't a member of it, so a misspelled slug rejects every login with the team error. Copy each slug from the team URL.
:::

At login, Okteto checks the team memberships of the user and admits active members of at least one of the listed teams:

- Members of a child team count as members of its parent team.
- Users with a pending invitation to a team are rejected until they accept it.
- Accounts listed in `allowList` skip the organization and team checks.

Users who aren't members of any of the teams see an error asking them to contact their administrator.

Okteto checks team membership only at login. Removing a user from the teams blocks their next login, but doesn't revoke the sessions and tokens they already have. To remove their access immediately, remove the user from the [Admin Dashboard](admin/dashboard.mdx#users).

### Permissions for reading team membership

GitHub doesn't include team membership in the OAuth response, so Okteto reads it from the GitHub API with the token of the user logging in. The permission it needs depends on the type of app you use for login:

| App type | Required permission |
|----------|---------------------|
| OAuth App | The `read:org` scope. Okteto already requests it when `organization` is set. |
| GitHub App | The `Members` organization permission set to `Read-only`, with the App installed in the organization, as described in [Installing the GitHub App in your organization](#installing-the-github-app-in-your-organization). |

If your GitHub App doesn't have the `Members` permission yet, add it from the App settings in GitHub. An organization owner must accept the updated permissions before they apply to the installation. Until then, GitHub doesn't show the organization to Okteto, and users see an error saying that their account isn't part of the organization, even when they are members.

If your organization restricts access from OAuth Apps, an organization owner must approve the OAuth App. Until then, GitHub hides the organization from Okteto, and users see the same error saying that their account isn't part of the organization.

When GitHub refuses to return a team membership, Okteto rejects the login and writes the GitHub error to the logs of the `okteto-api` pods.
