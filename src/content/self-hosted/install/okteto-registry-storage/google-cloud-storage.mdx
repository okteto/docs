The Okteto Registry can store your container images in Google Cloud Storage.

Create a Cloud Storage bucket in GCP, as described in [Create buckets](https://cloud.google.com/storage/docs/creating-buckets) in the Google Cloud documentation. The default settings work. Make sure your bucket doesn't have public access enabled.

Create a Google Cloud service account with access to your bucket, for example `GSA_NAME@GSA_PROJECT.iam.gserviceaccount.com`. The commands on this page use `$GSA_NAME` and `$GSA_PROJECT` for the name and the project of that service account, and `$GCP_PROJECT` for the project of your GKE cluster.

Run the following command to let the `okteto-registry` Kubernetes service account impersonate that Google Cloud service account through Workload Identity. With the `roles/iam.workloadIdentityUser` role binding, the Kubernetes service account authenticates as the Google Cloud service account, so it accesses the Cloud Storage bucket securely without long-lived service account keys:

```bash
gcloud iam service-accounts add-iam-policy-binding \
  $GSA_NAME@$GSA_PROJECT.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:$GCP_PROJECT.svc.id.goog[okteto/okteto-registry]" \
  --project $GCP_PROJECT
```

This requires [Workload Identity enabled](https://cloud.google.com/kubernetes-engine/docs/how-to/workload-identity#option_2_node_pool_modification) in your cluster. Workload Identity in Google Kubernetes Engine (GKE) secures the communication between Kubernetes workloads and Google Cloud services.

Configure the Okteto Registry to use Workload Identity in your Okteto Helm configuration file:

```yaml title="config.yaml"
registry:
  storage:
    provider:
      gcp:
        enabled: true
        bucket: <bucket-name>
        project: <<your-project-id>>
        workloadIdentity:
          enabled: true
  serviceAccount:
    annotations:
      iam.gke.io/gcp-service-account: "GSA_NAME@GSA_PROJECT.iam.gserviceaccount.com"
```

With Workload Identity, the Okteto Registry serves image layers itself. To have clients download them directly from Cloud Storage instead, grant the Google Cloud service account the `iam.serviceAccounts.signBlob` permission on itself, so the Okteto Registry can sign the URLs it redirects image pulls to. The `roles/iam.serviceAccountTokenCreator` role includes this permission:

```bash
gcloud iam service-accounts add-iam-policy-binding \
  $GSA_NAME@$GSA_PROJECT.iam.gserviceaccount.com \
  --role roles/iam.serviceAccountTokenCreator \
  --member "serviceAccount:$GSA_NAME@$GSA_PROJECT.iam.gserviceaccount.com" \
  --project $GSA_PROJECT
```

Then enable the redirects in your Okteto Helm configuration file:

```yaml title="config.yaml"
registry:
  storage:
    provider:
      gcp:
        workloadIdentity:
          enabled: true
          redirect: true
```

Clients that pull images, such as your Kubernetes nodes, the Okteto Build Service, and developer machines, then download image layers directly from `storage.googleapis.com`, so they need network access to it. Without the permission, image pulls fail with HTTP 500 errors and the Okteto Registry logs `Permission 'iam.serviceAccounts.signBlob' denied`.

[Upgrade your Okteto instance](self-hosted/manage/upgrade.mdx) to apply the new configuration.
Upgrade to the same version you already run: it keeps the changes to a minimum and makes any issue easier to troubleshoot.
