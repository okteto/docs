Okteto creates application environments on your Kubernetes infrastructure: isolated copies of your application, with its real dependencies, for every developer, pull request, and coding agent. They all come from one definition in your repository, so everyone builds, deploys, and tests the application the same way.

Without that definition, developers run the application one way on their laptops, coding agents another way in their sandboxes, and CI a third way with its own scripts. Changes wait for a shared staging environment that other developers and agents are using at the same time, and the issues that only show up with real dependencies don't appear until staging or production.

## Application environments

An [application environment](core/application-environments.mdx) is a running copy of your application in its own Namespace on Kubernetes. It includes your services, the databases and queues that run next to them in the cluster, and the cloud services they use, such as a managed database or a storage bucket.

Okteto supports two models for an environment, and you choose one for each application:

- **Full replica:** the environment runs every service of the application in its own Namespace. Every change is fully isolated, and nothing one environment does affects the others. It's the simplest model, and the right one for most applications.
- **Divert:** the environment deploys only the services that change, and shares a Namespace that runs the rest of the application. A request with the environment's divert header reaches its own services, and the shared version of everything else. For applications with dozens of services, hundreds of environments cost little more than the services that change.

Environments are ephemeral: you create one for a pull request or an agent task, and delete it when the work is done. Every environment gets HTTPS URLs that anyone on the team can open in the browser.

A dedicated environment for every change, with real dependencies, changes how a team tests:

- **Isolation:** developers, coding agents, and pull requests test in parallel, without competing for a shared staging environment or breaking each other's work.
- **Issues that reproduce:** the change runs against the application's real services and dependencies, so integration and configuration issues show up before the code merges, not in staging or in production.
- **Better output from coding agents:** agents exercise the running application. They call its endpoints, run the tests, and read the logs, and they fix what fails before they open a pull request.
- **One standard for every workflow:** developers, agents, and CI use the same definition, so their environments don't drift apart, and a test that fails in CI fails the same way in a developer's environment.

Coding agents such as Claude Code, Codex, Cursor, and GitHub Copilot use the definition through the Okteto skills, which teach them to build, deploy, and test their changes in their own environment. Builds, deployments, and tests run in the cluster, so the agent's sandbox stays light: it needs no Docker daemon and none of your application's dependencies.

## Governance for platform teams

Platform teams set the rules once, and Okteto applies them to every Namespace, including the ones that coding agents create. People sign in with your company's identity provider, and the kubeconfig that the Okteto CLI generates uses time-bound tokens, so nobody creates, distributes, or rotates cluster credentials.

Every developer, coding agent, and pull request works in its own Namespaces, isolated from the others:

- **RBAC:** Developers manage their own Namespaces, and Admins manage every Namespace and the platform.
- **Quotas:** a limit on CPU, memory, pods, and storage for each Namespace.
- **Network policies:** isolate the traffic of each Namespace, and block destinations such as the cloud metadata service.
- **Cloud and Registry Credentials:** deploy commands reach your cloud account and your private registries without anyone holding static keys.

With an environment for every developer, pull request, and agent task, a team runs hundreds of them at the same time, and most sit idle most of the day. Okteto keeps their cost close to what's actually in use:

- **Garbage Collector:** sleeps idle environments, and deletes the ones nobody uses.
- **Resource Manager:** sets the CPU and memory requests of each service from its real usage.
- **Smart Builds:** reuse an image when someone has already built it from the same code.
- **Okteto Insights:** dashboards with build times, deploy frequency, and resource usage across the cluster.

## Next steps

Okteto runs in your own Kubernetes cluster, including clusters in air-gapped networks. Where you start depends on your role:

- **Platform teams:** [install Okteto in your cluster](get-started/install/index.mdx) with its Helm chart, then [deploy your first application](get-started/deploy-your-app/index.mdx): you write its definition and create its first environment, ready for developers, coding agents, and pull requests.
- **Developers:** if your platform team already runs Okteto, [deploy your first application](get-started/deploy-your-app/index.mdx) and code against it in your own environment.
- **Coding agents:** [install the Okteto skills](agentic/index.mdx) in Claude Code, Codex, Cursor, or another agent, so it deploys and tests its changes in its own environment.
