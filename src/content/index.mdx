Okteto gives every application one standard environment definition in its repository, and creates the environments from it on your Kubernetes infrastructure, the same way for developers, for CI, and for coding agents, whatever agent or system runs them. Without it, developers run the application one way on their laptops, agents another way in their sandboxes, and CI another one with its own scripts. Changes wait for a shared staging environment that other developers and agents are using at the same time, and the issues that only show up with the real dependencies of the application can't be reproduced until they reach staging or production.

Each environment is an isolated copy of your application with its real dependencies: the databases, queues, and data services that run in Kubernetes next to your services, and the cloud services, such as a managed database or a storage bucket, that your cloud provider runs for it. That's what makes the environments useful for testing a change:

- **Isolation:** every change gets its own environment, so developers, coding agents, and pull requests test in parallel without competing for a shared staging environment or breaking each other's work.
- **Issues that reproduce:** the change runs against the real services and dependencies of the application, so integration and configuration issues show up, and reproduce, before the code merges, not in staging or in production.
- **Better output from coding agents:** agents exercise the running application in Kubernetes. They call its endpoints, run the tests, and read the logs, and fix what fails before they open a pull request.
- **One standard for every workflow:** the same definition creates the environments of developers, agents, and CI, so they don't drift apart, "it works on my machine" goes away, and a test that fails in CI fails the same way in a developer's environment.

## Application environments

An [application environment](core/application-environments.mdx) is a running copy of your application on Kubernetes. Its definition is a file in your repository, the Okteto Manifest (`okteto.yaml`), with three parts:

- **Build:** the images of your services. Okteto builds them in the cluster with BuildKit, so nobody needs a Docker daemon on their machine or in their sandbox.
- **Deploy:** the commands that deploy the application with the Helm charts, Kubernetes manifests, or Docker Compose files you already use, and that create its cloud resources, such as a managed database or a storage bucket. Okteto runs them in the cluster.
- **Test:** the containers that run your unit, integration, and end-to-end tests against the running environment.

Every environment gets HTTPS URLs that anyone on the team can open in the browser.

Coding agents such as Claude Code, Codex, Cursor, and GitHub Copilot use the same definition through the Okteto skills, which teach them to build, deploy, and test their changes in their own environment. The builds, deployments, and tests run in the cluster, so the sandbox of the agent stays light, with no Docker daemon and none of the dependencies of your application.

Okteto supports two models for an environment, and you choose one per application:

- **Full replica:** the environment runs every service of the application in its own namespace. Every change is fully isolated, and nothing one environment does affects the others. It's the simplest model, and the right one for most applications.
- **Divert:** the environment deploys only the services that change, and shares a namespace that runs the rest of the application. A request with the divert header of the environment reaches its own services and the shared version of everything else. For applications with dozens of services, hundreds of environments cost little more than the services that change.

## Governance and scale

Every developer, coding agent, and pull request works in its own Namespaces, isolated from the others. People sign in with the identity provider of your company, and the kubeconfig that the Okteto CLI generates uses time-bound tokens, so the platform team doesn't create, distribute, or rotate cluster credentials. The platform team sets the rules once, and they apply to every Namespace, including the ones that coding agents create:

- **RBAC:** Developers manage their own Namespaces, and Admins manage every Namespace and the platform.
- **Quotas:** a limit of CPU, memory, pods, and storage for each Namespace.
- **Network policies:** isolate the traffic of each Namespace and block destinations such as the cloud metadata service.
- **Cloud and Registry Credentials:** deploy commands reach your cloud account and your private registries without anyone holding static keys.

With an environment for every developer, pull request, and agent task, a team runs hundreds of them at the same time, and most sit idle most of the day. Okteto keeps their cost close to what's actually in use:

- **Garbage Collector:** sleeps idle environments and deletes the ones nobody uses.
- **Resource Manager:** sets the CPU and memory requests of each service from its real usage.
- **Smart Builds:** reuse an image when someone has already built it from the same code.
- **Okteto Insights:** dashboards with build times, deploy frequency, and resource usage across the cluster.

## Getting started

Okteto runs in your own Kubernetes cluster, including clusters in air-gapped networks. Where you start depends on your role:

- **Platform teams:** [install Okteto in your cluster](get-started/install/index.mdx) with its Helm chart, then [deploy your first application](get-started/deploy-your-app/index.mdx): you write its definition and create its first environment, ready for developers, coding agents, and pull requests.
- **Developers:** if your platform team already runs Okteto, [deploy your first Development Environment](get-started/dev-quickstart.mdx) and code against the running application.
- **Coding agents:** [install the Okteto skills](agentic/index.mdx) in Claude Code, Codex, Cursor, or another agent, so it deploys and tests its changes in its own environment.
