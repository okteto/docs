Developers run an application one way on their laptops, coding agents another way in their sandboxes, and CI a third way with its own scripts. Often none of them runs the application with its real dependencies, so the first real test of a change happens in a shared staging environment. Changes queue up for it, and integration issues stay hidden until staging or production.

Okteto creates application environments on your Kubernetes infrastructure, on demand: isolated copies of your application, with its real dependencies, for every developer, pull request, and coding agent. They all come from one definition in your repository, so everyone builds, deploys, and tests the application the same way.

## Application Environments

An [application environment](application-environments/index.mdx) is a running copy of your application in its own Namespace on Kubernetes. It includes your services and their dependencies, such as databases and queues.

Okteto supports two models for an environment, and you choose one for each application.

**Full replica:** the environment runs every service of the application in its own Namespace, so nothing one environment does affects the others. For an application with fewer than 20 services, full replicas are simpler to configure and give you full isolation.

<Image
  src={require("@site/static/img/environment-full-replica.webp").default}
  mobileSrc={require("@site/static/img/environment-full-replica-mobile.webp").default}
  borderless
  alt="Full replica: a developer and a coding agent each have their own application environment, an Okteto Namespace that runs the whole application: its API gateway, the Rent service and its MongoDB database, and the Catalog service and its MongoDB database"
/>

**Overlay Namespace:** the environment deploys only the services that change in an Overlay Namespace, and relies on a Shared Namespace for the rest of the application. [Divert](application-environments/divert/index.mdx) routes requests between the two: a request that carries the environment's divert header reaches the environment's own services, and the shared version of everything else. For an application with 20 services or more, Overlay Namespaces are more cost-effective, faster to deploy, and more reliable.

## Benefits

With Okteto, application environments on Kubernetes give your team:

- **One standard for every workflow:** developers, agents, and CI use the same definition, so their environments don't drift apart, and a test that fails in CI fails the same way in a developer's environment or in a coding agent's sandbox.
- **Isolation:** developers, coding agents, and pull requests test in parallel, without competing for a shared staging environment or breaking each other's work.
- **Issues caught before the merge:** every change runs on Kubernetes, against the application's real services and dependencies, so integration and configuration issues show up before the code merges, not in staging or in production.
- **A light setup everywhere:** Okteto runs builds, deployments, and tests as containers inside the cluster: builds with the [Okteto Build Service](application-environments/build-service.mdx), and deployments and tests with [Remote Execution](reference/remote-execution.mdx). You don't need Docker or the dependencies of your programming language to test your application. A laptop, a CI job, and an agent sandbox only need the Okteto CLI.

## Operating at Scale

When every developer, pull request, and agent task gets its own application environment, a platform team has hundreds, if not thousands, of them to operate. Okteto helps the platform team operate them at scale: the team sets the rules once, and Okteto applies them to every application environment, including the ones that coding agents create. Okteto generates time-bound tokens for every application environment, so nobody has to create, distribute, or rotate credentials.

Governance keeps every application environment within its limits, so none of them uses or reaches more than the platform team allows:

- **RBAC:** the platform team defines what Developers can do in their Namespaces.
- **Quotas:** a limit on CPU, memory, pods, and storage for each Namespace.
- **Network policies:** isolate the traffic of each Namespace, and block destinations such as the cloud metadata service.

With that many environments building, deploying, and testing all day, Okteto keeps the use of your infrastructure efficient:

- **[Garbage Collector](admin/cleanup.mdx):** sleeps the environments that nobody is using, and deletes the ones that are abandoned.
- **[Resource Manager](admin/resource-manager.mdx):** sets the CPU and memory requests of each service from its real usage.
- **[Okteto Insights](admin/okteto-insights.mdx):** shows the platform team where the bottlenecks are, with dashboards of build times, deploy frequency, and resource usage across the cluster.
- **[Smart Builds](reference/smart-builds.mdx):** skip work that's already done, and reuse an image when someone has already built it from the same code.

## Next Steps

Okteto runs in your own Kubernetes cluster, including clusters in air-gapped networks. Where you start depends on what you want to do:

- **[Install Okteto](get-started/install/index.mdx):** platform teams install Okteto in their Kubernetes cluster with the Okteto Helm chart.
- **[Quickstart](get-started/quickstart.mdx):** launch your first application environment, and build, deploy, and test a sample application with a frontend, an API, and a database.
- **[Use coding agents](coding-agents/okteto-skills.mdx):** install the Okteto skills in Claude Code, Codex, Cursor, or another agent, so it deploys and tests its changes in its own environment.
- **[Test every pull request](previews/index.mdx):** configure Preview Environments with GitHub Actions, GitLab CI/CD, or any other CI tool, so every pull request deploys its own environment and runs your tests against it.
