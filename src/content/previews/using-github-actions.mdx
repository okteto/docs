GitHub Actions deploys a Preview Environment for every pull request with the GitHub Actions for Okteto. Two workflows do it: one deploys the Preview Environment and runs your tests against it when a pull request opens or changes, and the other destroys it when the pull request closes.

## Prerequisites

- An Okteto instance, and an Admin who can create an [Admin Access Token](admin/admin-access-tokens.mdx) for it.
- A [GitHub account](https://github.com).

The steps use the [Movies app](https://github.com/okteto/getting-started) of [Deploy your app](get-started/deploy-your-app/index.mdx). Fork the repository to your GitHub account so you can configure secrets and open pull requests. GitHub turns off the workflows of a fork: open the **Actions** tab of your fork and enable them. If you're using your own application, make sure your Okteto Manifest defines the [`deploy`](application-environments/okteto-manifest.mdx#deploy) and [`test`](application-environments/okteto-manifest.mdx#test) sections.

## Step 1: Create the Workflow

Whenever a pull request opens or changes, this workflow deploys a Preview Environment with the code of the pull request, and comments its URL on the pull request.

Create a `.github/workflows` folder in the root of your repository and save the following workflow file in it. The sample repository already includes the [final version of this workflow](https://github.com/okteto/getting-started/blob/main/.github/workflows/preview.yaml), with the test steps you add in [Step 4](#step-4-run-your-tests-on-every-pull-request).

```yaml
# file: .github/workflows/preview.yaml
on:
  pull_request:
    branches:
      - main

permissions:
  contents: read
  pull-requests: write

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - name: Context
        uses: okteto/context@latest
        with:
          url: ${{ secrets.OKTETO_CONTEXT }}
          token: ${{ secrets.OKTETO_TOKEN }}

      - name: Deploy preview environment
        uses: okteto/deploy-preview@latest
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          name: pr-${{ github.event.number }}
          timeout: 15m
```

What each step does:

- `okteto/context` connects the workflow to your Okteto instance.
- `okteto/deploy-preview` deploys the Preview Environment `pr-<number>` with the `deploy` section of your Okteto Manifest, and comments its URL on the pull request.

The `permissions` block lets the `GITHUB_TOKEN` of the workflow comment on the pull request. Without it, repositories with restricted default permissions for workflows reject the comment.

:::warning
Keep `cancel-in-progress: false` in the [`concurrency`](https://docs.github.com/en/actions/using-workflows/workflow-syntax-for-github-actions#concurrency) block. With `true`, a new commit cancels the deployment in progress, which can leave the Preview Environment half deployed, leak resources in your cluster, or break its cleanup. The `concurrency` group queues the runs of each pull request, so two deployments never update the same Preview Environment at once. To skip a queued run, cancel it from the GitHub UI before it starts.
:::


## Step 2: Configure Your Secrets

The workflow reads your Okteto credentials from the `secrets.OKTETO_TOKEN` and `secrets.OKTETO_CONTEXT` secrets, so you don't commit them to your repository.

Create the following secrets in your repository:

- `OKTETO_TOKEN`: an Okteto [Admin Access Token](admin/admin-access-tokens.mdx).
- `OKTETO_CONTEXT`: the URL of your Okteto instance, for example `https://okteto.example.com`.

See [Using secrets in GitHub Actions](https://docs.github.com/en/actions/security-guides/using-secrets-in-github-actions#creating-secrets-for-a-repository) to add them to your repository.

The workflow also uses `secrets.GITHUB_TOKEN`, which GitHub populates automatically.

## Step 3: Open a Pull Request

Make a change in a new branch of your repository and open a pull request against `main`. On a fork, open the pull request against your fork, not the original repository: GitHub preselects the original one, and your secrets only exist in your fork. GitHub receives the event and starts your workflow. You can see the workflow's status and logs in the **Checks** section of the pull request.

## Step 4: Run Your Tests on Every Pull Request

Your automated tests run against the Preview Environment of every pull request, with [Okteto Test](application-environments/okteto-test.mdx). The Okteto Manifest of the Movies app defines two tests: `frontend` runs the frontend unit tests, and `e2e` runs [Playwright](https://playwright.dev/) end-to-end tests against the deployed application and exports their reports as artifacts:

```yaml title="okteto.yaml"
test:
  frontend:
    image: node:20
    context: frontend
    caches:
      - yarn/.cache
      - node_modules
    commands:
      - yarn install
      - yarn test

  e2e:
    image: ghcr.io/okteto/playwright:chromium
    context: e2e
    caches:
      - yarn/.cache
      - node_modules
    commands:
      - bash run_tests.sh
    artifacts:
      - test-results
      - playwright-report
```

Add the following steps at the end of the `preview` job in your `.github/workflows/preview.yaml` file:

```yaml
      - name: Checkout code
        uses: actions/checkout@v7

      - name: Run tests
        uses: okteto/test@latest
        with:
          namespace: pr-${{ github.event.number }}

      - name: Save Playwright report
        uses: actions/upload-artifact@v7
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: e2e/playwright-report/
          retention-days: 30
```

What each step does:

- `actions/checkout` clones the repository so the `okteto/test` action can read your Okteto Manifest and send the test `context` to Okteto.
- `okteto/test` runs the tests in the [`test` section](application-environments/okteto-manifest.mdx#test) of your Okteto Manifest, in the Namespace of the Preview Environment. The `namespace` value must match the `name` of the `okteto/deploy-preview` step. To run only some tests, use the `tests` input, for example `tests: e2e`.
- `actions/upload-artifact` attaches the Playwright report exported through the `artifacts` field to the workflow run. The `if: ${{ !cancelled() }}` condition uploads it even when a test fails, so you can inspect the results of a failed run.

The `okteto/test` action also accepts the `timeout` input (default `5m`), `variables` to pass variables to your tests, `no-cache` to ignore the `caches` of your tests, and `file` to set the path of your Okteto Manifest. See the [`okteto test` reference](reference/okteto-cli.mdx#test) for the behavior of each option.

Every pull request now runs the same tests that developers and coding agents run with `okteto test` against their own application environments. They iterate on the tests without pushing changes and waiting for CI, and the tests behave the same way when they run in CI.

## Step 5: Check Your Test Results

Push the workflow change to the branch of your pull request. The workflow redeploys the Preview Environment and runs your tests against it.

The `Run tests` step shows the output of each test. When a test fails, the step fails and the check on the pull request shows the failure, so you can block merging until the tests pass.

The Playwright report is available as the `playwright-report` artifact in the summary of the workflow run, for both passing and failing runs. The Preview Environment keeps running after the tests finish, so your team can still open it to review the changes.

## Step 6: Cleanup

The sample repository also includes a workflow [to destroy the Preview Environment](https://github.com/okteto/getting-started/blob/main/.github/workflows/preview-closed.yaml) when the pull request is closed or merged. Add it to your repository to remove Preview Environments automatically:

```yaml
# file: .github/workflows/preview-closed.yaml
on:
  pull_request:
    types:
      - closed

jobs:
  closed:
    runs-on: ubuntu-latest
    steps:
      - name: Context
        uses: okteto/context@latest
        with:
          url: ${{ secrets.OKTETO_CONTEXT }}
          token: ${{ secrets.OKTETO_TOKEN }}

      - name: Destroy preview environment
        uses: okteto/destroy-preview@latest
        with:
          name: pr-${{ github.event.number }}
```

## GitHub Actions for Okteto

The workflows on this page use the GitHub Actions for Okteto. They're all in the [GitHub Marketplace](https://github.com/marketplace?type=actions&query=okteto), and each one runs an Okteto CLI command:

- [Context](https://github.com/marketplace/actions/okteto-context) (`okteto/context`): connects the workflow to your Okteto instance.
- [Build](https://github.com/marketplace/actions/okteto-build) (`okteto/build`): builds an image with the Okteto Build Service.
- [Deploy Pipeline](https://github.com/marketplace/actions/okteto-pipeline) (`okteto/pipeline`): deploys an application from a Git repository.
- [Destroy Pipeline](https://github.com/marketplace/actions/destroy-okteto-pipeline) (`okteto/destroy-pipeline`): destroys an application deployed from a Git repository.
- [Deploy Preview](https://github.com/marketplace/actions/deploy-preview-environment) (`okteto/deploy-preview`): deploys a Preview Environment.
- [Destroy Preview](https://github.com/marketplace/actions/destroy-preview-environment) (`okteto/destroy-preview`): destroys a Preview Environment.
- [Test](https://github.com/marketplace/actions/okteto-test) (`okteto/test`): runs the tests of your Okteto Manifest.
- [Create Namespace](https://github.com/marketplace/actions/create-namespace) (`okteto/create-namespace`): creates a Namespace.
- [Activate Namespace](https://github.com/marketplace/actions/activate-namespace) (`okteto/namespace`): sets the Namespace that the next steps use.
- [Delete Namespace](https://github.com/marketplace/actions/delete-namespace) (`okteto/delete-namespace`): deletes a Namespace.

Each action has these tags:

| Tag | Okteto CLI version |
|-----|--------------------|
| `latest` | The latest stable release. |
| `v3` | The latest stable 3.x release. |
| <code>v{cliMinor}</code> | The latest patch release of {cliMinor}. |
| <code>{variables.cliVersion}</code> | Exactly {variables.cliVersion}. |
