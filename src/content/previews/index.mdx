Preview Environments automatically create a live, production-like instance of your application for every pull request or merge request. Your CI/CD pipeline deploys the Preview Environment and runs your automated tests against it, so every change is tested in a real environment before it merges to main.

The Okteto UI lists all Preview Environments with their repository, branch, pull request, owner, and status. You can filter the list by name, repository, status, owner, or last update, and sort it. Admins can also manage Preview Environments from the [Admin Dashboard](admin/previews.mdx).

## How It Works

Preview Environments follow the lifecycle of a pull request or merge request:

1. **Open a Pull Request or Merge Request**: when you create or update a pull request in GitHub or a merge request in GitLab, your CI/CD pipeline triggers an Okteto Preview Environment.
2. **Deployment**: Okteto deploys your application with the [`deploy`](core/okteto-manifest.mdx#deploy) section of your Okteto Manifest, the same section `okteto deploy` runs for your Development Environment. To change how your application behaves in a Preview Environment, see [How do I customize my application for Preview Environments?](reference/faqs.mdx#how-do-i-customize-my-application-for-preview-environments).
3. **Automated Tests**: your pipeline runs `okteto test` against the Preview Environment and reports the result on the pull request or merge request.
4. **Share and Collaborate**: the Preview Environment keeps running after the tests finish, so you can share its URL with your team for manual testing and feedback.
5. **Updates**: every new commit redeploys the Preview Environment and reruns your tests.
6. **Cleanup**: your pipeline destroys the Preview Environment when the pull request closes in GitHub, or when the merge request's branch is deleted in GitLab.
