Preview Environments are application environments for pull requests. For every pull request in GitHub or merge request in GitLab, your CI pipeline deploys the application with the change in its own Namespace, runs your tests against it, and links its URL from the pull request, so your team reviews the running change before it merges. When the pull request closes, the pipeline destroys the Preview Environment.

The Okteto UI lists every Preview Environment with its repository, branch, pull request, owner, and status. You can filter the list by name, repository, status, owner, or last update, and sort it. The menu (**⋯**) of each row puts the Preview Environment to sleep (**Put To Sleep**) or wakes it up (**Wake Up**). Any Developer can [wake a Preview Environment](admin/user-roles-and-permissions.mdx#access-to-global-preview-environments), but only its owner and Admins put it to sleep. Admins manage every Preview Environment of the instance from the [Admin Dashboard](admin/previews.mdx).

Set up Preview Environments with your CI system:

- [GitHub Actions](previews/using-github-actions.mdx): deploy a Preview Environment and run your tests on every pull request.
- [GitLab CI/CD](previews/using-gitlab-cicd.mdx): deploy a Preview Environment and run your tests on every merge request.
- [Other CI tools](previews/using-other-ci-tools.mdx): do the same from any CI tool, with three Okteto CLI commands.

## How Preview Environments Work

A Preview Environment follows the lifecycle of its pull request or merge request:

1. **Open:** when you open or update a pull request, your CI pipeline deploys a Preview Environment for it.
2. **Deploy:** Okteto deploys your application with the [`deploy`](application-environments/deploy.mdx) section of your Okteto Manifest, the same one that `okteto deploy` runs for any application environment. Your `deploy` commands see the [`OKTETO_IS_PREVIEW_ENVIRONMENT`](application-environments/okteto-variables.mdx#default-environment-variables) variable set to `true`, so they can change how the application runs in a Preview Environment. The Okteto Community forum has [examples](https://community.okteto.com/t/how-do-i-customize-my-application-for-preview-environments/1496).
3. **Test:** your pipeline runs [`okteto test`](application-environments/okteto-test.mdx) against the Preview Environment, and reports the result on the pull request.
4. **Review:** the Preview Environment keeps running after the tests, so your team opens its URL to try the change and leaves feedback on the pull request.
5. **Update:** every new commit redeploys the Preview Environment and runs your tests again.
6. **Clean up:** your pipeline destroys the Preview Environment when the pull request closes in GitHub, or when the merge request's branch is deleted in GitLab.

## The Same Tests as Developers and Coding Agents

In many teams, developers run the application on their laptops with Docker Compose, CI runs the tests on a virtual machine, and production runs on Kubernetes. Each stage has its own platform and its own configuration, so tests pass locally and fail in CI, and some bugs only show up in production.

The tests in the [`test` section](application-environments/okteto-test.mdx) of your Okteto Manifest run the same way against a developer's environment, an agent's environment, and the Preview Environment, so a test that fails in CI fails the same way on a developer's machine.

## A URL for Every Change

A Preview Environment is a running copy of the change, with its own HTTPS URL. Your automated tests, coding agents, developers, QA engineers, product managers, designers, and sales and marketing all use the same running application, with nothing to set up. Instead of screenshots or recordings, everyone tries the real change and gives feedback on the pull request before it merges.

## Light CI Jobs

A common way to run end-to-end tests in CI is to run the whole application inside the CI job: the job starts a Docker daemon, builds every image, starts the application with Docker Compose, and installs the test runtimes, browsers, and credentials that your tests need.

<Image
  src={require("@site/static/img/previews-ci-docker.webp").default}
  mobileSrc={require("@site/static/img/previews-ci-docker-mobile.webp").default}
  borderless
  alt="A fat CI job: the CI runner holds test runtimes, browsers, and credentials, and a Docker daemon runs the frontend, api, and mongoDB services"
/>

These CI jobs are heavy. They need privileged runners or access to the Docker socket, a common security concern. They rebuild the images and reinstall the dependencies on every run, and they run your application on a different platform than production.

With Okteto, the CI job only needs a Git checkout and the Okteto CLI. Okteto builds your images, deploys your application, and runs your tests inside your Kubernetes cluster, with [Remote Execution](reference/remote-execution.mdx).

<Image
  src={require("@site/static/img/previews-ci-okteto.webp").default}
  mobileSrc={require("@site/static/img/previews-ci-okteto-mobile.webp").default}
  borderless
  alt="A light CI job with only a Git checkout and the Okteto CLI, connected to a Preview Environment in its Okteto Namespace on Kubernetes, which runs the frontend, api, and mongoDB services and the frontend and e2e tests of Okteto Test"
/>

- CI jobs start faster and use fewer resources, because they don't run Docker or your application.
- [Smart Builds](application-environments/build-service.mdx#smart-builds) reuse the images that a pipeline, a developer, or an agent already built from the same code.
- The load on your CI system drops, because builds, deployments, and tests run in your cluster.
