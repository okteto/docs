**Admin > Build Service** shows the BuildKit pods that run the Okteto Build Service, with the metrics and status of each one. From there, Admins set the resource thresholds for the pods and restart a pod.

## Overview

The Okteto Build Service uses BuildKit to build images and to run [Remote Execution](application-environments/remote-execution.mdx). **Admin > Build Service** shows the health of the BuildKit pods, their resource usage, and their active builds.

To tune BuildKit for many builds, see [BuildKit High Performance](self-hosted/install/buildkit-high-performance.mdx).

## Build queue

The build queue routes each build to the least loaded BuildKit pod, and holds builds while every pod is at capacity. This prevents overload at peak times and keeps build times predictable.

The build queue is on by default. To turn it off, set the `OKTETO_BUILD_QUEUE_ENABLED` [feature flag](reference/feature-flags.mdx) to `false`.

## Metrics

The table shows these metrics for each BuildKit pod:

- **CPU Pressure**: how long processes waited for CPU over the last 10 seconds. A value above 50% can signal that builds are slowing down.
- **Memory Usage**: the percentage of the pod's memory in use. A value close to 70% raises the risk of Out-Of-Memory (OOM) kills.
- **I/O Pressure**: how long processes waited for I/O over the last 10 seconds. A value above 30% can signal that builds are slowing down.
- **Active Builds**: the number of builds that the pod runs at the same time.

### Configurable Thresholds

You set these thresholds in **Admin > Build Service**:

#### CPU Pressure Threshold

- **Default**: 50%
- **Description**: The maximum CPU pressure before Okteto marks a BuildKit pod as busy. CPU pressure is measured over 10-second intervals and shows how constrained the pod is on CPU.
- **When to adjust**: Increase it if builds wait in the queue while CPU usage is acceptable. Decrease it if builds slow down at the current value.

#### Memory Usage Threshold {#memory-pressure-threshold}

- **Default**: 70%
- **Description**: The maximum memory usage before Okteto marks a BuildKit pod as busy, as a percentage of the pod's memory.
- **When to adjust**: Increase it if the pods have spare memory and you want to use more of it. Decrease it if the pods hit OOM kills.

#### I/O Pressure Threshold {#iops-pressure-threshold}

- **Default**: 30%
- **Description**: The maximum I/O pressure before Okteto marks a BuildKit pod as busy. I/O pressure is measured over 10-second intervals and shows disk I/O contention.
- **When to adjust**: Increase it if your nodes use high-performance SSDs with more I/O capacity. Decrease it if builds slow down because of I/O.

### Pod Status

Each BuildKit pod shows one of these statuses:

- **Ready**: The pod is healthy and below every threshold.
- **Busy**: One or more metrics are above their threshold.
- **Starting**: The pod is starting and doesn't accept builds yet.
- **Stopping**: The pod is shutting down and lets its active builds finish.
- **Error**: The pod has an error.

### Restarting a BuildKit Pod

Admins can restart a BuildKit pod from **Admin > Build Service**. Okteto deletes the pod and creates a new one.

#### Reasons to Restart

- **Stuck builds**: A build shows no progress.
- **Repeated failures**: Builds keep failing on one pod.
- **Pod errors**: The pod shows the **Error** status and doesn't recover on its own.
- **Slow pod**: A pod performs worse than the others.

#### Effects of a Restart

- **Active builds are retried**: The builds that run on the pod are retried on another pod, or on the same pod once Okteto recreates it.
- **Queued builds are rerouted**: If the build queue is on, the builds waiting for the pod go to other pods.
- **The cache is kept**: The build cache is stored on a persistent volume, so it survives the restart.
- **Recovery time**: The new pod is usually ready in 30 to 60 seconds.

#### Restart Steps

1. Find the pod in the table of **Admin > Build Service**.
2. Click **Restart**.
3. Read the confirmation dialog and click **Delete and recreate**.

## Best Practices

### Threshold Configuration

- **Start with the defaults**: The default thresholds (50% CPU, 70% memory, 30% I/O) work for most workloads.
- **Monitor and adjust**: Watch the metrics over time and adjust the thresholds to match how your builds perform.
- **Balance usage and speed**: Higher thresholds use more of each pod's resources, but builds can get slower.
