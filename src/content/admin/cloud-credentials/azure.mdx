Azure Cloud Credentials let the commands in your Okteto Manifests authenticate to Microsoft Azure with your Okteto cluster's identity, without client secrets.
They use [Microsoft Entra workload identity federation](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation): an App Registration in your Entra tenant trusts a short-lived token that your Kubernetes cluster issues, and the Azure roles you grant to that App Registration define what the commands can do.

This page grants access to Azure Blob Storage in a resource group. To grant access to other Azure resources, assign the roles they require.

## Injected Environment Variables

When Azure Cloud Credentials are enabled, Okteto adds these environment variables to the commands of `okteto deploy`, `okteto destroy`, and `okteto test`:

| Variable | Value |
|----------|-------|
| `AZURE_TENANT_ID` | The Directory (tenant) ID configured in the Admin Dashboard |
| `AZURE_CLIENT_ID` | The Application (client) ID configured in the Admin Dashboard |
| `AZURE_AUTHORITY_HOST` | The authority host configured in the Admin Dashboard, `https://login.microsoftonline.com/` by default |
| `AZURE_FEDERATED_TOKEN_FILE` | The path to a file with a Kubernetes service account token for the Okteto cluster's identity, issued for the configured audience and valid for one hour |

[Azure Kubernetes Service workload identity](https://learn.microsoft.com/en-us/azure/aks/workload-identity-overview) uses the same variables, so the Azure SDKs (`DefaultAzureCredential` and `WorkloadIdentityCredential`) authenticate without extra configuration.
Unlike Okteto Cloud Credentials for [AWS](admin/cloud-credentials/aws.mdx) and [Google Cloud](admin/cloud-credentials/gcp.mdx), Okteto doesn't exchange the token for a cloud access token: Azure access tokens are scoped to a single resource, so each tool requests the token for the resource it needs.

:::note
Azure Cloud Credentials require Okteto CLI 3.25.0 or later. Earlier versions of the Okteto CLI receive `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and `AZURE_AUTHORITY_HOST`, but not `AZURE_FEDERATED_TOKEN_FILE`.
:::

:::danger
Every user who can run `okteto deploy` in your Okteto instance receives the federated token. Keep it limited to Azure:

- Use `api://AzureADTokenExchange` as the audience. The token belongs to the Okteto service account, which has admin access to your cluster, so Okteto refuses audiences that your Kubernetes API server accepts, such as your cluster's OIDC issuer URL, or `https://kubernetes.default.svc` on distributions that list it as an API server audience.
- Only add a federated credential for the Okteto service account to the App Registration you configure in Okteto. The token gives access to any App Registration that trusts the same issuer, subject, and audience.
:::

## Step 1: Getting your cluster's OIDC configuration

Azure validates the federated token against your Kubernetes cluster's OIDC issuer, which must be reachable from the internet.
To get the issuer and the Okteto service account's subject, click **Show Details** in the **OpenID Connect (OIDC)** row of [**Admin > Integrations > General**](admin/integrations.mdx#openid-connect-oidc):

<p align="center">
  <Image

    alt="The OpenID Connect (OIDC) row of the General Integrations section of the Admin Dashboard, with the issuer and the subject"
  />
</p>

Store these values as environment variables for the next steps:

```bash
export OIDC_ISSUER=https://<your-cluster-oidc-issuer>
export OKTETO_SERVICE_ACCOUNT=system:serviceaccount:okteto:okteto
```

## Step 2: Creating the App Registration

:::info
The commands on this page use the [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli). Install it and run `az login` first.
:::

The App Registration is the identity the commands in your Okteto Manifests act as. It doesn't need a client secret.

```bash
export APP_ID=$(az ad app create --display-name okteto-cloud-credentials --query appId -o tsv)
export APP_OBJECT_ID=$(az ad app show --id ${APP_ID} --query id -o tsv)
export TENANT_ID=$(az account show --query tenantId -o tsv)
```

Next, create the App Registration's service principal. Azure role assignments target the service principal:

```bash
az ad sp create --id ${APP_ID}
```

`APP_ID` is the Application (client) ID you configure in Okteto. `APP_OBJECT_ID` is only used to manage the App Registration.

## Step 3: Adding the federated credential

The federated credential tells Entra ID to trust tokens issued by your cluster for the Okteto service account:

```bash
az ad app federated-credential create --id ${APP_OBJECT_ID} --parameters "{
  \"name\": \"okteto\",
  \"issuer\": \"${OIDC_ISSUER}\",
  \"subject\": \"${OKTETO_SERVICE_ACCOUNT}\",
  \"audiences\": [\"api://AzureADTokenExchange\"]
}"
```

## Step 4: Assigning Azure roles

Grant the service principal the roles it needs. For example, to create storage accounts and manage blobs in a resource group:

```bash
export RESOURCE_GROUP_ID=$(az group show --name my-resource-group --query id -o tsv)

az role assignment create --assignee ${APP_ID} --role "Storage Account Contributor" --scope ${RESOURCE_GROUP_ID}
az role assignment create --assignee ${APP_ID} --role "Storage Blob Data Contributor" --scope ${RESOURCE_GROUP_ID}
```

Role assignments can take a few minutes to take effect.

## Step 5: Configuring Azure Cloud Credentials in Okteto

You can configure Cloud Credentials in two ways:

- **In the Admin Dashboard**, as [Adding Cloud Credentials Through the Admin Dashboard](#adding-cloud-credentials-through-the-admin-dashboard) explains.
- **With a CRD**, as [Cloud Credentials CRDs](self-hosted/manage/crds.mdx#cloud-credentials) explains.

:::note
The Admin Dashboard shows the credentials you add with CRDs, but you can't change them from the Admin Dashboard.
:::

### Adding Cloud Credentials Through the Admin Dashboard

Go to [**Admin > Integrations > Cloud Credentials**](admin/cloud-credentials/index.mdx) and click **Enable** in the **Azure Workload ID** row.

Enter these values:

- **Tenant ID**: your Entra tenant's Directory (tenant) ID, `TENANT_ID`.
- **Client ID**: the Application (client) ID, `APP_ID`, of the App Registration from [Step 2: Creating the App Registration](#step-2-creating-the-app-registration). Not the Object ID.
- **Audience JWT Claim**: `api://AzureADTokenExchange`, the audience of the federated credential from [Step 3: Adding the federated credential](#step-3-adding-the-federated-credential).
- **Authority Host**: only needed for sovereign clouds, such as `https://login.microsoftonline.us/` for Azure Government. Leave it empty for the Azure public cloud.

## Azure CLI and Terraform

The Azure CLI doesn't read the injected variables by itself. Log in with the federated token before running other `az` commands:

```bash
az login --service-principal \
  --username "$AZURE_CLIENT_ID" \
  --tenant "$AZURE_TENANT_ID" \
  --federated-token "$(cat "$AZURE_FEDERATED_TOKEN_FILE")"
```

Add `--allow-no-subscriptions` if the App Registration has no role assigned on any subscription.

The Terraform AzureRM provider uses its own `ARM_*` environment variables. Map the injected variables before running Terraform:

```bash
export ARM_USE_OIDC=true
export ARM_TENANT_ID="$AZURE_TENANT_ID"
export ARM_CLIENT_ID="$AZURE_CLIENT_ID"
export ARM_OIDC_TOKEN_FILE_PATH="$AZURE_FEDERATED_TOKEN_FILE"
export ARM_SUBSCRIPTION_ID=<subscription-id>
```

## Example Okteto Manifest

With Azure Cloud Credentials enabled, this Okteto Manifest creates a blob container on deploy, uploads a file on test, and deletes the container on destroy:

```yaml
deploy:
  image: mcr.microsoft.com/azure-cli:latest
  commands:
    - az login --service-principal -u "$AZURE_CLIENT_ID" -t "$AZURE_TENANT_ID" --federated-token "$(cat "$AZURE_FEDERATED_TOKEN_FILE")" -o none
    - az storage container create --account-name mystorageaccount -n okteto-demo --auth-mode login

test:
  azure:
    image: mcr.microsoft.com/azure-cli:latest
    commands:
      - az login --service-principal -u "$AZURE_CLIENT_ID" -t "$AZURE_TENANT_ID" --federated-token "$(cat "$AZURE_FEDERATED_TOKEN_FILE")" -o none
      - date > now.txt && az storage blob upload --account-name mystorageaccount -c okteto-demo -n "test-$(date +%s).txt" -f now.txt --auth-mode login

destroy:
  image: mcr.microsoft.com/azure-cli:latest
  commands:
    - az login --service-principal -u "$AZURE_CLIENT_ID" -t "$AZURE_TENANT_ID" --federated-token "$(cat "$AZURE_FEDERATED_TOKEN_FILE")" -o none
    - az storage container delete --account-name mystorageaccount -n okteto-demo --auth-mode login
```

`--auth-mode login` makes the storage commands use the federated identity instead of storage account keys.
