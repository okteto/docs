The Okteto Garbage Collector (GC) reduces infrastructure costs by scaling inactive Namespaces and Preview Environments to zero and then deleting them. **Admin > Garbage Collector** turns it on and off and sets how long each kind of environment stays idle before the GC puts it to sleep or deletes it.

## Enabling the Garbage Collector

The Garbage Collector is on by default. If it's off, go to **Admin > Garbage Collector**, in the Settings group, and turn on the **Garbage Collector** switch.

Once it's on, the GC scales idle environments to zero and deletes unused Namespaces and Preview Environments, based on your settings.

## Configuring the Sleep and Delete Periods

### Sleep Period and Delete Period

Admins set a sleep period and a delete period for Namespaces, and another pair for Preview Environments:

- **Sleep Period**: how long, in hours, an environment stays idle before the GC scales it to zero.
- **Delete Period**: how long, in hours or days, an environment stays idle before the GC deletes it for good.
If the sleep period is set, it's how long the environment stays asleep before the GC deletes it. If the sleep period is disabled, it's the time since the environment's last update.

**Default Values**:
  - **Namespaces**
    - Sleep period: 3h
    - Delete period: 14 days

  - **Preview Environments**
    - Sleep period: 1h
    - Delete period: 7 days

### Configuration Examples

These examples show how the periods add up:

**Example 1: Default Namespace Settings (3h sleep, 14d delete)**
- The environment becomes idle on Monday at 9:00 AM.
- It goes to sleep on Monday at 12:00 PM (3 hours later).
- It's deleted 14 days after it goes to sleep.

**Example 2: Aggressive Preview Environment Settings (1h sleep, 2d delete)**
- The Preview Environment is idle since Tuesday at 2:00 PM.
- It goes to sleep on Tuesday at 3:00 PM (1 hour later).
- It's deleted on Thursday at 3:00 PM (2 days after it goes to sleep).

**Example 3: Sleep Disabled, Delete Only (delete after 7d)**
- The environment becomes idle on Friday at 10:00 AM.
- It's deleted the following Friday at 10:00 AM (7 days after its last activity).

### Step-by-Step Configuration

1. Go to **Admin > Garbage Collector**.
2. In **Settings for Namespaces**:
   - Select the **Sleep Period** in hours, for example **3 hours**, or select **Disabled** to turn it off.
   - Select the **Delete Period**, for example **14 days**.
3. In **Settings for Previews**, set the same periods. Shorter periods suit temporary environments.
4. Each change applies as soon as you select it.

:::tip
Start with conservative periods and adjust them to your team's usage. Watch the effects for a few weeks before you shorten them.
:::

## Applying Garbage Collection to Personal Namespaces

[Personal Namespaces](application-environments/namespaces.mdx#personal-namespaces), which Okteto creates when a user logs in for the first time, follow the same Sleep and Delete Periods as other Namespaces. When a Personal Namespace reaches the Delete Period, the Garbage Collector deletes all its resources but keeps the Namespace.

Admins control this in the **Settings for Namespaces** section of **Admin > Garbage Collector**:

- **Include Personal Namespaces**: applies the Delete Period to Personal Namespaces. When it's off, the Garbage Collector still puts idle Personal Namespaces to sleep, but never deletes their resources.
- **Delete Volumes**: also deletes the Persistent Volume Claims (PVCs) and volume snapshots of Personal Namespaces. It's only available while **Include Personal Namespaces** is on. When it's off, the Garbage Collector deletes the rest of the resources and keeps the volumes.

Both settings are on by default in new installations. Installations upgraded from an earlier version keep their **Include Personal Namespaces** setting, and **Delete Volumes** stays off until an Admin turns it on.

**How It Works**
- Okteto never deletes the Personal Namespaces themselves, only the resources inside them.
- Turning on **Delete Volumes** applies to the next cleanups. The Garbage Collector deletes the volumes that an earlier cleanup kept the next time it cleans up that Personal Namespace, after someone uses it again.
- The Garbage Collector never deletes resources annotated with `dev.okteto.com/policy: keep`, volumes included.

## Manually Sleeping Resources

The Garbage Collector scales applications to zero once they've been idle for longer than the `sleep` period, to save resources in your cluster.

### Manual Sleep Process

You can also scale a Namespace to zero yourself:

1. Go to **Admin > Namespaces**, in the Cluster Management group.
2. Find the Namespace you want to put to sleep.
3. Click the menu (**⋯**) at the end of the Namespace's row.
4. Select **Put To Sleep**.
5. Confirm the action.

:::warning
Putting a Namespace to sleep scales down all its Deployments and StatefulSets right away. Nothing undoes it automatically: you wake the Namespace manually, or incoming traffic wakes it (if auto-wake is on).
:::

## Impact of Garbage Collection

### Sleep

When the Garbage Collector puts a Namespace to sleep, it:

**Scales to Zero:**
- Kubernetes Deployments (replicas set to 0, so the pods are deleted but the Deployment remains)
- StatefulSets (replicas set to 0, so the pods are deleted but the StatefulSet remains)
- DaemonSets (if configured to be managed by the GC)

**Keeps:**
- Service accounts, config maps, and secrets
- Persistent Volume Claims (PVCs) and their data
- Services and ingress configurations
- Custom Resource Definitions (CRDs)
- Okteto-specific configurations

**Performance Impact:**
- **Memory usage**: Sleeping Namespaces use little cluster memory.
- **Storage**: Persistent storage usage doesn't change.

### Deletion

When an environment reaches the delete period, the Garbage Collector:

**Removes:**
- The Namespace and everything inside it. For [Personal Namespaces](application-environments/namespaces.mdx#personal-namespaces), it deletes only the resources inside the Namespace, and the Namespace itself remains.
- All Deployments, Services, config maps, and secrets
- **Persistent Volume Claims and their data** (in [Personal Namespaces](application-environments/namespaces.mdx#personal-namespaces), only when [**Delete Volumes**](#applying-garbage-collection-to-personal-namespaces) is on)
- Any custom resources in the Namespace

**Can't Recover:**
- Deleted Namespaces
- Application data, which is lost for good
- Environments, which users must deploy again from source

:::danger
Deletion is permanent. Back up critical data, or [mark important Namespaces as persistent](#persistent-resources).
:::

## Activity {#what-counts-as-activity}

Okteto considers an application inactive if no user performed any of these tasks during the `sleep` period. The GC only puts environments to sleep when they've been inactive.

### Activities That Prevent Sleeping or Wake a Sleeping Namespace
- Deploying a Kubernetes Deployment or StatefulSet with `kubectl` or similar tools
- Running `okteto deploy`
- Running `okteto up`
- Keeping an `okteto up` session open. If the `upSessionByLastSyncedFile` setting is on, this only counts while files are syncing (based on the last synced file)
- Upgrading or redeploying from the UI or the command line

The `sleep` operation doesn't affect the service accounts, config maps, secrets, or volumes you create.

If you use the Okteto Nginx Ingress Controller, incoming requests also wake a sleeping Namespace.
These requests don't count as activity, though: they don't reset the inactivity counter or keep the Namespace awake.
To turn off auto-wake for incoming requests, [configure the `autowake` field](self-hosted/helm-configuration.mdx#autowake).

### Custom Error Pages

When a request to an endpoint fails (for example, because it reaches a sleeping Namespace before it wakes up, or because a service is unavailable), Okteto shows a custom error page with hints to solve the problem.

The [defaultBackend](self-hosted/helm-configuration.mdx#defaultbackend) component serves these pages.

Custom error pages appear when:
- A request reaches a sleeping Namespace (the page explains that the Namespace is waking up)
- A service is temporarily unavailable

They work without any configuration.

### Manually Waking Sleeping Resources {#manually-wake-sleeping-resources}

The Okteto UI shows a notification when your Namespace has sleeping applications.

**To wake all resources at once:**
1. Open your Namespace in the Okteto UI.
2. Find the banner about sleeping resources.
3. Click **Wake all** to start every sleeping resource.
4. Wait 1-2 minutes for all resources to start.

**To wake specific resources:**
1. Go to **Admin > Namespaces**.
2. Find the sleeping Namespace.
3. Click the menu (**⋯**) and select **Wake Up**.
4. The resources start automatically.

## Deleting Unused Namespaces

The GC deletes a Namespace, with all its resources and data, once it stays `sleeping` for longer than the `delete` period.

:::note
This only applies to [Non-Personal Namespaces](application-environments/namespaces.mdx). The GC doesn't delete Personal Namespaces when they're idle.
:::

## Persistent resources {#persistent-resources}

To keep the Garbage Collector away from a specific Namespace, mark it as `persistent`: add the label `dev.okteto.com/persistent` to it, or [use the Admin Dashboard](admin/namespaces.mdx).

To keep only some Deployments or StatefulSets of a Namespace, add the label `dev.okteto.com/persistent` to those resources.
The Garbage Collector then skips those resources and puts the rest of the Namespace to sleep.

## Troubleshooting

### Common Issues and Solutions

**Problem: Garbage Collector Not Sleeping Resources**

*Symptoms:* Resources stay active after the sleep period.

*Solutions:*
1. **Check GC Status**: Go to **Admin > Garbage Collector** and check that it's on.
2. **Verify Timing**: Check the sleep period and when the resource was last active.
3. **Check for Activity**: Look for recent deployments, `okteto up` sessions, or `kubectl` operations.
4. **Review Labels**: Check that the resources don't have the `dev.okteto.com/persistent` label.

**Problem: Resources Deleted Unexpectedly**

*Symptoms:* The GC deleted important resources.

*Solutions:*
1. **Mark as Persistent**: Add the `dev.okteto.com/persistent` label to critical Namespaces.
2. **Adjust Periods**: Increase the delete periods.
3. **Check Activity Tracking**: Make sure your team knows what counts as activity.

**Problem: Personal Namespaces Being Affected**

*Symptoms:* The GC deletes the contents of Personal Namespaces.

*Solutions:*
1. **Check Settings**: Check the **Include Personal Namespaces** and **Delete Volumes** switches in **Admin > Garbage Collector**.
2. **Understand Scope**: The GC cleans up the contents of Personal Namespaces, not the Namespaces themselves.
3. **Keep Volumes**: Turn off **Delete Volumes**, or annotate the PVCs to keep with `dev.okteto.com/policy: keep`.

**Problem: Auto-wake Not Working**

*Symptoms:* Incoming requests don't wake sleeping Namespaces.

*Solutions:*
1. **Check Ingress**: Make sure you use the Okteto Nginx Ingress Controller.
2. **Verify Configuration**: Check whether `autowake` is disabled in the Helm configuration.
3. **DNS/Routing**: Check that requests reach the right ingress endpoint.


## Best Practices and Use Cases

### Recommended Settings by Team Size

**Small Teams (5-15 developers):**
- **Namespaces**: Sleep 6h, Delete 21d
- **Preview Environments**: Sleep 2h, Delete 3d
- **Reasoning**: Longer periods account for time zones and different work schedules.

**Medium Teams (15-50 developers):**
- **Namespaces**: Sleep 4h, Delete 14d
- **Preview Environments**: Sleep 1h, Delete 2d
- **Reasoning**: More development activity calls for faster cleanup of unused resources.

**Large Teams (50+ developers):**
- **Namespaces**: Sleep 3h, Delete 10d
- **Preview Environments**: Sleep 1h, Delete 1d
- **Reasoning**: High resource usage calls for aggressive cleanup.


### Cost Optimization Strategies

**1. Graduated Cleanup:**
- Short sleep periods (1-2h) for immediate savings
- Moderate delete periods (7-14d) for safety
- Adjustments based on usage

**2. Labels:**
You can mark Namespaces as persistent from the Okteto UI, as [Persistent resources](#persistent-resources) explains.

To mark specific Deployments, or to script it, add the label with `kubectl`:

```yaml
# Mark production-like environments as persistent
kubectl label namespace staging dev.okteto.com/persistent=true

# Mark specific deployments as persistent within a Namespace  
kubectl label deployment database dev.okteto.com/persistent=true
```

**3. Resource Usage Monitoring:**
- Track sleeping and active resources every week
- Find the teams and projects with unused environments
- Adjust the periods to the actual usage

**4. Communication with Teams:**
- Tell developers what counts as activity
- Show developers how to wake and manage sleeping resources

### Environment Protection Strategies

**Critical Environments:**
- Mark them as persistent
- Set long delete periods (90d+)
- Back up important data

**Compliance Requirements:**
- Set longer retention periods for audit trails
- Back up data before deletion
- Document your GC policies for compliance reviews
