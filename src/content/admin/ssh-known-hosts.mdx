**Admin > Known Hosts** sets the SSH hosts that Okteto trusts for SSH-based Git operations across your organization. It keeps one `known_hosts` file for every repository clone, so you don't need custom runner images. It doesn't affect Git clones over HTTPS, which rely on certificate authorities.

## Key Benefits

- **One place for trust**: You manage SSH host keys in one place for every team.
- **Security**: Okteto verifies host keys, which prevents man-in-the-middle attacks.
- **Simpler operations**: You don't need custom images or SSH configuration for each job.

## Getting Started

### Enabling Known Hosts
- Go to **Admin > Known Hosts**.
- Turn on **Enable Known Hosts**. It's off by default.
- Once it's on:
  - Okteto uses this list for every SSH operation.
  - Okteto doesn't run `ssh-keyscan` automatically. Your commands can still run it.
  - Every Git clone and submodule uses this list.

### Trusted Hosts
- Add entries to the **known_hosts** list in the [OpenSSH `known_hosts` format](https://man.openbsd.org/sshd.8#SSH_KNOWN_HOSTS_FILE_FORMAT), and click **Save**.
- The list includes the well-known providers (GitHub, GitLab, Bitbucket, Azure DevOps) as commented placeholders.

### Clone Fallback Behavior
When a Git clone fails with one protocol, Okteto tries the other one:
- If the SSH clone fails (for example, because a known host is missing), Okteto tries HTTPS.
- If the HTTPS clone fails (for example, because credentials are missing), Okteto tries SSH.

:::note
The fallback only applies to the clone of the main repository. Submodules use the protocol set in the `.gitmodules` file, without a fallback.
:::

The fallback keeps public repositories reachable without weakening security, because certificate authorities (CA) secure HTTPS clones, not known hosts.

:::info
Private repositories need authentication over at least one protocol. Configure one of these:
- **SSH authentication:** Add the hosts to the known hosts list, and add the [SSH key that Okteto generates](admin/integrations.mdx#git-ssh-key) to your Git provider.
- **HTTPS authentication:** Use the [GitHub App integration](self-hosted/install/github.mdx).
:::

With the fallback, the deployment succeeds when either protocol is configured.

## How It Works

### Scope and Application
The `known_hosts` list applies to:
- **Installer jobs**: deploys, Preview Environments, and destroy operations started from the UI
- **Remote Execution commands**: commands that run from the Okteto Manifest
- **Okteto CLI operations**: `okteto deploy --remote`

### Runtime Behavior
- Okteto mounts the `known_hosts` file read-write in jobs, so jobs can add dynamic hosts at runtime.
- With `okteto deploy --remote`, the server's list always overrides your local `known_hosts`.
- Changes made during a job only last for that job, and don't change the list in **Admin > Known Hosts**.

### Impact on the Okteto CLI
- Remote executions fetch the list automatically.
- The Okteto CLI uses the list when you run `okteto deploy --remote`.

### Deploy Warnings
When an SSH clone fails because a known host is missing, the deployment UI can show a warning even if the deployment succeeds. That happens because:
- The first SSH clone failed and raised the warning.
- The HTTPS fallback succeeded.
- The warning tells you to update the known hosts list, so deployments don't depend on the fallback.

## Example Configuration
When Okteto clones a repository, it configures Git to use the `known_hosts` list:
```bash
GIT_SSH_COMMAND="ssh -o UserKnownHostsFile=/okteto/known_hosts -o StrictHostKeyChecking=yes"
```

## Advanced Scenarios

### Dynamic Hosts
- Pipelines that clone more repositories succeed as long as each host is in the `known_hosts` list.
- Your commands can still run `ssh-keyscan` to add hosts at runtime.
- Endpoints created during a deploy can add entries to the `known_hosts` file mounted in the job. These entries only last for the job, and don't change the list that Admins set.

### Submodules with SSH
Even if your main repository clones over HTTPS, its submodules can use SSH URLs. In that case:
- The main repository clones over HTTPS as usual.
- Submodule clones need the SSH host in the known hosts list.
- Add every submodule host to the known hosts list.
- Submodule clones don't fall back to HTTPS.

### Error Handling
If a host is missing from the list:
- The SSH clone fails with **Host key verification failed**.
- Okteto tries to clone over HTTPS instead.
- For public repositories, the HTTPS fallback usually succeeds.
- For private repositories, the HTTPS fallback needs credentials (the GitHub App integration, personal access tokens, and so on).
- The deploy logs show which protocol succeeded.
