**Admin > Integrations > Registry Credentials** stores the credentials for your private container registries. Okteto uses them when it builds and deploys your application environments, so developers don't need the credentials themselves: once you add them, every developer can use those registries through Okteto. You can also manage them with the [Kubernetes CRDs that Okteto installs](self-hosted/manage/crds.mdx#private-registries).

<Image
  src={require("@site/static/img/admin-registry-credentials.png").default}
  alt="The Registry Credentials section of the Admin Dashboard, with a table of credentials by type and hostname and an Add Credential button"
/>

The [Okteto Build Service](core/build-service.mdx) uses Registry Credentials to pull private base images in your Dockerfiles.

## Pull Rate Limits

Some container registries, most notably Docker Hub, enforce pull rate limits on unauthenticated requests. Without Registry Credentials, image pulls can fail with errors like:

```
toomanyrequests: You have reached your unauthenticated pull rate limit.
```

Rate limits affect two flows in Okteto:

- **Image builds**: Dockerfiles pull base images from public registries when Okteto builds your application environments.
- **Pod deployments**: the kubelet pulls the images for the pods running in the Namespaces that Okteto manages.

Authenticated requests have much higher rate limits, or none, so Registry Credentials avoid these failures in both flows.

### Registries that enforce rate limits

**Docker Hub** is the most common source of rate limit issues. It limits unauthenticated pulls to 100 every 6 hours per IP address, and authenticated users to 200 every 6 hours, with higher limits on paid plans. Many Dockerfiles use Docker Hub base images (for example, `python:3`, `node:18`, `ruby:3-slim`), so teams can hit this limit quickly.

Other registries, like **GitHub Container Registry (ghcr.io)**, don't enforce pull rate limits for public images today, but they throttle API requests (2,000 per minute). Configure credentials for them where you can, because registry policies change.

:::tip
Even if you only use public images, configure Docker Hub credentials so you don't hit rate limits as your team grows.
:::

## Read-Only Credentials

A **Read-only** tag next to a credential means that it was defined with a Custom Resource Definition (CRD). You can't change it from the Admin Dashboard: click **Show Config** to see its values, and update the [associated CRD](self-hosted/manage/crds.mdx#private-registries) to change it.

## Adding Registry Credentials

Click **Add Credential** in the top-right corner of **Admin > Integrations > Registry Credentials**. A dialog asks for the type of credentials, your registry's hostname, and the fields for that type:

<p align="center">
  <Image
    src={require("@site/static/img/registry_credentials_add.png").default}
    alt="Add Credential dialog with fields for type, hostname, username, and password"
    width="500"
  />
</p>

Okteto supports three types of Registry Credentials:

- **Static**: a username and a password, for registries like Docker Hub.
- **AWS IAM User**: an Access Key and a Secret Access Key for Amazon Elastic Container Registry (ECR). Okteto uses them to get a temporary ECR token from AWS.
- **AWS IAM Role (via OIDC)**: an AWS IAM Role for Amazon ECR. Okteto gets a temporary ECR token from AWS through [OIDC federation](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_oidc.html).

These guides explain how to get the credentials for each registry:

- [Amazon ECR](admin/registry-credentials/amazon-ecr.mdx)
- [Azure Container Registry](admin/registry-credentials/azure-acr.mdx)
- [Docker Hub](admin/registry-credentials/dockerhub.mdx)
- [Google Artifact Registry](admin/registry-credentials/google-artifact-registry.mdx)

If a registry listens on a port other than the default HTTP(S) ports, 80 and 443, include the port in the **Hostname** (for example, `my-registry.com:5000`).

Click **Add** in the dialog. Your Registry Credentials can take a few minutes to reach every component in the cluster.

## Editing Registry Credentials

To rotate a credential, click **Edit** next to it. For sensitive values, the **Edit Credential** dialog only shows the last few characters, so you can check which value is stored:

## Node-Level Credentials

Your cluster's nodes may already have registry credentials (for example, through instance profiles, credential helpers, or secrets pre-pulled on each node). Node-level credentials are a valid alternative to Registry Credentials, but Okteto can't see them. This means:

- The [Okteto Build Service](core/build-service.mdx) doesn't use them: node-level credentials only apply to the kubelet's image pulls, not to image builds.
- You can dismiss any installation task that asks you to configure Registry Credentials if your nodes already handle authentication.

If your builds also need authenticated access to private registries, configure Registry Credentials in the Admin Dashboard or with [CRDs](self-hosted/manage/crds.mdx#private-registries) in addition to your node-level setup.

## How it works

Okteto runs a Kubernetes controller that manages Registry Credentials. The controller keeps a [Docker config JSON](https://kubernetes.io/docs/concepts/configuration/secret/#docker-config-secrets) secret named `okteto-dockerconfig-static` in the Okteto namespace, up to date with the Registry Credentials you add in the Admin Dashboard or with CRDs.

Installer jobs use this secret as a pull secret, in case your installer job image is private.

Okteto adds the secret, named `okteto-regcred`, to every Namespace and Preview Environment it creates. The [Okteto Webhook](self-hosted/helm-configuration.mdx#webhook) injects `okteto-regcred` as a pull secret into every pod, so you can deploy private images.

:::note
By default, `okteto-regcred` only contains the credentials for the Okteto Registry.
:::

To disable this behavior, set this configuration in your Helm values:

```yaml
regcredsManager:
  pullSecrets:
    enabled: false
```

With this behavior disabled, Okteto can write the secret on every node instead, so the kubelet can pull private images at deployment time. To enable it, set this configuration in your Helm values:

```yaml
daemonset:
  configurePrivateRegistriesInNodes:
    enabled: true
```

:::note
`daemonset.configurePrivateRegistriesInNodes.enabled` is deprecated.
:::
