Okteto runs your ASP.NET Core application in Kubernetes while you edit it on your machine: every time you save a file, the change runs in your cluster a few seconds later, and you can debug it with breakpoints from your IDE. The [ASP.NET Core Sample App](https://github.com/okteto/aspnetcore-getting-started), a hello world web API, is configured so that Okteto builds, deploys, and tests it directly in your Kubernetes cluster. To do the same in your own repository, we recommend using an AI agent with the [Okteto agent skills](agentic/index.mdx).

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/) with the [C# extension](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csharp), and an `ssh` client on your machine.

Clone the ASP.NET Core Sample App:

```bash
git clone https://github.com/okteto/aspnetcore-getting-started
cd aspnetcore-getting-started
```

## The Dockerfile

The `Dockerfile` of the ASP.NET Core Sample App defines two images, one per stage:

```dockerfile title="Dockerfile"
FROM mcr.microsoft.com/dotnet/sdk:10.0.404-noble AS dev

RUN curl -sSL https://aka.ms/getvsdbgsh | bash /dev/stdin -v 18.7.10521.2 -l /usr/local/bin/vsdbg

WORKDIR /usr/src/app
COPY helloworld.csproj .
RUN dotnet restore
COPY . .
RUN dotnet build && \
    dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0.15-noble-chiseled AS prod

WORKDIR /app
COPY --from=dev /app .
ENTRYPOINT ["dotnet", "helloworld.dll"]
```

- `dev` is the development image. It contains the .NET SDK, which includes [`dotnet watch`](https://learn.microsoft.com/aspnet/core/test/hot-reload) for hot reload, [`vsdbg`](https://github.com/dotnet/vscode-csharp/wiki/Attaching-to-remote-processes) for debugging, and the source code. `dotnet build` fills the `bin` and `obj` folders of the image, so the first build of `dotnet watch` in the Development Container is incremental. `dotnet publish` writes the application to `/app`.
- `prod` is the application image. It contains only the ASP.NET Core runtime and the application published in the `dev` stage. [Chiseled images](https://learn.microsoft.com/dotnet/core/docker/container-images) have no shell or package manager, and run as a non-root user.

The `dev` stage follows the recommendations for [development images](development/images.mdx): every version is pinned, and the stage that builds the application doubles as the development image.

## The Okteto Manifest

The `okteto.yml` file is the [Okteto Manifest](reference/okteto-manifest.mdx) of the ASP.NET Core Sample App.

### Build

The [build](reference/okteto-manifest.mdx#build-object-optional) section builds both images:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

`target` selects a stage of the `Dockerfile`. `depends_on` makes Okteto build the `dev` image first, so `hello-world` reuses its cached layers. Okteto pushes both images to the [Okteto Registry](core/container-registry.mdx) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

### Deploy

The [deploy](reference/okteto-manifest.mdx#deploy-string-optional) section installs the Helm chart in the `chart` folder, with the application image that Okteto built:

```yaml title="okteto.yml"
deploy:
  image: alpine/helm:4.3.2
  commands:
    - helm upgrade --install hello-world chart --set image=${OKTETO_BUILD_HELLO_WORLD_IMAGE}
```

The command runs with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster that uses the image set in `deploy.image`, so you don't need Helm on your machine.

## Testing the ASP.NET Core Sample App

The `test` section of the Okteto Manifest defines a [Test Container](reference/okteto-manifest.mdx#test-object-optional) that runs the [xUnit](https://xunit.net/) tests of the `tests` folder:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.nuget/packages
    commands:
      - dotnet test --project tests --report-xunit-trx --report-xunit-trx-filename test-results.trx --results-directory .
    artifacts:
      - test-results.trx
```

- `image`: the development image, so the tests run with the same .NET SDK as the Development Container.
- `caches`: the NuGet packages folder, kept between runs of the Test Container.
- `commands`: the commands that run the tests. `dotnet test` builds the `tests` project, runs its tests, and writes the results to `test-results.trx`. The Test Container fails if any of them exits with a non-zero code.
- `artifacts`: the files that Okteto copies to your machine when the tests finish, in this case the test results.

xUnit v3 runs on [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro), and the `global.json` file tells `dotnet test` to use it:

```json title="global.json"
{
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

Test Containers run with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster.

Run the unit tests from the root folder of the ASP.NET Core Sample App:

```bash
okteto test
```

## Developing in a Development Container

If you use AI agents, the Development Container is optional: agents work well with the `okteto deploy` and `okteto test` cycle, and don't need one. A Development Container gives you the experience of developing on your machine, with hot reload and a debugger on every change. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the hot-reload and debugging tools of the development image in your cluster.

While `okteto up` is running, an AI agent with the [Okteto agent skills](agentic/index.mdx) skips the build and deploy cycle: your changes already reach the Development Container through File Sync, so the agent waits for you to tell it what to run next.

### Configuration

The [dev](reference/okteto-manifest.mdx#dev-object-optional) section of the `okteto.yml` file defines the Development Container of the ASP.NET Core Sample App:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: dotnet watch
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    securityContext:
      capabilities:
        add:
          - SYS_PTRACE
```

The `hello-world` key matches the name of the Deployment in the Helm chart. These are the fields of the Development Container:

- `image`: the development image built in the `build` section.
- `command`: starts `dotnet watch`, which builds and runs the application. When a `.cs` file changes, `dotnet watch` applies the change to the running application with hot reload, or rebuilds and restarts the application if hot reload can't apply it.
- `sync`: synchronizes the root folder of the ASP.NET Core Sample App with `/usr/src/app`, the working directory of the development image.
- `persistentVolume`: disables the persistent volume of the Development Container. Okteto synchronizes the files again on every `okteto up`, and the NuGet packages and the build output come from the development image, so there's no volume to create and attach. In projects with many dependencies, enable it and add `/root/.nuget/packages` to [volumes](reference/okteto-manifest.mdx#volumes-string-optional) to keep the NuGet cache between `okteto up` sessions.
- `securityContext`: adds the `SYS_PTRACE` capability that `vsdbg` needs to attach to the application.

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts `dotnet watch`, which builds and runs the application:

Open `Controllers/HelloWorldController.cs` in your IDE, change the response message on line 12 to `Hello world from Okteto!`, and save the file:

```csharp title="Controllers/HelloWorldController.cs"
    [HttpGet]

    {
```

Reload the endpoint in your browser to see the new message. The change runs in your cluster without building an image or redeploying the application.

Press `Ctrl+C` to stop `dotnet watch` and exit `okteto up`.

### Debugging with VS Code

`vsdbg` attaches to the application that `dotnet watch` runs, so keep `okteto up` running. VS Code starts `vsdbg` in the Development Container over SSH: `okteto up` adds the `hello-world.okteto` host to your SSH configuration, and the `.vscode/launch.json` file of the ASP.NET Core Sample App runs `vsdbg` through it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:pickRemoteProcess}",
      "pipeTransport": {
        "pipeProgram": "ssh",
        "pipeArgs": ["-q", "-T", "hello-world.okteto"],
        "debuggerPath": "/usr/local/bin/vsdbg/vsdbg",
        "pipeCwd": "${workspaceFolder}",
        "quoteArgs": true
      },
      "sourceFileMap": {
        "/usr/src/app": "${workspaceFolder}"
      }
    }
  ]
}
```

`sourceFileMap` maps `/usr/src/app`, the path in the `sync` field of the Okteto Manifest, to the folder that you open in VS Code. If you synchronize your code to another path, change `sourceFileMap` to match it. `vsdbg` only works with the Microsoft builds of VS Code and Visual Studio.

Open the ASP.NET Core Sample App in VS Code, open the **Run and Debug** view, and run the **Connect to okteto** configuration. VS Code lists the processes of the Development Container: select `helloworld`, the process of `/usr/src/app/bin/Debug/net10.0/helloworld`. Add a breakpoint on line 12 of `Controllers/HelloWorldController.cs` and reload the endpoint in your browser. Execution stops at the breakpoint, and you can inspect the request and the variables.

To end the debugging session, click **Disconnect** in the debug toolbar. `vsdbg` detaches, and the application keeps running with `dotnet watch`.

## Cleaning up

`okteto down` stops the Development Container and brings back the `hello-world` Deployment with the application image:

```bash
okteto down
```

When you're done, `okteto destroy` uninstalls the Helm release of the ASP.NET Core Sample App from your Namespace:

```bash
okteto destroy
```

## FAQ

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](core/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](reference/file-synchronization.mdx#ignoring-files) for File Sync. An AI agent with the [Okteto agent skills](agentic/index.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize your Development Environments](/tutorials/optimize-your-development-environment/) covers these and other optimizations.

### How do I deploy an application with several services and a database?

Follow [Deploy Your Application to Okteto](get-started/deploy-your-app/index.mdx) if you deploy with a Helm chart, or [Develop a Docker Compose application with Okteto](/tutorials/compose-getting-started/) if you use Docker Compose. If your services live in several repositories, see [Deploy a multi-repo application with dependencies](/tutorials/dependencies/).

### Do I need to deploy the whole application in every Namespace?

No. [Divert](core/divert.mdx) lets you deploy only the services you change and reuse the services of a shared environment.

### How do I start each environment with realistic data?

Create its database from a [Volume Snapshot](core/use-volume-snapshots.mdx) instead of running a seed script on every deploy. [Data from Volume Snapshots](/tutorials/optimize-your-development-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own cloud resources. [Create cloud infrastructure with Terraform](/tutorials/cloud-infrastructure/) shows how, with an Amazon S3 bucket for each environment.

### Where can I find every field of the Okteto Manifest?

The [Okteto Manifest reference](reference/okteto-manifest.mdx) lists every field of `build`, `deploy`, `destroy`, `test`, and `dev`.
