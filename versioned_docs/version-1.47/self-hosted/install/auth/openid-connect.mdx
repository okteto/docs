This guide will walk you through the steps necessary to configure OpenID Connect (OIDC) as the authentication provider for Okteto.

:::note
To configure private registry credentials for Amazon ECR with OIDC federation, see [Amazon ECR registry credentials](admin/registry-credentials/amazon-ecr.mdx#using-iam-roles-via-openid-connect-oidc-federation).
:::

The following providers have dedicated guides:

- [Azure Active Directory](self-hosted/install/auth/azure-ad.mdx)
- [GitLab](self-hosted/install/auth/gitlab.mdx)
- [Okta](self-hosted/install/auth/okta.mdx)

For other providers, follow your provider's documentation to create the application.

:::note
Your provider must support the [UserInfo endpoint](https://openid.net/specs/openid-connect-core-1_0.html#UserInfo) to work with Okteto.
This authentication option follows the OpenID standard, and Okteto has validated it with Okta, PingIdentity, and GitLab.
:::

## Prerequisites

- A working installation of [Okteto](get-started/install/index.mdx)
- [Helm](https://helm.sh/docs/intro/install/) 3.0+ installed on your local machine

## Create the OpenID Connect Application

When you create the application, provide the following values:

- Start SSO URL: `https://okteto.DOMAIN`
- Redirect URIs: `https://okteto.DOMAIN`, `https://okteto.DOMAIN/auth/callback`
- Scopes: `openid`, `email`, `profile`
- Response Type: `code`
- Grant Type: `authorization code`

## Configure Okteto

When the OpenID Connect application is ready, update the `auth` section of your Helm configuration file with the following values:

```yaml title="config.yaml"
auth:
  openid:
    enabled: true
    // highlight-next-line
    clientId: "REPLACE_ME_WITH_YOUR_APPLICATION_CLIENT_ID"
    // highlight-next-line
    clientSecret: "REPLACE_ME_WITH_YOUR_APPLICATION_CLIENT_SECRET"
    // highlight-next-line
    group: "REPLACE_ME_WITH_YOUR_GROUP"
    endpoints:
      // highlight-next-line
      issuer: "REPLACE_ME_WITH_YOUR_ISSUER_URL"
      // highlight-next-line
      authorization: "REPLACE_ME_WITH_YOUR_AUTHORIZATION_URL"
    mapping:
      externalIDKey: nickname
      nameKey: name
      emailKey: email
      pictureKey: picture
      groupsKey: groups
```

> You can also store the sensitive part of these credentials in a [Kubernetes secret](self-hosted/helm-configuration.mdx#store-sensitive-configuration-values-using-a-secret).

[Upgrade your Okteto instance](self-hosted/manage/upgrade.mdx) to apply the new configuration.
Upgrade to the same version you already run: it keeps the changes to a minimum and makes any issue easier to troubleshoot.

The `group` field is optional. When you set it, only members of the group can log in to your Okteto instance. An empty `group` field lets any user log in.

The `issuer` and `authorization` endpoints must match the values that your provider's configuration discovery returns.

The `mapping` fields are optional. Use them to configure the mapping between Okteto's user attributes and the claim coming from your authentication provider.
