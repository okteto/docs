This guide takes the [Node.js Sample App](https://github.com/okteto/node-getting-started) through the whole Okteto workflow, in an [application environment](core/application-environments.mdx) in your Kubernetes cluster. The Node.js Sample App is a hello world service. Its page shows a message, the Node.js version, and the pod that serves it.

The sample is small, but its configuration is optimized, so you can use it as a reference for your own Node.js application. Along the way, the guide points out what makes each step fast in a Node.js project: the cache mount that the build and the tests share, the ignore files that keep every upload small (`.dockerignore`, `.oktetoignore`, and `.stignore`), and the Node.js watch mode and inspector for hot reload and debugging from VS Code.

## Prerequisites

- The Okteto CLI, installed and configured to access your Okteto instance. See the [installation guide](get-started/install-okteto-cli.mdx).
- To debug the application: [VS Code](https://code.visualstudio.com/). Its built-in JavaScript debugger attaches to the Node.js inspector, so you don't need an extension.

Clone the Node.js Sample App and move into its folder. Every command in this guide runs from there:

```bash
git clone https://github.com/okteto/node-getting-started
cd node-getting-started
```

## Build

The Node.js Sample App uses two container images. `dev` is the image you develop in: it has the application's dependencies, and Node.js itself brings the tools to test, reload, and debug the application. `hello-world` is the production image: it installs only the production dependencies and runs the application with `NODE_ENV=production`. The [build](reference/okteto-manifest.mdx#build) section of the `okteto.yml` file defines both:

```yaml title="okteto.yml"
build:
  dev:
    context: .
    target: dev
  hello-world:
    context: .
    target: prod
    depends_on:
      - dev
```

Both images come from the same `Dockerfile`. `target` picks the stage each image builds, and `depends_on` tells Okteto to build `dev` first, so `hello-world` finds its packages in the npm cache that `dev` filled:

```dockerfile title="Dockerfile"
FROM node:26.13.1-trixie-slim AS dev

WORKDIR /usr/src/app
COPY package.json package-lock.json ./
# The cache mount keeps the npm cache in the Okteto Build Service, which reuses
# it between builds. The tests of the Okteto Manifest use the same cache
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .

FROM node:26.13.1-trixie-slim AS prod

WORKDIR /usr/src/app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev
COPY . .
ENV NODE_ENV=production
CMD ["node", "index.js"]
```

The `Dockerfile` doesn't install any tools: Node.js includes the [watch mode](https://nodejs.org/api/cli.html#--watch) for hot reload and the [inspector](https://nodejs.org/en/learn/getting-started/debugging) for debugging. Both stages run `npm ci` before `COPY . .`, so a code change doesn't install the dependencies again.

Both `RUN` instructions mount the npm cache (`/root/.npm`) as a [cache mount](https://docs.docker.com/build/cache/optimize/#use-cache-mounts), which the Okteto Build Service keeps between builds. When a change to `package-lock.json` runs `npm ci` again, npm doesn't download any package twice. The cache mount holds only npm's downloads: the `node_modules` folder stays in the image, because the application needs it at run time.

The build context makes the biggest difference, here and in any application. Every `okteto build` starts by uploading the `Dockerfile`'s folder to the Okteto Build Service, and the `.dockerignore` file decides what goes in. The Node.js Sample App's `.dockerignore` excludes everything and then allows only what `npm ci` and the application read: `package.json`, `package-lock.json`, the JavaScript files, and the `static` folder with the page. Its last line leaves out the JavaScript files of any `node_modules` folder on your machine.

```text title=".dockerignore"
*
!package.json
!package-lock.json
!**/*.js
!static
**/node_modules/**
```

The upload stays small, and a change to any other file, such as the README or `k8s.yml`, doesn't rebuild the images.

## Deploy

`okteto deploy` first builds the images that aren't built yet. Okteto pushes them to the [Okteto Registry](core/container-registry.mdx) and stores their references in the `OKTETO_BUILD_DEV_IMAGE` and `OKTETO_BUILD_HELLO_WORLD_IMAGE` [variables](core/okteto-variables.mdx#built-in-environment-variables-for-images-in-okteto-registry).

The Node.js Sample App deploys with a plain Kubernetes manifest. Its [deploy](reference/okteto-manifest.mdx#deploy) section has a single command, which applies `k8s.yml` with `kubectl`:

```yaml title="okteto.yml"
deploy:
  - envsubst < k8s.yml | kubectl apply -f -
```

In `k8s.yml`, the Deployment's image is the `OKTETO_BUILD_HELLO_WORLD_IMAGE` variable. `envsubst` replaces it with the image Okteto built, and then `kubectl` applies the file.

The deploy has its own ignore file. `okteto deploy` uploads your folder to the container that runs the command, and the `.oktetoignore` file decides what goes in. Its `deploy` section excludes everything except `k8s.yml`, the only file the command reads, so there's almost nothing to upload. Its `destroy` section does the same for `okteto destroy`:

```text title=".oktetoignore"
[deploy]
*
!k8s.yml

[destroy]
*
!k8s.yml
```

To deploy the application, run `okteto deploy`:

```bash
okteto deploy
```

Okteto builds the two images, runs the deploy command, and prints the application's endpoint:

## Test

The Node.js Sample App has unit tests in `index.test.js`, written for the Node.js [test runner](https://nodejs.org/api/test.html). The `test` section of the Okteto Manifest defines a [test](reference/okteto-manifest.mdx#test), `unit`, that runs them:

```yaml title="okteto.yml"
test:
  unit:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    caches:
      - /root/.npm
    commands:
      - npm ci
      - node --test --test-reporter=spec --test-reporter-destination=stdout --test-reporter=junit --test-reporter-destination=junit.xml
    artifacts:
      - junit.xml
```

The test runs with [Remote Execution](core/remote-execution.mdx), in a container inside your cluster. The container starts from the development image, so it has the same Node.js version as the Development Container. `npm ci` installs the dependencies next to the files that the Okteto CLI uploads, and `node --test` prints the results and writes a JUnit report to `junit.xml`. If any of the `commands` exits with a non-zero code, the test fails. When the test finishes, Okteto copies its `artifacts`, here the JUnit report, to your machine.

The [`caches`](reference/okteto-manifest.mdx#caches-string-optional) entry is the same folder that the `Dockerfile` mounts, and it's the same cache too: Okteto identifies a cache by its repository, context, and path, and the test and the build share all three. So `npm ci` starts with the packages the build downloaded, and doesn't download them again.

The tests have their own section in the `.oktetoignore` file, so `okteto test` uploads only what `npm ci` and `node --test` read:

```text title=".oktetoignore"
[test]
*
!package.json
!package-lock.json
!**/*.js
!static
**/node_modules/**
```

Run the unit tests with `okteto test`:

```bash
okteto test
```

## Develop

A [Development Container](development/containers/index.mdx) feels like developing on your machine: every change you save reloads the application, and you can attach a debugger. When you run `okteto up`, Okteto replaces the `hello-world` Deployment with the Development Container, keeps your local files synchronized with it, and runs the development image's hot reload and debugging tools in your cluster. This step is optional: coding agents work well with the `okteto deploy` and `okteto test` loop and don't need a Development Container.

While `okteto up` is running, a coding agent with the [Okteto skills](agentic/index.mdx) stops building, deploying, and testing, and only edits the code: File Sync copies each change to the Development Container, and hot reload applies it to the running application.

### The dev Section

The [dev](reference/okteto-manifest.mdx#dev) section of the Okteto Manifest defines the Node.js Sample App's Development Container:

```yaml title="okteto.yml"
dev:
  hello-world:
    image: ${OKTETO_BUILD_DEV_IMAGE}
    command: node --watch --inspect index.js
    sync:
      - .:/usr/src/app
    persistentVolume:
      enabled: false
    forward:
      - 9229:9229
```

The `hello-world` key is the name of the Deployment in `k8s.yml` that the Development Container replaces. This is what each field does:

- `image`: the development image from the `build` section.
- `command`: starts the application in watch mode (`--watch`), which restarts it every time one of its files changes, and with the inspector (`--inspect`), which listens for debuggers on port `9229`.
- `sync`: synchronizes the Node.js Sample App's root folder with `/usr/src/app`, the development image's working directory.
- `persistentVolume`: disables the Development Container's persistent volume, so there's no volume to create and attach. Okteto synchronizes every file on each `okteto up`, and the application starts without installing anything, because its dependencies are in the development image's `node_modules` folder. The npm cache isn't there, because the build's cache mount isn't part of the development image. For a larger project, keep the Development Container's npm cache in a persistent volume or a distributed cache. [Caches in Development Containers](/tutorials/optimize-your-application-environment/#caches-in-development-containers) explains both.
- `forward`: forwards port `9229`, where the inspector listens, to your machine.

The third ignore file is `.stignore`, for File Sync. `okteto up` synchronizes your folder with the Development Container in both directions, and this file leaves out what shouldn't travel. That's the Git metadata, which is large and only matters on your machine, the `node_modules` folder, which the Development Container already has from its image, and the JUnit report that the tests write:

```text title=".stignore"
.git
/node_modules
/junit.xml
.vscode
.idea
.DS_Store
```

### Hot Reload

Run `okteto up` to replace the `hello-world` Deployment with the Development Container:

```bash
okteto up
```

Okteto synchronizes your files and starts the application in watch mode, with the inspector:

```console
 i  Using cindy @ okteto.example.com as context
 i  'node-getting-started' was already deployed. To redeploy run 'okteto deploy' or 'okteto up --deploy'
 ✓  Images successfully pulled
 ✓  Files synchronized
    Context:   okteto.example.com
    Namespace: cindy
    Name:      hello-world
    Forward:   9229 -> 9229

Debugger listening on ws://127.0.0.1:9229/392fafa3-55b2-4d6c-a4da-7ff871cd3486
For help, see: https://nodejs.org/learn/getting-started/debugging
Started hello-world server on 3000
```

Now change the code. Open `index.js` in your IDE, edit the message on line 6, and save the file:

```javascript title="index.js"
const MESSAGE = 'Built, deployed, and tested on Okteto.';
```

Okteto synchronizes `index.js` to the Development Container. Node.js notices the change, clears the terminal, and restarts the application and the inspector:

```console
Change detected in '/usr/src/app/index.js'
Restarting 'index.js'
Debugger listening on ws://127.0.0.1:9229/844ccc13-d7b5-4400-9174-001bd1473c80
For help, see: https://nodejs.org/learn/getting-started/debugging
Started hello-world server on 3000
```

A moment later, the page in your browser shows the new message. You don't even have to reload it, because the page asks the service for its info every second. Your change is running in your cluster, and you didn't build an image or redeploy the application.

When you're done, press `Ctrl+C` to stop the application and exit `okteto up`.

### Debugging with VS Code

To debug the application, you don't need another command: the Development Container's `command` starts the inspector together with the watch mode, so you debug the same `okteto up` session that reloads your changes. If you stopped it, start it again:

```bash
okteto up
```

The inspector listens on port `9229`, and it starts again every time the watch mode restarts the application:

```console
Debugger listening on ws://127.0.0.1:9229/392fafa3-55b2-4d6c-a4da-7ff871cd3486
For help, see: https://nodejs.org/learn/getting-started/debugging
```

That's the port `okteto up` forwards to your machine, and the Node.js Sample App's `.vscode/launch.json` file tells VS Code to attach to it:

```json title=".vscode/launch.json"
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Connect to okteto",
      "type": "node",
      "request": "attach",
      "address": "127.0.0.1",
      "port": 9229,
      "localRoot": "${workspaceFolder}",
      "remoteRoot": "/usr/src/app",
      "restart": true,
      "skipFiles": [
        "<node_internals>/**"
      ]
    }
  ]
}
```

`remoteRoot` is the path of the code in the Development Container, the same one as in the `sync` field of the Okteto Manifest. If you synchronize your code to another path, change `remoteRoot` to match. `restart` attaches VS Code again every time the watch mode restarts the application.

Open the Node.js Sample App in VS Code, go to the **Run and Debug** view, and run the **Connect to okteto** configuration. Now add a breakpoint on line 19 of `index.js`, the first line of the `/api/info` handler. The page in your browser asks the service for its info every second, so execution stops at the breakpoint right away, and you can inspect the request and the variables.

To end the debugging session, stop the **Connect to okteto** configuration in VS Code. The application keeps running with hot reload until you press `Ctrl+C` to exit `okteto up`.

### Stopping the Development Container

When you finish developing, run `okteto down`. It stops the Development Container and brings back the `hello-world` Deployment with the production image:

```bash
okteto down
```

```console
 i  Using cindy @ okteto.example.com as context
 ✓  Development container 'hello-world' deactivated
```

## Destroy

To delete the application, run [`okteto destroy`](reference/okteto-cli.mdx#destroy). It removes the Node.js Sample App's Deployment and Service from your Namespace:

```bash
okteto destroy
```

```console
 i  Using cindy @ okteto.example.com as context
 i  Images were already built. To rebuild your images run 'okteto build'
 ✓  Development environment 'node-getting-started' successfully destroyed
```

## FAQ

### How do I set up my own repository the same way?

Use a coding agent with the [Okteto skills](agentic/index.mdx). Ask it to set up your repository for Okteto: it discovers your services, writes the Okteto Manifest, and validates it with `okteto build` and `okteto deploy`.

### How do I make builds, deploys, and `okteto up` faster?

Upload only the files that each command needs: the context upload is key to performance. Every `okteto build`, `okteto deploy`, `okteto test`, and `okteto up` uploads files from your machine, and three ignore files decide what gets uploaded: `.dockerignore` for the image builds, [`.oktetoignore`](core/remote-execution.mdx#ignoring-files) for `okteto deploy`, `okteto test`, and `okteto destroy`, and [`.stignore`](reference/file-synchronization.mdx#ignoring-files) for File Sync. A coding agent with the [Okteto skills](agentic/index.mdx) configures them for your application and measures how much faster your builds, deploys, and `okteto up` get. [Optimize Your Application Environment](/tutorials/optimize-your-application-environment/) covers these and other optimizations.

### Do I need to deploy the whole application in every Namespace?

No. Okteto supports two models, and you choose one for your application:

- **Full replica:** every service of the application runs in your Namespace. In a monorepo, the `deploy` section of the Okteto Manifest deploys every service, as in the [quickstart](get-started/quickstart.mdx), where one Helm chart deploys the three services of Kube Movies. In a multirepo, each repository has its own Okteto Manifest and lists the other repositories in its [`dependencies`](reference/okteto-manifest.mdx#dependencies) section, as in [Deploy a Multi-Repo Application with Dependencies](/tutorials/dependencies/). Full replicas are simpler to configure and give you full isolation: nothing one environment does affects the others. Use them for an application with fewer than 20 services.
- **Overlay Namespace:** your Namespace runs only the services you change, and [Divert](development/divert/index.mdx) routes every other request to a Shared Namespace that runs the rest of the application. Overlay Namespaces are more cost-effective, faster to deploy, and more reliable, because each environment builds, deploys, and runs only the services it changes. Use them for an application with 20 services or more.

### How do I create a Preview Environment of my application for every pull request?

Add a workflow to your CI pipeline that deploys the application in a [Preview Environment](previews/index.mdx) when a pull request opens or changes, runs `okteto test` against it, and destroys it when the pull request closes. The workflow uses the Okteto Manifest, so `okteto build`, `okteto deploy`, and `okteto test` work the same way in your CI pipeline, for coding agents, and on developer machines. Follow the guide for [GitHub Actions](previews/using-github-actions.mdx) or for [GitLab CI/CD](previews/using-gitlab-cicd.mdx).

### How do I start each environment with realistic data?

Load the data with a script in your `deploy` commands, or copy the data of another application environment with a [Volume Snapshot](core/use-volume-snapshots.mdx), which creates the volumes of your database from a snapshot of its volumes. [Data from Volume Snapshots](/tutorials/optimize-your-application-environment/#data-from-volume-snapshots) shows how.

### How do I create resources outside Kubernetes, such as a cloud database?

Create them in the `deploy` and `destroy` commands with your infrastructure as code tool, so every environment gets its own resources. See the [Create Cloud Infrastructure with Terraform](/tutorials/cloud-infrastructure/) tutorial, which creates an Amazon S3 bucket for each environment.

### Can I access my application environment with `kubectl`?

Yes. Run `okteto kubeconfig` to add the credentials of your Okteto Namespaces to your kubeconfig file, and use `kubectl` as usual: `kubectl get pods`, `kubectl logs`, or `kubectl describe`. See [Kubernetes Credentials](core/credentials/kubernetes-credentials.mdx) for how Okteto generates those credentials.
