Welcome to the Okteto troubleshooting guide. This page provides answers to some common issues encountered while using Okteto.
Please also review our [FAQ Guide](reference/faqs.mdx) for additional help.

## How to extract logs from Okteto when asking for help

### For Developers

Run [`okteto doctor`](reference/okteto-cli.mdx#doctor) to generate a doctor file with the Okteto logs for a Development Container. Attach it when you contact Okteto support or ask in the [Okteto Community](http://community.okteto.com).

### For Administrators of Okteto

Use the [Okteto Diagnostics tool](self-hosted/manage/diagnostics.mdx) to create a support bundle with cluster information, logs for the Okteto components, and other relevant information.

### 2. Wait for workloads to become "Available"

Check that all Deployments and StatefulSets have completed their rollouts and that all Pods are in the Ready state:

```bash
# Deployments & StatefulSets rollouts
kubectl rollout status deploy -l app.kubernetes.io/instance="okteto" -n okteto --timeout=120s
kubectl rollout status sts   -l app.kubernetes.io/instance="okteto" -n okteto --timeout=120s

# All pods to Ready (every container ready)
kubectl wait pod -l app.kubernetes.io/instance="okteto" -n okteto --for=condition=Ready --timeout=180s
```
If a command times out, go to [8. Anything looks bad?](#8-anything-looks-bad) to investigate.


### 3. Spot Unhealthy Pods

Check for Pods that aren't Ready or that have container restarts:

```bash
# Pods not Ready
kubectl get pods -l app.kubernetes.io/instance="okteto" -n okteto --field-selector=status.phase!=Running -o wide

# Restarts > 0
kubectl get pods -l app.kubernetes.io/instance="okteto" -n okteto -o custom-columns='POD:.metadata.name,READY:.status.containerStatuses[*].ready,RESTARTS:.status.containerStatuses[*].restartCount'| (read; echo "$REPLY"; sort -k3 -nr)
```

### 8. Anything looks bad?

Check the events, and describe the failing Pods or other resources to find out what's wrong:

```bash
# a) Events (cluster is telling you what’s wrong)
kubectl get events -n okteto --sort-by=.lastTimestamp | tail -n 40

# b) Describe the failing thing (image pulls, scheduling, probe failures)

```

## Daemon fails with "open /etc/hosts: permission denied"

The node's operating system doesn't allow Okteto to modify the `/etc/hosts` file. Okteto needs write access to `/etc/hosts` on the cluster nodes to configure [internal registry resolution](self-hosted/helm-configuration.mdx#overrideregistryresolution). When it can't write to it, the `okteto-daemon` pods fail with an error like this one:

```json
{"level":"fatal","service":"daemon","error":"open /etc/hosts: permission denied","timestamp":"...","message":"tasks initialization failed"}
```

This commonly happens with an unsupported node OS, such as [Bottlerocket](https://aws.amazon.com/bottlerocket/) on AWS EKS. Bottlerocket uses a read-only root filesystem, which prevents Okteto from writing to `/etc/hosts`.

To fix it:

1. **Switch to a supported node OS.** On AWS EKS, use Amazon Linux 2023 (AL2023) or Amazon Linux 2 (AL2). The [Amazon EKS installation requirements](get-started/install/amazon-eks.mdx) have the details.
2. **Recreate your node group** with the supported AMI family. For example, using `eksctl`:
   ```bash
   eksctl create nodegroup \
     --cluster=”${CLUSTER_NAME}” \
     --region=”${AWS_REGION}” \
     --node-type=”m5.xlarge” \
     --node-ami-family=”AmazonLinux2023”
   ```
3. **Drain and delete the old node group** running the unsupported OS.

## UPGRADE FAILED: "okteto" has no deployed releases

This error occurs on your second install or upgrade when your initial install failed. Delete the failed install before you try again:

```bash
helm uninstall okteto --namespace okteto
```

## Registry pods keep restarting

The usual cause is that the registry pods can't read from or write to your cloud storage bucket. Check that the cloud IAM you created has read and write access to the bucket.

## Deployment pipelines stay in "progressing" forever

A pipeline can get stuck for several reasons: for example, the installer job couldn't start because of an error in the Kubernetes API, or because the cluster is overloaded. To find the problem, list the jobs and pods for the pipeline.

You need the pipeline name (the name displayed in the Okteto UI) and the Namespace where it's deployed. For example, for the `movies` pipeline in the `cindy` Namespace, list its jobs and pods with these commands:

```console
kubectl get jobs -l=dev.okteto.com/pipeline-name=movies -l=dev.okteto.com/pipeline-namespace=cindy --namespace=okteto
```

```console
kubectl get pods -l=dev.okteto.com/pipeline-name=movies -l=dev.okteto.com/pipeline-namespace=cindy --namespace=okteto
```

## Using a Custom CNI

If your cluster uses a custom CNI, the webhooks may need additional configuration. In some cases, the CNI on the worker nodes isn't the same as the CNI of the control plane, and the webhooks need host networking. The ports may also need to change to avoid collisions.

The Okteto Webhook is configured by setting`webhook.hostNetwork` to `true`. The ports are set with `webhook.port`.
More information on the Okteto Webhook configuration can be found [here](self-hosted/helm-configuration.mdx#webhook).

## Docker Hub credentials misconfiguration

Okteto lets you [configure your own Docker Hub account](admin/dashboard.mdx#registry-credentials). If its credentials are wrong, kubelet can't pull public images from Docker Hub, which can cause serious issues in the cluster.

To fix it:

- [Update the container image used by the daemonset pods](self-hosted/helm-configuration.mdx#daemonset). Use a container registry other than Docker Hub, so the pods pull the image without the credential problem. For example, `ghcr.io/okteto/busybox`.
- Change or remove the credentials for the Docker Hub registry.
- [Upgrade your Okteto instance](self-hosted/manage/upgrade.mdx) with the new configuration.

The Okteto daemonset then configures the right credentials for Docker Hub. Once you verify that everything works, you can restore the original base image for the Okteto daemonset.
